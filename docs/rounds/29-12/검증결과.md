# 29-12 검증 결과

## 1. 테스트가 내 코드에서 결함 둘을 잡았다 — 이 라운드의 근거

새 단언을 먼저 넣고 돌렸을 때 셋이 실패했다. 둘은 실제 결함, 하나는 테스트 자체의 실수였다.

```
× 잠긴 계정도 재설정하면 곧바로 들어온다
  AuthError: 로그인이 잠겨 있습니다 — 15분 후 다시 시도해 주세요
```

**잠금 키가 둘인데 하나만 지웠다.** 계정 단위(`acct|…`)만 지우고 (계정, IP) 키를 남겼다. 비밀번호를
잊어 5회 틀린 사람이 새 비밀번호를 정하고도 15분을 기다려야 했다.

```
× 저장을 넘어 살아남는다
  AuthError: 휴대폰 인증이 완료되지 않았습니다 — 인증 후 로그인할 수 있습니다
```

**막다른 길.** 가입을 중간에 그만둔 계정이 복구에 성공해도 들어올 길이 없었다. 재설정 인증번호를
받았다는 것이 곧 그 번호를 쥐고 있다는 뜻이므로, 복구 성공 시 인증 표시를 함께 세운다.

세 번째는 내 테스트가 `new AuthService({ storage })`로 불렀는데 생성자는 저장소를 위치 인자로
받는다. 아무것도 저장되지 않아 실패했다 — 코드가 아니라 테스트를 고쳤다.

## 2. 서버에서만 확인되는 것 — 세션 폐기

도메인은 세션을 모른다. `tests/passwordReset.http.test.ts`가 실제 DB에서 본다.

```
✓ 복구가 끝나면 그 계정의 기존 세션이 살아 있지 않다
✓ 복구도 인증번호를 전달할 방법이 없으면 받지 않는다 — 가입과 같은 문
✓ 개발용 인증번호를 내주지 않는 자리에서는 응답에 코드가 없다
```

이 파일을 처음에는 전용 스키마에 세웠는데 `handleAuth`가 **자기 풀을 스스로 연다** — 검색 경로를
끼워 넣을 자리가 없어 쓰는 쪽과 읽는 쪽이 다른 곳을 봤다. "로그인했는데 세션이 없다"로 실패했고,
다른 통합 테스트와 같이 `public`을 쓰되 번호를 실행마다 다르게 만들어 해결했다.

**CI 단계도 함께 넣었다.** `gates` job에는 DB가 없어 이 파일은 건너뛰어진다. `server` job에
`test:reset` 단계를 넣지 않았으면 어디서도 돌지 않았을 것이다 — 28-77이 이름 붙인 그 상태다.
