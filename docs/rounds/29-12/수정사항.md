# 29-12 수정사항 — 역할이 주소에 남고, 비밀번호를 되찾을 수 있다

새 명세의 2절(가입·로그인 화면)과 3절(인증 보안과 비밀번호 복구)을 구현한다. 29-11이 세운 두 문
(`devOtpAllowed`·`smsConfigured`)을 복구도 똑같이 지난다.

## 1. 역할이 주소에 남는다

명세 2절이 요구하는 것은 둘이다. 주소의 `role`을 초기값으로 쓰고, 화면에서 바꾸면 주소도 갱신한다.

```
/login?role=partner       파트너를 고른 채로 열린다
/login/customer           고객 전용 자리 (기존 /login/partner 와 짝)
/signup?role=partner      파트너 가입으로 열린다
/signup/customer          고객 전용 자리
```

알 수 없는 값은 **고객으로 본다.** 404로 떨어뜨리거나 화면을 비우지 않는다. `?role=admin`도 마찬가지다 —
29-10에서 공개 화면에서 관리자를 내렸고, 주소로도 되돌아오지 않는다.

화면에서 역할을 바꾸면 `history.replaceState`로 주소만 고친다. `router.replace`가 아닌 이유는, 이
주소가 되돌아갈 지점이 아니라 **지금 화면의 표기**이기 때문이다. 뒤로 가기 기록에 역할을 바꾼
횟수만큼 쌓이면 안 되고, 서버를 다시 부를 일도 아니다.

로그인·가입 화면이 서로 링크할 때도 고르던 역할을 들고 간다.

## 2. 비밀번호 찾기 — `/password/reset`

휴대폰 → 재설정 인증번호 → 새 비밀번호. 세 걸음이다.

### 가입용 인증을 복구에 재사용하지 않는다

가입 OTP는 `role:phone`에, 재설정 OTP는 `reset:role:phone`에 둔다. 키가 다르므로 한쪽 코드로 다른
쪽을 통과할 수 없다. 목적이 섞이면 "가입 확인"이 곧 "비밀번호 바꾸기"가 된다. 양방향을 단언으로
고정했다.

### 끝나면 기존 세션이 사라진다

비밀번호를 도둑맞아 바꾸는 것이라면, 그 도둑의 세션이 살아 있는 채로 끝나는 복구는 복구가 아니다.
`resetPassword`가 성공하면 서버가 그 계정의 세션을 모두 폐기한다.

도메인은 세션을 모른다 — 서버 계층의 일이라 `tests/passwordReset.http.test.ts`가 실제 DB에서 본다.

### 가입 코드를 묻지 않는다

이미 가입한 사람이 자기 번호로 받는 것이다. 코드를 요구하면 가입 코드를 바꾼 뒤 기존 회원이 복구할
수 없게 된다.

### 계정이 있는지 알려 주지 않는다

없는 번호에도 코드를 돌려주되 **저장하지 않는다.** 응답만 보고 가입 여부를 훑을 수 없다. 저장하지
않으므로 뒤이은 재설정은 "인증번호가 없다"에서 멈춘다.

### 만료·시도 제한은 가입과 같다

5분 만료, 5회 시도. 재설정 요청과 확정 모두 IP 반복 실패 제한을 받는다.

## 3. 테스트가 잡은 것 둘

**잠금 키가 둘인데 하나만 지웠다.** 복구에 성공하면 로그인 잠금도 풀어야 하는데, 계정 단위 키
(`acct|…`)만 지우고 (계정, IP) 키를 남겼다. 그래서 5회 틀려 잠긴 사람이 새 비밀번호를 정하고도
15분을 기다려야 했다. 그건 복구가 아니다. 접두 일치로 그 계정의 기록을 모두 지운다.

**막다른 길.** 가입을 중간에 그만둔 계정(휴대폰 인증 전)이 복구에 성공해도 "인증이 완료되지
않았습니다"에 막혀 들어올 길이 없었다. 재설정 인증번호를 받았다는 것은 그 번호를 쥐고 있다는
뜻이고, 그것이 휴대폰 인증이 확인하려는 바로 그것이다. 복구 성공 시 인증 표시를 함께 세운다.

## 하지 않은 것

- **문자 발송 연동** — 여전히 없다. 운영에서는 복구도 가입과 같이 503이다.
- **고객 가입 코드 해제** — 실제 문자 인증 검증 뒤로 미뤄 둔 그대로다.
- **업체 찾기·편집기·Q&A·상담방** — 다음 순서다.
