# 29-27 — 비밀번호 찾기에 이메일 길을 낸다

## 1. 왜 이 라운드인가

사장님 지적: **"비밀번호 찾기할 때 이메일로도 구현해야지."** 확인해 보니 이메일이 없는 정도가 아니었다.

| 있던 것 | 없던 것 |
|---|---|
| 휴대폰 인증번호로 비밀번호 찾기 (29-12) | **계정에 이메일 칸 자체가 없다** — `Account` 에 `email` 이 없다 |
| 문자 발송 **설정 확인** (`smsConfigured`) | 문자를 실제로 보내는 코드 (환경변수 셋이 갖춰졌는지만 본다) |
| 서버의 `changePassword` (28-33) | 로그인한 사람이 **비밀번호를 바꿀 화면** — Next 로 옮기며(29-3) 따라오지 않았다 |
| 내 계정 화면 (`/profile`) | 이메일·비밀번호 같은 **계정 보안을 다루는 자리** — 이름과 `AC-0001@accounts.local` 같은 표 안의 식별자만 보여 줬다 |

이메일로 찾으려면 이메일이 있어야 하고, 이메일이 있으려면 등록할 자리가 있어야 하고, 등록한 주소는 **인증**해야
쓸 수 있다. 넷을 한 라운드로 묶었다.

고치기 전 코드로 확인한 것(`검증결과.md` §1): 이메일로 재설정을 요청하면 `휴대폰 번호는 010으로 시작하는
10~11자리여야 합니다` 로 거절됐고, `setEmail` 은 `알 수 없는 op` 였다.

## 2. 설계 — 인증한 주소만 복구에 쓴다

오타로 적은 **남의 주소**로 내 복구 코드가 가면 안 된다. 그래서 이메일은 등록하는 것과 쓰는 것 사이에
**인증**이 있다. 인증하지 않은 주소는 복구에서 없는 주소와 같다 — 코드는 돌려주되 저장하지 않고, 메일도
보내지 않는다. 응답 모양은 같아서 밖에서는 가입 여부를 훑을 수 없다(29-12 의 규칙 그대로).

```
가입(선택) 또는 내 계정 → 이메일 저장 + 인증번호 발급 → 메일로 받은 번호 입력 → emailVerifiedAt
비밀번호 찾기 → [휴대폰 번호 | 이메일] → 인증번호 → 새 비밀번호 → 기존 세션 전부 폐기
```

### 도메인 (`server/domain/auth.ts`)

- `Account.email?`(소문자 정규화) · `Account.emailVerifiedAt?`. 한 역할 안에서 한 주소는 한 계정 — 휴대폰과 같은 규칙.
  탈퇴 계정은 세지 않는다. 고객과 파트너가 같은 주소를 쓰는 것은 된다(한 사람이 둘 다일 수 있다).
- `setEmail(role, email)` — 로그인한 본인. 주소를 바꾸면 인증이 풀린다. 같은 주소를 다시 넣으면 인증 메일만
  다시 낸다. 이미 인증된 주소는 거절한다(할 일이 없다).
- `verifyEmail(role, code)` — 5분·5회, 가입 인증과 같다. 키는 계정 단위(`emailverify:role:accountId`).
- `requestPasswordReset(role, target)` — `target` 에 `@` 가 있으면 이메일 길. 키는 `reset:email:role:email`.
  휴대폰 키(`reset:role:phone`)·가입 키(`role:phone`)·인증 키와 모두 다르다 — **한쪽 코드로 다른 쪽을 통과할 수
  없다.** 돌려주는 `to` 는 서버가 실제로 보낼 곳(계정이 없으면 `null`).
- `resetPassword(role, target, code, next)` — 같은 갈림. 이메일로 복구해도 **휴대폰 인증(`verified`)은 세우지
  않는다** — 쥔 것은 메일함이지 휴대폰이 아니다. 잠금 해제는 휴대폰 기준 키로(로그인은 휴대폰 번호로 하니까).
- 감사 로그에 이메일은 `k***@example.test` 로만 남는다.

### 문 (`server/authSafety.ts`)

문자와 같은 규칙으로 **메일 쪽 문**을 하나 더 뒀다. `mailConfigured` 는 `MAIL_PROVIDER`·`MAIL_API_KEY`·
`MAIL_SENDER` 셋을 모두 요구하고, `emailDeliverable` 은 개발용 인증번호를 보여도 되는 자리(로컬·CI·켜 둔
프리뷰)이거나 메일이 갖춰진 자리다. 운영에 메일 설정이 없으면 이메일 인증·이메일 복구는 503 이고, 문구가
**휴대폰이라는 다른 길**을 말한다. 문자 설정이 있어도 메일 문은 따로 닫혀 있다 — 서로 대신하지 않는다.

### 발송 (`server/mail.ts`)

HTTP API 하나로 보낸다(의존성 없음, 서버리스에 SMTP 소켓 없음). 아는 발송사는 `resend` 하나 —
`POST https://api.resend.com/emails`. 모르는 이름이면 **보내는 척하지 않고** 던진다. 발송사가 거절하면
상태 코드만 남긴다(응답 본문에 키가 섞일 수 있어 로그에 쓰지 않는다). `fetch` 를 주입받아 CI 는 진짜
발송사를 부르지 않는다.

메일 두 통(인증·재설정) 모두 코드, 5분 안내, "본인이 아니면 무시" 를 담는다. 재설정 메일은 "모든 기기에서
로그아웃된다" 도 말한다.

### 서버 (`server/handlers/auth.ts`)

- `requestPasswordReset` 의 둘째 인자가 이메일이면 메일 문을, 아니면 문자 문을 본다.
- 메일이 갖춰진 자리에서는 코드가 **응답이 아니라 메일로** 간다. 계정이 없으면(`to === null`) 보내지 않는다.
- **메일이 안 나가면 502 이고 코드도 남지 않는다.** 발송은 트랜잭션 안에서 하고 `MailError` 는 트랜잭션째
  되돌린다 — 오지 않을 메일을 기다리며 "인증번호가 없다" 에 막히는 대신, 다시 요청하면 새 코드가 나간다.
- 새 세션 op 둘: `setEmail`(인증 메일 발송) · `verifyEmail`. `register` 는 `email` 을 선택으로 받는다(미인증 저장).
- `handleAuth(req, env, deps)` — `deps.sendMail` 로 발송사를 끼운다. 운영은 기본값(`server/mail.ts`).

### 화면

- **비밀번호 찾기** (`/password/reset`) — "인증번호를 어디로 받을까요?" 휴대폰 번호 / 이메일. 이메일 쪽에는
  "내 계정에서 인증한 이메일만 쓸 수 있습니다" 를 붙였다. 개발용 안내 문구도 갈래에 따라 문자/메일로 바뀐다.
- **가입** — 이메일(선택) 칸. "가입 뒤 내 계정에서 인증하면 쓸 수 있습니다".
- **내 계정** (`/profile`, `/partner/profile`) — 새 카드 **계정 보안** (`components/marketplace/account-settings.tsx`):
  이메일 저장·인증 메일 받기·인증번호 입력, 인증 상태 표시, 그리고 **비밀번호 변경**(서버는 28-33 부터
  있었고 화면이 없었다). 머리의 `AC-0001@accounts.local` 표시는 뺐다 — 사람에게 보내는 주소가 아니다.

## 3. 봇 — `e2e:live` 여섯 걸음

휴대폰(M)은 로그인된 채로 두고, 다른 창(G)에서 이메일로 비밀번호를 바꾼다. **M 의 세션이 죽어야 한다.**

```
✓ 이메일을 등록하면 인증번호가 발급된다
✓ 인증번호가 맞으면 인증됨으로 바뀐다
✓ 인증된 이메일로 요청하면 인증번호가 나온다
✓ 새 비밀번호를 정하면 로그인 화면으로 간다
✓ 비밀번호를 바꾸면 켜 두었던 휴대폰 세션이 풀린다
✓ 새 비밀번호로 들어온다
```

## 4. 사장님이 하실 것 — 메일 발송사

운영에서 메일이 실제로 나가려면 발송사 계정이 있어야 한다. Resend(https://resend.com) 에서 **보내는
도메인을 인증**하고 API 키를 만든 뒤, Vercel 환경변수에 셋을 넣는다: `MAIL_PROVIDER=resend`,
`MAIL_API_KEY=(키)`, `MAIL_SENDER=반듯집수리 <no-reply@인증한도메인>`. **값은 채팅이나 저장소에 적지 않는다.**
넣기 전까지 운영은 이메일 인증·이메일 복구를 503 으로 막고 휴대폰 길을 안내한다.

## 5. 이번에 하지 않은 것

- **문자 발송 코드.** 이 라운드가 드러낸 대로 `smsConfigured` 는 값만 본다. 문자 발송사(알리고·솔라피·NHN 등)는
  사장님이 고르셔야 하고, 그 API 에 맞춘 어댑터는 `server/mail.ts` 와 같은 모양으로 붙는다. 운영 가입이
  막혀 있는 이유는 그대로다.
- **이메일로 로그인.** 로그인 아이디는 휴대폰 번호 그대로다. 이메일은 복구 길이지 아이디가 아니다.
- **가입 때 이메일 인증.** 가입 인증(휴대폰)과 이메일 인증을 한 화면에서 둘 다 받으면 가입이 길어진다.
  가입 때는 저장만 하고 내 계정에서 인증한다 — 화면이 그렇게 말한다.
- **배포된 주소 확인** — 여전히 세션에서 막혀 있다(프록시 403).

## 6. 자체 감사 — 승인 전에 스스로 본 여덟 가지

사장님 지시("미비점 자체확인 필요. 그후 승인")로, 이 라운드가 새로 넣은 것을 공격자·운영자·다음 개발자의
눈으로 다시 읽었다. 여덟 가지가 나왔고 **전부 이 브랜치에서 고쳤다.** 항목마다 고치기 전에 실패하는 테스트를
먼저 두었다(`검증결과.md` §7).

| # | 미비점 | 고친 것 |
|---|---|---|
| 01 | **탈퇴해도 이메일이 남았다.** `withdraw()` 는 휴대폰·이름만 지웠다 — 28-40 의 "식별 정보는 즉시 파기" 가 이메일 앞에서 거짓이 됐다 | `withdraw()` 가 `email`·`emailVerifiedAt`·진행 중인 인증 코드까지 지운다 |
| 02 | **메일이 무한히 나갈 수 있었다.** 이메일 등록·복구 요청 하나가 진짜 메일 하나다. 같은 주소로 반복하면 발송사 요금과 수신자 스팸함이 무너지고, 한 IP 가 여러 주소로 쏟는 것도 막지 못했다 | 도메인: 같은 주소는 **60초 재발송 간격**(`OTP_RESEND_COOLDOWN_MS`) — 등록은 "방금 보냈습니다" 로 거절, 복구는 살아 있는 코드를 그대로 두고 **보낼 곳 없음**(`to: null`)을 돌려준다(응답은 똑같다). 서버: 메일이 나갈 수 있는 요청은 **IP당 10분에 5회**(`mailThrottled`, 실패가 아니라 성공을 센다) → 429 |
| 03 | **발송사 호출이 트랜잭션 잠금 안에 시한 없이 있었다.** 발송사가 멈추면 계정 트랜잭션이 함께 멈춘다 | `sendMail` 에 8초 시한(`AbortSignal.timeout`) — 넘기면 `MailError` 로 끊고 롤백. 트랜잭션 **안**에 두는 것은 의도다: 코드가 저장되기 전에 메일이 나가면 그 코드는 무효 코드고, 발송 실패 시 저장이 저절로 되돌아간다. 대가는 "최대 8초 잠금" 이고 문서에 적는다 |
| 04 | **주소 선점.** 인증도 안 한 주소를 적어만 두면 진짜 주인이 등록하지 못했다 — 남의 이메일을 미리 적어 복구 길을 막을 수 있었다 | 유일성은 **인증한 주소끼리만** 본다. 인증에 성공하면 같은 주소를 적어만 둔 다른 계정에서 **거둔다**(`verifyEmail`). 이미 인증된 주소를 다른 계정이 인증하려 하면 그때 거절한다 |
| 05 | **가입 여부가 새어 나갔다.** 메일 발송 실패가 502 인데, 모르는 주소는 메일을 보내지 않으니 실패할 리 없다 → 502 가 오면 "가입된 주소" 다 | 복구 요청은 메일이 실패해도 **모르는 주소와 같은 200** 을 돌려주고, 저장한 코드를 버린다(`discardPasswordReset`) — 다음 요청이 간격 제한 없이 새 코드를 낸다. 실패는 서버 로그에만 남는다. **남는 것:** 발송사를 부르는 시간만큼의 응답 지연 차이(타이밍 오라클)는 남아 있다 — 발송사가 정상일 때 수십 ms 이고, 없애려면 발송을 요청 밖(큐)으로 빼야 한다. 이월로 적는다 |
| 06 | **내 계정 카드가 읽기 실패에도 사라졌다.** `account === null` 이면 카드를 안 그렸는데, 관리자(계정 없음)와 "읽기 실패" 를 구분하지 않았다 | 오류가 있으면 카드를 남겨 오류를 보여 준다(`error === ''` 일 때만 숨긴다) |
| 07 | **인증번호가 `Math.random()` 이었다.** 가입 때부터 그랬고(28-31), 이 라운드가 그 줄을 세 곳으로 복제했다 | `newOtp()` 하나 — WebCrypto `getRandomValues` 에 거부 샘플링(편향 없음). 난수원이 없는 환경이면 던진다 |
| 08 | **같은 판별이 세 곳에 복제됐다.** "이메일이면 정규화·인증 확인, 아니면 휴대폰" 이 요청·재설정·폐기에 각각 있었다 | `recoveryTarget()`·`findRecoverable()` 둘로 모았다 — 위 01~05 를 고치면서 세 곳을 따로 고쳤다면 하나는 빠졌을 것이다 |

02 의 IP 표는 `server/rateLimit.ts` 의 실패 표와 같은 한계(인스턴스마다 따로)를 갖는다 — 저장소의 서버리스
가드(`server/serverlessState.test.ts`)가 그 사실을 주석에 적으라고 잡았고, 적었다.
