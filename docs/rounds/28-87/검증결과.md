## 4. 이 컨테이너에서 확인하지 못한 것 / 알고도 남긴 것

- **라이브 도메인을 직접 열지 못한다.** 이 컨테이너의 이그레스가 `bandut-partner-platform.vercel.app`을
  막는다. 그래서 §5의 `deploy-check`(GitHub Actions)가 그 자리를 대신한다.
- **서버 모드로 켜지 않았다.** 이것은 못 한 것이 아니라 **하지 않기로 한 것**이다 —
  실제 사용자 데이터가 걸린 판단이라 사장님 몫이고, `28-87/서버_모드_전환.md`가 그 판단에 필요한
  것을 갖췄다. 따라서 05의 `bandut-auth-mode:server` 경로는 **로컬 빌드로만** 확인됐고,
  프로덕션에서 그 값을 실제로 보는 것은 켜는 날의 일이다.
- **엣지 레이트리밋 없음.** 03이 DB 부하는 막았지만 요청 수 자체는 안 막는다. 이월.
- **별칭 추적 없음.** 가드는 한 번 복사된 값을 다른 함수로 넘겨 거기서 부르는 것을 못 잡는다.
  이번에는 **그 한계를 문서와 코드 주석에 실제 범위대로 적었다** — 28-86이 좁게 적었다가 뚫렸다.
- **`server/db.ts`의 `max: 3`은 그대로다.** 03의 두 조치로 공개 경로가 풀을 잠식하지 않게 됐으므로
  지금 올릴 이유가 없다고 판단했다. 트래픽이 늘면 이 값부터 본다(전환 문서 6절에 적었다).

## 4-1. 병합 뒤에 드러난 것 — 03의 TTL이 낡은 값을 굳혔다 (#240에서 고침)

**이 라운드가 만든 결함이고, 병합 뒤에야 잡혔다.** 순서대로 적는다.

1. Copilot이 #238에서 "없는 workspace는 캐시하지 않아 TTL을 우회한다"를 지적했다. 맞는 말이라
   **없다는 사실도 기억하도록** 고쳤다(첫 판). `check` 514 통과, 계약 54 통과 — **그런데
   `e2e:server`를 로컬에서 돌리지 않고 올렸다.**
2. CI의 `server` 잡이 빨간색이 됐다: `50 passed, 1 failed` /
   **「익명: 집계가 실제로 담겨 온다 (고객 요청 1건이 반영됨)」.**
3. 원인을 찾다가 **더 나쁜 사실**이 나왔다. 음수 캐시를 되돌린 뒤에도 **빈 DB에서 3회 중 1회**
   같은 자리가 깨졌다:

   ```
   회차 1: [e2e:server] 50 passed, 1 failed   ← 익명: 집계가 실제로 담겨 온다
   회차 2: [e2e:server] 51 passed, 0 failed
   회차 3: [e2e:server] 51 passed, 0 failed
   ```

   즉 범인은 음수 캐시가 아니라 **03이 넣은 5초 TTL 그 자체**다. 첫 요청이 올라가기 직전에
   랜딩이 부른 값이 캐시에 남아, 방금 올린 것이 최대 5초 동안 보이지 않았다.
   **이 경합은 #238이 병합된 시점부터 `main`에 있었고**, #238의 CI가 초록이었던 것은 타이밍이
   맞았기 때문이다. "CI가 초록이었다"는 없다는 증거가 아니다.
4. 고친 방법: **쓴 쪽이 캐시를 버린다.** `api/snapshot.ts`의 PUT 성공 경로(삽입·갱신 둘 다)가
   `invalidatePublicStats(workspaceId)`를 부른다. 스냅샷을 쓰는 쪽은 언제 바뀌었는지 정확히
   아니까 시간이 지나기를 기다릴 이유가 없다. 인스턴스가 여러 개면 자기 것만 버리고 나머지는
   TTL 뒤 rev로 알아차린다 — 최선 노력이고 이 캐시의 성격에 맞다.
5. 그리고 **자원 보호의 방법도 바꿨다.** 캐시는 *같은* workspace의 반복만 줄인다.
   `workspace`는 누구나 정하는 파라미터라 **이름을 바꿔 가며** 보내면 음수 캐시든 아니든 전부
   빗나간다 — Copilot의 제안을 그대로 따랐어도 그 경우는 못 막았다. 그래서 공개 경로가
   **동시에 잡는 커넥션 수에 상한(1)**을 뒀다. 이름이 몇 개로 오든 풀 `max: 3` 중 둘은 언제나
   로그인·저장의 몫으로 남는다.

   ```
   × 공개 경로는 커넥션을 동시에 하나만 잡는다 (#238 리뷰 2차)
   AssertionError: 공개 경로가 커넥션을 동시에 여러 개 잡았습니다: expected 20 to be 1
   ```

**검증(#240)**: `check` 516 passed · `e2e` OK · `visual-check` OK · `audit` 0 ·
계약 54 · **빈 DB에서 `e2e:server` 5회 연속 51 passed**(수정 전 1/3 실패).

**남는 교훈 두 가지.** (a) 게이트를 골라 돌리면 고른 만큼만 안다 — 이번에 건드린 것이 서버 경로인데
`e2e:server`를 건너뛰었다. (b) **"CI가 초록"과 "결함이 없다"는 다른 말이다.** 3회 중 1회 깨지는
경합은 한 번의 초록으로 가려진다.

### 05가 실제로 작동했다 — 그리고 그것이 이 라운드의 핵심이다

**계측이 스무 라운드 만에 처음으로 말했다.** `서빙 인증 모드: local`은 **예상된 값이고 실패가 아니다** —
이번 라운드는 켤 준비만 했지 켜지 않았기 때문이다. 확인된 것은 세 가지다:

1. 표식이 서빙 번들에 실제로 실렸다(없으면 워크플로가 `::error::`로 **실패**하도록 만들어 뒀다).
2. 읽어낸 값이 지금의 실제 상태(`local`)와 맞다.
3. 로컬 모드일 때 **경고가 실제로 뜬다**(`##[warning]`) — 요약 카드에도 ⚠️ 줄이 붙는다.

즉 다음에 누군가 `VITE_AUTH_MODE`를 넣거나 빼면, **그 사실이 배포마다 자동으로 보고된다.**
28-68 이후 스무 라운드 동안 아무도 이것을 몰랐던 상태가 여기서 끝난다.

### 이 확인이 말하지 않는 것

- **01·02·04의 가드는 번들에 들어가지 않는다.** 테스트 시점에만 도는 것이라 배포 확인의 대상이
  아니고, 그 값어치는 CI가 증명한다(§1·§2).
- **03의 TTL·단일 비행은 배포는 됐지만 라이브에서 실행되지 않는다.** 로컬 모드에서는
  `/api/public-stats`를 부르는 코드 경로 자체가 돌지 않는다. 서버 모드로 켜는 날 실제로 확인된다.
- **`bandut-auth-mode:server` 경로는 로컬 빌드로만 확인됐다**(§2 05). 프로덕션에서 그 값을 보는 것은
  켜는 날의 일이다.

이번 §5가 확인하는 것은 **라운드 문자열이 반영됐다**는 사실과 **모드 계측이 살아 있다**는 사실
둘이다. 그 이상을 주장하지 않는다.
