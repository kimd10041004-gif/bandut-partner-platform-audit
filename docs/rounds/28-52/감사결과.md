# 28-52 감사결과 (GPT 역할 — Claude 세션 대리 수행)

감사 범위: `28-52` 전체 — 계정 보안 반영 후, **낙찰 전 수정 경로(요청·견적)** 점검.
사전 확인: `npm run check` exit 0 (vitest 218/218), e2e 119/119 PASS, visual-check 전 항목 PASS, `npm audit` 0건, 프로덕션 배포 그린(PR #138 머지). 28-51 감사 4건 전부 수정 확인됨.

핵심 지적: 요청은 올리는 순간 **고정**된다. 고객이 지역을 잘못 적거나 희망일이 바뀌면(집수리에서 흔하다) 취소하고 새로 올려야 하고, 그러면 사진·답변·이미 받은 견적이 전부 사라진다. 파트너 쪽도 같다 — 채팅으로 현장 사정을 듣고 나서 금액을 고치고 싶어도 "재제출은 자기 견적 교체"라는 규칙이 코드에만 있고 화면에는 없으며(카드에 "내 입찰 완료"만), 고객은 견적이 바뀌었는지 알 길이 없다. 입찰을 물리는 방법도 없어 파트너는 마감까지 묶인다. 낙찰 전 수정은 **기록(횟수·시각)과 통지**만 있으면 안전하다.

## 상 (High)

### 28-52-01 · 고객 요청 수정
→ 요구: `updateRequest(requestId, patch, today)` — 낙찰 전(`requested`/`estimated`)만. 수정 가능: `description`·`region`·`desiredDate`·`desiredTime`·`budget`·`budgetRange`·`answers`(카테고리는 불가 — 질문·매칭의 축). `addRequest`와 같은 검증(빈 문자열·날짜·시간대·예산·답변). 희망일이 현재 마감보다 앞당겨지면 마감을 기본값으로 재계산. `editedAt`·`editCount` 기록. 입찰자 전원에게 계정 범위 알림("요청 내용이 수정되었습니다 — 견적을 확인해 주세요"). **도메인 테스트 필수**(상태·검증·마감 재계산·알림·스냅샷).

### 28-52-02 · 파트너 견적 수정·입찰 철회
→ 요구: `submitEstimate` 재제출 시 `StoredEstimate.revision`(n차)·`submittedAt` 기록 + 고객 알림 "견적이 수정되었습니다 (n차)". `withdrawBid(requestId, partnerId, today)`: 낙찰 전·마감 전, 내 입찰만, 제거 후 남은 입찰이 없으면 `requested`로(재오픈 메서드 확장), 고객 알림(남은 견적 수). 낙찰 후 철회(28-50)와 달리 **신뢰 지표에 기록하지 않는다**(낙찰 전 철회는 정상 행위). 테스트.

## 중 (Medium)

### 28-52-03 · 화면
→ 요구: 고객 거래 상세(낙찰 전) "요청 수정" → 인라인 폼(내용·지역·희망일·시간대) + 저장, "수정됨 n회" 표시(`[data-edit-count]`). 파트너 일감 카드: 내 입찰이 있으면 "견적 수정"(폼 대상 선택) + "입찰 철회", "내 입찰 완료 (n차 수정)". 고객 견적함 견적 카드에 "n차 수정" 태그(`[data-revision]`).

### 28-52-04 · e2e + 실측
→ 요구: e2e — 고객 요청 수정 → 상세 반영·수정됨 표시 → 파트너 견적 수정 → 견적함 "1차 수정" 태그·금액 변경 → 파트너 입찰 철회 → 일감 탭 다시 입찰 가능(입찰 0건). 검증·마감 재계산·알림은 vitest. 실측: 수정 폼·수정 태그·철회 후 카드.
