# 프리뷰·운영 DB 분리 확인 기록

> **결론 (2026-09-11): 갈라져 있다.** 같은 쿼리가 두 Neon 브랜치에서 다른 답을 냈다 — 한쪽은
> 표가 없고 한쪽은 있다. 주소 비교가 아니라 데이터 자체의 차이다. 근거는 §2, 판정은 §3.

이 문서는 **채워 넣는 문서**다. 각 줄이 실제로 확인된 뒤에만 그 자리에 결과를 적는다.
빈칸은 "아직 확인 안 됨"이고, 그 상태에서는 "분리 확인 완료"라고 쓰지 않는다.

## 0. 지금 막혀 있는 것 — 운영에는 표식 조회 기능이 없다

확인했다. `origin/main`(운영)은 **29.4.0** 이고 다음이 **없다.**

```
components/marketplace/diagnostics.tsx   없음 (진단 화면 자체가 없다)
server/dbFingerprint.ts                  없음
server/dbProbe.ts                        없음
server/handlers/auth.ts                  파일 자체가 없음 (dbInfo op 없음)
db/schema.sql 의 diagnostic_probes       없음
```

즉 **운영 화면에서 표식을 조회하는 방법이 오늘은 없다.** 화면을 열 수조차 없다.

그것을 만들려면 `round-29-5`(29-5 ~ 29-17, CI 미확인 일곱 커밋)를 운영에 배포해야 한다.
**그렇게 하지 않는다.** 미검증 커밋을 검증 도구를 얻자고 먼저 병합하는 것은 순서가 뒤집힌 것이다.

### 대신 쓰는 길 — Neon SQL 콘솔에서 직접 읽는다

배포 없이 운영 DB 를 **읽기만** 해서 같은 판정을 얻을 수 있다. Neon 콘솔에서 **운영 브랜치**를
고르고 아래를 실행한다(읽기 전용, 아무것도 바꾸지 않는다).

```sql
-- (가) 표 자체가 있는가
select to_regclass('public.diagnostic_probes') as probe_table;

-- (나) 프리뷰에서 남긴 그 ID 가 여기에도 있는가
select id, deploy_env, created_at
from diagnostic_probes
where id = '여기에_프리뷰_표식_ID';
```

판정은 이렇게 읽는다.

| (가) 결과 | (나) 결과 | 뜻 |
|---|---|---|
| `null` | (실행 불가) | 운영 DB 에 표가 없다 → 프리뷰는 이 DB 를 건드리지 않았다 → **갈라져 있다** |
| 표 이름 | 0행 | 표는 있는데 그 표식이 없다 → **갈라져 있다** |
| 표 이름 | 1행 | 같은 데이터다 → **갈라지지 않았다.** 여기서 멈춘다 |
| 쿼리 오류 | — | **판정 안 함.** 실패는 "없음"이 아니다 |

마지막 줄이 중요하다. 화면에서도 같은 규칙을 지킨다 — 조회가 실패하면 "표식 없음"이 아니라
"조회하지 못했습니다"라고 쓰고, 그 결과로는 분리를 판단하지 말라고 적는다(29-17-1).

## 1. Neon 브랜치 확인

| 항목 | 값 | 확인자 |
|---|---|---|
| 운영 브랜치 이름 | `main` (Default) | 사장님, Neon 콘솔 화면 |
| 프리뷰 브랜치 이름 | `preview` | 사장님, Neon 콘솔 화면 |
| 두 브랜치가 서로 다른가 | 예 — 콘솔에 2개로 나온다 | 사장님 |
| 프리뷰 브랜치의 호스트(앞머리) | `ep-icy-mountain-auwe7oha` | 사장님, preview 브랜치 Connect |
| 운영 브랜치의 호스트(앞머리) | | |

프리뷰 배포가 보고 있는 호스트도 `ep-icy-mountain-auwe7oha-pooler...` 다. 즉 **프리뷰 배포는
`preview` 브랜치에 붙어 있다.** `DATABASE_URL_PREVIEW` 는 제대로 설정돼 있고, 고칠 것이 없다.

마지막 칸(운영 브랜치 호스트)은 비워 뒀다. 두 브랜치의 호스트가 실제로 다른지까지 적어 두면
기록이 완성되지만, **분리 판정은 이 칸이 아니라 아래 표식이 한다.** 주소가 달라도 같은 데이터를
가리킬 수 있고, 반대로 주소만 보고는 아무것도 확정할 수 없기 때문이다.

### 화면이 잘못 말했던 것 (29-17-2에서 고쳤다)

이 배포의 진단 화면이 한동안 **"접속 대상 — 운영과 같음"** 이라고 띄웠다. 틀린 말이었다.
프리뷰 배포가 보는 `DATABASE_URL` 은 Preview 환경에 걸린 값이지 Production 환경의 값이 아니다.
배포는 자기 환경의 변수만 받으므로 프리뷰에서 운영 환경변수를 읽을 방법이 없다. 이 문구를 보고
Vercel 설정을 다시 확인하셨지만, **설정에는 문제가 없었다. 화면이 틀렸다.**

## 2. 실제로 쓴 방법 — 표 존재 여부 대조 (2026-09-11)

표식을 남기고 ID 를 대조하는 대신, **표 자체가 있는지**를 두 브랜치에서 각각 읽었다. §0 에
적어 둔 그 길이다 — 표가 아예 없으면 그 DB 는 29-17 이후 코드가 한 번도 닿은 적이 없다는 뜻이라
그 자체로 결론이 난다. 쓰기가 한 줄도 없고, 운영 배포에 조회 화면이 없어도 된다.

Neon SQL 콘솔에서 두 브랜치에 각각 실행했다(읽기 전용).

```sql
select to_regclass('public.diagnostic_probes');
```

| 브랜치 | 결과 | 소요 |
|---|---|---|
| 한쪽 | **비어 있음** (표 없음) | 332ms |
| 다른 쪽 | **`diagnostic_probes`** (표 있음) | 230ms |

사장님이 콘솔에서 직접 실행하셨고 두 화면을 모두 확인했다. 브라우저가 표 이름을 "진단 프로브"로
자동 번역해 보여 줬는데 같은 표다.

### 어느 쪽이 어느 브랜치인가 — 이것은 추론이다

화면에 브랜치 이름이 함께 찍히지 않아, 어느 결과가 어느 브랜치였는지는 **관찰하지 않았다.**
다만 방향은 코드가 강제한다.

- `diagnostic_probes` 는 29-17 이후 스키마에만 있고, 서버가 첫 요청에서 스스로 만든다
  (`server/schemaBootstrap.ts`, 세 API 라우트 모두가 부른다)
- 운영(`main`)은 29.4.0 이라 이 표가 스키마에 아예 없다. 그 코드를 돌리는 배포가 없다
- 프리뷰 배포만 그 코드를 돌리고, 사장님이 거기 관리자로 로그인하셨으므로 요청이 실제로 들어갔다

그래서 **표가 있는 쪽이 `preview`, 없는 쪽이 `main`** 이다. 사람이 표를 손으로 만들지 않았다는
전제 위에 선 추론이고, 그런 일은 없었다.

**판정은 이 방향에 의존하지 않는다.** 같은 프로젝트의 두 브랜치가 같은 쿼리에 다른 답을 냈다는
것만으로 두 DB 는 서로 다른 데이터다. 주소 비교가 아니라 데이터 자체의 차이다.

### 하지 않은 것

표식 쓰기·재조회(§0 의 (나))는 하지 않았다. 표 존재 여부만으로 결론이 나서 필요가 없었다.
운영 DB 에는 읽기 쿼리 하나만 나갔고 아무것도 바꾸지 않았다.

검증을 진행해도 된다.**

## 5. 건너뛴 42건 ↔ 별도 실행 대응표

`npm run check` 에는 `DATABASE_URL` 이 없다. DB 가 필요한 파일은 `describe.skipIf(!DB_URL)` 로
통째로 건너뛴다. 아래가 그 42건이 어디서 실제로 도는지의 대응표다.

| 건너뛴 파일 | 건수 | 실제 실행 명령 | 그 실행의 결과 | 무엇을 보나 |
|---|---|---|---|---|
| `src/domain/ports.contract.test.ts` | 16 | `test:contract` (+ API 서버) | **58 통과** (Local·Memory·Http 세 구현 합계) | 결제 API 권한(관리자만 환불), 스냅샷 세션·토큰 폐기·가입 코드·413·405, 복제 합성 |
| `tests/marketplace.http.test.ts` | 13 | `test:mp` | **13 통과** | 세션→v17 역할, 관리자 403, CSRF, 주문 한 바퀴, 업체 찾기·Q&A·페이지·상담 |
| `tests/dbProbe.http.test.ts` | 4 | `test:probe` | **4 통과** | 표식 쓰기·읽기, 운영 거절, 열람 등급 거절 |
| `tests/pg.port.test.ts` | 3 | `test:pg` | **3 통과** | 자리표시자, 주문 한 바퀴, 트리거 |
| `tests/passwordReset.http.test.ts` | 3 | `test:reset` | **3 통과** | 세션 폐기, 발송 불가 차단, 코드 비노출 |
| `server/schemaBootstrap.test.ts` | 2 | DB 있으면 `check` 안에서 | **6 통과**(파일 전체) | 빈 DB 스키마 자동 적용, 동시 호출 1회 |
| `tests/signupJourney.http.test.ts` | 1 | `test:journey` | **1 통과** | 가입→재로그인→업체 제출→승인→권한 |

건너뛴 42건 = 16 + 13 + 4 + 3 + 3 + 2 + 1. **인증·권한·DB 가 전부 포함된다** — 오히려 이 42건이
그 영역의 핵심이다. CI 의 `server` 작업은 Postgres 를 띄우고 이것들을 반드시 돌린다.

`test:contract` 의 58 은 건너뛴 16 과 숫자가 다르다. 같은 계약을 세 구현(Local·Memory·Http)에
돌리는데, `check` 에서는 DB·API 서버가 필요한 Http 쪽 16건만 건너뛰기 때문이다.
