# 29-17 — 접속 대상과 데이터 분리를 나눈다

## 1. 한 문장이 두 가지를 뭉개고 있었다

`/admin/diagnostics` 는 호스트와 DB 이름을 비교해 **"분리됨"** 이라고 썼다. 그 말이 지나쳤다.

주소가 다르다고 데이터가 다르다는 보장은 없다. 읽기 전용 복제본, 같은 클러스터의 별칭,
풀러와 직결 엔드포인트 — 서로 다른 접속 주소가 같은 데이터를 가리키는 경우가 여럿 있다.
주소 비교는 분리의 **필요조건이지 충분조건이 아니다.**

그래서 두 줄로 나눈다.

| 줄 | 무엇을 말하나 | 무엇으로 아나 |
|---|---|---|
| **접속 대상** | 운영과 다른 곳에 붙는가 | 호스트·DB 이름 비교 (`dbFingerprint`) |
| **데이터 분리** | 데이터가 정말 갈라져 있는가 | 표식 (`dbProbe`) |

필드 이름도 `separated` → `differentTarget` 으로 바꿨다. 이름이 사실보다 앞서가지 않게.

## 2. 표식으로 확인한다

프리뷰에서 표식을 하나 남기고, **운영 화면에서 그 표식이 보이지 않는 것**을 사람이 눈으로
확인한다. 보이면 같은 데이터다. 안 보이면 갈라져 있다.

```
diagnostic_probes (id, deploy_env, created_at)
```

이 방식이 가진 값은 **운영 접속 정보를 프리뷰로 가져오지 않는다**는 것이다. 한쪽 화면에서
양쪽을 비교하려면 운영 주소를 프리뷰 환경에 넣어야 하는데, 그것이야말로 우리가 막으려는 일이다.
두 배포가 각자 자기 DB 만 읽고, 대조는 사람이 한다.

**운영에는 표식을 남기지 않는다.** `VERCEL_ENV === 'production'` 이면 서버가 400 으로 거절하고,
화면에도 쓰기 단추가 나오지 않는다. 표는 만들되 행은 넣지 않는다. 지우는 코드도 두지 않았다 —
사장님이 "기존 데이터 삭제나 초기화는 하지 마세요"라고 하셨고, 표식은 몇 바이트짜리 행이다.

표식 남기기는 `operate` 등급이다. 열람 등급 관리자는 읽기만 한다.

## 3. 검사

`tests/dbProbe.http.test.ts` 네 건. 셋째 줄이 이 검사의 이유다.

```
✓ 표식을 남기면 그 DB 에서 실제로 읽힌다
✓ dbInfo 가 그 표식을 함께 준다 — 화면이 대조할 목록이다
✓ 운영에서는 표식을 남기지 않는다 — 이 줄이 이 검사의 이유다
✓ 열람 등급은 표식을 남길 수 없다 — 쓰기다
```

`npm run test:probe` 로 돌리고 CI 의 `server` 작업에 넣었다.

## 4. 사장님이 하실 일 — 순서대로

1. **Neon 에서 프리뷰 전용 브랜치를 만든다.** 기존 브랜치를 가리키는 다른 주소가 아니라
   **별도 브랜치**여야 한다. 브랜치마다 호스트가 다르다.
2. 그 브랜치의 연결 문자열을 Vercel → 이 프로젝트 → Settings → Environment Variables 에서
   **`DATABASE_URL_PREVIEW`** 이름으로, **Preview 환경에만** 넣는다. 값은 채팅으로 주지 않으신다.
3. 새 프리뷰 배포가 뜨면 `/admin/diagnostics` 에서 **접속 대상 = 운영과 다름**을 확인한다.
4. 같은 화면에서 **표식 남기기**를 누른다. 표식 ID 를 적어 둔다.
5. 운영 주소의 같은 화면을 열어 **그 표식이 없는 것**을 확인한다. 여기까지 와야 분리 확인이다.
6. 그 뒤에 가입 → 재로그인 → 업체 제출 → 관리자 승인 → 권한 반영을 실제 브라우저로 돈다.

## 하지 않은 것

- **Neon API 로 브랜치 여부를 직접 조회하는 것.** API 키가 필요하고, 그 키를 배포 환경에 두는
  것이 새 위험이다. 브랜치 구분은 호스트로 보이고, 확정은 표식이 한다.
- **운영 표식 자동 삭제.** 애초에 운영에는 넣지 않는다.

# 29-17-2 — 이 화면은 운영과 비교할 수 없다

## 1. 화면이 없는 사실을 말하고 있었다

프리뷰 배포의 `/admin/diagnostics` 가 이렇게 띄웠다.

```
접속 대상   운영과 같음 — 이 배포는 운영과 같은 곳에 접속합니다
```

이 줄을 만든 코드는 이랬다.

```ts
differentTarget: isPreview ? usingPreviewUrl && !same(preview, env['DATABASE_URL']) : null
```

**프리뷰 배포가 보는 `DATABASE_URL` 은 Preview 환경에 걸린 값이다.** Production 환경의 값이
아니다. 배포는 자기 환경의 변수만 받는다 — 프리뷰에서 운영 환경변수를 읽을 방법이 애초에 없다.
그러니 저 비교로는 운영을 말할 자격이 없다. 화면은 확인하지 않은 것을 확인했다고 썼다.

사장님이 저 줄을 보고 Vercel 설정을 다시 들여다보셨다. 설정에는 문제가 없었다. **잘못된 것은
화면이었다.** 없는 근거로 사람을 움직인 것이라, 진단 도구로서는 가장 나쁜 종류의 오류다.

## 2. 비교 상대가 없을 때도 "다름"이라고 답했다

같은 줄에 두 번째 구멍이 있었다. `DATABASE_URL` 이 비어 있으면 `same()` 이 빈 주소
(`{host:'', database:''}`)와 비교해 놓고 "다르다"고 답했다. 프리뷰 환경에 `DATABASE_URL_PREVIEW`
만 걸고 `DATABASE_URL` 을 걸지 않는 설정은 흔하다. 그 설정에서 이 화면은 **아무것도 확인하지
않은 채 "갈라져 있다"** 고 말한다.

수정 전 코드에서 실제로 나온 출력이다.

```
FAIL  server/dbFingerprintPrefix.test.ts > 비교할 기본값이 아예 없어도 "다름"이라고 단정한다
AssertionError: expected true to be null

- Expected:  null
+ Received:  true
```

**없는 것과 다른 것은 다르다.** 분리 판정을 뒤집는 종류의 오류라 29-17-1(조회 실패를 "없음"으로
접지 않는다)과 같은 급으로 다룬다.

## 3. 말할 수 있는 것까지만 말한다

필드 이름을 `differentTarget` → `differentFromFallback` 으로 바꿨다. 비교 상대가 무엇인지
이름에 넣었다 — **이 배포의 기본값**이지 운영이 아니다.

| 값 | 뜻 |
|---|---|
| `true` | 지금 붙은 곳이 이 배포의 기본값(`DATABASE_URL`)과 다른 곳이다 |
| `false` | 같은 곳이다 |
| `null` | 비교할 기본값이 없다 — **모른다** |

화면도 같이 바꿨다.

```
이 배포의 기본값   ep-xxxx-pooler... / neondb   (또는 "설정돼 있지 않음")
지금 붙은 곳       기본값과 다른 곳입니다
```

그 아래에 한 줄을 고정으로 둔다.

> **이 화면은 운영과 비교하지 못합니다.** 배포는 자기 환경의 변수만 받기 때문에, 이 배포가 보는
> 기본값은 이 환경에 걸린 값이지 운영의 값이 아닙니다. 게다가 주소가 달라도 같은 데이터를 가리킬
> 수 있습니다. 운영과 갈라졌는지는 아래 표식으로만 확인됩니다.

기본값의 호스트·DB 이름도 화면에 같이 띄운다. "지금 붙은 곳"과 나란히 보이면 사람이 직접 대조할
수 있고, 우리가 대신 결론 내리지 않아도 된다. 비밀은 여전히 담기지 않는다 — 호스트와 DB 이름뿐이다.

**운영과의 대조는 표식 하나만 남는다.** 그것이 29-17에서 표식을 만든 이유였고, 이제 화면에
경쟁하는 다른 판정이 없다.

## 4. 검사

`server/dbFingerprint.test.ts` 8건. 두 줄이 이 라운드의 이유다.

```
✓ 비교할 기본값이 없으면 다르다고 말하지 않는다 — 없는 것과 다른 것은 다르다
✓ 비교 상대는 이 배포의 기본값이다 — 운영 값이 아니다
```

# 29-17-3 — 만들었지만 닿지 않는 화면

## 1. 메뉴에 없는 화면을 만들어 놓고 주소를 불러 드렸다

`/admin/diagnostics` 는 29-11에 만들어 29-17까지 세 번 고쳤다. 그런데 **왼쪽 메뉴에 넣지 않았다.**
라우트는 살아 있는데 화면 어디에도 그리로 가는 길이 없었다. 그래서 사장님이 그 화면을 여실 때마다
우리가 채팅으로 주소를 불러 드려야 했고, 실제로 그렇게 했다.

만들었지만 닿지 않는 화면은 만들지 않은 것과 같다. 사람이 주소를 외우는 것으로 때우면 그 부채는
드러나지 않고 계속 쌓인다.

**사이트 운영 → 저장소 진단**으로 넣었다.

## 2. 같은 실수를 기계가 잡게 한다

`lib/adminRoutes.test.ts` — 라우터가 처리하는 `admin/...` 경로를 전부 걷고, 그 각각이 관리자
메뉴에 링크로 있는지 본다. 수정 전 출력이다.

```
FAIL  주소를 직접 쳐야만 닿는 관리자 화면이 없다
AssertionError: expected [ 'admin/diagnostics' ] to deeply equal []

- []
+ [ "admin/diagnostics" ]
```

정확히 하나였다. 일부러 메뉴에 두지 않는 경로는 `UNLISTED` 에 **이유와 함께** 적는다
(`admin/dashboard` 가 `/admin` 과 같은 화면이라 한 줄만 둔다). 조용히 빠뜨리는 것과 이유를 적고
빼는 것은 다르다.

이 가드의 한계도 적어 둔다 — 문자열 대조라서 **링크가 실제로 보이는지**(권한·반응형·접힘)는
검사하지 못한다. 막는 것은 "메뉴에 넣는 걸 잊는 것"이지 "잘못 넣는 것"이 아니다.

## 3. README 를 지금 상태로 맞췄다

README 첫머리가 SPA 시절 그대로였다. 셋을 고쳤다.

**접속 주소를 표로 정리했다.** 운영·프리뷰 주소와, 역할별 로그인 문을 나눠 적었다. 관리자 문은
`/login/admin` 한 자리뿐인데(29-10) README 는 `/admin` 이라고만 적혀 있어 로그인 주소처럼 읽혔다.

**계정 값을 지웠다.** `관리자 초기 계정: admin / bandut1234!` 가 그대로 적혀 있었다. 서버는 이
값을 거부하지만(`ADMIN_PASSWORD` 가 시연값이면 503), 비밀번호를 저장소에 적어 두지 않기로 한
규칙에 어긋난다. `UI_가이드.md` 의 같은 줄도 고쳤다.

`scripts/e2e-server.mjs` 와 `server/handlers/auth.test.ts` 에 남은 같은 문자열은 **그대로 둔다.**
그 줄들은 "이 값으로는 로그인되지 않는다"를 증명하는 단언이라, 지우면 가드가 사라진다.

**저장소 구조를 다시 썼다.** `app/` · `components/` · `lib/` 가 한 줄도 없고, 없어진 루트 `api/`
가 남아 있었다. 게이트 목록에도 `e2e:next` · `e2e:layout` · `test:journey` · `test:probe` 가
빠져 있었다. DB 검사가 `check` 에서 통째로 건너뛰고 CI 의 `server` 작업에서 도는 것도 적었다.

## 4. 검사

`lib/adminRoutes.test.ts` 3건. 첫 줄이 유도가 헛도는 것을 먼저 막고(경로를 하나도 못 찾으면
가드는 언제나 통과한다), 둘째 줄이 이 파일의 이유다.
