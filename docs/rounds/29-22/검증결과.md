# 29-22 검증결과

## 1. 봇이 첫 실행에서 진짜 결함을 잡았다

새 검사를 만들면 보통 먼저 자기가 틀린다. 이번은 아니었다 — **첫 실행이 앱의 결함에서 죽었다.**

```
[e2e:roles] http://127.0.0.1:3216 (로컬)
[e2e:roles] 실행 중 오류: Error: customer 가입이 거절됐습니다: 서버 저장소 오류 — 잠시 후 다시 시도해 주세요

--- 서버 로그 ---
[api/auth] duplicate key value violates unique constraint "auth_state_pkey"
```

고객과 파트너를 `Promise.all` 로 같이 가입시킨 첫 줄에서 났다. 이것이 이 라운드의 근거다 —
**차례로 도는 검사는 이 줄을 영원히 통과한다.**

## 2. 그것을 테스트로 붙잡았다

`tests/concurrentSignup.http.test.ts`. 수정 전 실패:

```
× 빈 저장소에 두 사람이 동시에 가입해도 둘 다 들어간다
  AssertionError: expected [ 200, 503 ] to deeply equal [ 200, 200 ]
  [ 200, -200 +503 ]
```

같은 파일의 둘째 줄 — **행이 선 뒤의 동시 가입** — 은 수정 전에도 통과했다. 그 대비가 원인을
가리킨다: `for update` 는 행이 있을 때만 잠근다.

수정 뒤 둘 다 통과.

## 3. 두 번째 실행이 두 번째 것을 잡았다

경쟁을 고치니 봇이 끝까지 돌았고, 거기서 한 줄이 빨갰다.

```
✓ 관리자: 관리자 화면 15장이 모두 자기 내용을 그린다
✓ 고객: 관리자 화면 15장이 모두 막힌다
✗ 파트너: 관리자 화면 15장이 모두 막힌다 — /admin/settlements (막히지 않았다)
```

실패가 **어느 주소인지 이름으로** 말한다. 29-20-3 에서 이유 없는 실패 하나 때문에 두 번을
헛돈 뒤로, 실패에 이유를 싣는 것을 규칙으로 두고 있다.

새는 것은 없었다(§4에서 확인). 주소가 게이트를 정하도록 고쳤다.

## 4. 새지 않는다는 것을 코드로 확인했다

파트너가 `/admin/settlements` 를 열면 **자기 정산만** 보인다. 화면이 그렇게 그리는 것이 아니라
서버가 그것만 돌려준다.

```ts
// lib/trade.ts — ledger()
'SELECT s.*,o.title FROM settlements s JOIN orders o ON o.id=s.order_id'
  + (u.role === 'ADMIN' ? '' : ' WHERE s.partner_id=?')
```

**그래도 고친 이유**는 문서에 적어 뒀다 — 주소로 문을 나눠 놓고 한쪽만 잠그면, 다음 사람이 그
주소에 관리자 전용 기능을 얹을 때 아무도 다시 보지 않는다.

보이는 것만 재면 아무것도 확인하지 못한다.
