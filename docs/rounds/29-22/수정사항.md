# 29-22 — 세 역할을 동시에 앉혀 놓고 감사한다

## 1. 왜 동시인가

`e2e:signup`(29-18)은 한 사람이 차례로 움직인다. 그것으로 못 보는 것이 둘 있었다.

**하나. 관리자 화면을 아무도 열어 본 적이 없다.** 봇이 연 관리자 화면은 승인 목록 하나뿐이었다.
나머지 열네 장은 코드를 읽어 "게이트가 걸려 있다"고 확인했을 뿐이다. 읽은 것은 잰 것이 아니다 —
29-20 에서 로그인 성공 판정이 `/login/admin` 주소에도 맞아 **실패한 로그인이 통과로 찍힌** 적이
있다. 그때도 코드는 맞아 보였다.

**둘. 막혀야 할 문을 남이 밀어 본 적이 없다.** 파트너나 고객이 관리자 주소를 직접 치면 어떻게
되는지를 아무도 재지 않았다.

그래서 `scripts/e2e-roles.mjs` 는 관리자·파트너·고객 창을 한 브라우저에 셋 띄우고 같은 시각에
움직인다. 빨라지는 것은 덤이다. 목적은 **같은 주소를 세 사람이 동시에 열었을 때 서로 다른 답을
받는가**이다.

## 2. 재는 것 열여섯 줄

| 갈래 | 무엇 |
|---|---|
| 준비 | 두 사람이 **동시에** 가입 · 관리자 로그인 · 파트너 승인 |
| 관리자 | 관리자 화면 15장이 각각 자기 내용을 그린다 |
| 파트너 | 같은 15장이 전부 막힌다 · 자기 화면 6장은 열린다 |
| 고객 | 같은 15장이 전부 막힌다 · 자기 화면 5장은 열린다 |
| 채팅 | 고객이 상담을 걸고 → 업체 창에 도착하고 → 답이 오고 → 고객 창에 도착한다 |
| 채팅 | 관리자가 방 주소를 그대로 들고 가도 남의 대화가 보이지 않는다 |

화면이 "열렸다"를 200 으로 세지 않는다. 셸이 내거는 거절 문구가 없고 `h1` 이 있어야 열린 것으로
센다 — 빈 껍데기를 통과로 세지 않기 위해서다.

## 3. 첫 실행이 잡은 것 — 빈 저장소 동시 가입 (29-22-1)

봇이 시작하자마자 죽었다.

```
[e2e:roles] customer 가입이 거절됐습니다: 서버 저장소 오류 — 잠시 후 다시 시도해 주세요
[api/auth] duplicate key value violates unique constraint "auth_state_pkey"
```

`loadAuth` 는 행을 `select ... for update` 로 잠근다. 그런데 **행이 없으면 잠글 것이 없다.**
빈 저장소에 두 요청이 동시에 오면 둘 다 "행이 없다"를 보고 둘 다 `insert` 한다. 늦은 쪽이
기본키에서 터지고, 그 사람에게는 "서버 저장소 오류"가 나간다.

**이것은 플랫폼의 첫 두 사용자가 겪는 일이다.** 차례로 도는 검사는 구조적으로 못 본다 — 첫
요청이 끝난 뒤에는 행이 있으니까.

없는 행은 잠글 수 없으니 **이름을 잠갔다.**

```ts
await c.query('select pg_advisory_xact_lock(hashtext($1))', [`auth_state:${workspaceId}`])
```

트랜잭션 자문 잠금은 행의 존재와 무관하게 걸리고 커밋·롤백에서 자동으로 풀린다. 늦은 쪽은
기다렸다가 먼저 선 행을 읽고 그 위에 자기 계정을 얹는다.

`on conflict do update` 로 막지 않았다. 이 행은 **계정 전부**를 담은 한 덩어리라, 늦은 쪽이
자기 상태로 덮으면 먼저 가입한 사람이 조용히 사라진다. **터지는 것보다 나쁘다.**

`tests/concurrentSignup.http.test.ts` 가 이것을 붙잡아 둔다. "둘 다 성공한다"와 "둘 다 남아
있다"를 함께 본다.

## 4. 두 번째로 잡은 것 — 관리자 주소를 파트너가 열었다 (29-22-2)

```
✗ 파트너: 관리자 화면 15장이 모두 막힌다 — /admin/settlements (막히지 않았다)
```

정산 화면은 `/partner/settlement` 와 `/admin/settlements` 두 주소가 같은 부품을 쓴다. 게이트를
`kind` 로만 골라서 **두 주소의 합집합**이 됐다.

```tsx
<Access roles={kind === 'disputes' ? ['ADMIN'] : ['PARTNER', 'ADMIN']}>
```

**새는 것은 없었다.** 서버가 파트너에게는 자기 것만 돌려준다(`lib/trade.ts` 의 `ledger` 에
`WHERE s.partner_id=?`). 그래도 고쳤다 — 문을 주소로 나눠 놓고 한쪽만 잠그면, 다음 사람이 그
주소에 관리자 전용 기능을 얹을 때 아무도 다시 보지 않는다.

주소가 게이트를 정하도록 `audience` 를 넘긴다.

## 5. 안전 가드는 한 벌만 둔다

두 번째 봇을 만들면서 첫 봇의 앞부분을 베낄 뻔했다. 그 안에 베끼면 안 되는 조각이 하나 있다 —
**운영 주소 거부**다. 두 벌이 되면 언젠가 한쪽에만 호스트가 추가되고, 그날 다른 한쪽이 진짜
손님 데이터 옆에 봇 계정을 만든다.

`scripts/bot-kit.mjs` 로 한 벌만 둔다. 두 봇이 같은 함수를 부른다.

## 6. 하지 않은 것

- **주문·입찰·계약·결제 흐름의 동시 감사.** 이번 봇은 화면과 권한, 그리고 상담 채팅까지다.
  거래 채팅(주문에 붙는 쪽)과 입찰 경쟁은 다음 라운드로 넘긴다.
- **관리자 등급(소유자·열람) 분리 감사.** SPA 쪽에는 있는데 Next 관리자 화면에는 아직 등급이
  없다. 등급이 붙는 라운드에서 같이 잰다.
