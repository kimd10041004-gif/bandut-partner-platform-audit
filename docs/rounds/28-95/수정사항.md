# 28-95 수정사항 — 계약서(버전·예약금·수수료) · 일정 변경 제안·수락 (참고 v12 대조 5)

`../28-90/참고_v12_대조.md` "더할 것" 5번. 참고 시안은 낙찰 뒤 **파트너가 계약서를 발행**(예약금·조건·방문 일정, 관리자가 정한
주문별 수수료 bps를 담는다)하고 **고객이 동의**해야 일정이 확정되며, 방문 일정 변경은 **파트너가 제안하고 고객이 승인**한다
(`lib/trade.ts` `terms`/`proposeContract`/`decideContract`/`proposeSchedule`/`decideSchedule`). 28-94까지 우리는 파트너가
일정 탭에서 바로 예약했고(고객 동의 없음), 예약금은 낙찰가의 10%로 고정, 수수료는 3% 고정, 일정 변경은 양쪽 모두 단독이었다.

## A. 도메인 (`types.ts` · `platform.ts`)

- **`Contract`** `{ id CT-####, requestId, partnerId, version, total(낙찰 총액 스냅샷), deposit, commissionBps, terms, date/startHour/endHour,
  status proposed|accepted|declined|superseded, createdAt, decidedAt? }`. **`CommissionTerms`** `{ requestId, bps, reason, by, at }`.
  **`ScheduleChange`** `{ id SC-####, requestId, partnerId, date/hours, reason, status proposed|approved|rejected|superseded, … }`.
- `setCommissionTerms(requestId, bps, reason, adminId)`: 낙찰 상태·동의된 계약 없음·0~10000·사유 필수. 제안 중인 계약은 옛 수수료를
  담고 있으니 `superseded`로 돌리고 파트너에게 다시 보내라고 알린다. 운영 기록 `수수료 조건`. `commissionBpsFor` = 동의된 계약 > 관리자
  조건 > 기본 300(=`PLATFORM_FEE_RATE`).
- `proposeContract(requestId, partnerId, {deposit, terms, date, startHour, endHour}, today)`: 낙찰 파트너만, 낙찰 상태에서, 예약금
  0~총액, 조건 2자 이상, 일정은 `validateSlot`·지난 날짜·휴무일·충돌(`addSlot` 검사만, 저장 안 함). 이전 제안은 `superseded`, 버전 +1,
  고객 알림.
- `decideContract(requestId, contractId, accept, today)`: 고객. 거절 → `declined` + 파트너 알림("수정을 요청"). 동의 → 슬롯 생성 +
  `scheduled` + `accepted`, 양쪽 알림(예약금이 있으면 결제 안내). **`scheduleVisit`(직접 예약)은 계약서가 오간 요청에서는 막힌다** —
  계약 없는 구 경로(테스트 픽스처·구 데이터)에만 남는다.
- `payDeposit`: 동의된 계약이 있으면 **계약의 예약금**을 방문 예정(scheduled)에서 낸다(0원이면 거절). 계약 없는 구 경로는 종전(낙찰 상태,
  10%). `depositAmountFor(requestId)`.
- `completeJob`: 수수료 = `total × commissionBpsFor / 10000` (추가 작업까지 같은 율). 계약이 없으면 종전 3%와 같다.
- `proposeSchedule(requestId, partnerId, {date, hours, reason}, today)`: 담당 파트너·방문 예정·사유 필수, 28-56의 검증(과거·동일·휴무·
  자기 슬롯 제외 충돌) 그대로. 이전 제안 `superseded`, 고객 알림. `decideSchedule(requestId, changeId, accept, today)`: 승인이면 28-56의
  슬롯 교체 본체(`applyReschedule`)를 지나 `rescheduleCount`·알림, 거절이면 파트너 알림.
  **`rescheduleVisit(…, 'partner')`는 던진다** — 고객 직접 변경(`'customer'`)만 남는다.
- 타임라인에 `contract`(v{n} 확인 대기 / 동의) 이벤트. 스냅샷 `contracts`·`contractSeq`·`commissionTerms`·`scheduleChanges`·
  `scheduleChangeSeq` + 검증(금액·bps·일정·상태, 요청당 동의 계약 1건). 가명본: 계약·수수료·일정 변경을 담되 `terms`·`reason`(자유 서술)은
  뺀다.

## B. 화면

- **파트너 일정 탭**(`Schedule.tsx`): 낙찰 건 → "계약서 보내기"(예약금 `aria-label="계약 예약금"`, 비우면 낙찰가 10% · 조건
  `aria-label="계약 조건"` · 날짜/시각 · `[data-contract-fee]`에 총액·수수료·"v{n} 고객 확인 대기"). 방문 예정 건 → "일정 변경 제안"
  (사유 `aria-label="일정 변경 사유"`, `[data-schedule-pending]`). 결과 문구 `[data-schedule-msg]`. "방문 예약"·"일정 변경" 버튼은 없어졌다.
- **고객 거래 상세**(`CustomerHome.tsx`): 제안된 계약서 카드 `[data-contract=<id>]`(총액·예약금·수수료·방문·조건) + "계약 내용 확인"
  체크(`aria-label`) → "계약 동의" / "수정 요청". 동의된 계약 카드 `[data-contract-accepted]`. 일정 변경 제안 카드
  `[data-schedule-change=<id>]` → "변경 승인" / "거절 (기존 일정 유지)". **예약금 카드는 동의된 계약이 있을 때만**(계약 v{n} 금액),
  계약 전 낙찰 건에는 `[data-contract-wait]` 안내. 고객의 직접 "방문일 변경"은 그대로다.
- **관리자 거래 상세**(`AdminRequests.tsx`): 수수료 예상이 적용 bps로, 낙찰·계약 전에는 `[data-commission-form]`(bps·사유 → "주문별
  수수료 확정"), 계약 이력 `[data-contract-history]`.
- **파트너 내 작업**: 낙찰 건에 `[data-contract-hint]`("계약서 v{n} 고객 확인 대기" / "계약서 보내기는 '일정' 탭에서").

## C. 하지 않은 것

- 참고안처럼 관리자 수수료 확정을 **계약 발행의 전제**로 두지 않았다 — 기본 3%가 있어 막을 이유가 없다(정하면 우선한다).
- 계약서 본문(PDF·전자서명)은 없다. `terms`는 한 줄 자유 서술이다.
- 예약금 0원 계약이면 결제 없이 바로 방문 예정이다(참고안과 같다). 최종 결제는 종전대로 완료 뒤.
- 계약 동의 뒤 고객이 직접 일정을 바꾸는 28-56 경로는 그대로 두었다(고객이 당사자다). 파트너만 제안 경로다.
