# 28-75 수정 사항 — 「보관함이 진 의무를 지게」

**사용자 결정: 감사 4건만.**

28-74는 보관함(28-72-03이 만든, 덮이는 스냅샷을 지키는 장치)을 **정식 시민**으로 만들었다 — 용량 회계에 넣고,
예산을 두고, 전체 목록을 꺼낼 수 있게 했다. 이번 감사(`28-74/감사결과.md`)가 짚은 것은 그 다음이다:
**정식 시민이 되면서 생긴 의무를 아직 아무도 지지 않는다.** 용량은 먹기 시작했는데 치울 수 있는 사람은
관리자뿐이고, 보관에 실패해도 화면은 보관했다고 말한다. 그리고 같은 라운드가 넣은 신뢰 IP는
전화번호를 키에 담은 채 만료되지 않는다.

---

## 28-74-01 (상) 보관은 **남은 자리**를 넘지 않는다

28-74의 예산은 한도의 1/4 **고정**이었다. 스냅샷이 이미 76%를 쓰고 있어도 그만큼을 더 보관하므로,
보관 뒤 합계가 한도를 넘고 `assertRoom`이 그 기기의 **모든 저장을 막는다**. 그리고 보관함을 비우는 화면은
관리자에게만 있으므로(`AdminSettings.tsx` 한 곳) 파트너·고객 기기는 풀 방법이 없다.
"저장을 막느니 보관을 포기한다"는 예산의 취지가 그 기기에서는 뒤집혀 있었다.

```ts
// bootstrap.ts — 상한과 **남은 자리** 중 작은 쪽
export function stashBudget(platform: PlatformService): number {
  const u = platform.storageUsage()
  return Math.max(0, Math.min(OVERWRITTEN_BUDGET, u.limit - u.chars))
}
// 지금 있는 보관함은 어차피 이번 쓰기로 덮이므로 빼지 않는다
stashOverwritten(storage, body, at, stashBudget(platform))
```

이제 보관 뒤의 합계가 한도를 넘지 않는다 — **보관이 저장을 막는 일이 구조적으로 사라진다.**
자리가 없으면 보관하지 않고(그것이 28-73-01이 정한 우선순위다), 그 사실은 아래 04가 말한다.
관리자 전용 UI 자체는 이번 범위(감사 4건)에서 옮기지 않는다 — 막지 않게 된 이상 급한 문제가 아니고,
역할 무관 자리로 옮기는 것은 화면 3개를 건드리는 별개의 결정이다. 이월한다.

## 28-74-02 (상) 탈퇴·파기가 전화번호를 정말로 지운다 + 신뢰 IP가 실제로 만료된다

`trustedIps`의 키는 `acct|${role}:${전화번호}`다. 28-73-03은 TTL 30일을 `rememberTrustedIp` 안에서만,
즉 **그 계정이 다시 성공적으로 로그인할 때만** 적용했다. 탈퇴·파기·휴면 계정은 다시 오지 않으므로 영영 남았다.
`withdraw`의 안내는 "식별 정보는 즉시 파기되었고"라고 말하는데, 계정 행만 비우고 있었다.

두 곳을 고쳤다:

```ts
// 탈퇴 — 번호를 아직 아는 지금 버린다 (파기 시점에는 phone이 이미 '')
this.forgetAccountKeys(account.role, account.phone)   // trustedIps + loginFails의 그 번호 키 전부
account.name = '탈퇴 회원'; account.phone = ''; ...

// login() — pruneLoginFails 옆에서 시간으로도 쓸어낸다
this.pruneTrustedIps(now)   // 30일 지난 IP·빈 계정 항목 (그 계정이 다시 오지 않아도)
```

앞의 것이 이후를 막고, 뒤의 것이 **이미 남아 있는 것**을 30일 안에 정리한다.

## 28-74-03 (중) 믿을 수 없는 IP로는 면제도 기록도 하지 않는다

`api/auth.ts`는 `clientIpOf`에서 IP와 `trusted`를 함께 받고, 못 믿으면 경고까지 찍는다. 그러면서
로그인에는 IP만 넘겼다. 헤더가 없으면 그 값은 모두가 공유하는 `'unknown'`이고, 그것이 신뢰 IP로 기록되면
그 뒤 **누구나** 그 계정의 계정 잠금(30회)에서 면제된다. 코드가 방금 "못 믿는다"고 외친 값으로
잠금을 면제할지 정한 셈이다.

```ts
const { ip, trusted: ipTrusted } = clientIpOf(req.headers)
warnUntrustedIpOnce(ipTrusted)
const lockScope = ipTrusted ? ip : undefined     // 못 믿으면 범위 없이 간다
...
auth.login(..., { ...(lockScope !== undefined ? { lockScope } : {}) })
```

`isTrustedIp`/`rememberTrustedIp`는 범위가 없으면 면제도 기록도 하지 않는다 — 28-73-03의 주석이
이미 그렇게 말하고 있었고, 이제 경계가 그 계약을 지킨다. 서버 e2e가 이 환경(프록시 없음)이라
`auth_state`에 `'unknown'`이 남지 않는지 그 자리에서 확인한다.

## 28-74-04 (중) "보관했습니다"는 보관했을 때만

복제기의 문구는 `overwroteLocal` 하나만 보고 정해졌다. 보관은 최선 노력이라 두 갈래로 실패한다 —
`setItem`이 던지거나(할당량), 예산에 안 들어가거나(01로 더 흔해졌다). 그때도 "덮인 내용은 보관했습니다"라고
말하면, 잃었을 때 잃지 않았다고 알리는 것이다. 사용자는 그 말을 믿고 되살리기를 시도하지 않는다.

```ts
stash?: (body: string, at: string) => boolean          // void → boolean
...
stashed = this.stash?.(mine, new Date(this.now()).toISOString()) === true
...
: stashed
  ? '... 덮였습니다(덮인 내용은 보관했습니다)'
  : '... 덮였습니다(저장 공간이 없어 보관하지 못했습니다)'
```

## PR 리뷰(Copilot) 반영 1건

**보관 실패의 원인을 단정하지 않는다 (`src/domain/replicator.ts`).** 04를 고치면서 실패 문구를
"저장 공간이 없어 보관하지 못했습니다"로 썼는데, `stashed === false`는 예산 초과·할당량 초과만이 아니라
**저장소가 아예 없는 경우**(비공개 모드 등)나 `stash`를 넘기지 않은 경우에도 나온다. 원인을 찍어 말하면
이 항목이 없애려던 "말과 사실의 어긋남"을 다른 자리에 다시 만드는 셈이다.
문구를 "(보관하지 못했습니다)"로 줄이고, 회귀에 `expect(detail).not.toContain('저장 공간')`을 더해
다음 사람이 원인을 다시 써 넣지 못하게 고정했다.
