# 28-55 감사결과 (GPT 역할 — Claude 세션 대리 수행)

감사 범위: `28-55` 전체 — 데이터 위생 반영 후, **같은 브라우저의 여러 탭이 한 저장소를 공유할 때의 정합성** 점검.
사전 확인: `npm run check` exit 0 (vitest 226/226), e2e 133/133 PASS, visual-check 전 항목 PASS, `npm audit` 0건, 프로덕션 배포 그린(PR #150 머지 `8df3e5e`). 28-54 감사 4건 전부 수정 확인됨.

핵심 지적: 이 플랫폼의 시연 방식 자체가 **한 브라우저에서 고객·파트너·관리자 탭을 나란히 여는 것**인데(역할별 세션이 한 저장소에 공존하는 설계, 28-30), 각 탭은 기동 시 스냅샷을 한 번 읽어 메모리에 들고 이후 **자기 메모리를 통째로 저장소에 덮어쓴다**. 고객 탭에서 요청을 올려도 파트너 탭은 새로고침 전까지 모르고, 그 사이 파트너 탭이 프로필을 저장하면 고객의 요청이 **조용히 사라진다**(last-write-wins, 감지 없음). 인증도 같다 — 한 탭에서 로그아웃해도 다른 탭은 계속 로그인 상태다. 28-50에서 "무언의 유실"을 저장 실패에 대해 막았지만, 탭 간 덮어쓰기라는 더 흔한 유실 경로가 남아 있다.

## 상 (High)

### 28-55-01 · 스냅샷 리비전 + 저장소 동기화
→ 요구: 스냅샷에 `rev`(저장마다 +1)와 `savedAt`. `save()`는 별도 키(`<key>:rev`)에도 리비전을 써서 다른 탭이 큰 JSON을 파싱하지 않고도 변경을 감지하게 한다. `syncFromStorage()`: 저장소 리비전이 메모리와 다르면 스냅샷을 다시 적용하고 true. 앱 셸이 `storage` 이벤트·탭 포커스·`visibilitychange`에서 호출해 화면을 갱신하고, 반영 시 1회성 안내(`[data-sync-notice]`). **도메인 테스트 필수**(두 서비스가 한 저장소 공유: A 저장 → B 동기화 true, 재호출 false, 리비전 단조 증가).

### 28-55-02 · 덮어쓰기 충돌 감지
→ 요구: `save()`가 쓰기 전에 저장소 리비전을 읽어 메모리 리비전과 다르면(내가 모르는 사이 다른 탭이 저장) `conflictCount += 1`·`onConflict` 통지 후 새 리비전으로 저장(사용자의 방금 행동은 보존). 관리자 저장 용량 카드에 "탭 충돌 n회"(`[data-conflicts]`), 앱 셸 배너 "다른 탭의 변경과 겹쳤습니다 — 그 탭이 최신 상태로 갱신됩니다". 테스트: A·B 같은 리비전에서 A 저장 → B 저장 시 충돌 1, 리비전은 max+1, A 동기화 true.

## 중 (Medium)

### 28-55-03 · 인증 동기화
→ 요구: `AuthSnapshot.rev`, `AuthService.syncFromStorage()`. 한 탭의 로그인·로그아웃·잠금·세션 만료가 다른 탭에 반영된다(게이트 전환). 테스트: A 로그인 → B 동기화 후 세션 있음, A 로그아웃 → B 세션 없음.

### 28-55-04 · e2e + 실측
→ 요구: e2e — 같은 컨텍스트의 두 번째 페이지: 고객 탭에서 요청 등록 → 파트너 탭 일감 목록에 새로고침 없이 나타남 / 파트너 탭 로그아웃 → 다른 파트너 탭도 게이트로. 충돌 규칙은 vitest. 실측: 두 탭 동기화·충돌 카운터.
