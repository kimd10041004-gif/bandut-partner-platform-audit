# 28-74 감사 결과 — 「보관함이 저장을 막지 않게」를 감사한다

감사자 관점: 이 라운드가 **새로 넣은 것**만 본다. 28-73 감사 4건을 고쳤고 PR 리뷰 2건까지 반영했으므로,
그 수정들이 만들어 낸 새 표면이 대상이다. 병합 `b46eec3`(+ §7 후속 `3b351a7`), 게이트 전부 초록,
배포 확인됨(`/assets/index-BTR_azXN.js`). 아래는 그 위에서 발견한 것이다.

한 줄 요약: **보관함을 "정식 시민"으로 만든 것은 옳았다. 그런데 정식 시민이 되면서 생긴 의무를 아직 아무도 지지 않는다.**
용량은 먹기 시작했는데 그것을 치울 수 있는 사람은 관리자 한 명뿐이고, 보관에 실패해도 화면은 보관했다고 말한다.

## 28-74-01 (상) 보관함을 만든 기기가 그것을 치울 수 없다 — 그런데 이제 정식으로 용량을 먹는다

`initReplicator`의 `stash`는 **모든 기기**에 걸린다(`bootstrap.ts`). conflict는 파트너 기기에서도 고객
기기에서도 난다 — 서버 e2e의 기기 D가 파트너인 것이 그 증거다. 그런데 보관함을 **보고 꺼내고 비우는 UI는
관리자 화면 한 곳뿐**이다:

```
$ grep -rn "readOverwritten\|clearOverwritten\|data-overwritten" src/ --include=*.tsx
src/features/admin/AdminSettings.tsx:8   import { readOverwritten, clearOverwritten, ... }
src/features/admin/AdminSettings.tsx:22  const [overwritten, setOverwritten] = useState(() => readOverwritten())
src/features/admin/AdminSettings.tsx:103 clearOverwritten()
src/features/admin/AdminSettings.tsx:174 <div className="overwritten-box" ...>
```

28-73-04는 "3개를 보관하면서 1개만 꺼낼 수 있다"를 고쳤다. 남은 문제는 **누가** 꺼낼 수 있느냐다.
파트너 기기에서 conflict가 나면 그 브라우저에 최대 1MB가 쌓이는데, 그 파트너에게는 목록도 비우기 버튼도 없다.
보관함은 그 브라우저의 것이라 서버로 올라가지도 않으므로, 관리자가 자기 자리에서 꺼내 줄 수도 없다.

이번 라운드가 이것을 **아프게** 만들었다. 28-74 이전에는 보관함이 회계 밖이라 가드가 몰랐다(그래서 브라우저
할당량에서 조용히 터졌다 — 그것이 28-73-01이었다). 이제는 `assertRoom`이 합계로 판정한다:

```ts
if (usage.totalChars + extraChars > usage.limit) { ... }
```

한도의 1/4까지 보관하므로, 사용량이 75%를 넘긴 파트너 기기는 conflict 한 번으로 **모든 저장이 막힌다**.
그리고 그 파트너는 막은 것을 치울 방법이 없다. "저장을 막느니 보관을 포기한다"는 예산의 취지가 파트너
기기에서는 뒤집혀 있다 — 포기하는 대신 막고, 풀 방법을 주지 않는다.

곁들여, 그때 나오는 문구가 엉뚱한 처방을 준다:

```
저장 공간이 부족합니다 (사용 3,900KB, 보관함 1,024KB 포함 / 한도 4,096KB)
  — 오래된 사진을 정리하거나 사진 수를 줄이세요
```

원인의 26%가 보관함인데 처방은 사진이다. 사진을 다 지워도 보관함은 그대로 남는다.

**고칠 방향**: 보관함을 역할과 무관한 자리(마이페이지/설정)에 두거나, 최소한 용량 가드가 걸릴 때
"보관함 비우기"를 그 자리에서 제시한다. 문구도 가장 큰 소비자를 가리켜야 한다.

## 28-74-02 (상) 파기된 계정의 전화번호가 `trustedIps`에 남는다 — 그리고 영영 만료되지 않는다

`accountFailKey`는 `acct|${failKey(role, idOrPhone)}`이고, `failKey`는 관리자가 아니면
`${role}:${normalizePhone(idOrPhone)}`이다. 즉 **`trustedIps`의 키에 전화번호가 그대로 들어 있다.**

`loginFails`도 같은 모양이지만 `pruneLoginFails`가 마지막 실패로부터 15분 뒤 지운다(28-71-02 · 28-72 리뷰).
`trustedIps`에는 그런 청소가 없다. TTL 30일은 **`rememberTrustedIp` 안에서만**, 즉 그 계정이 **다시 성공적으로
로그인할 때만** 적용된다:

```ts
private rememberTrustedIp(accountKey, scope, now) {
  ...
  for (const [ip, at] of ips) if (now - at > TRUSTED_IP_TTL_MS) ips.delete(ip)   // 여기서만 만료된다
}
```

다시 로그인하지 않는 계정 — 탈퇴한 계정, 파기한 계정, 그냥 안 쓰는 계정 — 의 항목은 **영원히 남는다.**
그리고 `purgeAccount`는 계정 행만 지운다:

```ts
purgeAccount(accountId: string): void {
  ...
  this.accounts.splice(idx, 1)
  this.save()          // trustedIps는 건드리지 않는다
}
```

28-40이 만든 파기는 "그 사람의 것을 지운다"는 약속이고, 28-61·28-62는 개인정보를 다룬 라운드였다.
그 약속이 이번 라운드에 뚫렸다: **파기 뒤에도 전화번호가 스냅샷에 남고**, 서버 모드에서는 그것이
`auth_state` 행이라 DB에 남는다. 게다가 저장할 때마다 통째로 직렬화되므로 계정 수만큼 무한히 커진다.

**고칠 방향**: `purgeAccount`(그리고 탈퇴)가 그 계정의 `trustedIps` 항목을 지운다.
`pruneLoginFails` 옆에 `pruneTrustedIps`를 두어 로그인 때마다 30일 지난 항목·빈 계정을 쓸어낸다.

## 28-74-03 (중) 보안 면제를 "믿을 수 없다"고 스스로 선언한 값으로 판정한다

`api/auth.ts`는 IP와 그 값을 믿을 수 있는지를 **함께** 받는다. 그런데 로그인에 넘길 때는 IP만 쓴다:

```ts
const { ip, trusted: ipTrusted } = clientIpOf(req.headers)
warnUntrustedIpOnce(ipTrusted)                                    // 경고만 하고
...
auth.login(..., { lockScope: ip })                                // 값은 그대로 쓴다
```

프록시 헤더가 없으면 `ip === 'unknown'`이다(`UNKNOWN_IP`). 그러면 `rememberTrustedIp(accountKey, 'unknown')`이
기록되고, 그 뒤 **인터넷의 모든 클라이언트**가 그 계정의 계정 잠금(30회)에서 면제된다 — 전원이 같은 `'unknown'`을
제시하기 때문이다. 28-73-03의 주석은 이 위험을 알고 있었지만 막은 것은 다른 경우다:

```ts
if (scope === undefined || scope === '') return   // 로컬 모드(범위 없음)는 면제도 기록도 없다
```

`undefined`와 `''`는 걸러 내면서 `'unknown'`은 통과시킨다. 실제 무차별 대입이 그 환경에서 열리지는 않는다
((계정, `'unknown'`) 5회 잠금이 먼저 걸린다 — 대신 그 잠금이 전원 공유라 더 나쁜 DoS다). 문제는 결과가
아니라 **판단 근거**다: 코드가 방금 "이 값은 믿을 수 없다"고 로그로 외친 값을 가지고, 바로 다음 줄에서
잠금을 면제할지 결정한다. 28-72-04c가 `trusted` 플래그를 만든 이유가 이것이었는데 쓰이지 않는다.

또 하나. `clientIpOf`는 `x-forwarded-for`의 **맨 앞** 값을 취하고 `trusted: true`로 표시한다. 프록시가
헤더를 덧붙이는 배치에서는 맨 앞이 클라이언트가 넣은 값이다 — 즉 `trusted`는 "프록시를 검증했다"가 아니라
"헤더가 있다"는 뜻이다. 28-74 이전에는 이 값이 카운터를 **나누기만** 했으므로 위조해도 공격자가 자기 칸을
얻을 뿐이었다. 이제는 같은 값이 **면제 자격**을 정한다 — 위조의 대가가 달라졌다.

**고칠 방향**: `lockScope: ipTrusted ? ip : undefined`. 믿을 수 없으면 면제도 기록도 하지 않는다
(28-73-03의 주석이 이미 그렇게 말하고 있다). 겸해서 `trusted`라는 이름이 실제로 보장하는 범위를 문서에 적는다.

## 28-74-04 (중) "덮인 내용은 보관했습니다"가 거짓일 수 있다

복제기의 문구는 `overwroteLocal` **하나만** 보고 정해진다:

```ts
try { this.stash?.(mine, new Date(this.now()).toISOString()) } catch { /* 보관 실패가 동기화를 막지는 않는다 */ }
...
this.setStatus('conflict', overwroteLocal
  ? '다른 기기의 변경을 받아들였습니다 — 이 기기에서 반영되지 않은 변경은 덮였습니다(덮인 내용은 보관했습니다)'
  : '...')
```

보관이 실패하는 길이 이번 라운드에 **하나 더 늘었다**:

1. `storage.setItem`이 던진다(할당량) → `stashOverwritten`의 `catch`가 삼킨다.
2. **(28-74에서 추가)** 덮인 본문 하나가 예산(1MB)보다 크다 → `next.length === 0`이 되어 조용히 `return`.
   스냅샷 상한이 4MB이므로 이것은 가정이 아니라 흔한 경우다 — 사진 몇 장이면 1MB를 넘는다.

두 경우 모두 화면은 "보관했습니다"라고 말한다. 잃지 않기 위해 만든 장치가, 잃었을 때 잃지 않았다고 알린다.
사용자는 그 말을 믿고 되살리기를 시도하지 않는다 — 배너는 4초 뒤 사라지고 근거도 남지 않는다.

**고칠 방향**: `stash`가 보관 여부를 돌려주고(`boolean`), 문구가 그것을 반영한다.
보관하지 못했으면 그렇게 말한다("덮였습니다 — 보관하지 못했습니다(용량)"). 예산을 넘는 본문은
버리는 대신 **잘라서라도** 남길지는 별개 판단이지만, 최소한 말과 사실이 어긋나서는 안 된다.

## 이번 라운드가 잘한 것 (되돌리지 말 것)

- `externalChars`로 도메인이 저장소를 모르는 채 합계를 알게 한 것. 경계를 지키면서 사실을 말하게 했다.
- 수정 전 실패를 **출력째** 인용하는 관례가 리뷰 대응(§6-1)에서도 지켜졌다. `1e999 → Infinity` 경로로
  스냅샷을 조작해 계정 잠금 우회를 재현한 것은 특히 좋다.
- 서버 e2e의 새 단계를 **reload 없이** 확인하도록 짠 것. 새로고침하면 마운트가 다시 되어 버그가 가려진다는
  것을 알고 그렇게 짰다.
- §7을 같은 라운드 안에서 닫는 관례가 두 라운드 연속 지켜졌다.
