## 과거 코드 회수 가능성 — 실제로 꺼내 봤다

기준은 **재구성 직전 커밋 `2c27089`** 다. `origin/main`의 이력에 영구히 남아 있다.

```
$ git show 2c27089:28-30/src/domain/platform.ts | wc -l
1576
$ git ls-tree --name-only 2c27089 | grep -c '^28-'

```

**태그를 원격에 만들지 못했다 — 정직하게 적는다.** `archive-28-65`라는 태그를 붙여 두려 했는데
이 세션의 git 자격 증명이 브랜치 푸시는 되고 태그 푸시는 거부한다:

```
$ git push origin archive-28-65:refs/tags/archive-28-65
error: RPC failed; HTTP 403 curl 22 The requested URL returned error: 403
```

회수 가능성 자체는 영향을 받지 않는다(커밋 해시가 이력에 있다). 다만 "태그를 만들어 뒀다"고
쓸 수는 없다. 저장소 소유자가 원하면 웹에서 `2c27089`에 태그/릴리스를 붙이면 되고,
그러지 않아도 위 명령은 그대로 동작한다.
## 회귀 증명 — 새 테스트가 수정 전 코드에서 실패한다

### 28-65-01 가명본 중첩 검사

감사 때 쓴 탐침을 그대로 회귀 테스트로 넣었다(`src/domain/pseudonymous-shape.test.ts`).
28-65 코드에서는 두 경우가 **통과**했고, 지금은 실패해야 정상이다:

```
$ npx vitest run src/domain/pseudonymous-shape.test.ts
 Tests  6 passed (6)
   ✓ 중첩된 견적의 자유 서술 memo를 잡는다 — 28-62-01이 막았다고 선언한 필드
   ✓ 중첩된 지급 기록의 예금주를 잡는다 — 28-61-02가 "자체 검사가 잡아낸 경로"라 적은 필드
   ✓ 중첩 허용 목록을 선언하지 않은 객체는 통과가 아니라 실패다
   ✓ 검사할 수 없는 형태의 행은 조용히 건너뛰지 않는다 — 28-64-02가 없앤 패턴의 재발 방지
   ✓ 점 경로로 중첩 컬렉션에 닿는다 (28-64-02)
   ✓ 허용 목록을 지킨 결과는 통과한다
```

**"검사할 수 없으면 실패"라는 새 규칙이 곧바로 하나를 찾아냈다.** 재귀 검사를 켜자마자:

```
PlatformError: 가명 처리에 실패했습니다 — estimates.breakdown가 객체인데
중첩 허용 목록이 선언되지 않았습니다. 검사할 수 없는 형태는 통과가 아니라 실패입니다.
```

`estimates[].breakdown`은 28-62-01 이후 줄곧 결과에 들어가고 있었는데 한 번도 검사되지 않았다.
`PSEUDONYMOUS_BREAKDOWN_KEYS`를 만들어 선언했다. 지금 새고 있던 값은 아니다(전부 숫자) —
그러나 아무도 보지 않는 통로였다는 사실 자체가 이 항목의 요점이다.

### 28-65-02 열람권 통째 전개

**처음에 쓴 테스트가 공허했다.** "결과의 키가 허용 목록 안에 있다"만 확인했는데,
통째 전개의 결과가 마침 현재 타입의 필드 전부라 수정 전 코드에서도 통과했다.
알아채고 다시 썼다 — 저장된 레코드에 목록 밖 필드를 심는 방식으로.
수정 전 코드(`{...p}`·`{...f}`·`{...j}`)로 되돌려 확인한 실제 출력:

```
FAIL  저장된 레코드에 목록 밖 필드가 생겨도 고객 내보내기에 따라오지 않는다 (28-65-02)
AssertionError: expected '{\n  "exportedAt": ...' not to contain '내부메모'
+       "내부메모": "PG 대사 담당 박준서"
+       "내부메모": "환불 승인자 메모"

FAIL  저장된 정산 기록에 목록 밖 필드가 생겨도 파트너 내보내기에 따라오지 않는다 (28-65-02)
AssertionError: expected '{\n  "exportedAt": ...' not to contain '내부메모'
+       "내부메모": "정산 담당 메모",
+         "holder": "반듯설비"
```

수정 후 두 테스트 모두 통과한다. `holder`(예금주)가 결과에서 사라진 것도 함께 확인된다.

### 28-65-03 도메인 오류 상속

`PlatformReopenError`를 일부러 `extends Error`로 되돌려 확인:


**이것이 28-65 테스트와의 차이다.** 28-65의 `isKnownError` 테스트는 목록을 베꼈기 때문에
같은 조작을 해도 22개 전부 통과했다. 새 테스트는 훑어서 발견하므로 잡는다.

## 남은 위험 — 정직하게

**이 라운드에서 가장 위험한 것은 배포 경로다.** `vercel.json`의 빌드 명령·출력 경로가 통째로 바뀌었다.
로컬 빌드가 되는 것과 Vercel이 빌드하는 것은 다른 문제다. `deploy-check`이 병합 후 라이브 번들에서
`28-66` 문자열을 찾는 것으로만 확인된다 — **그 결과를 보고 보고한다. 그 전에는 "배포된다"고 적지 않는다.**

`npm audit`은 이제 락파일 하나만 본다. 옛 라운드의 취약한 의존성 사본이 저장소에서 사라졌다는 뜻이지,
그 코드가 어딘가 배포돼 있었다는 뜻은 아니다 — 배포된 것은 늘 최신 라운드 하나뿐이었다.
