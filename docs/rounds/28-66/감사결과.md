## 28-66-01 (상) spec 목록의 **완전성**을 아무도 검사하지 않는다 — `daysOff`가 그래서 빠졌다

`exportPseudonymous()`가 `out`에 채우는 컬렉션을 전부 세면 **`daysOff`(`src/domain/platform.ts:3414`)와
`chats`(`:3423`)만 spec 목록(`:3435-3461`)에 없다.**

`daysOff`는 결과에 실제로 실리는데 **`pick()`도 spec도 없는 유일한 컬렉션**이다 — 허용 목록 층이 0겹이다.
손으로 쓴 재조립 한 줄에만 의존한다:

```ts
// platform.ts:3413-3417
// 28-64-02: 통째 통과를 끊는다 — [partnerId, 날짜 문자열[]] 형태만 재조립해 …
out.daysOff = (snap.daysOff ?? []).map(([partnerId, dates]) => [
  partnerId,
  (dates ?? []).filter((d): d is string => typeof d === 'string'),
])
```

**오늘 새는 값은 없다.** 현재 타입이 `daysOff?: Array<[string, string[]]>`(`:320`)이고 `filter`가 비문자열을 떨군다.
결함은 **다음 변경에서 조용히 깨진다**는 것이다:

- 휴무 사유가 붙어 `[string, {date, reason}]`이 되면 → `filter`가 객체를 전부 버려 **데이터가 소리 없이 사라진다.**
- `Array<{partnerId, dates, memo}>`가 되면 → 구조분해 `([partnerId, dates])`가 `[undefined, []]`를 뱉는다.

어느 쪽도 검사에 걸리지 않는다. e2e의 가명본 검증(`scripts/e2e-journey.mjs:1156-1170`)도 `chats`·`store.requests`·
`notifications`·`auditLog`·`profiles`·`estimates`·`refunds`·`partnerCancels`·`settings`만 보고 **`daysOff`는 한 줄도 보지 않는다.**
`src/domain/pseudonymous-shape.test.ts`에도 없다.

### 구조적 원인 — 이게 진짜 항목이다

`assertPseudonymousShape`는 **"spec에 적힌 것"만 확인하고 "적히지 않은 것이 있는지"는 묻지 않는다.**
게다가 경로를 못 찾으면 조용히 통과한다:

```ts
// platform.ts:237
if (node === undefined || node === null) continue
```

spec 경로에 오타가 나거나(`'notifcations'`) 산출물 키 이름이 바뀌면(`out.auditLog` → `out.audit`)
그 컬렉션의 검사가 **아무 소리 없이 사라진다.** 28-64-01이 "죽은 코드를 검사해 초록을 만들던 게이트"라고 지적한
실패 형태가, 28-66이 "검사할 수 없는 형태는 통과가 아니라 실패"(`:204`, `:226-227`)라고 선언하며 재귀까지 넣은
바로 그 함수 안에 fail-open으로 남아 있다. **28-66이 `daysOff`를 놓친 이유가 이것이다.**

### 곁들여 — 최상위와 중첩의 비대칭

```ts
// :242-249 (최상위) — 배열 행은 무조건 [id, obj] 쌍으로 간주, row[1]만 본다
const rec = Array.isArray(row) ? row[1] : row
// :207-212 (중첩) — 배열 행이면 즉시 실패
if (Array.isArray(row) || ...) throw ...
```

최상위에서는 `row[0]`(id)과 `row[2]` 이후 원소를 **아무도 보지 않는다.**
`[['E-1', {허용된 것만}, { memo: '김하늘 010-1234-5678' }]]`는 `row[2]`가 그대로 `JSON.stringify`에 실리고 **통과한다.**
같은 모양이 최상위에서는 "정상 레코드", 한 겹 아래에서는 "즉시 실패"라 규칙을 예측할 수 없다.
현재 조립부는 정확히 2원소만 만들므로(`:3400-3403`, `:3429-3432`) **도달하지 않는 잠재 구멍**이다.

**상으로 두는 이유**: 이 앱에서 유일하게 브라우저를 떠나는 산출물이고, 두 라운드 연속으로 이 함수의
보장 문구가 실제보다 넓었다. 이번엔 "빠진 것을 못 찾는다"는 층위의 결함이다.

## 28-66-02 (중) `EXPORT_PAYOUT_KEYS`가 `account`를 떨어뜨려 파트너 열람권이 후퇴했다 — **28-66이 만든 회귀**

```ts
// platform.ts:156-158
/** 파트너 본인의 정산 기록 — 지급 근거(payout)는 통째로 담지 않고 아래 키만 담는다 */
export const EXPORT_JOB_KEYS = [...] as const
export const EXPORT_PAYOUT_KEYS = ['paidAt', 'amount'] as const
```
```ts
// types.ts:290-297
export interface PayoutRecord {
  paidAt: string
  amount: number
  /** 이체 계좌 표기(마스킹) — 분쟁 시 근거 */
  account: string          // ← 목록에 없다
}
```

diff로 확인한 변경:
```diff
-  jobs: … .map((j) => ({ ...j })),
+  jobs: … .map((j) => ({
+    ...pick(j, EXPORT_JOB_KEYS),
+    ...(j.payout ? { payout: pick(j.payout, EXPORT_PAYOUT_KEYS) } : {}),
+  })),
```

`exportPartnerData()`(`:3539`)는 **파트너 본인이 정보주체**인 열람권 산출물이다.
28-65까지 `{...j}`라서 `payout.account`가 포함됐는데 28-66부터 빠진다.
이미 마스킹된 본인 값이고 주석이 "분쟁 시 근거"라고 적은 값이다 — 과다 노출이 아니라 **과소 제공**이다.

일관성도 깨졌다. 같은 값을 다른 산출물은 여전히 준다:
- `src/features/Settlement.tsx:98` — 파트너 "내 정산 내역" CSV가 `r.account`를 그대로 내보낸다
  (`platform.ts`의 `partnerLedger`가 `account: j.payout?.account ?? ''` 제공)
- `src/features/admin/AdminSettlement.tsx:177` — 관리자 화면 표시

**CSV로는 주고 열람권 JSON에서는 빼는 상태**다. 상수 주석(`:156`)은 "통째로 담지 않고"라고만 적었을 뿐
`account`를 왜 빼는지 근거가 없다. 허용 목록으로 바꾸면서 실수로 떨어뜨린 것으로 보인다.

**나머지 4개 상수는 타입과 정확히 일치한다** — 결함 없음:
`EXPORT_PAYMENT_KEYS` 7/7, `EXPORT_REFUND_KEYS` 10/10(`reason` 포함), `EXPORT_REVIEW_KEYS` 6/6,
`EXPORT_JOB_KEYS` `payout` 제외 7/7. `PSEUDONYMOUS_*`에서도 과다 노출은 발견하지 못했다.

## 28-66-04 (중) 오류 발견 테스트의 범위가 `errors.ts`가 약속한 것보다 좁다

`src/domain/errors.ts:11-12`:
> 새 오류를 만들면서 이 클래스를 상속하지 않으면 `src/domain/errors.test.ts`가 잡는다

```ts
// errors.test.ts:17
const modules = import.meta.glob(['./*.ts', '!./*.test.ts'], { eager: true })
```

`./*.ts`는 **`src/domain/` 직속의 export된 클래스만** 본다. 사각지대: `src/ui/`·`src/app/`·`src/features/`,
하위 디렉터리(`./**` 아님), `.tsx`(28-64-01이 vitest에서 막은 바로 그 구멍), 비export 클래스.

실재하는 사각지대 — 전부 **사용자에게 보여주려고 쓴 한국어 메시지**인데 `DomainError` 계열이 아니다:
```
src/ui/image.ts:14   throw new Error('이미지 처리를 지원하지 않는 브라우저입니다')
src/ui/image.ts:23   throw new Error('사진이 너무 큽니다 — 더 작은 사진을 선택해 주세요')
src/features/auth/MyAccount.tsx:44, :47   진행 중인 거래/작업이 있어 탈퇴 불가 안내
```

**오늘 화면이 깨지지는 않는다** — 호출부가 `isKnownError`가 아니라 `err instanceof Error`로 받는다
(`CustomerRequest.tsx:48-50`, `Work.tsx:126-128`, `MyAccount.tsx:52-55`). 활성 버그가 아니라
**보증 문구가 실제보다 넓은 것**이다. `src/ui/`에 `export class XError extends Error`를 만들고 흔한
`if (isKnownError(err)) … else throw err` 패턴(현재 수십 곳)으로 받으면 ErrorBoundary가 화면 전체를 교체하는데
테스트는 초록이다.

곁들여:
- `errors.test.ts:37`의 `if (name === 'DomainError') continue`는 **이름 기반**이라
  `export { DomainError as BaseError }` 같은 재export에 오탐한다. 동일성(`value === DomainError`) 비교가 맞다.
- `MyAccount.tsx:53`의 `if (isKnownError(err) || err instanceof Error)` — 28-66에서 `DomainError extends Error`가 됐으므로
  좌변은 **완전히 죽은 조건**이다. 이 분기는 `TypeError` 같은 진짜 버그의 메시지까지 사용자에게 노출한다.
  28-66 이전에도 그랬으니 회귀는 아니다.
- `expect(found.length).toBeGreaterThanOrEqual(9)`(`:44`)는 하한이라 클래스가 늘어도 유지보수가 필요 없다 — 문제 없음.

## 28-67 권고

사용자 결정 두 가지를 반영한다 — **복제 포트** / **감사와 함께**.

1. **01**: `assertPseudonymousShape`에 **완전성 검사**를 넣는다(`out`의 키 중 spec에 없는 컬렉션이 있으면 실패).
   `:237`의 fail-open `continue`를 실패로 바꾼다. `daysOff`를 표현할 수 있게 `ShapeSpec`에 `[key, 스칼라배열]` 행 모양을
   더하고 `daysOff`·`chats`를 spec에 넣는다. 최상위 `row[0]`·`row[2..]`도 검사해 비대칭을 없앤다.
2. **02**: `EXPORT_PAYOUT_KEYS`에 `'account'`를 복원하고, 열람권 JSON과 CSV가 같은 값을 담는지 테스트로 고정한다.
3. **03**: README를 새 구조로 다시 쓴다. `package.json` description과 워크플로 주석을 실제 구현에 맞춘다.
4. **04**: `errors.test.ts`의 glob을 `src/**`(`.ts`+`.tsx`)로 넓히고 `DomainError` 제외를 동일성 비교로 바꾼다.
   드러나는 사각지대는 도메인 오류로 승격하거나 **명시적 면제 목록**에 넣는다 — 조용히 통과시키지 않는다.
