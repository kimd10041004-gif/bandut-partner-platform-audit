사전 확인: `npm run check` exit 0 (vitest 191/191), e2e 76/76 PASS, visual-check 전 항목 PASS, `npm audit` 0건, 프로덕션 배포 그린(PR #98 머지). 28-41 감사 4건 전부 수정 확인됨.

핵심 지적: 랜딩은 "집수리, 비교하고 맡기세요"라고 약속하는데 **요청 1건에 견적은 1개만 저장된다**(`estimates: Map<requestId, 견적>`). 첫 파트너가 견적을 내면 요청은 `estimated`가 되고, 다른 파트너는 일감 탭에서 그 요청을 볼 수 없으며(28-42에서 "타 파트너 견적 건 제외"로 봉인), 고객 견적함에는 비교할 대상이 없다. 즉 현재 구조는 "선착순 1인 견적"이지 비교 입찰이 아니다. 상용 가치의 근거인 비교 기능이 없으므로 이 구조는 이번 라운드에서 바꿔야 한다.

## 상 (High)

### 28-42-01 · 다중 입찰 도메인
→ 요구: 견적 저장을 **요청 × 파트너**로 (`bids: Map<requestId, Map<partnerId, StoredEstimate>>`). `submitEstimate`는 requested/estimated 상태에서 파트너별 1건(재제출은 자기 견적 교체). `bidsFor(requestId)`(견적 합계 오름차순) / `bidOf(requestId, partnerId)`. **`acceptBid(requestId, partnerId)`** — estimated → accepted, `RepairRequest.acceptedPartnerId` 기록, 낙찰 파트너 알림 + 나머지 입찰자 **각자 미낙찰 알림**(알림에 계정 범위 `accountId`). `transitionRequest(…, 'accepted')`는 입찰이 1건일 때만 하위 호환, 여러 건이면 거부. 거절(`lost`)은 전 입찰자에게 알림. 일정·완료·타임라인·정산은 **낙찰 견적** 기준(`primaryBid`: acceptedPartnerId 없으면 단일 견적으로 폴백 — 구 스냅샷 호환). 스냅샷 `estimates` 항목은 같은 requestId가 여러 번 나올 수 있게(구 스냅샷은 그대로 읽힘). `bidStats/statusCounts(partnerId)`는 "타 파트너에게 낙찰"을 미낙찰로 계산. **도메인 테스트 필수**.

### 28-42-02 · 고객 견적함: 비교·선택
→ 요구: 요청별로 **받은 견적 전부**를 금액 오름차순 카드로(업체명·합계·메시지·업체 정보 보기), 각 카드에 "이 견적 수락", 요청 단위 "전체 거절". 거래 상세·홈 목록은 낙찰 전에는 "견적 n건 도착" 표시.

### 28-42-03 · 파트너 일감·내 작업
→ 요구: 일감 탭은 requested **와 estimated 전부** 노출(타 파트너가 먼저 견적해도 입찰 가능), 카드에 "입찰 n건" + 내 입찰 여부, 내 견적이 없으면 "이 일감에 입찰", 있으면 "제안 수정". 내 작업 탭은 내 입찰 건 중 결정된 건 — 타 파트너에게 낙찰된 건은 **미낙찰**로 표시(종결 필터).

## 중 (Medium)

### 28-42-04 · e2e + 실측
→ 요구: e2e — 고객이 새 요청 등록 → 파트너1·파트너2가 각각 입찰 → 고객 견적함에 2건(금액순) → 저가 견적 수락 → 낙찰 파트너 내 작업 '낙찰', 미낙찰 파트너 내 작업 '미낙찰' + 알림 → 이후 흐름(일정·완료·결제) 낙찰 파트너 기준. 28-42의 "타 파트너 입찰 건 제외" 단계는 "입찰 n건 표시 + 입찰 가능"으로 교체. 견적함 비교 화면 스크린샷.
