# 28-1 감사결과 (GPT 역할 — Claude 세션 대리 수행)

감사 범위: `28-1` 전체 (src/domain, src UI, scripts, tests, 설정 파일).
기준: 기존 원바이원 라운드와 동일 — 재현 가능한 결함만 항목화하고, 재현 근거를 명시한다.

사전 확인: `tsc --noEmit` 오류 0, `vitest run` 39/39 통과, `node --test` 6/6 통과, `vite build` 성공 — 타입/기존 테스트 수준에서는 깨진 곳 없음. 아래는 코드 검토 + 실측 재현으로 찾은 결함.

---

## 상 (High)

### 28-1-01 · schedule.validateSlot이 달력에 없는 날짜를 통과시킴
`src/domain/schedule.ts`의 날짜 검증이 정규식(`^\d{4}-\d{2}-\d{2}$`)뿐이라 존재하지 않는 날짜가 그대로 저장된다.

재현 (node):
```
2026-02-31 passes regex: true
2026-13-99 passes regex: true
```
영향: 파트너 일정에 2026-13-99 같은 슬롯이 생성 가능. 충돌 감지는 문자열 비교라 실제 달력과 어긋난 예약이 조용히 공존한다.

### 28-1-02 · settlement.isoWeekLabel이 잘못된 입력에 'NaN-WNaN'을 반환
`src/domain/settlement.ts`가 입력 형식을 검증하지 않고 `split('-').map(Number)` 결과를 그대로 `Date.UTC`에 넣는다.

재현 (node):
```
isoWeekLabel(invalid) year: NaN
```
영향: 오염된 completedDate가 섞이면 정산 집계에 `NaN-WNaN` 주차 버킷이 조용히 생기고, 금액이 유효 주차 밖으로 새어 나간다. 정산은 돈 계산이므로 조용한 실패가 아니라 즉시 오류여야 한다.

### 28-1-03 · weeklySettlements가 partnerId를 무시하고 전 파트너를 합산
`weeklySettlements()`의 그룹 키가 주차뿐이라, 서로 다른 파트너의 완료 작업이 한 정산 행으로 합쳐진다. `CompletedJob.partnerId` 필드가 존재하는데도 집계에 쓰이지 않는다.

영향: 파트너가 2명 이상이 되는 즉시 지급액이 잘못 계산된다 (A 파트너 지급액에 B 파트너 매출이 섞임). 현재 시드 데이터가 P-001 하나뿐이라 드러나지 않았을 뿐, 도메인 함수 자체의 결함.

## 중 (Medium)

### 28-1-04 · formatDateKo가 존재하지 않는 날짜를 롤오버된 요일로 표기
`scripts/format.mjs`가 연/월/일 문자열은 입력 그대로 출력하면서 요일만 `Date.UTC` 롤오버 결과에서 가져온다.

재현 (node):
```
2026-02-31 rolls to: 2026-03-03 day: 2(화)
```
→ `formatDateKo('2026-02-31')`은 "2026년 2월 31일 (화)"를 반환 — 존재하지 않는 날짜에 3월 3일의 요일을 붙인 라벨.

### 28-1-05 · 견적 입력 파싱: 빈 값이 조용히 0원이 됨
`src/App.tsx` EstimateForm이 `Number(입력값)`으로 파싱한다.

재현 (node):
```
Number("")= 0 / Number("  ")= 0 / Number("12e3")= 12000
```
영향: 인건비 칸을 비우면 오류 없이 0원 견적이 계산·표시된다. 지수 표기('12e3')도 통과. 금액 입력은 명시적 숫자만 허용하고 빈 값은 오류로 알려야 한다.

### 28-1-06 · RequestStore.add가 desiredDate를 전혀 검증하지 않음
`src/domain/store.ts`의 `add()`는 `desiredDate`에 아무 문자열이나 허용한다 ('내일', '2026/09/05', '2026-02-31' 전부 저장됨). 저장소에 들어간 뒤 일정/정산 로직과 만나면 28-1-01/02와 같은 문제로 이어진다.

## 하 (Low)

### 28-1-07 · updateStatus의 미존재 요청 오류가 generic Error
`store.updateStatus()`가 요청을 못 찾으면 `new Error(...)`를 던져, 호출부에서 `InvalidTransitionError`(비즈니스 규칙 위반)와 "요청 없음"(조회 실패)을 타입으로 구분할 수 없다. 전용 오류 클래스가 필요하다.

### 28-1-08 · Schedule UI: requestId 하드코딩 + 취약한 슬롯 id 생성
`src/App.tsx` Schedule 컴포넌트가 새 슬롯의 requestId를 `'REQ-0002'`로 하드코딩하고, id를 `S-${slots.length + 1}`로 생성한다 (삭제 기능이 생기면 즉시 중복). 요청 선택 입력과 안정적 id 생성으로 바꿔야 한다.
