## 중 (Medium)

### 28-2-01 · 요청 목록 탭의 상태 전이 버튼에 오류 처리가 없음
`src/App.tsx` Requests 컴포넌트의 전이 버튼 onClick이 `store.updateStatus()`를 try/catch 없이 호출한다. 렌더 지연/중복 클릭으로 이미 전이된 상태에서 다시 누르면 `InvalidTransitionError`가 잡히지 않고 React 렌더 트리까지 전파되어 화면 전체가 깨질 수 있다. 견적/일정 탭은 오류를 잡아 메시지로 보여주는데 요청 탭만 예외 처리에서 빠져 있다 (일관성 결여).

### 28-2-02 · parseHourInput이 25~99를 통과시키면서 오류 메시지는 "0~24"라고 주장
`src/domain/money.ts`의 `parseHourInput` 정규식이 `^\d{1,2}$`라 25~99가 그대로 통과한다.

재현 (node):
```
parseHourInput regex accepts 99: true / 25: true
```
현재는 뒤따르는 `validateSlot`이 범위를 걸러주지만, 함수 스스로 내건 계약("0~24 사이 정수만")을 지키지 않아 다른 호출부가 생기면 즉시 결함이 된다. 파싱 단계에서 범위 검증을 완결할 것.

### 28-2-03 · 탭 간 데이터 단절 — 완료한 작업이 정산에 반영되지 않음
요청 목록에서 '시공 완료'까지 전이시켜도 정산 탭은 하드코딩된 `SEED_JOBS`만 집계한다. 견적 계산 탭도 어느 요청과도 연결되지 않은 독립 계산기다. 도메인 함수(estimate/jobStatus/settlement)는 준비되어 있으나 이를 잇는 플랫폼 계층이 없다.
→ 요구: 견적 제출 → `estimated` 전이 연동, `completed` 전이 시 저장된 견적으로 `CompletedJob` 생성, 정산 탭은 실제 완료 작업을 집계. (플랫폼의 핵심 흐름이므로 이번 라운드에서 구현할 것.)

## 하 (Low)

### 28-2-04 · parseWonInput이 비정상 쉼표 그룹핑/선행 0을 허용
재현 (node):
```
WON_RE accepts 0,100: true → value 100
WON_RE accepts 007: true → value 7
```
'0,100'·'007' 같은 입력은 오타일 가능성이 높은데 조용히 다른 값으로 해석된다. 그룹핑 규칙을 강제할 것 (단독 '0'은 허용).

### 28-2-05 · slotsOn이 UI와 연결되지 않은 채 남아 있음
`schedule.ts`의 `slotsOn`은 테스트에서만 사용된다. 일정 탭에 날짜별 조회를 연결하거나 제거해야 한다 (죽은 표면적).
