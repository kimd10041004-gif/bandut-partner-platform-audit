# 29-5 전환 전 준비 — 라이브 환경변수와 그 앞에 놓인 것들

**상태: 배포 전환은 멈춰 있다.** 세 환경변수가 Vercel에 설정됐다는 확인이 없어서다(사용자 지시).
이 문서는 **무엇을 준비해야 하는지**, 그리고 **준비만으로는 아직 검증되지 않는 것이 무엇인지**를 적는다.

## 0. 비밀값은 저장소에 오지 않는다

`ADMIN_PASSWORD`·`SIGNUP_CODE`의 실제 값은 채팅·커밋·이 문서 어디에도 쓰지 않는다.
**Vercel 환경변수에만** 둔다. 저장소에 있는 `ci-admin-pass-1`·`ci-signup-code-1`은
`.github/workflows/gates.yml`의 **CI 전용 값**이다 — 운영 값이 아니고, 운영에 쓰면 안 된다.

## 1. 준비할 것 세 가지

| 변수 | 무엇 | 없으면 |
|---|---|---|
| `DATABASE_URL` | PostgreSQL 접속 문자열 | `/api/auth`가 503 "서버 저장소가 아직 연결되지 않았습니다" |
| `ADMIN_PASSWORD` | 관리자 초기 비밀번호. **8자 이상**, 시연값(`bandut1234!`)과 달라야 한다 | `/api/auth`가 503 — 시연값으로 조용히 열리지 않는다 |
| `SIGNUP_CODE` | 가입 코드. **12자 이상**, 무작위 값 | `register`만 503. 로그인은 된다 |

Vercel 프로젝트 → Settings → Environment Variables에서 **Production과 Preview 양쪽**에 넣는다.
Preview에도 넣어야 전환 전에 프리뷰 배포로 검증할 수 있다.

DB는 어느 PostgreSQL이어도 된다(Vercel Postgres · Neon · Supabase 등).

**스키마는 손으로 넣지 않아도 된다** (29-5). 서버가 첫 요청에서 스스로 적용한다 —
`server/schemaBootstrap.ts`. 빈 DB를 붙여 두면 표 33개가 알아서 선다. 이미 찬 DB면 아무것도 하지 않는다.
직접 넣고 싶으면 다음도 그대로 쓸 수 있고, 여러 번 돌려도 된다:

```
psql "$DATABASE_URL" -f db/schema.sql
psql "$DATABASE_URL" -f db/marketplace.pg.sql
```

`ADMIN_PASSWORD`는 **행이 처음 만들어질 때 한 번** 적용된다. 그 뒤로는 관리자 화면의 비밀번호 변경이
진실이고, 환경변수를 바꿔도 이미 만들어진 비밀번호는 바뀌지 않는다.

## 2. 준비만으로는 검증되지 않는 것 — 지금 라이브의 실제 상태

세 변수를 넣고 재배포해도 **지금 배포에서는 관리자 로그인·회원가입이 서버를 타지 않는다.**
이유가 둘 있고, 둘 다 환경변수와 무관하다.

### 2-1. 라이브 SPA는 로컬 모드로 빌드돼 있다

인증 모드는 **빌드 시점**에 번들에 박힌다(`build/authMode.ts`). `VITE_AUTH_MODE=server`로 빌드하지
않으면 화면은 서버 API를 아예 부르지 않고 브라우저 저장소만 쓴다. 배포 확인이 매번 이렇게 말해 왔다:

```
서빙 인증 모드: local
⚠️ 로컬 모드입니다 — 서버 계정·세션 API는 라이브에서 실행되지 않습니다.
```

즉 지금 라이브에서 "관리자 로그인"을 해 봐도 그것은 **브라우저 안의 로그인**이지 서버 로그인이 아니다.

### 2-2. 라이브의 서버리스 함수는 호출 즉시 500이다 (29-5에서 새로 발견)

29-5에서 배포 확인에 넣은 검사가 라이브 `/api/auth`를 GET으로 한 번 두드렸다. 그 응답:

```
HTTP 500  A server error has occurred  FUNCTION_INVOCATION_FAILED
이웃 함수 확인: /api/snapshot → HTTP 500
```

`/api/auth`는 `DATABASE_URL`·`ADMIN_PASSWORD`를 **DB에 닿기 전에** 검사하고 서로 다른 503으로 답하게
돼 있다(`api/auth.ts:150-156`). 그 503에 닿지도 못하고 500이 났다는 것은 **함수 자체가 뜨지 못한다**는
뜻이다. 이웃 함수도 같으므로 원인은 개별 핸들러가 아니라 `api/` 함수 빌드 쪽이다.

28-68 이후 스무 라운드의 서버 작업이 프로덕션에서 한 번도 동작한 적이 없었다는 뜻이고,
라이브가 로컬 모드라 아무도 그 함수를 부르지 않아 지금까지 드러나지 않았다.

**따라서 환경변수를 넣어도 이 경로는 여전히 500이다.** 이 결함은 옛 `api/*` 서버리스 빌드의 것이고,
Next.js로 전환하면 API가 Next 자신의 빌드(`app/api/...`)로 넘어가므로 같은 경로를 타지 않는다 —
로컬에서 `e2e:next` 13건으로 확인돼 있다.

## 3. 그래서 검증 순서

준비가 끝나면, **라이브를 건드리지 않고** 프리뷰 배포에서 먼저 잰다.

1. 세 변수를 Production·Preview 양쪽에 설정한다.
2. 전환 브랜치(`vercel.json`을 Next로 바꾼 것)를 PR로 올리면 Vercel이 프리뷰를 만든다.
3. 그 프리뷰 주소로 배포 확인을 돌린다 — 29-5에서 `base_url` 입력을 열어 뒀다:
   Actions → deploy-check → Run workflow → `base_url`에 프리뷰 주소.
   결과의 **서버 환경변수 준비**가 `yes`(둘 다 설정됨)로 나오면 준비가 끝난 것이다.
4. 같은 프리뷰에서 사람 눈으로 확인한다: 첫 화면이 뜨는가 · 관리자 로그인 · 회원가입(가입 코드) ·
   `/partner`·`/admin` 경로. (스키마는 첫 요청에서 자동으로 선다 — 따로 넣을 것이 없다.)
5. 넷 다 통과하면 그때 전환을 병합한다. 병합 뒤 배포 확인의 **서빙 인증 모드**가 `local`에서
   `server`로 바뀌는 것이 전환이 실제로 일어났다는 증거다.

되돌리기는 `vercel.json` 한 파일이다 — 커밋 하나로 옛 SPA 배포로 돌아온다.

## 4. 전환과 함께 사라지는 것 (미리 알아 둘 것)

지금 라이브는 로컬 모드라 **방문자의 데이터가 각자의 브라우저 안에** 있다. 전환하면 화면이 v17로
바뀌므로 그 데이터는 새 화면에서 읽히지 않는다. 시연 성격의 데이터라 문제가 없다면 그대로 진행하면 되고,
남겨야 할 것이 있으면 전환 전에 기존 화면의 백업 기능으로 내려받아 둔다.
