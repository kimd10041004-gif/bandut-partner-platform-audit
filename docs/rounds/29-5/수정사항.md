# 29-5 — 배포를 Next.js로 옮긴다 (프리뷰에서 먼저 잰다)

29-4는 전환을 막고 있던 세 가지를 치우고 멈췄다. 이번 라운드가 실제로 `vercel.json`을 옮긴다.
다만 **프로덕션은 건드리지 않는다** — 프리뷰에서 같은 기준으로 재고, 사용자 승인을 받은 뒤에 간다.

이 라운드는 길었다. 배포 설정 한 줄을 바꾸는 일이 프리뷰 실패 **세 번**과 거짓 초록 **한 번**을 낳았다.
그 넷이 서로 다른 원인이었고, 원인이 겹쳐 보인 이유까지가 이 라운드의 내용이다.
자세한 경과는 `함수_경로_충돌.md`에 있다. 여기에는 무엇이 바뀌었는지를 적는다.

## 1. 배포 설정 — 세 줄

```json
{ "framework": "nextjs", "buildCommand": "npm run build:next", "outputDirectory": null }
```

`outputDirectory: null`이 셋 중 가장 늦게 찾은 것이다. Vercel 대시보드에는 옛 SPA를 위한 `dist`가
남아 있고, `vercel.json`이 선언하지 않은 설정은 대시보드 값이 이긴다. `framework: null`일 때는
`npm run build`가 실제로 `dist`를 만들었으니 맞았지만, Next는 `.next`를 만든다. `null`은
"자동 감지"를 뜻하며 대시보드 값을 덮는다.

CSP는 `vercel.json`에서 뺐다. 요청마다 다른 nonce가 필요하기 때문이다 — 아래 3번.
SPA 리라이트도 뺐다. `app/[...slug]`가 그 경로들을 받는다.

## 2. 옛 핸들러를 루트 `api/` 밖으로

Vercel은 저장소 루트 `api/` 안의 파일을 **프로젝트 종류와 무관하게** 전부 함수 진입점으로 본다.
`framework: null`이던 동안에는 Next를 빌드하지 않으니 문제가 없었지만, `"nextjs"`로 바꾸는 순간
`/api/auth`와 `/api/payments`를 옛 `api/`와 App Router가 동시에 주장한다.

핸들러 셋과 그 테스트를 `server/handlers/`로 옮겼다. 로직은 한 줄도 바뀌지 않았다. `server/**`가
이미 타입 검사·테스트 수집·포맷의 대상이었으므로 참조 갱신은 대부분 줄을 지우는 것으로 끝났다.

## 3. 콘텐츠 보안 정책 — 요청마다 nonce

App Router는 스트리밍 데이터를 인라인 `<script>`로 심는다. 28-41의 `script-src 'self'`를 그대로 두고
배포만 옮겼다면 그 스크립트가 전부 차단되어 **화면이 하이드레이트되지 않았을 것이다.**

쉬운 길은 `'unsafe-inline'`이지만 그건 정책을 버리는 것이다. 루트 `middleware.ts`가 요청마다 nonce를
만들어 응답 헤더와 인라인 스크립트에 같은 값을 쓴다. 허용되는 것은 이 응답이 만든 스크립트뿐이다.

정책 문자열은 `server/csp.ts`에 남겼다 — 프레임워크 없이 단위 테스트가 내용을 볼 수 있는 자리다
(`server/csp.test.ts`, 회귀 5건). nonce가 실제로 인라인 스크립트에 가 닿는지는 `e2e:next`가
실제 응답에서 확인한다(헤더 nonce == 본문 nonce).

## 4. 스키마가 스스로 선다

서버 전환 시점에 빈 DB를 만나면 첫 요청이 "relation does not exist"로 죽는다. `server/schemaBootstrap.ts`가
첫 요청에서 스키마를 적용한다. `pg_advisory_xact_lock`(트랜잭션 범위 — PgBouncer/Neon 풀링을 통과한다)으로
동시 요청이 겹쳐도 한 번만 적용되게 한다. 생성 DDL은 전부 멱등으로 바꿨다(`IF NOT EXISTS`, FK는
`duplicate_object` 예외 처리).

CI가 이것을 **실제로** 확인한다 — 빈 스키마에 부트스트랩을 걸어 표가 서는지, 두 번째 호출도 되는지,
동시 세 호출이 모두 끝나는지(회귀 6건).

## 5. 가드 둘이 조용히 빠질 뻔했다 — 둘 다 이 라운드에서 잡혔다

구조를 옮기면 가드가 **초록인 채로 아무것도 안 보게** 되는 자리가 생긴다. 이 라운드에서 두 번 나왔다.

**(1) 서버리스 상태 검사가 하위 폴더를 못 봤다.** `server/serverlessState.test.ts`가 대상 폴더를
평평하게 읽고 있었다. 핸들러가 `server/handlers/`로 들어가면 검사 대상에서 통째로 빠지고 테스트는
초록으로 남는다. 재귀로 바꾸고, `server/handlers/auth.ts:warnedUntrustedIp`가 여전히 잡히는지를
단언으로 못 박았다. 옮기는 커밋 안에서 함께 고쳤다.

**(2) 환경변수 판정이 거짓 초록을 실제로 보고했다.** 배포 확인은 `/api/auth`에 GET을 보내 405면
"둘 다 설정됨"으로 읽었다. 옛 구조에서는 맞았다 — GET이 우리 핸들러까지 갔고 405는 환경변수 검사를
**지나간 뒤**의 답이었다. App Router의 `route.ts`는 POST만 내보낸다. 그래서 GET은 **우리 핸들러를
부르기도 전에** Next가 405로 돌려보낸다. 같은 숫자인데 뜻이 정반대다.

이건 (1)과 달리 **거짓 초록을 보고한 뒤에** 잡혔다. 프리뷰에 `ADMIN_PASSWORD`가 없는데 있다고 말했다.

## 6. 배포 확인이 세 변수를 이름으로 판정한다 (쓰기 없이)

판정을 POST 하나로 바꿨다 — 우리 핸들러에 반드시 들어가는 유일한 메서드다. 핸들러가 세 값을 DB보다
먼저, 인자 검증보다도 먼저 보는 순서를 그대로 읽는다:

| 응답 | 뜻 |
| --- | --- |
| 503 · "아직 연결되지" | `DATABASE_URL` 없음 |
| 503 · "ADMIN_PASSWORD" | 없거나 8자 미만이거나 시연값 |
| 503 · "SIGNUP_CODE" | 없거나 12자 미만 |
| 503 · "저장소 오류" | 셋 다 있는데 **DB에 닿지 못한다** |
| 400 · "가입 정보가 없습니다" | 셋 다 있고 **DB 왕복까지 된다** |
| 405 | 이 경로가 POST를 안 받는다 — 라우트가 바뀐 것이다 |

빈 `args`로 물으므로 계정도 OTP도 만들어지지 않는다. 네 갈래를 로컬에서 실제 서버로 확인했다.
**값은 묻지도 찍지도 않는다** — 이름과 설정 여부만 남긴다. 위 문구는 모두 고정 문자열이다.

`base_url` 입력도 열었다. 프리뷰를 라이브 전에 **같은 기준으로** 잴 수 있어야 하기 때문이다.
마지막 줄(405)은 이번 함정 자체를 다음에 알아보게 하려고 남겼다.

## 7. 프리뷰가 운영 DB를 보지 않게 — 이름을 하나 더 둔다

프리뷰 배포가 **운영 DB를 그대로 봤다**. Neon 브랜치가 `main` 하나뿐이고, `DATABASE_URL`이
Production과 Preview 양쪽에 같은 값으로 걸려 있었다. 그 상태로 검증하면 테스트 계정이 운영
데이터에 섞인다.

보통의 해법은 Vercel에서 `DATABASE_URL`의 Preview 값만 바꾸는 것인데, 이 프로젝트에서는 막힌다.
그 변수는 **Neon 연동이 만들고 소유한다.** 실제로 세 가지가 다 거부됐다:

- 행 메뉴에 **Edit가 없다** — `Manage Connection`·`Rotate Integration Secrets`뿐이다.
- 같은 이름으로 Preview 전용 변수를 추가하면
  `A variable with the name DATABASE_URL already exists for the target production,preview`.
- 그 변수를 **git 브랜치까지 지정해도** 같은 오류가 난다.

이름을 못 쓰면 **이름을 하나 더 두면 된다.** `server/databaseUrl.ts`의 `resolveDatabaseUrl()`이
프리뷰 배포에서 `DATABASE_URL_PREVIEW`가 있으면 그것을, 그 밖에는 언제나 `DATABASE_URL`을 고른다.
프리뷰 여부는 Vercel이 주는 `VERCEL_ENV`로 판정한다.

**운영은 이것 때문에 달라질 수 없다.** `VERCEL_ENV`가 `'production'`이면 첫 줄에서 끝나므로
프리뷰용 값이 운영으로 새는 경로가 없다. 로컬·CI에는 `VERCEL_ENV`가 없어 역시 `DATABASE_URL`만
본다 — **게이트가 보는 것과 운영이 보는 것이 같다**는 뜻이다. 회귀 6건이 이 여섯 갈래를 못 박는다.

DB를 여는 자리는 이제 전부 이 함수를 지난다(핸들러 셋, App Router 라우트 셋, 화면 구성 로더).
`server/`·`app/`·`lib/`에서 `DATABASE_URL`을 직접 읽는 곳은 이 파일 하나뿐이다.

## 8. 배포 확인이 경로를 전수로 본다 (읽기만)

홈 하나만 보고 있었다. 그런데 배포를 옮기면 **주소 체계가 통째로 갈린다**. 옛 SPA는 어떤 경로든
`index.html`을 주고 브라우저가 해시로 갈랐다. 새 셸은 서버가 경로마다 다른 화면을 고른다
(`app/[...slug]/page.tsx`). 홈만 보고 "됐다"고 하면 나머지가 404여도 모른다 — 손님은 그 나머지에서 만난다.

그래서 31개 경로를 전부 GET으로 두드린다. **읽기만 하므로 계정도 데이터도 만들어지지 않는다.**
로그인이 필요한 화면은 셸이 게이트를 그려 주므로 200이다 — 여기서 보는 것은 "그 주소가 존재하는가"이지
"내용이 맞는가"가 아니다. 내용은 사람이 본다.

로컬에서 빌드한 새 셸에 대고 먼저 확인했다: 31개 전부 통과, 없는 경로(`/nope`)는 404 —
가드가 실제로 잡는다는 뜻이다.

## 하지 않은 것

- **프로덕션 전환** — 프리뷰 검증과 사용자 승인 뒤에 간다.
- **SPA·스냅샷 스택 삭제** — 전환이 확인된 뒤다. 지우고 나서 되돌리는 것보다 순서가 중요하다.
- **`middleware.ts` → `proxy.ts`** — Next 16이 권하는 새 규약이다. 빌드는 된다. 전환과 규약 변경을
  같은 커밋에 넣으면 또 원인이 둘이 되므로 전환 확인 뒤로 미뤘다.
