# 29-5 · `framework: "nextjs"`로 바꾸자 프리뷰가 깨진 이유

배포 설정 한 줄을 바꾸는 라운드에서 프리뷰가 세 번 연달아 실패했다. 그 세 번을 어떻게 좁혔고
무엇이 원인이었는지를 남긴다 — 같은 함정을 다음에 또 밟지 않기 위해서다.

## 1. 처음 지목한 것은 틀렸다

첫 실패(`4f70e7e`)는 루트 `middleware.ts`를 더한 커밋에서 났다. 직전 커밋은 초록이었으니
middleware가 범인처럼 보였고, 실제로 그것을 `server/csp.ts`로 내리자 프리뷰가 초록이 됐다.
그래서 "Vercel이 SPA 배포에서도 루트 `middleware.ts`를 엣지 함수로 빌드한다"고 결론지었다.

**그 결론은 그 시점에는 맞았지만 원인의 전부가 아니었다.** 다음 커밋(`46b11c6`)에서
`vercel.json`을 `framework: "nextjs"`로 바꾸자 middleware 없이도 똑같이 실패했다.
그것을 확인하려고 `bd4cd6d`에서 middleware를 아예 내리고 framework 전환만 남겼는데, 여전히 빨갰다.

여기서 배운 것: **"고쳤더니 초록이 됐다"는 원인을 특정하지 못한다.** 한 커밋에 두 변화가
들어 있었고, 되돌린 쪽이 마침 둘 중 하나였을 뿐이다.

## 2. 진짜 원인 — 같은 함수 경로를 둘이 정의한다

Vercel은 저장소 루트의 `api/` 폴더 안 파일을 **프로젝트 종류와 무관하게** 전부 서버리스 함수
진입점으로 본다. 우리 저장소에는 옛 SPA 시절의 핸들러 셋이 거기 있었다:

| 옛 `api/`가 만드는 함수 | Next 앱이 만드는 라우트 |
|---|---|
| `/api/auth` | `/api/auth` |
| `/api/payments` | `/api/payments` |
| `/api/snapshot` | `/api/[...path]` |

`framework: null`이던 동안에는 Next를 빌드하지 않으니 오른쪽 열이 존재하지 않았고, 충돌도 없었다.
`"nextjs"`로 바꾸는 순간 양쪽이 동시에 생기면서 같은 경로를 둘이 주장한다.

## 3. 고친 방법

핸들러를 루트 `api/` 밖으로 옮겼다 — `api/` 폴더 자체가 사라졌다.

```
api/auth.ts      → server/handlers/auth.ts
api/payments.ts  → server/handlers/payments.ts
api/snapshot.ts  → server/handlers/snapshot.ts   (테스트도 함께)
```

로직은 한 줄도 바뀌지 않았다. 옮긴 뒤 이 자리들이 새 경로를 가리키게 했다:
App Router의 두 라우트, `server/marketplaceApi.ts`, `tests/marketplace.http.test.ts`,
`scripts/api-server.mjs`, `vitest.config.ts`, `package.json`의 포맷 대상,
`tsconfig.next.json`·`tsconfig.api.json`의 `include`, CI 단계 이름.

`server/**`가 이미 세 곳 모두의 대상이었으므로 대부분은 **줄을 지우는 것**으로 끝났다.

## 4. 옮기면서 조용히 빠질 뻔한 가드

`server/serverlessState.test.ts`는 모듈 전역 가변 상태에 인스턴스 경계 설명이 붙어 있는지 본다.
그 파일이 대상 폴더를 **평평하게** 읽고 있었다 — `readdirSync('server')`가 하위 폴더로
내려가지 않는다. 핸들러가 `server/handlers/`로 들어가면 검사 대상에서 통째로 빠지고,
테스트는 **초록으로** 남는다. 가드가 스스로 빠지는 그 모양이다.

그래서 옮기는 커밋 안에서 함께 재귀로 바꿨고, `server/handlers/auth.ts:warnedUntrustedIp`가
여전히 목록에 잡히는지를 단언으로 못 박았다.

## 5. middleware는 제자리로 돌아왔다

배포가 Next로 넘어가므로 루트 `middleware.ts`가 정당해졌다. 정책 문자열은 `server/csp.ts`에
남겨 둔다 — 프레임워크 없이 단위 테스트가 볼 수 있는 자리다. `e2e:next`가 헤더의 nonce와
본문 인라인 스크립트의 nonce가 같은 값인지를 실제 응답에서 확인한다(13/13 통과).

**남은 것 하나**: Next 16은 `middleware.ts`를 `proxy.ts`로 바꾸라고 경고한다(빌드는 된다).
배포 전환과 규약 변경을 같은 커밋에 넣으면 또 원인이 둘이 되므로, 전환이 확인된 뒤에 옮긴다.

## 6. 그것도 원인의 전부가 아니었다 — 대시보드에 남은 출력 폴더

핸들러를 옮긴 커밋(`57b7fd9`)에서도 프리뷰는 실패했다. 그러나 **빌드 자체는 문제가 없다**:
깨끗한 클론에서 Vercel과 같은 순서로 돌려 성공을 확인했다.

```
git clone --branch round-29-5 …
npm ci --include=dev     → 23초, 취약점 0
npm run build:next       → 21초, 성공 (라우트 6개, Proxy 1개)
```

그리고 타이밍이 말해 준다. Vercel은 22:26:30에 시작해 **22:27:19에 실패**했다 — 49초다.
위 두 단계의 합(44초)과 거의 같다. 즉 **빌드가 끝난 다음에** 깨졌다는 뜻이다.

빌드 다음에 오는 단계는 산출물을 찾는 일이다. 이 프로젝트의 Vercel 대시보드에는 옛 SPA를 위한
**Output Directory `dist`** 가 남아 있다. `vercel.json`이 선언하지 않은 설정은 대시보드 값이 이긴다:

- `framework: null` 시절 — `npm run build`가 `dist`를 만들었으니 맞았다.
- `framework: "nextjs"` — Next는 `.next`를 만드는데 Vercel은 여전히 `dist`를 찾는다.

`vercel.json`에 `"outputDirectory": null`을 명시하면 "자동 감지"로 되돌아가 대시보드 값을 덮는다.
이것이 이 커밋의 한 줄이다.

이 진단은 빌드 로그 없이 세운 것이었다 — 이 세션의 Vercel 연결은 이 프로젝트를 보지 못한다
(`list_projects`가 빈 목록, 배포 조회는 404). 근거는 위의 타이밍과 재현 결과뿐이었다.

**그리고 맞았다.** 그 한 줄을 넣은 `8644eb4`의 프리뷰가 처음으로 `Ready`가 됐다
(22:30:23 시작 → 22:31:19 Ready). 앞선 세 커밋은 모두 같은 자리에서 실패했다.

## 7. 세 번의 실패에서 남길 것

원인이 셋이었다. 그 셋이 한 줄로 보인 이유는 **한 번에 하나씩 바꾸지 않았기 때문**이다.
`4f70e7e`는 루트 `middleware.ts`와 다른 변경을 함께 담았고, `46b11c6`은 framework 전환과
middleware 제거를 함께 담았다. 실패가 겹치면 "되돌렸더니 초록"이 원인을 특정한 것처럼 보인다.

| 커밋 | 바뀐 것 | 결과 | 진짜 원인 |
|---|---|---|---|
| `a3d02cf` | (framework null) | 초록 | — |
| `4f70e7e` | 루트 middleware 추가 | 빨강 | SPA 배포가 `next/server`를 번들하려 함 |
| `46b11c6` | framework nextjs | 빨강 | 함수 경로 충돌 |
| `bd4cd6d` | middleware 제거 | 빨강 | 위와 같음 (middleware가 아님을 증명) |
| `57b7fd9` | 핸들러 이동 | 빨강 | 대시보드 출력 폴더 `dist` |
| `8644eb4` | outputDirectory null | **초록** | — |

빌드 로그를 못 읽는 상황에서 원인을 좁힌 것은 **타이밍과 재현**이었다. 깨끗한 클론에서 Vercel과
같은 순서로 돌려 빌드가 성공하는 것을 보고, 실패까지 걸린 49초가 그 성공에 걸리는 44초와
거의 같다는 데서 "빌드 다음"이라는 답이 나왔다. 로그가 없을 때 쓸 수 있는 방법이다.

## 8. 판정이 거짓 초록이었다 — GET 405의 뜻이 뒤집혔다

프리뷰가 뜨자 배포 확인이 "DATABASE_URL·ADMIN_PASSWORD 둘 다 설정됨"이라고 답했다.
**그 답은 틀렸다.**

옛 판은 `/api/auth`에 **GET**을 보내 405면 통과로 읽었다. 옛 구조에서는 맞았다 — GET이 우리
핸들러까지 갔고, 405는 핸들러가 환경변수 검사를 **지나간 뒤** 내는 답이었기 때문이다.

App Router로 옮기면서 그 전제가 깨졌다. `app/api/auth/route.ts`는 POST만 내보낸다. 그래서
GET은 **우리 핸들러를 부르기도 전에** Next가 405로 돌려보낸다. 같은 숫자인데 뜻이 정반대다.

POST로 물었더니 진짜 답이 나왔다:

```
{"ok":false,"error":"ADMIN_PASSWORD가 없거나 시연값입니다 — 8자 이상의 다른 값을 설정하세요"}
```

이것이 29-5가 세 번째로 밟은 같은 모양이다 — **구조를 옮기면서 가드가 조용히 거짓 초록이 된다**.
앞의 둘은 서버리스 상태 검사(하위 폴더를 못 봄)와 이 판정이었고, 앞의 하나는 옮기는 커밋 안에서
잡혔다. 이건 **거짓 초록을 실제로 보고한 뒤에** 잡혔다는 것이 다르다.

### 고친 방법

판정을 POST 하나로 바꿨다. 우리 핸들러에 반드시 들어가는 유일한 메서드다. 핸들러가 세 값을
DB보다 먼저, 인자 검증보다도 먼저 보는 순서를 그대로 읽는다:

| 응답 | 뜻 |
| --- | --- |
| 503 · "아직 연결되지" | DATABASE_URL 없음 |
| 503 · "ADMIN_PASSWORD" | 없거나 8자 미만이거나 시연값 |
| 503 · "SIGNUP_CODE" | 없거나 12자 미만 |
| 503 · "저장소 오류" | 셋 다 있는데 **DB에 닿지 못한다** |
| 400 · "가입 정보가 없습니다" | 셋 다 있고 **DB 왕복까지 된다** |
| 405 | 이 경로가 POST를 안 받는다 — 라우트가 바뀐 것이다 |

빈 args라 마지막 줄에서 끝나므로 계정도 OTP도 만들어지지 않는다. 네 갈래를 로컬에서 실제
서버로 전부 확인했다. 405 줄은 이번 함정 자체를 다음에 알아보게 하려고 남겼다.

### 이 시점의 프리뷰 상태

| 값 | 상태 | 근거 |
| --- | --- | --- |
| DATABASE_URL | 설정됨 | 이 게이트가 먼저인데 지나갔다 |
| ADMIN_PASSWORD | **없거나 8자 미만 또는 시연값** | 위 응답 |
| SIGNUP_CODE | 모름 | 앞 게이트에서 막혀 도달하지 못했다 |
| DB 실제 연결 | 모름 | 같은 이유 |
