# 28-93 수정사항 — 여러 분야 동시 선택 · 안전 질문 · 관리자 접수 검토 (참고 v12 대조 3-2)

`../28-90/참고_v12_대조.md` "더할 것" 3-2다. 참고 시안은 요청에 **분야를 여러 개** 싣고, 분야가 정하는 **안전 질문 둘**(문 잠김·
긴급 증상)을 접수 전에 묻고, 답·설명·분야로 `AUTO_PASS` / `MANUAL_REVIEW`를 정해 **수동 검토는 관리자가 확인한 뒤에야
파트너에게 공개**한다(`lib/policy.ts` `questions()`/`safety()`, `lib/service.ts` `review`). 28-92까지 요청은 분야 하나였고, 잠긴
집·타는 냄새 같은 위험 신호를 묻는 칸이 없었으며, 올린 요청은 곧바로 모든 파트너에게 보였다.

## A. 도메인 — `src/domain/safety.ts` (신설)

- `safetyQuestions(categories)`: 카탈로그 **코드**(28-92)로 판단한다. `lock`은 `LOCK`·`UNKNOWN`, `urgent`는 `PLUMBING`·`ELECTRIC`·
  `LOCK`·`UNKNOWN` + 범위 검토 코드 전부. 분야가 여럿이면 합집합.
- `SCOPE_REVIEW_CODES` 15개(잠금·방충망·커튼·시설 설치를 뺀 나머지) — `needsScopeReview()`.
- `assessSafety({categories, description, answers})` → `{reviewStatus, flags}` 또는 `SafetyError`(사용자에게 그대로 보여도 되는 문구):
  묻는 질문에 `null`이면 "안전 질문에 답해 주세요", 묻지 않는 질문에 답이 있으면 거절, 잠김·긴급이면 `ack` 필수,
  `isLocked===false`인데 설명에 `문.{0,5}잠겨|잠겨.{0,5}못|못.{0,5}들어|갇혀`, `urgent===false`인데 `타는\s*냄새|가스\s*냄새|연기|감전|
  물이\s*계속|불꽃`이면 "다시 확인해 주세요"(RECHECK). 답변 형태(boolean|null, boolean)도 여기서 검사한다 — 스냅샷·API 값을
  믿지 않는다. 결과: 잠김·긴급·`UNKNOWN`·범위 검토 중 하나면 `MANUAL_REVIEW`, 플래그 `LOCKOUT`/`URGENT_SYMPTOM`/`WORK_SCOPE_REVIEW`.
- 참고안과 다른 점 하나: "긴급이면 희망일 생략"은 두지 않았다 — 이 저장소의 `desiredDate`는 늘 필수다(일정·마감·리마인더가 그 위에 있다).

## B. 도메인 — 요청 (`types.ts` · `platform.ts` · `store.ts`)

- `RepairRequest.categories?`(고른 순서, **첫 항목 = `category`**), `safety?`, `reviewStatus?`, `reviewFlags?`, `review?{at,by,note}`.
  분야가 하나면 `categories` 키가 없다 — 구 데이터와 같은 모양. `categoriesOf(r)`·`heldForReview(r)`(수동 검토인데 `review` 없음).
- `addRequest`: 분야 묶음을 전부 `normalizeCategory`로 옮기고 중복을 빼며 목록 밖은 거절. `safety`가 실려 오면 `assessSafety`를 거쳐
  `reviewStatus`/`reviewFlags`를 저장한다. **안전 답이 없는 요청(구 데이터·직접 호출·테스트 픽스처)은 검토 대상이 아니다** —
  위저드는 항상 보낸다. 검토 보류면 파트너 알림 대신 고객에게 "접수 확인 중"을 보낸다.
- `reviewRequest(requestId, {note, contactChecked, safetyDelivered, identityChecked?, scopeChecked?}, adminId)`: 참고안의 `review`
  조건 그대로 — 사유 5자 이상(`REVIEW_NOTE_MIN`), 연락·안전 안내 확인 필수, `LOCKOUT`이면 신원 확인, `WORK_SCOPE_REVIEW`면 범위 확인.
  접수 상태(`requested`)에서 한 번만. 완료되면 매칭 파트너에게 새 일감 알림, 고객에게 "접수 확인 완료", 운영 기록 `접수 검토`.
- 파트너 쪽: `matchedRequests`가 보류 요청을 빼고, `submitEstimate`가 보류 요청을 거절한다(화면에서 숨겨도 도메인이 막는다).
  `profileMatch`는 분야 묶음 중 하나라도 겹치면 맞는다. `questionsFor`가 분야 배열을 받아 분야 순서대로 합친다.
  `reqLabel`(알림 문구)은 `[주방·욕실 공사 + 급배수·누수·설비] …`.
- `updateRequest`: 설명을 고치면 저장된 안전 답과 다시 대조한다 — "아니오"라 해 놓고 설명에 "타는 냄새"를 쓰는 경로를 막는다.
- `opsQueue().reviewQueue` + `counts.reviewQueue`(오래된 순).
- 스냅샷: `migrateLegacyCategories`가 `categories`도 옮기고(못 옮기면 버림, 주 분야가 첫 항목), 검증이 `categories`(비어 있지 않고,
  첫 항목=`category`, 중복 없음, 카탈로그 라벨)·`safety`·`reviewStatus`·`reviewFlags`·`review`의 형태를 본다.
- 가명본: `PSEUDONYMOUS_REQUEST_KEYS`에 `categories`·`safety`·`reviewStatus`·`reviewFlags`. `safety`는 중첩 객체라
  `PSEUDONYMOUS_REQUEST_SPEC = { keys, nested: { safety: [isLocked, urgent, ack] } }`로 선언했다 — 선언 없이 넣었더니
  e2e의 백업 내보내기가 `가명 처리에 실패했습니다 — store.requests.safety가 객체인데 중첩 허용 목록이 선언되지 않았습니다`로
  던져 화면이 통째로 교체됐다(28-65-01의 가드가 제 일을 한 것이다; 검증결과 §2). 검토 메모(`review.note`)는 자유 서술이라 넣지 않는다.

## C. 화면

- **위저드 1단계**(`CustomerRequest.tsx`): `CategoryPicker multi` — 처음엔 비어 있고(히어로에서 고른 분야만 실린다) 고른 순서대로
  `[data-picked-categories]`에 "선택한 분야: A + B". 하나도 없으면 "작업 분야를 하나 이상 고르세요". 그 아래 **안전 확인**
  (`[data-safety]`, 분야가 묻는 질문만 `[data-safety-q="lock|urgent"]` 예/아니요 토글). "예"면 안내문 + 확인 체크
  (`[data-safety-ack]`, `aria-label="안전 안내 확인"`). 다음으로 넘어갈 때 `assessSafety`를 그대로 돌려 같은 문구로 막는다 —
  규칙은 도메인 한 곳이다. 등록 확인 단계는 분야 묶음과, 수동 검토가 예상되면 `[data-review-notice]` 안내. 등록 뒤 문구도
  "관리자가 안전·작업 범위를 확인한 뒤 파트너에게 공개됩니다"로 갈린다.
- **고객 홈** 카드: 제목 `[A + B] 설명`, 보류 중이면 `[data-review-hold]` "접수 확인 중 — …" 배지(`.review-hold`, amber 토큰).
- **파트너 일감·입찰**(`Jobs.tsx`): 목록·입찰 폼 후보에서 보류 요청 제외, 카테고리 필터는 묶음 중 하나라도, 제목은 묶음.
- **관리자 현황 조치 필요**(`AdminOverview.tsx`): 맨 위 `[data-ops="review"]` "접수 검토 필요 N건" — 행마다 플래그 태그
  (`[data-review-flag=…]`, 한글 라벨 `REVIEW_FLAG_LABEL`), 잠김/긴급 답, 확인 체크박스(연락·안전 안내·[신원]·[범위]),
  사유 입력(`aria-label="검토 사유"`), "검토 완료". 조건이 비면 도메인 문구가 카드 상단 오류로 뜬다. 총 건수에 포함된다.

## D. 하지 않은 것 (조용히 빼지 않는다)

- 참고안의 **직영/중개 라우팅**(`route DIRECT|MARKETPLACE`)은 이 플랫폼이 중개뿐이라 검토 완료 = 공개로 접었다.
- 요청 관리 탭·거래 상세에는 플래그가 아직 없다(현황 카드에만). CSV·내 데이터 반출의 `category`는 주 분야 하나다.
- 파트너 입찰 자격에 "전문 분야가 요청의 범위 검토 코드를 포함"(참고안 `bid`)은 두지 않았다 — 맞춤 토글·매칭 알림이 그 역할이고,
  입찰은 열려 있다.
- 상세 주소·연락처·사진 열람 게이트는 28-94.
