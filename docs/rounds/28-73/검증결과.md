## 2. 수정 전 코드에서 실패한 출력

각 항목의 회귀를 **먼저** 쓰고, 수정 전 로직(= `6e5c0a0`의 해당 부분)으로 되돌려 실패시킨 것을 확인했다.

**28-72-01** — `sync()`가 남의 sync를 돌려주던 판:

```
 × sync는 자기 일이 끝나야 resolve된다 (28-72-01) > 진행 중 push가 있을 때 뒤이은 sync는
   자기 원격 확인이 끝나기 전에 resolve되지 않는다
   → expected +0 to be 1 // Object.is equality
```

0이라는 것은 **로그인이 "첫 접촉이 끝났다"고 판단한 시점에 서버와 한 번도 이야기하지 않았다**는 뜻이다.

같은 결함을 실제 배선으로 본 통합 테스트(28-72-04b):

```
 × login은 진짜 복제기의 첫 접촉을 기다린다 (28-72-01) > 다른 sync가 진행 중이어도 login은
   원격을 받아들인 뒤에 resolve된다
   → expected false to be true // Object.is equality
```

**28-72-02** — 계정 카운터가 없던 판(다른 IP 6곳에서 30회 실패):

```
 × 잠금 범위 (28-71-02) > 다른 IP 6곳에서 각 5회 실패하면 30회째에 계정이 잠긴다 —
   IP를 바꿔도 무한히 시도할 수 없다
   → expected '관리자 계정 정보가 일치하지 않습니다 — 5회 실패로 15분간 로그…'
     to match /여러 곳에서 30회 실패해 이 계정이 15분간 잠겼습니다/
```

30회를 채워도 **그 IP만** 잠기고 계정은 멀쩡했다 — 아직 쓰지 않은 IP로 계속 시도할 수 있었다.

**28-72-03** — 덮이는 본문을 보관하지 않던 판:

```
 × 덮이는 본문은 보관한다 (28-72-03) > conflict로 덮일 때 덮인 로컬 본문이 stash로 넘어온다
   → expected [] to have a length of 1 but got +0
```

**타이밍 주의(이번 라운드에서 배운 것).** 01의 첫 회귀는 스텁 포트가 마이크로태스크로 끝나면 **수정 전에도
통과한다**. 실제 네트워크처럼 `setTimeout(…, 0)` 한 틱을 넣어야 결함이 드러난다 — 테스트에 그 이유를 주석으로
적어 두었다. `stop()` 회귀는 수정 전에는 매달릴 큐 자체가 없어 통과했다. 새 기구를 지키는 가드이지
수정 전 실패를 인용할 수 있는 회귀가 아니라는 것을 그대로 적는다.
