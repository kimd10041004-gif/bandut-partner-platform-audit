# 28-88 수정사항 — 한 프로세스에서만 참인 가정을 걷어낸다

28-87 감사 4건은 **둘이 같은 뿌리에서 나왔다**: 모듈 전역 상태가 Vercel에서는 **함수마다 따로**다.
그래서 이번 라운드는 그 넷을 고치고, **같은 뿌리의 다른 가지가 또 있는지 전수조사**해 가드로 남겼다.

---

## 01 (상) 상한의 근거를 프로덕션 실제에 맞게 다시 적었다

**원인.** 28-87-03과 #240은 이렇게 적었다:

> 풀은 `max: 3`이고 `/api/snapshot`·`/api/auth`가 같은 셋을 쓴다. 익명 요청 몇 개로 로그인이 대기한다.

Vercel에서 `api/`의 파일은 **각각 별도 함수**다 — `server/db.ts` 자신의 주석이 그렇게 말한다.
그러므로 `getPool`의 `pool`은 함수마다 하나씩 생기고, **셋이 나눠 쓰는 풀은 존재하지 않는다.**

**수정.** 상한을 없애지 않았다(개발·CI 서버에서는 그 공유가 실제로 있고, 해롭지도 않다).
**적어 둔 이유를 둘로 나눠 다시 썼다:**

- 개발·CI 서버(`scripts/api-server.mjs`, 세 라우트가 한 프로세스) → **나눠 쓰는 풀**을 지킨다.
- 프로덕션 → **한 인스턴스가 DB에 동시에 여는 연결 수**를 1로 묶는다. 인스턴스가 늘면 곱해지므로
  **전체 요청 수를 막는 것은 이것이 아니다.** 그것은 엣지 레이트리밋의 일이고 계속 이월이다.

`server/db.ts`의 `getPool`에도 같은 사실을 적었다 — `max: 3`이 보장하는 것은 인스턴스 하나의
동시 연결이지 서비스 전체가 아니다.

**이것으로 위험의 이름을 세 라운드 연속 잘못 적었다**(28-85 "유출 가치" → 28-86 "CPU·메모리" →
28-87 "풀 max:3 공유"). 매번 "이번에는 제대로 이름 붙였다"고 적었다. 그래서 이번에는
**보장하지 못하는 것을 같은 문단에 함께** 적었다.

## 02 (상) TTL을 걷어냈다 — 무효화가 필요했던 이유가 사라진다

**원인.** 28-87-03이 5초 TTL을 넣었고, 그 때문에 생긴 낡은 값을 #240이 "쓴 쪽이 캐시를 버린다"로
막았다. 그런데 `api/snapshot.ts`가 지우는 `memo`는 **`snapshot` 함수의 사본**이고, 읽는 것은
**`publicStats` 함수의 사본**이다. **서로 보지 못한다** — 확률적 손실이 아니라 구조적 무효다.
즉 #240이 고친 것은 `scripts/api-server.mjs`(한 프로세스)에서만 고쳐졌다.

**수정.** 무효화를 더 정교하게 만드는 대신 **TTL을 없앴다.** 28-86의 모양으로 돌아간다:

- 매 요청 `select rev` 한 번(인덱스 조회)
- `rev`가 그대로면 **본문(최대 4MB)은 읽지도 파싱하지도 않는다**
- `rev`가 바뀌었을 때만 본문을 읽는다

**낡은 값이 굳는 창이 아예 없고, 프로세스 밖 가정도 없다.** `invalidatePublicStats`는 삭제했다 —
28-86-03이 `guard-ok`를 없앤 것과 같은 모양이다(필요했던 이유가 사라지면 장치를 지운다).

**수정 전 실패 인용** (28-87 구현 `d01084b`에 새 테스트만 붙였다):

```
× 시간에 기대지 않는다 — 쓰이자마자 다음 요청이 새 값을 본다 (28-87 감사 02)
AssertionError: 시간에 기대는 지름길이 남아 있습니다: expected [] to deeply equal [ 'rev', 'body' ]
```

**비용**: 요청당 인덱스 조회 하나가 늘었다. 그것이 문제가 되는 경우(요청 수 폭주)는 캐시로 푸는
문제가 아니라 레이트리밋으로 푸는 문제다 — 01에서 그렇게 적었다.

## 03 (중) 공개 경로가 DB 오류에 500 대신 503으로 접는다

**원인.** `api/publicStats.ts`의 주석은 "공개 화면을 500으로 만들지 않는다"고 적었는데,
`try/catch`가 걸린 곳은 **본문 파싱 한 군데뿐**이었다. `db.query`가 던지면 예외가 그대로 나갔다.
`api/snapshot.ts`는 같은 상황을 503 + 안내 문구로 처리한다 —
**로그인한 사람보다 로그인하지 않은 방문자가 덜 방어된 상태**였다. 순서가 거꾸로다.

**수정.** 같은 규칙을 적용한다: 원문은 서버 로그로, 클라이언트에는 일반 문구로 503.

```
× DB가 던지면 500이 아니라 503으로 접는다 (28-87 감사 03)
Error: connection terminated unexpectedly     ← 수정 전: 예외가 그대로 새어 나갔다
```

## 04 (중) 모드 표식 검사를 **병합 전** 게이트로 앞당겼다

**원인.** 28-87-05는 "표식이 없으면 실패시켜 계측이 조용히 끊기는 것을 막는다"고 했는데,
그 검사가 `deploy-check`에만 있었다 — **`main` 병합·배포 뒤에 도는 워크플로**다.
계측이 끊긴 것을 아는 시점이 이미 깨진 것이 프로덕션에 올라간 뒤였다.

**수정.** `visual-check`(병합 전 게이트, 이미 `dist`를 검사한다)에 두 줄을 더했다 —
표식이 번들에 **정확히 하나** 있는지, 그 값이 **빌드 모드와 맞는지**.
`deploy-check`의 검사는 그대로 둔다: 여기는 "빌드가 표식을 만든다", 거기는 "그 빌드가 실제로
서빙된다"로 **묻는 것이 다르다.**

**수정 전 실패 인용** — `App.tsx`에서 `data-build`를 지우고 빌드했다:

```
FAIL  모드 표식이 번들에 정확히 하나: 0개:  (기대: one)
FAIL  모드 표식 값 = 빌드 모드: (없음) (기대: local)
VISUAL-CHECK FAIL: 2건
```

28-87은 이 실측을 **손으로** 했다. 손으로 한 확인은 다음 사람에게 남지 않는다 — 28-87-02가
바로 그 교훈이었는데 자기 계측에는 적용하지 않았다.

## 05 서버리스 가정 **전수조사** + 유도 가드

01·02가 같은 뿌리에서 나왔으니, **같은 뿌리의 다른 가지**를 찾았다.
`api/`·`server/`의 모듈 전역 가변 상태 전부:

| 상태 | 판정 |
|---|---|
| `server/db.ts` `pool` | 28-87이 **잘못 해석**했다 (감사 01) → 선언 옆에 사실을 적었다 |
| `api/publicStats.ts` `memo` | 28-87이 **잘못 해석**했다 (감사 02) → TTL 제거로 가정 자체를 없앴다 |
| `api/publicStats.ts` `inflight`·`dbInFlight`·`waiting` | 합치는 범위가 한 인스턴스까지임을 적었다 |
| **`server/rateLimit.ts` `fails`** | **이미 정직하게 적혀 있었다** (28-70-03c) — 선언 옆으로 옮겨 적기만 했다 |
| `api/auth.ts` `warnedUntrustedIp` | 경고 한 번 찍기용. 판단에 쓰지 않으므로 그대로 둔다(그 사실을 적었다) |

**가장 중요한 발견은 `rateLimit.ts`다.** 이 저장소는 28-70에 **이미 알고 정확히 적어 두었다** —
"서버리스 인스턴스마다 따로 세므로 분산 공격은 못 막는다". 그런데 28-87이 같은 사실을 잊었다.
**한 번 알았다가 잊는 것은 사람이 지키는 규칙의 성질이다.** 그래서 기계에게 맡긴다.

`server/serverlessState.test.ts` — `api/`·`server/`의 모듈 스코프 가변 상태를 **유도로** 찾고,
각각의 선언 바로 위 주석에 인스턴스 경계를 **언급했는지** 검사한다.

- 모양이 아니라 **실제 변형 여부**를 본다. `const PUBLIC_OPS = new Set([...])`처럼 읽기만 하는
  표는 대상이 아니다 — **거짓 경보는 가드를 죽인다**(28-85 감사 03의 `guard-ok`가 그 교훈이다).
- 대상이 비면 공허해지므로, 실제 목록을 하한으로 고정한다(28-78-04).

**이 가드의 한계를 좁게 적지 않는다** — 주석이 **참인지**는 검사하지 못한다. 주석은 코드가 아니다.
막는 것은 "생각하지 않고 지나가는 것"이지 "틀리게 생각하는 것"이 아니다.
그래도 값이 있다: **28-87의 두 결함은 둘 다 이 자리에서 멈췄을 것이다.** "이건 인스턴스마다
따로다"를 적는 순간, `api/snapshot.ts`가 남의 캐시를 지우려 한다는 것이 눈에 보인다.

> **정정 (28-89, 28-88 감사 03).** 위 문장은 과장이다. 멈췄을 것은 결함 02(다른 함수의 캐시 무효화)
> 하나다. 결함 01(풀 공유 오해)은 `getPool` 위 주석에 28-87 이전부터 "서버리스"가 있어 `MENTIONS`
> 검사를 통과했을 것이다 — 바로 위 문단이 적은 한계("주석이 참인지는 검사하지 못한다") 밖의 값을
> 같은 문서가 주장했다.
