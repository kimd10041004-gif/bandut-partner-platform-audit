## 2. 이번 라운드의 검증 — `npm run test:mp` (9건)

v17 도메인이 **우리 세션으로** 도는지. 진짜 `sessions` 행에서 나온 토큰이 v17 `User`가 되고, v17의 `role()`이
그 사용자로 판단하는 것까지 실제 Postgres에 대고 확인한다.

| # | 확인 | 왜 |
|---|---|---|
| 1 | 로그인 없이는 401 | 신원이 없으면 도메인에 닿지 않는다 |
| 2 | 형식만 맞는 가짜 토큰도 401 | 토큰은 `sessions` 행이어야 한다 |
| 3 | 처음 보는 계정 → `CUSTOMER` 행 | 우리 세션이 v17 표의 신원이 된다 |
| 4 | 관리자 세션 → `ADMIN` | 우리 로그인이 이미 등급을 확인했다 (§2 아래) |
| 5 | 고객이 감사 기록 조회 → **403** | 인가는 어댑터가 아니라 **도메인**이 한다 |
| 6 | 다른 출처의 POST → 403 | v17의 CSRF 방어를 그대로 옮겼다 |
| 7 | 잘못된 입력 → **400**, 이유 포함 | 503으로 뭉개지 않는다 |
| 8 | 사진 경로 → **503** | 저장소가 아직 없다고 말한다 (29-4) |
| 9 | 주문 한 바퀴 | 접수 → 안전 검토 → 중개 → 입찰 → 확인 |

9번이 이 라운드의 본 검증이다. 한 요청도 건너뛰지 않고 HTTP 경계를 통과한다:

- 고객이 주문을 넣고(201), 파트너가 신청하고, **관리자가 승인**한다.
- 안전 검토에서 도메인이 **작업 범위 확인을 요구**한다(바닥·타일은 범위 검토 대상이다). 빠뜨리면 400이다.
- 낙찰 전에는 파트너에게 **주소가 보이지 않는다**(`address`가 응답에 없다).
- 견적 공급가 480,000 → 총액 **528,000**. 금액은 도메인이 계산한다.

CI `server` job에 단계를 더했다. `gates` job에는 DB가 없어 `skipIf`로 건너뛰므로, **거기 없으면 어디서도 안 돈다.**

## 3. HTTP 경로가 새로 드러낸 방언 차이 2종

29-1이 7종을 잡았는데, 실제 요청을 태우자 두 개가 더 나왔다. 둘 다 **요청 수 제한과 채팅 읽음 표시** 쪽이라
29-1의 도메인 테스트로는 닿지 않던 자리다.

```
column reference "count" is ambiguous (42702)
  at Object.rate (lib/service.ts:31)
```

- **3-1** `ON CONFLICT ... SET count=count+1` — SQLite는 대상 표의 열로 읽고, Postgres는 `excluded`와 겹쳐
  모호하다고 거절한다. 표 이름을 붙였다(`rate_limits.count+1`). 두 방언 모두 유효하고, 같은 파일이 이미
  `request_drafts.revision+1`로 그렇게 쓰고 있었다.
- **3-2** `MAX(a, b)` — SQLite는 스칼라, Postgres는 집계(인자 하나)다. 29-1의 `instr()`과 같은 방법으로
  **스키마에서 흡수**했다: 같은 이름의 2인자 함수. 앱 SQL은 그대로다.

3-1이 두 방언 모두에서 유효하다는 것은 **v17 원본 테스트가 말해 준다** — `tests/` 5개 파일 107건이 node:sqlite로
그대로 통과한다(29-1의 141건 중 이 저장소에 반입한 범위).

## 4. 원인을 삼키지 않기 — 되살린 한 줄

옮기면서 v17의 마지막 줄을 빠뜨렸다:

```ts
console.error('marketplace request failed', e)
```

없으면 어디에도 안 걸린 오류가 **503 한 줄로만** 보이고 원인이 사라진다. 실제로 3-1을 찾다가 한 번 헤맸고,
이 줄을 되살리자 다음 실행에서 스택과 함께 바로 나왔다. 옮길 때 빠뜨리기 쉬운 종류라 기록으로 남긴다.
