# 29-2 — v17 도메인을 우리 세션으로 HTTP에 올린다

29-1은 v17 도메인이 **Postgres에서** 도는 것까지 증명했다. 이번에는 그 위에 **우리 로그인**을 얹어, 도메인이
실제 요청을 받는 자리까지 올린다. 화면은 한 줄도 바뀌지 않는다.

## 1. 라운드를 왜 쪼갰나

원래 계획은 앱 셸·화면·세션·배포를 29-2 한 번에 하는 것이었다. v17 코드를 실제로 읽고 나눴다.

v17은 Next.js 16 + React 19, 우리는 Vite + React 18이다. 한 `package.json`에 React 두 개를 둘 수 없으니
프레임워크를 바꾸는 순간 SPA·`vite build`·`e2e`·`visual-check`가 **동시에** 깨진다. 화면 전환은 쪼갤 수 없는
덩어리다. 거기에 인증과 저장소까지 얹으면 무엇이 실패했을 때 원인을 가릴 수 없다.

그래서 쪼갤 수 있는 절반을 먼저 뗐다. 이번 라운드는 **서버만** 바꾼다 — 실패하면 원인은 한 곳뿐이다.

## 2. 신원: v17이 물어보는 자리는 한 곳이다

v17은 전체 API가 `app/api/[...path]/route.ts` 파일 하나이고, 신원은 그 안에서 **딱 한 번** 만들어진다:

```ts
const who = await getChatGPTUser()
const userId = h.get('oai-authenticated-user-id')
if (!who || !userId) return json({ error: '로그인이 필요합니다.' }, 401)
const u = await svc.identity(userId, who.email, who.displayName)
```

그 아래 모든 서비스가 이 `User`를 첫 인자로 받고, 각자 안에서 `role(u, 'ADMIN')`으로 막는다. 즉 **인가는 도메인에
있고, 바깥은 누구인지만 정한다.** 그래서 로그인 교체는 이 세 줄을 우리 것으로 바꾸는 일이었다.

`app/chatgpt-auth.ts`(86줄)는 반입하지 않았다. 대신 `server/identity.ts`가 우리 세션을 v17 `User`로 옮긴다.

### 관리자만 다르게 본 곳

v17의 `identity()`에는 이런 주석이 있다 — *"Public sign-in never grants administration."* 로그인이 ChatGPT
헤더 하나였기 때문이다. 헤더는 관리자인지 아닌지 말해 주지 못하니, 가입만으로는 절대 ADMIN을 주지 않는다.

우리는 다르다. 관리자 세션은 `ADMIN_PASSWORD`와 등급(owner·manager·viewer)을 통과해야만 나온다(28-89-A).
**우리 세션이 말하는 admin은 이미 인증된 admin이다.** 그래서 어댑터가 그 역할을 v17 표에 반영한다 — 다만 그
판단은 오직 세션에서만 오고, 요청 본문이나 헤더에서는 절대 오지 않는다.

PARTNER 승격은 그대로 v17이 한다(`registerPartner` → 신청, `approve` → 승인). 어댑터는 올리지 않는다.

## 3. 파일

| 파일 | 하는 일 |
|---|---|
| `server/identity.ts` (신규) | 우리 `AuthSession` → v17 `User`. 신원을 만드는 **유일한** 자리 |
| `server/marketplaceApi.ts` (신규) | v17 route.ts의 경로 표를 그대로. Cloudflare 결합만 교체 |
| `scripts/api-server.mjs` | `/api/mp/*` 접두사 라우터 — 기존 `ROUTES`는 정확 경로 매칭이라 세그먼트를 못 받는다 |
| `tests/marketplace.http.test.ts` (신규) | 이번 라운드의 검증 9건 |
| `lib/service.ts` · `lib/trade.ts` | 방언 수정 1종 (아래) |
| `lib/model.ts` | `bid_count?:number` → `|undefined` (타입만) |
| `scripts/pg-schema.mjs` | 스칼라 `max(a,b)` 흡수 |

바깥 결합 교체:

| v17 | 여기 |
|---|---|
| `getChatGPTUser()` + `oai-authenticated-user-id` | `sessionOf` → `identityOf` |
| `env.DB` (D1) | `pgDatabase(pool)` (29-1) |
| `env.BUCKET` (R2) | 아직 없다 → 사진·포트폴리오 경로는 **503** (29-4) |
| `env as PaymentConfig` | 우리 환경변수 |

사진 경로를 조용히 비워 두지 않고 503으로 말하게 한 이유는, 나중에 화면을 붙였을 때 "왜 안 되지"가 아니라
"아직 안 붙었구나"가 보이게 하기 위해서다.

## 4. 이번에 드러난 방언 차이 2종

29-1에서 7종을 잡았는데, **HTTP 경로로 실제 요청을 태우자 두 개가 더 나왔다.** 둘 다 도메인 테스트(SQLite)로는
드러나지 않는 자리다.

### 4-1. `count=count+1`이 Postgres에서는 모호하다

```
column reference "count" is ambiguous (42702)
```

`INSERT ... ON CONFLICT(key) DO UPDATE SET count=count+1`. SQLite는 이 `count`를 대상 표의 열로 읽는다.
Postgres는 대상 행과 `excluded` 양쪽에 같은 이름이 있어 **모호하다고 거절한다.**

고친 방법: 표 이름을 붙였다 — `SET count=rate_limits.count+1`. 두 방언 모두 유효하고, 같은 파일의
`request_drafts.revision+1`이 이미 그 방식이라 원본의 문법을 따른 셈이다. `lib/service.ts`와 `lib/trade.ts`
두 곳(요청 수 제한). 나머지 upsert는 전부 `excluded.`를 써서 애초에 모호하지 않았다.

### 4-2. `max(a, b)`는 SQLite에서 스칼라, Postgres에서 집계

`lib/workspace-service.ts`의 `MAX(chat_reads.last_seq, excluded.last_seq)`. Postgres의 `max`는 집계 함수라
인자가 하나뿐이다.

29-1의 `instr()`과 **같은 방법으로 흡수했다** — 앱 SQL을 고치지 않고, 스키마에 같은 이름의 2인자 함수를 만든다:

```sql
CREATE OR REPLACE FUNCTION max(a bigint, b bigint) RETURNS bigint AS $$
  SELECT GREATEST(a, b);
$$ LANGUAGE sql IMMUTABLE;
```

인자 수로 구분되어 1인자 집계와 충돌하지 않는다. 원본과 대조 가능한 상태가 유지된다.

## 5. 되살린 것: 원인을 삼키지 않기

옮기면서 v17의 마지막 줄 하나를 빠뜨렸다가 되돌렸다:

```ts
console.error('marketplace request failed', e)
```

이 줄이 없으면 어디에도 안 걸린 오류가 503 한 줄로만 보이고 원인은 사라진다. 실제로 4-1을 찾는 데 한 번
헤맸고, 이 줄을 되살리자 다음 실행에서 바로 나왔다. 기록으로 남긴다.

## 6. 화면·배포는 그대로

`index.html`·`vercel.json`은 손대지 않았고, `src/` 전체에서 바뀐 줄은 **라운드 표기 한 줄뿐이다**:

```
 src/App.tsx | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

그래서 CSS 번들은 이름까지 그대로다(`index-CaMRNJjP.css`). JS 번들 이름만 바뀌는데
(`index-DuPzFkcw.js` → `index-D_iVE8hH.js`), 그 차이는 화면에 찍히는 `29-1` → `29-2` 문자열 하나다.
새 코드는 아직 어떤 화면에서도 불리지 않는다.

다음(29-3)에서 Next.js 앱 셸과 v17 화면·디자인을 올리고, 그때 SPA·스냅샷·보관함·가명본·용량 가드를 함께
지우고 배포를 전환한다. 서버가 이미 증명돼 있으니 그때 깨지는 것은 화면뿐이다.
