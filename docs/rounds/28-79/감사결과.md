# 28-79 감사결과 (GPT 감사자 역할)

**대상**: `80cfce7`(#218) + `f3edfb9`(#219) — 28-79가 새로 넣은 것.

라운드는 28-78 감사 01(시연 숫자를 실적처럼 내건다)을 정면으로 받아 `seeded` 표식 → `hasRealActivity()`
→ 랜딩 게이트로 닫았고, 나머지 3건도 코드로 닫았다. §5(deploy-check)도 같은 라운드 안에서 채웠고,
**번들 해시가 일치하지 않는다는 사실을 감추지 않고 적은 것**은 28-78보다 나아진 점이다.

그런데 게이트는 **켜지는 쪽을 보지 않았다**. 숨기는 조건만 만들고 켜진 뒤의 숫자는 그대로 두었기 때문에,
가장 위험한 상태(실적이 갓 하나 생긴 시점)에서 28-78 감사 01이 지적한 문제가 **더 나쁜 모습으로 돌아온다**.
01이 그것이고, 이번 감사에서 유일한 「상」이다.

---

## 01 (상) 게이트가 켜지는 순간, 시드 6건이 **실적으로 둔갑한다**

`hasRealActivity()`는 참/거짓만 정한다. 정작 화면에 나가는 네 숫자는 시드를 **하나도 걸러내지 않는다**:

```ts
// platform.ts:3216
totalRequests: this.store.list().length,          // 시드 6건 포함
completedOrSettled: counts.completed + counts.settled,   // 시드 이력 3건 포함
// platform.ts:2145  bidStats()
for (const r of this.store.list()) { ... }        // 시드 입찰 포함
```

부팅 경로를 그대로 태워 확인했다(시드 주입 → 실제 요청 1건 추가):

```
hasRealActivity = true
누적 요청 = 7 (실제는 1건)
완료된 수리 = 3 (실제는 0건)
파트너 낙찰률 = 100 (실제 입찰 0건)
평균 만족도 = null (실제 리뷰 0건)
```

즉 **첫 고객이 요청 하나를 올린 그 순간** 랜딩이 "누적 요청 7 · 완료된 수리 3 · 파트너 낙찰률 100%"를
내건다. 완료 3건과 낙찰률 100%는 **단 하나도 실제가 아니다**. 28-78 감사 01이 지적한 바로 그 문장이,
이번에는 "실적이 생겼으니 켠다"는 명분까지 달고 나간다.

게다가 이 상태는 **되돌릴 수 없다**. 시드를 지우는 통로가 없고(`grep -rn '시연 데이터\|clearSeed\|purgeSeed' src` → 없음),
`hasRealActivity()`가 한 번 true가 되면 다시 false가 되지 않는다. 운영자는 그 기기에서 랜딩을 다시
정직하게 만들 방법이 없다.

라운드가 코드 주석에 적은 문장 — "비어 있는 것은 정직하지만 없는 실적을 내거는 것은 아니다" — 이
기준으로 재면, 지금 상태는 **비어 있지도 정직하지도 않다**. 0/0/—/— 를 보여 주던 28-78 이전보다,
7/3/100% 를 보여 주는 지금이 더 나쁘다.

**고치는 방향**: 게이트를 켜고 끄는 대신 **숫자에서 시드를 빼야 한다**. `adminOverview`·`bidStats`·
`reviewStats`가 `seeded` 요청을 제외한 값도 낼 수 있어야 하고(예: `excludeSeeded` 옵션 또는 별도
`publicStats()`), 랜딩은 그 값을 쓴다. 그러면 게이트는 "실적 0이면 숨긴다"라는 단순한 규칙으로 줄고,
켜진 뒤에 나가는 숫자는 전부 진짜다. 관리자 화면에는 **시연 데이터 지우기**를 함께 둔다 — 표식이 있으니
지우는 것은 한 줄이고, 그것이 없으면 라이브 기기는 영영 6건을 짊어진다.

## 02 (중) 런타임 보관함 정리가 **실제 삭제 개수를 버리고 `1`을 기록한다**

28-79-02는 "부팅에만 기록하는 것은 절반이다"라며 런타임 경로에 기록을 넣었다. 그런데 넣은 숫자가 상수다:

```ts
// bootstrap.ts — 런타임(trimExternal)
trimOverwritten(storage, Math.min(budget, Math.max(0, before - need)))   // ← 반환값을 버린다
const freedChars = before - overwrittenChars(storage)
if (freedChars > 0) svc?.recordStashTrim(1)                              // ← 항상 1
```

`trimOverwritten`은 **삭제한 항목 수**를 돌려준다:

```ts
// bootstrap.ts:218
return current.length - next.length
```

부팅 경로는 이 값을 제대로 쓴다(`service.recordStashTrim(trimmedStash)`). 런타임 경로만 그것을 버리고
`1`을 쓴다. 보관함 상한은 3건이므로, 사진 한 장을 올리다 **3건이 한꺼번에 지워져도 운영 기록에는
"보관함 정리 · 1"** 로 남는다. 이 기록은 관리자 화면과 감사 로그 CSV로 그대로 나간다.

28-78 감사가 "기록이 없는 것"을 지적했고 28-79가 "기록을 넣었다"고 답했는데, 넣은 기록의 절반이 사실과
다르다. **없는 기록보다 틀린 기록이 더 나쁘다** — 없으면 모른다는 것을 알지만, 틀리면 안다고 착각한다.

**고치는 방향**: `const removed = trimOverwritten(...)` 로 받아 `recordStashTrim(removed)`. 회귀는
"런타임 정리로 2건이 지워지면 감사 로그의 대상이 `2`다"(수정 전: `1`).

## 03 (중) 새 규칙과 **새로 저장되는 필드**가 문서에 0줄

28-79는 두 가지를 새로 만들었다. 하나는 **제품 규칙**(실적이 없으면 랜딩이 지표를 내걸지 않는다),
다른 하나는 **영속 데이터 필드**(`RepairRequest.seeded`, 스냅샷에 저장되고 백업 JSON에도 실린다).
둘 다 문서 어디에도 없다:

```
$ grep -rn '28-79\|hasRealActivity\|seeded' --include=*.md . | grep -v '^./28-79/\|^./28-78/'
(출력 없음)
```

`UI_가이드.md`는 28-29부터 라운드마다 절을 남겨 왔는데 마지막 절이 **28-64**이고, `README.md`의 라운드
기록은 **28-76**에서 멈췄다. 28-77·28-78·28-79 세 라운드가 연속으로 문서를 건너뛴 것이고, 그중 28-79는
**저장 스키마를 늘린 라운드**다. 이 저장소는 "스키마를 늘렸으면 어디에 적는가"를 28-49·28-50·28-55에서
이미 규칙으로 세웠는데, 그 규칙만 지켜지지 않고 있다.

실질적 위험은 추상적이지 않다: `seeded`가 문서에 없으면 다음 라운드가 (ㄱ) 복원/서버 업로드 경로에서
이 필드를 걸러야 하는지 모르고, (ㄴ) 랜딩 말고 다른 화면에 지표 블록을 새로 넣을 때 같은 게이트를
붙여야 한다는 것도 모른다. 규칙이 코드 주석에만 있으면, 그 파일을 열지 않는 사람에게는 없는 규칙이다.

**고치는 방향**: `UI_가이드.md`에 "시연 데이터 표식과 공개 지표 (28-79)" 절 — `seeded`의 의미, 누가
설정하는가(시드만), 지표를 내거는 화면이 지켜야 할 규칙. `README.md` 라운드 기록에 28-77~28-79 세 줄.

## 04 (하) 회귀가 **숨는 쪽만** 본다 — 지표가 나타나는 것을 단언하는 테스트가 0건

`data-hero-stats`를 언급하는 테스트·스텝은 하나뿐이고, 그것은 **없다**는 단언이다:

```
$ grep -rn 'data-hero-stats' src scripts
src/features/landing/Landing.tsx:102:        <div className="hero-stats" data-hero-stats>
scripts/e2e-journey.mjs:146:        (await page.$('[data-hero-stats]')) === null,
```

`hasRealActivity()` 단위 테스트(2곳)는 **도메인 메서드**를 볼 뿐 화면을 보지 않는다. 그래서
`const showStats = false` 로 굳혀도 `check`·`e2e`·`visual-check` 네 게이트가 전부 통과한다 — 랜딩에서
지표가 영원히 사라진 것을 아무도 잡지 못한다. 이 라운드가 만든 것은 **조건부 렌더링**인데, 회귀는
조건의 한쪽만 고정했다.

같은 성격의 잔여물이 하나 더 있다. `trimExternal`의 `svc === undefined` 분기는 **도달할 수 없다** —
`assertRoom`은 사진 경로 3곳(`platform.ts:873,910,936`)에서만 불리고, 그 경로는 `load()`가 끝난 뒤에만
열린다. 그런데 그 죽은 분기 안에 28-79-02가 "틀렸다"고 선언한 옛 정책(`Math.max(0, before - need)`)이
그대로 남아 있다. "정책은 한 곳에 둔다"고 적어 놓고 두 곳에 두었다.

**고치는 방향**: e2e 여정의 실제 요청 등록 **뒤에** "이제 히어로 지표가 보인다" 스텝을 더한다(01을
고치면 그 숫자가 실제값과 일치하는지까지 단언한다). `svc === undefined` 분기는 지우고, 도달 불가능하다는
근거를 주석 한 줄로 남긴다.

## 이번 감사에서 **문제 삼지 않은 것** (조용히 넘기지 않는다)

- **§5에서 번들 해시 일치를 주장하지 않은 것** — 오히려 옳다. 마지막 로컬 빌드가 서버 모드였으므로
  해시가 다른 것이 정상이고, 그것을 "확인했다"고 쓰지 않은 판단은 이 루프가 요구하는 정직함에 맞는다.
- **`assertRoomForTest` 제거**(28-79-03) — 회귀가 실제 경로(`addPhoto`)로 옮겨 갔음을 확인했다. 테스트
  전용 통로를 늘리지 않고 줄인 방향이 맞다.
- **`recordStashTrim`으로 인자를 좁힌 것**(28-79-03) — 앱이 감사 로그의 행위명을 정하던 통로를 닫았다.
  02는 이 변경 자체가 아니라 **호출자가 넘기는 개수**의 문제다.
