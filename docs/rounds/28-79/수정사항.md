# 28-79 수정사항 — 시연 지표를 내걸지 않는다

**대상**: `28-78/감사결과.md` 4건. 사용자 결정: **"지표를 숨긴다 + 감사 4건"**.

---

## 28-79-01 (상) 실적이 없으면 **실적을 내걸지 않는다**

28-78이 시연 데이터를 복구하면서, 랜딩 히어로가 그 숫자를 실적으로 내걸게 됐다. 부팅 경로를 그대로 태워
첫 방문자가 보는 값을 확인했다:

```
누적 요청 6 | 완료된 수리 3 | 낙찰률 100 | 평균 만족도 null
```

전부 시드가 만든 숫자이고 "시연"이라는 표시는 어디에도 없었다. **낙찰률 100%**는 시드의 우연(입찰 3건이
모두 낙찰)인데 마케팅 문구처럼 읽힌다. 복구 이전에는 시드가 던져서 이 자리가 0·0·—·—이었다 —
비어 있는 것은 정직했지만, 없는 실적을 내거는 것은 아니다.

**세 겹으로 고쳤다:**

1. **도메인이 판단 근거를 갖는다**: `RepairRequest.seeded?: true` — 시드가 만든 요청에만 붙는다.
2. **도메인이 답한다**: `hasRealActivity()` — 시드가 아닌 요청이 하나라도 있는가.
3. **화면이 그것을 따른다**: `Landing.tsx`가 `showStats`일 때만 히어로 지표를 그린다.

실적이 생기면 **저절로 켜진다** — 관리자가 스위치를 켤 필요가 없다. 브라우저로 양쪽을 확인했다:

```
오류: 0 | 히어로 지표 노출: false      ← 시연 데이터뿐일 때
누적/낙찰률 문구 존재: false
실제 요청 추가 뒤 지표 노출: true      ← 진짜 요청이 하나 생긴 뒤
```

e2e 여정에도 단계를 더했다 — `첫 방문(시연 데이터뿐): 히어로 실적 지표가 없다 (28-79-01)`.

## 28-79-02 (중) 정리 정책은 **하나**다

28-78은 부팅은 예산(한도−스냅샷, 최대 1MB), 런타임은 "모자란 만큼만"이었다. 간신히 통과한 기기는 다음
저장에서 또 걸리고 그때마다 조금씩 지워졌으며, **그 지움은 기록에도 남지 않았다**(기록은 부팅 경로에만).

정책을 한 곳(`bootstrap.ts`)에 모았다 — 런타임도 `stashBudget` 기준으로 맞추고, 지운 것이 있으면
`recordStashTrim`으로 남긴다. 도메인은 여전히 저장소를 모른다(숫자와 함수 하나다).

## 28-79-03 (중) 행위명은 **도메인이 정한다**

`recordExternalTrim(action: string, count)`은 앱이 아무 행위명이나 감사 로그에 넣을 수 있는 통로였다.
28-59·28-60이 감사 로그의 무결성을 다룬 저장소에서 통로가 넓은 것 자체가 다음 라운드의 함정이다.
`recordStashTrim(count)`로 좁혔다 — 이름은 도메인 안에 있다.

## 28-79-04 (하) 테스트 편의로 넓힌 표면을 되돌렸다

`assertRoomForTest`를 지우고, 28-78의 회귀 세 건을 **실제 경로**(`addPhoto`)로 다시 태웠다.
사진 첨부가 원래 이 가드의 주인이라, 회귀도 그쪽이 진짜다.

## 이 라운드에서 하지 않은 것

- **관리자·파트너 화면의 시연 데이터 표기** — 내부 화면이라 오도의 대상이 다르고, 시연 계정 안내가 이미
  있다. 필요하면 다음 라운드에서.
- `scripts/api-server.mjs` 포트 인자, `clientIpOf`의 `trusted` 의미 문서화, `otps` 키 평문,
  병합·보관함 서버 업로드·SMS OTP·쿠키 세션·CSP·scrypt·엣지 레이트리밋.
