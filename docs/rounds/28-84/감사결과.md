# 28-84 감사결과 (GPT 감사자 역할)

대상: `761598e`(#229) + `5b98e8b`(#230) + `1e0d4de`(#231).
28-83 감사 4건을 받아 "유도의 양 끝"을 근거 위에 올린 라운드다.

**방향은 옳았고, 실행도 정직했다.** 항목마다 결함을 실제로 심어 수정 전 실패를 인용했고,
02는 감사가 지적한 그 변이(게이트 488건을 전부 통과하던)를 정확히 잡는 것을 보였다.
병합 뒤 Copilot 지적 2건을 받아 **둘 다 실제 문제임을 실행으로 확인하고** 고친 것도 좋다 —
특히 "이번 라운드가 세운 원칙이 그 라운드 자신의 테스트에 덜 적용돼 있었다"고 스스로 적은 것.

그런데 이 라운드가 만든 가드는 **네 가지 방법으로 조용히 뚫린다.** 아래 01~04는 전부
**수정 후 코드(`main`, `1e0d4de`)에서 실행해** 확인했고, 넷 다 `Tests 5 passed (5)` — 초록이다.

01은 **#231의 리뷰 수정이 넓힌 구멍**이라 특히 아프다. 03은 **28-84-03이 거짓 경보를 막으려고
넣은 조치 자체가** 만든 구멍이다. 즉 이번 라운드의 두 수정이 각각 새 우회로를 열었다.

## 01 (상) `hidden` 판정이 **메서드 이름까지** 본다 — 공개 API가 조용히 사라진다

```ts
for (const m of src.matchAll(/\n {2}(private |protected |public |static |async )*([a-zA-Z][a-zA-Z0-9_]*)\(/g)) {
  const hidden = /private|protected/.test(m[0])      // ← m[0] 은 이름을 포함한다
```

`m[0]`은 `\n  ` + 수식어 + **이름** + `(` 전체다. 수식어만 봐야 하는데 이름까지 본다.
그래서 **이름에 `private`/`protected`가 들어간 공개 메서드는 `publicNames`에서 빠진다.**

개인정보를 여러 라운드(28-61·28-62) 다룬 이 저장소에서 `privateNotes…` 같은 이름은 충분히 그럴듯하다.
`platform.ts`에 **공개** 메서드를 심고 확인했다:

```ts
privateNotesSummary(partnerId: string, options: { excludeSeeded?: boolean } = {}): number
```

```
 Test Files  1 passed (1)
      Tests  5 passed (5)
```

유도가 못 잡으니 `SEED_INCLUSIVE`에 넣으라는 요구도 없고, 목록에 없으니 첫 테스트도 침묵한다.
**고객 카드(`PartnerCard`)가 그것을 실제로 부르게 해 봐도 여전히 초록이다** (`Tests 5 passed (5)`).

이것은 28-79부터 여섯 라운드가 쫓아온 바로 그 실패다 — 시드 섞인 집계가 고객 화면에 뜨는데 CI는 초록.
그리고 **#231에서 `private` → `private|protected`로 넓히며 이 구멍이 두 배가 됐다.**
리뷰 지적 자체는 옳았지만, 고치면서 판정 대상을 좁히지 않았다.

**제안**: 수식어만 따로 캡처해서 본다.
`const [, mods = '', name] = m` 후 `/\b(private|protected)\b/.test(mods)`.
그리고 이 구멍 자체를 회귀로 고정한다 — 이름에 `private`가 들어간 공개 메서드를 픽스처로 두고
`publicNames`에 포함되는지 검사한다.

## 02 (상) 대괄호 접근이 가드를 완전히 지나간다

```ts
const s = platform['partnerSummary'](partnerId)
```

```
 Test Files  1 passed (1)
      Tests  5 passed (5)
```

28-84-03은 `.이름(` 호출 형태 대신 **식별자**를 보게 바꿨다 — 구조 분해 우회를 막은 것은 맞다.
그런데 같은 항목이 거짓 경보를 막으려고 넣은 `stripNonCode()`가 **문자열 리터럴을 지운다.**
API 이름을 문자열로 쓰면 검사 전에 사라진다.

같은 원인의 더 현실적인 형태 — **템플릿 리터럴**:

```tsx
const label = `완료 ${platform.partnerSummary(partnerId).done}건`
```

```
      Tests  5 passed (5)
```

JSX에서 `aria-label`이나 툴팁 문자열을 만들 때 흔한 모양인데, 백틱 전체가 지워져 안이 보이지 않는다.
**이쪽이 01보다 실수로 일어나기 쉽다** — 우회할 의도 없이 자연스럽게 쓰는 코드다.

**그리고 문서가 이 구멍을 덮지 못한다.** `UI_가이드.md`와 파일 상단은 한계를 이렇게 적었다:

> *못 잡는다* — 이름을 하나도 부르지 않고 **원자료에서 같은 숫자를 직접 계산하는 것**.

위 두 경우는 **이름을 부른다.** 문자열로 부를 뿐이다. 적어 둔 한계가 실제 한계보다 좁아서,
문서를 읽은 사람은 가드가 이것을 잡는다고 믿는다. 28-84가 "한계를 아는 것이 먼저"라고 한 것은
옳은데, **적은 한계가 틀렸다.**

**제안**: 템플릿 리터럴은 `${…}` 안을 **남기고** 바깥만 지운다(중괄호 깊이를 세면 된다).
따옴표 문자열은 지우되, 지우기 **전에** `SEED_INCLUSIVE` 이름이 문자열 안에 있으면 그것도 위반으로 본다
(정당한 예외 — 문서 문구·에러 메시지 — 는 주석 표식으로 면제). 그리고 문서의 한계 서술을
실제 한계에 맞게 고친다.

## 03 (중) 진입점 유도에 **손으로 적은 이름이 하나 남았다**

`customerRoots()`는 라우팅에서 유도한다는 것이 요지인데, 랜딩만은 이렇게 잡는다:

```ts
for (const m of src.matchAll(/<([A-Z][\w$]*)\b/g)) {
  if (m[1] === 'Landing') names.add(m[1])
}
```

실제 유도 결과를 찍어 보면:

```
유도된 진입 컴포넌트: CustomerHome, CustomerRequest, CustomerEstimates, CustomerMy, Landing
```

앞의 넷은 `APPS`의 `view:`에서 나왔고, **`Landing`만 함수 안에 적힌 문자열**이다.
28-84가 28-83에 대해 지적한 것("출발점이 손으로 적혀 있다")이 **한 칸 안쪽으로 옮겨졌을 뿐**이다.
공개 화면을 하나 더 붙이거나(`<Promo/>`) 랜딩을 이름만 바꾸면, 유도는 조용히 그것을 빼놓는다.

덧붙여 이 루프는 **App.tsx 전체의 JSX 태그를 훑어 이름 하나를 비교한다** —
`src.includes('<Landing')` 과 같은 일을 하면서 라우팅에서 유도하는 것처럼 보이는 모양이다.

**근거는 실제로 있다.** App.tsx에 `const showLanding = activeApp.key === 'customer' && landing`이 있고
`showLanding ? <Landing …>` 로 렌더한다. 즉 "고객 앱의 비로그인 첫 화면"이라는 라우팅 사실이 코드에 있다.

**제안**: `showLanding ?` 삼항의 참 가지에서 컴포넌트 이름을 뽑는다(`/showLanding\s*\?\s*\(?\s*<([A-Z][\w$]*)/`).
그러면 이름을 바꾸거나 다른 화면으로 갈아 끼워도 따라온다. 최소한 유도된 진입점 **개수**가
줄어들면 실패하는 단언을 둔다(지금은 두 파일만 이름으로 확인한다 — 셋째가 사라져도 통과한다).

## 04 (중) 문서가 가드를 실제보다 강하게 말한다 (02의 문서 쪽 짝)

02에서 짚은 한계 서술 외에도, `UI_가이드.md`의 이 문장이 이제 사실과 다르다:

> 호출 형태를 보지 않으므로 `const { partnerSummary } = platform` 같은 구조 분해로 **우회되지 않는다**.

맞는 말이지만 읽는 사람은 "우회되지 않는다"를 일반화한다. 실제로는 위 01·02의 세 가지 형태로 우회된다.
가드의 자기 설명(파일 상단 주석)도 「**잡는다** / **못 잡는다**」 두 항목으로 단정적으로 적혀 있어,
새 기여자가 "이 가드를 통과했으니 괜찮다"고 결론 내리기 쉽다.

이 저장소는 28-78-04에서 "규칙이 아니라 목록이 CI를 좌우한다"를 스스로 이름 붙였고,
28-83·28-84가 그것을 두 층에서 고쳤다. 그런데 **문서가 가드의 능력을 과장하면 같은 함정이 사람 쪽에서 되풀이된다** —
가드가 조용하다는 것이 안전하다는 뜻이 되어 버린다.

**제안**: 한계 절을 "정적 텍스트 검사가 원리적으로 못 하는 것"의 **목록**이 아니라
"**이 가드는 부주의를 잡지 악의를 잡지 않는다**"는 한 문장으로 바꾸고, 구체 예는 그 아래 둔다.
그리고 고객 화면 리뷰 체크리스트(사람이 보는 것)를 `UI_가이드.md`에 한 줄 추가한다.

## 이번 감사에서 **문제 삼지 않은 것** (조용히 넘기지 않는다)

- **`domainFiles()`가 `ports-testkit.ts`까지 훑는 것.** 테스트 보조 파일이지만 `excludeSeeded`가 없고,
  생기면 잡히는 편이 안전하다. 과검출 쪽이라 문제 없음.
- **`customerRoots()`의 `key: 'customer'` ~ `key: 'partner'` 슬라이스.** APPS 순서가 바뀌면 빈 문자열이
  되는데, 그때 `CustomerEstimates` 단언이 **시끄럽게** 실패한다. 거짓 안심이 아니라 거짓 경보 쪽이다.
- **`App.tsx`를 잎으로만 넣는 결정.** 근거가 분명하고(세 앱을 전부 import한다) 경계를 테스트로 고정했다. 좋다.
- **#230(§5)의 관례와 주장 범위.** 번들 해시 일치를 정확히 그 범위까지만 주장했다.
- **#231의 두 수정.** 지적은 옳았고 확인도 실행으로 했다. 다만 01은 그 수정이 넓힌 구멍이라 위에 올렸다.
- **서버 모드 익명 방문자 문제.** 28-84의 결함이 아니라 **네 라운드째 이월된 설계 과제**다
  (28-82 발견 → 83 → 84 → 지금). 28-84-02가 서버 모드 절반을 테스트로 닫았지만 화면으로는 열려 있다.
  이월 횟수를 문서에 적어 둔 것은 정직했다. **그러나 네 번은 적어 두는 것으로 넘길 횟수를 넘었다** —
  다음 라운드에서 다루거나, 다루지 않기로 명시적으로 결정할 때다.
