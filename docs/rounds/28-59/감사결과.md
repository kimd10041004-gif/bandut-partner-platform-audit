# 28-59 감사결과 (GPT 역할) — 백업 권한·감사 무결성 라운드

28-59는 파트너 앱에 열려 있던 전체 백업 문을 닫고, 복원이 감사 로그를 지우지 못하게 했으며,
인증 보안 이벤트를 기록으로 끌어올렸다. 방향은 맞다. 그런데 **같은 잣대를 들이대면 아직 세 군데가 비어 있다.**
"기록을 지울 수 없게 했는가"는 해결됐지만, "기록을 **밀어낼** 수 없게 했는가", "**반출**은 기록되는가",
"복원 실수는 되돌릴 수 있는가"에는 아직 답이 없다. 4건을 지적한다.

---

## 28-59-01 (상) 데이터 반출이 기록되지 않는다

`AdminSettings.tsx:50`은 `platform.exportData()`를 직접 호출해 파일을 내려준다.
복원(`restoreBackup`)은 기록하면서 **내보내기는 아무 기록도 남지 않는다.**
감사 관점에서 순서가 뒤바뀌었다 — 상태를 덮어쓰는 일보다 **데이터가 밖으로 나가는 일**이 먼저 추적돼야 한다.
내려받은 JSON에는 고객 이름·요청 내용·현장 사진·채팅 전문이 평문으로 들어 있어,
파일 한 번 유출되면 그대로 노출된다. "누가 언제 무엇을 얼마나 내보냈나"를 답할 수 없다.

**요구**: 내보내기를 도메인 메서드로 감싸 `백업 내보내기` 기록(리비전·요청 건수·크기)을 남긴다.
화면에는 파일이 평문이라는 사실을 명시한다.

## 28-59-02 (상) 감사 로그가 로그인 실패에 밀려난다

28-59는 로그인 실패를 **매 시도마다** 한 줄씩 기록한다(`recordFail`).
그런데 `pruneAuditLog`는 상한 초과 시 **오래된 것부터 무차별로** 자른다
(`this.auditEntries.slice(this.auditEntries.length - AUDIT_CAP)`).

즉 존재하지 않는 번호로 로그인을 1000번 시도하면, 그 실패 기록만으로 상한(1000건)이 차고
**그동안 쌓인 관리자 행위 기록이 전부 밀려난다.** 감사 로그를 지키려고 만든 장치가,
외부인이 로그를 지우는 수단이 된 셈이다. 잠금(15분)은 같은 대상에만 걸리므로 번호만 바꾸면 계속된다.

**요구**: (1) 짧은 시간 안의 동일 행위·대상 반복은 한 줄로 접고 횟수를 남긴다(첫 시각 보존).
(2) 상한 초과 시 **시스템 기록을 먼저** 버리고 관리자 행위 기록을 지킨다.
기록의 양이 아니라 **기록의 가치** 순으로 버려야 한다.

## 28-59-03 (중) 복원 실수를 되돌릴 수 없다

`restoreBackup`은 확인 문구 한 단계를 두었지만 여전히 비가역이다.
잘못된 파일을 올리면 직전 상태는 사라진다 — 운영 기록만 보존될 뿐 거래·결제·요청은 되돌릴 수 없다.
확인 문구는 오타를 막을 뿐 **잘못된 파일**을 막지 못한다.

**요구**: 복원 직전 상태를 자동으로 파일로 내려주고(되돌릴 수단 확보),
같은 세션 안에서는 "직전 상태로 되돌리기"를 제공한다. 되돌리기도 감사 기록으로 남긴다.

## 28-59-04 (중) 위 3건의 테스트·e2e·실측이 없다

특히 28-59-02는 **수치로 증명해야 하는** 항목이다. 상한을 넘겨 잠식을 재현하고,
접기·우선 폐기 후 관리자 기록이 살아남는지 도메인 테스트로 못 박아야 한다.
