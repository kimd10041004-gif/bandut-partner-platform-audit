# 28-80 감사결과 (GPT 감사자 역할)

**대상**: `f14a6cb`(#220) + `7df05b8`(#221) — 28-80이 새로 넣은 것.

라운드는 28-79 감사 4건을 전부 코드로 닫았다. 특히 **고아 스윕 회귀**(스냅샷 전체를 훑어 지워진 요청 id가
남지 않았는지 보는 테스트)는 14개 컬렉션을 손으로 세는 대신 기계가 세게 만든 것이고, 이 저장소가 오래
반복해 온 "빠뜨린 하나" 실수를 구조적으로 막는다. §6에서 번들 해시 일치를 **근거와 함께** 주장한 것도
28-79보다 나아진 점이다.

그런데 두 라운드를 들여 고친 것은 "**무엇을** 세는가"(시드를 빼는 것)였고, **"누구의 것을 세는가"는 아무도
보지 않았다.** 01이 그것이고, 이번 감사에서 유일한 「상」이다.

## 01 (상) `publicStats()`는 플랫폼 실적이 아니라 **이 브라우저의 실적**이다

지금 배포된 모드는 **로컬 모드**다:

```ts
// bootstrap.ts:19
export const AUTH_MODE: 'local' | 'server' = import.meta.env['VITE_AUTH_MODE'] === 'server' ? 'server' : 'local'
// bootstrap.ts:26 — 로컬 모드의 저장소
const s = window.localStorage
```

`vercel.json`에도 배포 설정 어디에도 `VITE_AUTH_MODE`가 없다(`grep -rn 'VITE_AUTH_MODE' src vercel.json
.github/workflows/*.yml` → 서버 모드 지정은 CI의 `server` job에만 있다). 즉 라이브는 **브라우저마다 별도의
localStorage**를 쓴다.

그러면 랜딩의 "누적 요청 N"이 세는 것은 **그 방문자가 자기 브라우저에서 만든 요청 수**다. 플랫폼 누적이
아니다. 28-80은 이 값에 `publicStats`라는 이름을 붙이고 문서에 "**공개 화면이 내거는 숫자**", 주석에
"**실제 실적만**"이라고 못 박았는데, 그 숫자가 세는 대상은 플랫폼이 아니라 한 대의 브라우저다.

구체적으로 지금 라이브에서 일어나는 일:

- 처음 온 방문자 → 시드뿐 → 지표 숨김. **여기까지는 28-80이 의도한 대로다.**
- 그 방문자가 요청을 하나 올림 → 그 사람 화면에만 "**누적 요청 1 · 완료된 수리 0 · 낙찰률 — · 만족도 —**".
- 옆자리 다른 방문자 → 여전히 아무것도 없음. **두 사람이 서로 다른 "플랫폼 누적"을 본다.**

이것은 28-78 감사 01이 세운 잣대("말과 사실을 맞추는 것")에 여전히 걸린다. 시드 숫자를 내걸지 않게 된 것은
맞지만, 남은 숫자도 **레이블이 말하는 것과 다른 것을 센다**. 게다가 하필 그 시점의 값이 "완료된 수리 0"이라
**아무 실적도 없다고 광고하는 화면**이 된다 — 숨기던 때보다 나은지도 분명하지 않다.

28-80의 e2e는 이 상태를 **정답으로 고정했다**:

```
PASS  히어로 지표가 시드를 빼고 센다 — 누적 1 · 완료 0 · 낙찰률 — (28-80-01):
      1 누적 요청 0 완료된 수리 — 파트너 낙찰률 — 평균 만족도
```

회귀가 "이 화면이 옳다"고 못 박아 두면 다음 라운드가 이것을 문제로 보기 더 어려워진다.

**고치는 방향**(택일):
1. **서버 모드에서만 지표를 내건다.** `AUTH_MODE === 'server'`일 때만 히어로 지표 블록을 그린다 —
   그때의 숫자는 실제로 플랫폼 전체다. 로컬 모드는 원래 시연·단독 사용이므로 내걸 실적이 없는 것이 맞다.
2. 게이트 문턱을 **의미 있는 값**으로 올린다(예: `completedOrSettled > 0`). "완료된 수리 0"을 광고하지 않는다.
3. 레이블을 정직하게 바꾼다(예: "내 이용 내역"). 다만 히어로에 둘 내용은 아니다.

1번이 가장 정직하고, 2번은 1번과 겹쳐서 해도 손해가 없다.

## 02 (중) 시연 데이터 삭제에 **확인도, 되돌리기도, 무엇을 지웠는지도** 없다

이 저장소는 **훨씬 덜 파괴적인** 백업 복원에 이만큼을 요구한다:

```tsx
const RESTORE_CONFIRM = '복원'
const armed = confirm.trim() === RESTORE_CONFIRM        // 타이핑 확인 전에는 파일 선택 자체가 비활성
…
step('복원 직전 상태 자동 내려받기', dlPrev.suggestedFilename().startsWith('banded-before-restore-'))
step('복원 완료 안내 + 되돌리기 버튼', … (await page.$('[data-undo-restore]')) !== null)
```

`clearSeedData`에는 **아무것도 없다** — 버튼 하나에 요청·입찰·정산·결제·리뷰·채팅·A/S가 즉시 사라지고,
직전 상태를 파일로 내려주지도, 되돌리기 버튼을 남기지도 않는다. 운영 기록에 남는 것은 **건수뿐**이다:

```ts
this.record('admin', '시연 데이터 삭제', String(removed))   // 대상 자리에 "6" — 무엇이 지워졌는지는 없다
```

그래서 실수로 눌렀을 때 **무엇을 잃었는지조차 알 수 없다**. 정산 이력 3건이 사라지면 관리자 원장·월별
리포트·지급 대기 목록이 한꺼번에 달라지는데, 되돌릴 수단이 없다.

**「상」이 아닌 이유를 분명히 해 둔다**: 지워지는 것은 `seeded === true`인 행뿐이라 **실제 고객·파트너의
데이터는 이 버튼으로 사라지지 않는다.** 손실 범위가 시연 데이터로 묶여 있다는 점에서 복원과는 급이 다르다.
그래도 이 저장소가 스스로 세운 "비가역 조작에는 확인과 되돌림" 규칙을 새 비가역 조작이 지키지 않은 것은
사실이고, 지금은 그 규칙이 **28-59에만 있고 관례가 아니다**는 뜻이 된다.

**고치는 방향**: 백업 카드와 같은 모양 — 확인 문구(예: `시연 삭제`) 또는 최소한 2단계 확인, 그리고 삭제 전
상태를 `banded-before-clearseed-` 파일로 내려주기(복원 경로가 이미 있으므로 되살릴 수 있다). 운영 기록
`detail`에 지운 요청 id 목록을 남긴다(28-58의 `detail` 자리가 그 용도다).

## 03 (중) `hasRealActivity()`가 **프로덕션 호출자 0**이 됐고, 낙찰률 계산이 두 곳이 됐다

```
$ grep -rn 'hasRealActivity' src --include=*.ts --include=*.tsx | grep -v '\.test\.'
src/domain/platform.ts:3357:  hasRealActivity(): boolean {
src/domain/platform.ts:3362:   * 공개 지표 (28-80-01) — … 28-79는 `hasRealActivity()`로 지표를
```

정의 한 줄과 **다른 메서드의 주석**뿐이다. 28-79가 만들고 28-80이 유일한 호출자(`Landing.tsx`)를
`publicStats()`로 바꾸면서 남았다. 단위 테스트는 4건이 그대로 살아 있다(`platform.test.ts` 2건,
`bootstrap.test.ts` 2건) — **앱이 실행하지 않는 코드를 게이트가 초록으로 지키고 있다.** 이 저장소가
28-79 감사 04에서 지적한 것과 정확히 반대 방향의 같은 병이다: 그때는 테스트가 화면을 안 봤고, 지금은
테스트가 아무도 안 쓰는 것을 본다.

같은 라운드가 **낙찰률 계산을 하나 더 만들었다**. `bidStats()`의 won/lost 루프와 `publicStats()`의 루프가
따로 있고, 공유하는 것은 `WON_STATUSES` 상수뿐이다. 한쪽에서 판정 규칙이 바뀌면(예: `cancelled`를 lost로
세기로 하면) 관리자 화면과 랜딩이 **조용히 다른 낙찰률을 말한다**. 28-80 스스로 "관리자용과 공개용은 다른
것을 봐야 한다"고 했지만, 그것은 **모수**가 달라야 한다는 뜻이지 **계산 규칙**이 갈려도 된다는 뜻이 아니다.

**고치는 방향**: `hasRealActivity()`를 지우고 그 테스트를 `publicStats().totalRequests`로 옮기거나,
반대로 `hasRealActivity()`를 `publicStats()` 위에 얹어 한 줄로 만든다(둘 중 하나만 남는다).
`bidStats(partnerId?)`에 요청 필터를 받는 인자를 하나 더 두어 `publicStats`가 그것을 부르게 하면
루프가 하나가 된다.

## 04 (하) `chatReads` 키를 **새로 해체했다** — 같은 파일에 정확한 방법이 이미 있다

```ts
// clearSeedData (28-80) — 문자열 파싱
if (ids.has(key.slice(0, key.indexOf(':')))) this.chatReads.delete(key)

// pruneChats (28-54-02, 같은 파일 아래쪽) — 키를 그대로 만들어 지운다
this.chatReads.delete(`${r.id}:customer`)
this.chatReads.delete(`${r.id}:partner`)
```

키 모양을 아는 곳이 두 곳이 됐고, 새로 만든 쪽이 더 약하다: 콜론이 없는 키가 들어오면 `indexOf(':')`가
`-1`이라 `slice(0, -1)`이 되어 **키의 마지막 글자만 뗀 문자열**로 비교한다. 오늘의 키는 항상
`REQ-0001:customer` 꼴이라 도달하지 않지만, 이 저장소가 28-63-03·28-76-04에서 반복해 잡아 온
"같은 규칙이 두 곳에" 그대로다. 위쪽 코드만 보고 아래쪽을 모르는 사람이 다음에 또 만든다.

**고치는 방향**: `pruneChats`와 같은 방식으로 `for (const id of ids) { chatReads.delete(`${id}:customer`);
chatReads.delete(`${id}:partner`) }`, 또는 뷰어 목록을 상수로 빼서 두 곳이 같은 것을 쓰게 한다.

## 이번 감사에서 **문제 삼지 않은 것** (조용히 넘기지 않는다)

- **고아 스윕 회귀** — 컬렉션을 손으로 세는 대신 스냅샷 전체를 문자열로 훑어 확인한다. 감사 로그를 제외한
  근거(복원에도 보존되는 별도 장부)까지 테스트 주석에 적혀 있다. 이 라운드에서 가장 잘한 것이다.
- **관리자용 집계를 건드리지 않은 판단** — `adminOverview`·`bidStats`·`reviewStats`의 의미를 바꾸지 않고
  새 메서드를 낸 것은 옳다. 운영 화면은 기기에 있는 것을 그대로 봐야 한다.
- **§6의 해시 일치 주장** — "이름이 같으면 내용이 같다"는 근거(Vite 콘텐츠 해시)를 함께 적었고, 28-79에서
  같은 주장을 하지 않은 이유까지 남겼다. 주장의 강도와 근거가 맞는다.
- **`SeedDataCard`가 지운 뒤에도 결과를 남기는 것** — 지우자마자 카드가 사라져 결과를 못 읽던 것을
  구현 중에 잡았고, 스텝 이름도 "카드 사라짐"에서 "지우기 버튼 사라짐"으로 고쳤다. 말과 동작을 맞췄다.
