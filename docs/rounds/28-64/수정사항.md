## 28-63-01 (상) 실제 서비스가 그 빌드를 서빙하는지 아무도 확인하지 않던 문제
63라운드 동안 게이트는 전부 개발 컨테이너 안에서 끝났다. 이 라운드에서 **마지막 구간을 기계에 넘겼다.**

- **`.github/workflows/deploy-check.yml` 신설**(저장소 루트). GitHub Actions는 개발 환경의 네트워크 제약
  밖에서 돌기 때문에 라이브 주소를 직접 받을 수 있다.
- 트리거: `push`(main) · `workflow_dispatch` · `schedule`(하루 1회).
- 검사: ① 라이브 주소가 HTTP 200인지(최대 5회 재시도) ② `index.html`이 참조하는 **실제 서빙 번들**에
  현재 라운드 문자열이 있는지. 다르면 실패한다.
- 기대 라운드는 `vercel.json`의 `outputDirectory`에서 읽는다 — **라운드마다 이 파일을 고칠 필요가 없다.**
  `workflow_dispatch`의 `expect_round` 입력으로 일부러 틀린 값을 넣어 "틀리면 잡는지" 시험할 수 있다.
- 로컬 `visual-check`(서빙 번들 = 로컬 dist 대조)와 같은 발상을 프로덕션에 적용한 것이다.

### 왜 이제야 가능한가 — 막힘의 원인을 이번에 확정했다
- **네트워크**: 이 환경의 프록시가 외부 도메인을 전면 차단한다(`example.com`도 `CONNECT tunnel failed, response 403`).
  우리 사이트 문제가 아니다.
- **Vercel MCP**: `list_teams`는 올바른 팀(`team_lqWG0vyxcJC3nKngoETpyeKZ`)을 돌려주는데
  `list_projects`가 빈 배열, `get_project` 404, `list_deployments` 403 — 계정은 맞고 **권한 범위가 없다.**
- 둘 다 코드로 못 고친다. 그래서 **확인 주체를 GitHub Actions로 옮겼다.**
- 덤: Vercel 배포 결과는 **GitHub 커밋 상태**에도 남아 읽을 수 있다는 것을 확인했다
  (28-61 #174 / 28-62 #178 / 28-63 #182 모두 `success — Deployment has completed`).

## 28-63-02 (중) 자체 검사가 아는 이름의 범위가 좁던 문제
- `platform.extraNames`(주입형)를 두고 `PlatformProvider`가 `auth.listAccounts()`의 이름을 채운다.
  스냅샷에는 **요청을 낸 고객**과 **프로필을 쓴 파트너** 이름만 있어, 가입만 한 회원은 검사 대상이 아니었다.
- 비어 있어도 기존 동작 그대로다 — 검사 범위만 넓힌다.

## 28-63-03 (중) 토글 부품화가 절반만 되던 문제
- `filter-group` **인라인 구현이 0곳**이 됐다. 남아 있던 4곳(위저드 질문 보기·희망 시간대·파트너 작업/정산 필터)을
  모두 `ToggleGroup`으로 옮겼다.
- 선택 해제가 필요한 그룹(질문 보기)은 `deselectable` 옵션으로 흡수하고, **판별 유니온**으로 타입을 갈라
  해제 그룹만 빈 문자열을 다루게 했다 — 일반 필터 호출부는 `''`를 신경 쓰지 않는다.
