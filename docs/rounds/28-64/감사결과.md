# 28-64 감사 결과

> 28-64는 배포 확인을 개통한 라운드다(deploy-check 워크플로 + 가명 처리 이름 출처 확대 + ToggleGroup 정리).
> 그 결과물과 28-64 코드 전반을 다시 읽었다. 아래는 전부 코드를 직접 읽거나 실행해 확인한 것이다.

## 이 감사에서 먼저 확인한 전제 — 이 플랫폼에는 서버가 없다

소스 전체에 `fetch`·XHR·WebSocket이 **0건**이고, 모든 상태는 방문자 브라우저의 `localStorage`
(`banded-platform-v1`, `banded-auth-v1`)에만 있다. 시드도 가짜 데모 데이터다(`src/app/bootstrap.ts:22`).

그래서 지금까지 만든 입찰·채팅·결제·정산·A/S는 **한 브라우저 안에서 한 사람이 3역할을 다 할 때만** 성립한다.
고객이 휴대폰에서 올린 요청을 파트너가 노트북에서 볼 수 없다. 그리고 최근 6라운드(28-59~28-64)를 쏟은
개인정보 보호 장치가 지키는 경계 중 **실재하는 것은 "관리자가 내려받는 파일" 하나뿐**이다 —
역할 간 분리는 실제 테넌트 경계가 아니다.

이 전제에 맞춰 아래 심각도를 매겼다. 브라우저 안에서만 성립하는 문제는 과장하지 않되,
서버가 생기는 순간 그대로 사고가 되는 것은 그렇게 적었다.

## 28-64-01 (상) 게이트가 거짓 초록이라 실제 버그가 배포됐다

`test:node`(`package.json:12`)가 도는 유일한 파일 `tests/node/format.test.mjs`는 `scripts/format.mjs`를
import하는데, **그 파일을 쓰는 앱 코드가 한 줄도 없다**. `# pass 7`은 전부 여기서 나온다.

하필 그 죽은 파일이 28-1-04(달력에 없는 날짜 거부)를 구현·검증하고, **실제 배포되는**
`src/ui/format.ts:12 koreanDate`에는 그 가드가 없다. 실행해 확인한 결과:

```
koreanDate('2026-02-31')  ->  "3월 3일 화요일"   ← 없는 날짜를 다른 날짜로 조용히 바꿔 보여준다
koreanDate('2026-02-30')  ->  "3월 2일 월요일"
```

도메인에는 이미 올바른 `isValidDateStr`/`assertValidDateStr`(`src/domain/date.ts:32`)가 있는데
UI가 그것을 쓰지 않고 잘못 재구현했다. `krw`·`isKnownError`는 테스트 0건이다.

게이트 전체가 명예제도라는 점도 같은 뿌리다. `.github/workflows/`의 유일한 파일은 `deploy-check.yml`이고
라이브 URL만 본다 — `check`/`e2e`/`visual-check`/`audit` 넷 다 CI에서 안 돌아, 타입 오류나 테스트 실패가 있는
커밋도 main에 들어가 그대로 배포된다. `vitest.config.ts:5`의 `include: ['src/**/*.test.ts']`는
`.tsx` 테스트를 **오류 없이 침묵으로** 버린다(현재 `.tsx` 30개, `.test.tsx` 0개).

## 28-64-02 (상) 가명본 구조 검사가 정작 요청 컬렉션에 닿지 못한다

`assertPseudonymousShape`(`src/domain/platform.ts:104`)는 `out[path]` **단일 조회**라 경로 탐색이 없다.
그런데 요청은 `out.store.requests`에 **중첩**돼 있다(`:3181`) — `out['store.requests']`는 `undefined`라
검사를 통째로 건너뛴다. `customerName`·`region`·`description`·`answers`·`photos`를 이고 있는
유일한 컬렉션이 무방비다.

**이미 살아 있는 증거**: `photoCount`(`:3189`)가 방출되는데 `PSEUDONYMOUS_REQUEST_KEYS`(`:73`) 밖이다.
아무도 안 잡는다. `:100` 주석의 "새 필드가 생기면 기본이 '제외'다"는 지금 코드에서 이미 거짓이다.

같은 이유로 무력한 것들:
- `['estimates', []]`(`:3226`) — 행이 `[id,{...}]` 배열이라 `:108`에서 `continue`. 무의미한 항목이 검사처럼 보인다.
- `profiles`(`:3219`) — 같은 이유로 검사 불가. 목록에도 없다.
- `settings`(`:3210`) — 객체라 `Array.isArray` 실패로 건너뜀. 목록에 없다.
- `daysOff`(`:3207`) — `out.daysOff = snap.daysOff`, **컬렉션 통째 통과**. 28-62-01이 없앴다고 선언한 바로 그 패턴.

값 대조도 좁다. `assertNoRealNames`(`:118`)는 **이름만** 본다. `extraNames`에 넣는 건 `a.name`뿐인데
(`src/app/PlatformContext.tsx:37`) `AccountView`에는 `phone`·`bizNo`가 있다(`src/domain/auth.ts:62,68`).

지역 축약은 휴리스틱이다. `city = (r) => r.split(/\s+/).slice(0,2).join(' ')`(`:3175`)에 자유 입력이
들어온다(`src/features/customer/CustomerRequest.tsx:166`, 플레이스홀더만 있는 `<input>`). 실행해 확인:

```
"서울강서구화곡동123-45 202호"  ->  "서울강서구화곡동123-45 202호"   ← 상세 주소 그대로
"강서구 화곡로12길 3"          ->  "강서구 화곡로12길"              ← 도로명까지
```

구조 검사가 요청을 안 보고 값 검사가 주소를 안 보므로 **둘 다 놓친다.** 이 앱에서 유일하게 실재하는
데이터 경계(브라우저를 떠나는 다운로드 파일)라 상으로 둔다.

## 28-64-03 (중) 열람권 범위 오류 — 서버가 생기는 날 그대로 사고가 된다

`exportPartnerData`(`platform.ts:3293`)에서 형제 줄은 전부 파트너로 좁히는데 `claims`만 안 좁힌다:

```ts
visits:  ... ids.has(s.requestId) && s.partnerId === partnerId          // 범위 있음
jobs:    ... ids.has(j.requestId) && j.partnerId === partnerId          // 범위 있음
reviews: ... ids.has(v.requestId) && ...acceptedPartnerId === partnerId // 범위 있음
claims:  this.claims.filter((c) => ids.has(c.requestId))                // 범위 없음
```

`ids`는 **입찰했거나 철회한** 요청 전부다(`:3296`). 낙찰 실패한 파트너가 낙찰 파트너의 자유 서술
`partnerReply`(`types.ts:343`)를 받는다. `Claim`에 `partnerId`가 없으므로 `reviews`와 같은 판정을 써야 한다.

대칭도 무너져 있다. `exportCustomerData`(`:3267`)는 **자체 검사가 없고** 통째 전개다
(`requests: mine.map((r) => ({ ...r }))`, `claims: ...({ ...c })`). 관리자 내부 메모 `Claim.resolution`
(`platform.ts:2619`에서 관리자가 작성)이 정보주체에게 그대로 간다. 파트너 경로는 필드를 골라 담고
자체 검사까지 하는데 고객 경로는 기본이 "포함" — 28-64-02와 같은 실패 형태다.

지금은 한 브라우저 안이라 실사고가 아니지만, 다중 사용자가 되는 순간 그대로 유출이다.

## 28-64-04 (중) 감사 로그가 남겨야 할 것을 지운다

**병합이 내용을 덮어쓴다.** `record`(`:3101`)의 병합 키는 `actor/action/target/by`인데 `detail`은 키가
아니면서 최신 값으로 덮어쓴다(`:3112`). `updateSettings`는 target이 상수 `'settings'`이고 바뀐 필드 목록을
`detail`에 넣는다(`:2692`). 5분(`AUDIT_COLLAPSE_MS`) 안에 설정을 두 번 바꾸면 한 줄로 접히고 `count: 2`가
되지만 **첫 변경 내역은 사라진다.** "불변 기록"(`types.ts:110`)이 서로 다른 내용을 조용히 버리는 것은
표시 선택이 아니라 결함이다.

**상한 축출이 보안 이력을 먼저 버린다.** `pruneAuditLog`(`:3415`)는 `actor === 'system'`을 오래된 것부터
먼저 버리는데, 인증 보안 이벤트(로그인 실패·잠금·비밀번호 변경·탈퇴)가 전부 `system`으로 들어온다
(`PlatformContext.tsx:41`). 주석(`:3413`)의 의도("무차별 로그인이 운영 기록을 밀어내지 못한다")와
**반대로**, 평범한 관리자 작업 폭주가 잠금 이력을 지운다. 28-58-03이 인증 이벤트를 같은 `system` 바구니에
넣은 뒤로 정책과 코드가 어긋났다.

**파싱 불가 타임스탬프는 영구 잔류.** `:3409` `Number.isNaN(t) ? true : t > cut` — 보관 정책을 영원히
통과하고 `:3108`에서 병합도 영구히 막는다. `importSnapshot`은 `at`이 문자열인지만 본다(`:2153`).

## 이번 감사에서 확인했지만 항목으로 올리지 않은 것

다음 라운드 후보로 남긴다. 근거는 모두 확인했다.

- **단일 번들.** `App.tsx` 정적 import 26개, 동적 import 0. 익명 방문자가 받는 411,488 B 단일 청크에
  관리자 전용 문자열("백업 모드"·"가명본"·"운영 기록")이 실제로 들어 있다.
- **ToggleGroup 접근성 미완.** `MyProfile.tsx:120`·`AuthGate.tsx:168`(사업자/개인, 필수 가입 분기)이
  28-62-03 이행에서 누락돼 CSS 클래스로만 상태를 표현한다. 단일 선택 그룹은 `aria-pressed`가 아니라
  `radiogroup`/`aria-checked` + roving tabindex가 맞다.
- **visual-check가 로그인을 안 한다.** 17개 실제 화면을 한 번도 렌더링하지 않고 저장된 베이스라인도 없다
  (CSS 값 4개 비교 + 읽히지 않는 스크린샷). 레이아웃 회귀를 못 잡는다.
- **랜딩 SEO.** `index.html`에 description·Open Graph·canonical이 없고 `robots.txt`/`sitemap.xml`도 없다.
  히어로 이미지가 `loading="lazy"`라 LCP를 스스로 늦춘다(`Landing.tsx:114`).
