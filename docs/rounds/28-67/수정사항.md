## A. 서버 경계 — 복제 포트

### 먼저 세어 봤다

"서버를 붙인다"의 자연스러운 첫 수는 `save()`·`load()`를 `Promise`로 바꾸는 것이다.
그 전에 코드를 세었고, 그 수가 **한 라운드에 끝낼 수 없다**는 것이 드러났다:

- UI가 도메인을 **동기 호출하고 반환값을 즉시 쓰는 곳 245곳**
- `this.save()` 호출이 **57개 메서드에 하나씩** (배칭 계층 없음)
- `AuthService` 생성자가 `this.load()`를 직접 부른다 (생성자는 await 불가)
- `auth.sessionFor()`는 읽기처럼 보이지만 만료 시 쓰고, 그것이 **렌더 중에** 호출된다
- `fetch`/XHR/WebSocket **0건**

그래서 경계를 다른 곳에 뒀다.

### 놓은 것

```
UI (245곳, 동기)  →  PlatformService  →  localStorage      ← 진실은 여기. 지금과 같다.
                            │
                            └─ Replicator ──→ SnapshotPort ──→ 원격
                               (합침·재시도·충돌)   ↑ 28-68에서 여기만 갈아 끼운다
```

| 파일 | 역할 |
|---|---|
| `src/domain/ports.ts` | `SnapshotPort` 계약 — `read()` / `write(rec, expectedRev)` |
| `src/domain/ports/localPort.ts` | localStorage 어댑터 (기존 키 레이아웃 그대로) |
| `src/domain/ports/memoryRemotePort.ts` | 가짜 원격 — 지연·실패·충돌 주입 가능 |
| `src/domain/replicator.ts` | write-behind 복제기 |
| `src/domain/ports.contract.test.ts` | **두 구현이 모두 통과해야 하는** 공유 계약 |

**도메인은 한 줄도 고치지 않았다.** 복제기는 `revision()`·`body()`·`accept()` 세 개만 요구하는
좁은 인터페이스(`ReplicationSource`)를 받고, `bootstrap.ts`가 `PlatformService`를 거기에 맞춰 감싼다.

### 계약이 고친 것

현재 `save()`는 "rev 읽기 → 본문 쓰기 → rev 쓰기"로 **2키 비원자 쓰기**를 한다.
본문은 저장됐는데 rev 저장이 실패하는 창이 있다. 포트는 그 둘을 한 번의 `write`로 묶고
`expectedRev`로 낙관적 동시성을 계약 수준에서 요구한다.

### 계약 테스트가 실제로 버그를 잡았다

`LocalSnapshotPort.write()`를 처음엔 `await this.read()`로 썼다. 계약의
"동시 writer 둘 중 하나만 성공"에서 **둘 다 성공**했다 — `await`가 비교와 쓰기 사이에
양보를 만들어 다른 writer가 끼어들었다. 비교-쓰기 사이에 `await`가 없도록 고쳤다.
서버를 붙이는 날 발견했을 종류의 결함이다.

### 동작은 바뀌지 않았다

원격은 아직 메모리 가짜다. 복제는 **탭 복귀·다른 탭 저장 때만** 돌고
(매 변경마다 전체 스냅샷을 직렬화하지 않는다), 보내는 도중의 변경은 합쳐서 마지막 상태만 보낸다.
**e2e 194단계가 그대로 통과한다.**

남은 것 다섯 가지(HTTP 어댑터·DB 프로비저닝·인증 토큰·사용자별 스코프·부분 저장)는
`28-67/서버_경계.md`에 적었다. **"서버를 붙였다"고 말하지 않기 위한 문서다.**

## B. 28-66 감사 4건

### 28-66-01 (상) spec 목록의 완전성 검사 + fail-closed

`assertPseudonymousShape`가 "spec에 적힌 것"만 확인하고 "적히지 않은 것이 있는지"는 묻지 않았다.
그래서 `daysOff`가 결과에 실리면서도 `pick()`도 spec도 없는 유일한 컬렉션으로 남아 있었다.

셋을 고쳤다:

1. **완전성 검사**(`assertSpecCoverage`) — `out`을 훑어 spec 없는 컬렉션이 있으면 실패.
   *켜자마자 `daysOff`를 잡았다* (아래 검증결과에 출력 인용).
2. **fail-closed** — spec 경로를 결과에서 찾지 못하면 조용히 통과하던 것(`continue`)을 실패로.
   경로 오타나 산출물 키 변경으로 검사가 소리 없이 사라지던 통로였다.
3. **비대칭 제거** — 최상위 `[id, obj]` 행에서 `row[1]`만 보던 것을, 원소 개수와 `row[0]` 타입까지 확인.

`ShapeSpec`에 `{ pairOf: 'scalars' }` 행 모양을 더해 `daysOff`를 표현했다.
값 배열에 객체가 섞이면 실패한다 — 휴무 사유 같은 필드가 붙는 날 조용히 사라지지도, 조용히 새지도 않는다.

기존 테스트 한 줄(`'없는 경로는 여전히 건너뛴다'`)이 **이 fail-open을 단언하고 있었다.**
그 줄이 곧 결함이었으므로 새 계약으로 바꿨다.

### 28-66-04 (중) 오류 발견 범위를 소스 전체로

`errors.test.ts`의 glob이 `src/domain/*.ts`뿐이라 `errors.ts`가 약속한 보증이 실제보다 넓었다.

- 파일을 `src/errors.test.ts`로 옮기고 glob을 **`src/**` 의 `.ts`·`.tsx`** 로 넓혔다.
  제외는 브라우저 진입점 `src/main.tsx` 하나뿐이고(import만으로 `window`를 건드린다)
  **그 사실이 glob 한 줄에 드러나 있다.**
- `DomainError` 제외를 이름이 아니라 **동일성 비교**로 (재export 오탐 제거).
- glob이 다시 좁아지면 잡는 테스트를 더했다(모듈 30개 초과 + `domain`·`ui`·`app`·`features` 포함).
- 넓힌 sweep이 곧바로 **`src/ui/image.ts`의 맨 `Error` 2건**을 드러냈다 → `ImageError extends DomainError`로 승격.
- `MyAccount.tsx`의 업무 규칙 위반 2건도 `PlatformError`로. 같은 파일의
  `if (isKnownError(err) || err instanceof Error)`는 **죽은 조건**이었고(좌변이 우변에 포함)
  `TypeError` 같은 진짜 버그 메시지까지 노출하고 있어 다른 화면과 같은 규약으로 맞췄다.
- `errors.ts`의 보증 문구를 실제 범위와 일치시켰다.
