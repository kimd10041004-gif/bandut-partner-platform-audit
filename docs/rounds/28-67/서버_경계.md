# 서버 경계 — 지금 어디까지 왔고, 진짜 서버까지 무엇이 남았나 (28-67)

> 그 값으로 기다리는 타이머가 없었고, `markChanged()`를 부르는 프로덕션 코드도 없었다(28-67-03).

> `write(body, expectedRev)`이고 rev는 저장소가 발급한다(28-68-01).


## 왜 도메인을 비동기로 바꾸지 않았나

"서버를 붙인다"의 자연스러운 첫 수는 `save()`·`load()`를 `Promise`로 바꾸는 것이다.
그러기 전에 코드를 세어 봤고, 그 수가 이 저장소에서는 **한 라운드에 끝낼 수 없다**는 것이 드러났다.

| 사실 | 근거 |
|---|---|
| UI가 도메인을 **동기 호출하고 반환값을 즉시 쓰는 곳 245곳** | `Jobs.tsx`가 `submitEstimate()`의 반환값으로 안내 문구를 조립한다. `await`·Promise는 앱 소스에 이미지 리사이즈 말고 없다 |
| `this.save()` 호출이 **57개 메서드에 하나씩** | 배칭·큐잉 계층이 없다. "변경 → 즉시 저장"이 57번 반복된다 |
| `AuthService` 생성자가 `this.load()`를 직접 부른다 | 생성자는 `await`할 수 없다. 정적 팩토리가 없어 구조 변경이 필요하다 |
| `auth.sessionFor()`는 읽기처럼 보이지만 만료 시 **쓴다** | 그리고 **렌더 중에** 호출된다(`PlatformContext.tsx`) |
| 첫 렌더 중 시드 + sweep/prune 7종이 수십 회의 동기 쓰기를 낸다 | `bootstrap.ts`의 `initPlatform()` |
| `fetch`/XHR/WebSocket **0건** | 네트워크 코드가 애초에 없다 |

전부 동시에 풀어야 하는 변경이고, 중간에 깨지면 무엇이 원인인지 구분할 수 없다.

## 그래서 놓은 것 — 복제 포트 (write-behind)

**도메인은 동기로 둔다.** 로컬에 즉시 쓰므로 화면은 지금처럼 빠르고 오프라인에서도 동작한다.
원격 반영은 뒤에서 도는 복제기가 맡는다.

```
UI (245곳, 동기)  →  PlatformService  →  localStorage      ← 지금과 같다. 진실은 여기.
                            │
                            └─ Replicator ──→ SnapshotPort ──→ 원격
                               (합침·재시도·충돌)   ↑
                                       28-68에서 여기만 갈아 끼운다
```

| 파일 | 역할 |
|---|---|
| `src/domain/ports.ts` | `SnapshotPort` 계약 — `read()` / `write(rec, expectedRev)` |
| `src/domain/ports/localPort.ts` | localStorage 어댑터. 기존 키 레이아웃 그대로 |
| `src/domain/ports/memoryRemotePort.ts` | 가짜 원격. **지연·실패·충돌을 주입**할 수 있다 |
| `src/domain/replicator.ts` | write-behind 복제기. 합침 · 지수 백오프 · 충돌 시 원격 수용 |
| `src/domain/ports.contract.test.ts` | **두 구현이 모두 통과해야 하는** 공유 계약 |

### 계약이 고친 것

현재 `save()`는 "rev 읽기 → 본문 쓰기 → rev 쓰기"로 **2키 비원자 쓰기**를 한다.
본문은 저장됐는데 rev 저장이 실패하는 창이 있다. 포트는 그 둘을 한 번의 `write`로 묶고,
`expectedRev`로 낙관적 동시성을 **계약 수준에서** 요구한다. 서버 구현은 이걸 트랜잭션으로 만족시키면 된다.

### 계약 테스트가 실제로 버그를 잡았다

`LocalSnapshotPort.write()`가 처음엔 `await this.read()`로 현재 값을 읽었다.
계약의 "동시 writer 둘 중 하나만 성공"에서 **둘 다 성공**했다 — `await`가 비교와 쓰기 사이에
양보를 만들어 다른 writer가 끼어들었다. 비교-쓰기 사이에 `await`가 없도록 고쳤다.
**계약 테스트가 없었으면 서버를 붙이는 날 발견했을 종류의 결함이다.**

## 지금 상태 — 동작은 바뀌지 않았다

`bootstrap.ts`의 `initReplicator()`가 붙이는 원격은 **메모리 가짜**다. 페이지를 새로 열면 사라진다.
즉 사용자 눈에 보이는 변화가 없고, e2e 194단계가 그대로 통과한다. 그래도 지금 배선해 두는 이유는
**서버가 생기는 날 바꿀 것이 포트 한 줄이 되게** 하기 위해서다.

복제는 매 변경마다 돌지 않는다. `save()` 지점이 57개라 조작 한 번이 저장을 여러 번 낼 수 있고
전체 스냅샷 직렬화는 비싸다. 그래서 **탭 복귀·다른 탭 저장 때만** 돌고, 보내는 도중의 변경은 합쳐서
마지막 상태만 보낸다(부분 저장이 없는 모델이라 중간 상태를 건너뛰어도 잃는 것이 없다).

## 진짜 서버까지 남은 것

1. **HTTP 어댑터** — `HttpSnapshotPort implements SnapshotPort`. 계약 테스트에 한 줄 추가하면
   로컬 구현과 같은 스위트를 통과해야 한다.
2. **DB 프로비저닝** — 계정 생성과 연결 문자열 발급이 필요하다. **제 손 밖의 작업**이라
   28-68에서 이것부터 여쭙는다.
3. **인증 토큰** — 지금 `AuthService`는 브라우저 안에서만 판정한다. 서버가 생기면 세션이
   서버에서 발급·검증돼야 하고, 그때 `sessionFor()`의 렌더 중 쓰기가 실제 장애물이 된다.
4. **사용자별 스코프** — 지금은 스냅샷이 **하나**다. 고객·파트너·관리자가 같은 문서를 본다.
   서버에서는 요청·입찰 단위로 쪼개고 누가 무엇을 읽는지 **서버가** 판정해야 한다.
   28-59~28-66이 만든 가명본·열람권 장치는 그때 비로소 진짜 경계를 지키게 된다.
5. **부분 저장** — 전체 스냅샷 push는 사진이 쌓이면 감당이 안 된다. 엔티티 단위 쓰기가 필요하고,
   그건 도메인의 57개 `save()` 지점을 다시 보는 일이다.

이 문서의 목적은 "서버를 붙였다"고 말하지 않기 위해서다. **경계를 놓았을 뿐이고,
위 다섯이 남아 있다.**
