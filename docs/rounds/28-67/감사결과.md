# 28-67 감사 결과 (GPT 역할)

대상 커밋 `5843ab7` (PR #199, `main` 병합본). 라운드 문서 3종(`수정사항.md`·`검증결과.md`·`서버_경계.md`)과
실제 코드를 대조했다.

인정할 것부터. 이 라운드는 **경계를 옳은 곳에 놓았다.** "도메인을 비동기로 바꿀 수 없다"는 근거
(245개 동기 호출부 · 57개 `save()` · 생성자 `load()` · 렌더 중 쓰기)를 실제로 세어서 적었고,
그래서 write-behind를 골랐다. 계약 테스트가 자기 구현의 진짜 동시성 버그를 잡아낸 것도
(`LocalSnapshotPort.write()`의 `await this.read()` 양보) 이 방법이 작동한다는 증거다.

그런데 **그 복제기가 실제 원격을 만나는 날 발현할 치명 결함 셋**을 가지고 있다.
지금 원격이 메모리 가짜라 셋 다 조용하다. 서버를 붙이기 전에 고쳐야 한다.

## 28-67-01 (상) `payout.account`에 예금주 실명이 평문이고, 그래서 파트너 본인 내보내기가 실패할 것으로 읽힌다

28-67은 `EXPORT_PAYOUT_KEYS`에 `'account'`를 복원하며 근거를 *"이미 마스킹된 본인 값"*이라 적었다.
**절반만 참이다.** 마스킹되는 것은 계좌번호뿐이다:

```ts
// src/domain/auth.ts:106-107
export function payoutAccountLabel(a: PayoutAccount): string {
  return `${a.bank} ${maskAccountNumber(a.number)} (${a.holder})`   // 번호만 마스킹, 예금주는 평문
}
```

`markPayout`이 이 문자열을 **통째로** `job.payout.account`에 넣는다
(`platform.ts`: `job.payout = { paidAt, amount, account: account.trim() }`).
즉 파트너 열람권 JSON에 `"국민 123-**-**7890 (김반듯)"`처럼 사람 이름이 그대로 실린다.

그런데 `exportPartnerData`의 자체 검사는 **업체명 하나만** 제외한다:

```ts
assertNoRealIdentifiers(json, this.realIdentifiers().filter((n) => n !== this.profiles.get(partnerId)?.name))
```

`realIdentifiers()`에는 `extraNames`(= `auth.listAccounts()`의 모든 이름·전화·사업자번호)가 들어간다.
그리고 **가입명·업체명·예금주는 서로 별개의 자유 입력**이다 — `Settlement.tsx`의 예금주 placeholder가
`"예: 반듯설비 (사업자) / 김반듯 (개인)"`인 것이 그 증거다. 셋이 어긋나는 흔한 조합에서:

| 값 | 어디서 오는가 | 자체 검사에서 |
|---|---|---|
| 업체명 `반듯설비` | `profiles.get(partnerId).name` | 제외됨 ✅ |
| 가입명 `김반듯` | `extraNames` | **제외 안 됨** |
| `payout.account` = `"국민 123-**-**7890 (김반듯)"` | 결과 JSON | **가입명을 포함** |

→ `assertNoRealIdentifiers`가 잡아 **파트너 본인의 "내 데이터 내보내기"가 `PlatformError`로 실패**한다.
개인정보 보호 장치가 정보주체 본인의 열람권을 막는 형태다.

**세 번째 공허한 테스트.** 28-67의 회귀 테스트는 `markPayout(r.id, '국민 123-**-**7890')` —
**예금주가 없는 문자열**을 넣었고 `extraNames`도 비어 있어 이 경로를 태우지 않았다.
28-65(`'김반듯'`을 `customerId` 자리에 넘김), 28-66(키 목록만 확인)에 이어 **같은 실패 형태가 세 번째**다.
"회귀 테스트를 썼다"가 "그 경로를 태웠다"를 뜻하지 않는다.

> 코드를 읽어 내린 결론이고 **아직 재현하지 않았다.** 28-68의 첫 작업이 재현 테스트다.

## 28-67-02 (상) 복제기의 치명 결함 셋 — 실제 원격이 붙는 순간 전부 발현

`src/domain/replicator.ts`

**(a) `write()`에 try/catch가 없다** (`:140`). 바로 위 `read()`는 감쌌는데 write는 맨몸이다.
그리고 `ports.ts`의 계약은 *"write는 던지지 않는다"*를 **어디에도 적지 않았다.**
`HttpSnapshotPort`에서 `fetch`가 네트워크 오류로 reject하면:

```
run() reject → sync()의 `await this.inFlight`가 throw
            → `if (this.again)` 블록에 도달 못 함 → again이 영구히 true
            → 상태 'syncing' 고정(offline로 안 넘어감), failures 안 늘어 백오프도 안 자람
            → PlatformContext가 `void replication.sync()` → unhandledrejection
이후 매 sync가 2회씩 돈다. 회복 불가.
```

**(b) `knownRemoteRev`를 `accept()`보다 먼저 갱신한다** (`:149-150`; read 분기도 `:124,127`에서 같은 형태):

```ts
this.knownRemoteRev = res.remote.rev                              // 먼저
if (res.remote.body !== '') this.source.accept(res.remote.body)   // 던질 수 있다
```

`accept`는 `platform.importSnapshot()`이고, **손상 본문에 던지도록 설계돼 있다**
(`replicator.ts:13-14` 주석이 그렇게 적었다). 던지면 `knownRemoteRev`는 이미 갱신된 뒤라
**다음 sync가 read를 건너뛰고 곧장 write해서, 더 새로운 원격을 더 오래된 로컬로 덮는다.**
`:148`이 적은 `"남의 변경을 덮지 않는다"`가 정확히 깨진다.

**(c) `{rev: 0, body: ''}` 센티널이 영구 conflict 루프를 만든다.**
두 어댑터가 "expectedRev는 non-null인데 원격이 비었다"에 같은 센티널을 돌려주는데
(`localPort.ts:60`, `memoryRemotePort.ts:65`) **`ports.ts`에 문서화돼 있지 않다.**
`knownRemoteRev = 5`인 상태에서 원격이 사라지면(초기화·삭제):

```
sync#1  write(rec, 5) → 원격 없음 → conflict(센티널) → knownRemoteRev = 0
sync#2  write(rec, 0) → 원격 없음 → conflict(센티널) → knownRemoteRev = 0
sync#3… 무한. 상태 'conflict' 고정, failures = 0이라 백오프도 안 걸린다
```

`knownRemoteRev`를 `undefined`로 되돌리는 코드가 어디에도 없어 **다시 `read()`하지 않는다.**

곁들여: offline 실패 뒤에도 되돌리지 않아 `:120`의 주석 **"첫 동기화·재접속"의 "재접속"이 거짓**이다.
오래 오프라인이었다가 돌아오면 read를 건너뛰고 stale한 expectedRev로 곧장 write한다.

## 28-67-03 (중) 배선이 죽어 있는데 문서는 완성된 기능으로 선언했다

```
markChanged()                  프로덕션 호출 0곳 (정의 + 테스트 3곳뿐)
replication                    PlatformContext 밖 소비자 0곳
onStatus                       initReplicator()가 옵션을 안 넘김 → 항상 no-op
currentStatus() / backoffMs()   프로덕션 사용 0곳
LocalSnapshotPort              프로덕션 사용 0곳 (계약 테스트에서만)
```

`markChanged()`를 아무도 부르지 않으므로 **`'pending'` 상태는 절대 도달하지 않는다.**
그런데 `수정사항.md`·`서버_경계.md`는 복제기를 *"합침 · **지수 백오프** · 충돌 시 원격 수용"*이라 적었다.
**재시도 스케줄러가 없다** — `backoffMs()`는 값을 돌려줄 뿐 아무도 그 값으로 기다리지 않고 타이머가 없다.
재시도는 사용자가 탭을 포커스할 때만 일어나고, 그때 백오프는 무시된다.
`검증결과.md`의 "정직하게 남기는 것"은 "원격이 메모리 가짜"만 적었지 **이 죽은 배선은 적지 않았다.**

성능도 붙는다. `run()`이 상태를 보지 않고 **매번** `platform.exportData()`
(= `JSON.stringify(snapshot, null, 2)`, 들여쓰기 포함 전체 스냅샷)를 만든다. 조기 반환이 없다.
`PlatformContext`가 `focus`와 `visibilitychange`를 **둘 다** 등록해서, 탭 전환 한 번에
사진 포함 수 MB 직렬화가 **메인 스레드에서 두 번** 돈다. 얻는 것은 페이지를 닫으면 사라지는 메모리 객체뿐.

`LocalSnapshotPort`의 독스트링도 사실과 다르다 — *"복제기가 로컬을 읽는 데 쓴다"*고 적었지만
`initReplicator()`는 이 포트를 거치지 않고 `platform.exportData()`를 직접 읽는다.

## 28-67-04 (중) 오류 규약이 계약에 없고, 넓힌 glob의 보증이 또 실제보다 넓다

**(a)** `SnapshotPort`는 **`read()`가 던져도 되는지 한 줄도 적지 않았다.** `WriteResult`에만
`unavailable`이 있어 write만 결과값 규약이다. 그런데 계약 테스트 헤더는
*"닿을 수 없으면 unavailable (예외가 아니라 결과값)"*이라 선언해 놓고,
`MemoryRemotePort.read()`는 **예외를 던지고**(`:56`), `LocalSnapshotPort.read()`는 catch해서
**절대 던지지 않는다**(`:41-43`). **두 구현의 read 실패 동작이 이미 다른데 공유 계약이 못 잡는다.**
게다가 던지는 것이 맨 `new Error`라 `isKnownError`가 거짓 — 같은 라운드가 `ImageError`로 고쳤다는 그 패턴이다.

**(b)** `src/ui/image.ts:47`에 맨 `Error`가 **아직 남아 있다**:

```ts
img.onerror = () => { URL.revokeObjectURL(url); reject(new Error('이미지 파일을 읽을 수 없습니다')) }
```

3곳 중 2곳만 고쳤고, 남은 하나가 **손상된 이미지 파일을 고르는 가장 흔한 실패 경로**다.
그리고 넓힌 glob은 이걸 **원리적으로 못 잡는다** — `errors.test.ts`는 모듈이 **export한 클래스**를 찾지
`throw new Error(...)` 문장을 찾지 않는다. `errors.ts`의 새 보증 문단은 그 구분을 하지 않아
28-64-01·28-65-03이 반복 지적한 **"실제보다 넓은 보증"을 그대로 재생산**했다.

**(c)** `ImageError` 승격의 목적이 달성되지 않았다 — 두 호출부(`CustomerRequest.tsx:49`, `Work.tsx:127`)가
여전히 `err instanceof Error`다. 같은 라운드가 `MyAccount.tsx`에서는 이 패턴을 "진짜 버그 메시지까지
노출된다"며 조였는데, **타입을 새로 만들어 준 그 두 화면은 그대로 뒀다.**

## 그 밖에 기록만 (28-68 범위 밖 — 조용히 빼지 않는다)

  **무의미한 간접층**이다(같은 저장소 `localPort.ts`는 `./platform`에서 직접 import한다). 삭제 대상.

- README 체크리스트의 `_원바이원_감사대기_상태.json`을 **어떤 게이트도 검사하지 않는다.**
