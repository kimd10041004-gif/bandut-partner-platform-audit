# 28-3 감사결과 (GPT 역할 — Claude 세션 대리 수행)

감사 범위: `28-3` 전체. 사전 확인: `tsc --noEmit` 0 오류, vitest 72/72, node --test 7/7. 28-2 감사 6건은 전부 수정 확인됨. PlatformService 통합 계층의 설계는 타당하며 실패 시 부작용 미발생(전이 실패 → job 미생성) 보장도 테스트로 증명됨.

이번 감사는 결함 수리를 넘어 **제품을 완성 상태로 끌어올리기 위한 필수 격차**를 우선순위로 다룬다 (사용자 지시: "발전하고 끝까지").

---

## 상 (High — 제품 성립 요건)

### 28-3-01 · 모든 데이터가 새로고침 한 번에 소멸함 (영속화 부재)
`PlatformService`와 일정 슬롯이 전부 메모리에만 존재한다. 브라우저 새로고침 시 요청·견적·완료·정산 이력이 전부 초기 시드로 되돌아간다. 실사용이 불가능한 수준의 격차.
→ 요구: 저장 계층 도입. 테스트 가능성을 위해 `Storage` 인터페이스 주입식으로 설계하고(직렬화/복원 round-trip, 손상된 데이터 폴백을 서비스 레벨 테스트로 증명), UI에서는 localStorage에 연결. try/catch 필수 (프라이빗 모드 등 접근 불가 환경).

### 28-3-02 · 일정 탭이 플랫폼과 여전히 단절됨
28-2-03에서 견적·정산은 연결했지만 일정 탭은 아직 컴포넌트 로컬 상태다: 요청 번호를 자유 입력하고(존재하지 않는 REQ 허용), 슬롯을 만들어도 요청 상태(`accepted → scheduled`) 전이와 무관하며, 새로고침 시 소멸(28-3-01과 중첩).
→ 요구: `scheduleVisit(requestId, slot)`을 PlatformService로 이동 — accepted 상태의 실제 요청만 예약 가능, 슬롯 충돌 검사 후 `scheduled` 전이까지 원자적으로 수행. 요청 탭의 'scheduled' 직접 전이는 차단(일정 경로 강제 — estimated와 동일한 패턴).

## 중 (Medium)

### 28-3-03 · 정산 집계가 정산 확정 여부를 구분하지 않음
`settlements()`가 completed와 settled 작업을 구분 없이 합산한다. 파트너 입장에서 "이번 주 지급 예정(미정산)"과 "이미 정산된 금액"은 완전히 다른 숫자다. `settle()`이 요청 상태만 바꾸고 `CompletedJob`에는 아무 표시도 남기지 않는 것이 원인.
→ 요구: job에 정산 여부를 기록하고, 집계에 미정산/정산 구분(또는 최소한 미정산 합계)을 제공.

### 28-3-04 · EstimateForm의 요청 선택이 최초 렌더 시점에 고정됨
`useState(candidates[0]?.id ?? '')`는 마운트 시 한 번만 평가된다. 다른 탭에서 요청 상태가 바뀌어 후보 목록이 달라져도 선택값이 이미 목록에 없는 요청을 가리킬 수 있다 (제출 시 PlatformError로 막히긴 하나 UX 결함). 후보 목록과 선택값의 동기화 필요.

### 28-3-05 · 파트너가 신규 요청을 등록할 방법이 없음
시드 3건 외에 요청을 추가할 UI가 없다. `RequestStore.add`는 검증까지 갖춰져 있는데 노출되지 않았다. 요청 등록 폼(고객명/지역/카테고리/설명/희망일)을 추가할 것.

## 하 (Low)

### 28-3-06 · 취소된 요청의 견적이 남아 카드에 계속 표시됨
estimated 상태에서 cancelled로 전이해도 저장된 견적이 남아 요청 카드에 견적액이 표시된다. 이력 보존 목적이면 문서로 명시하고, 아니면 취소 시 표시를 구분할 것 (결정 자체는 수정 라운드에 위임).
