# 28-76 수정 사항 — 「보관함은 그 자리의 사람 것이다」

**사용자 결정: 감사 4건 + 보관함을 역할 무관 자리로.**

28-75는 28-74-01에 "보관이 저장을 막는 일이 **구조적으로** 사라진다"고 적었다. 이번 감사(`28-75/감사결과.md`)가
짚은 것은 그 문장이 성립하려면 두 가지가 더 필요하다는 것이다 — 예산이 **받아들일 본문**까지 세어야 하고,
이미 쓰여 있는 초과분을 **누군가 줄여야** 한다. 둘 다 없었다. 그리고 세 라운드에 걸쳐 미뤄 온 것,
**보관함을 꺼낼 수 있는 사람이 관리자뿐**이라는 것도 이번에 닫는다.

---

## 28-75-01 (상) 예산이 "이번에 받아들일 원격 본문"을 센다

예산을 재는 시점은 `accept` **직전**이라, 그때의 로컬 크기로 재면 곧 로컬이 될 원격 본문을 놓친다.
원격이 더 크면 보관 뒤 합계가 한도를 넘고 그 기기의 저장이 다시 막힌다.

복제기는 그 크기를 이미 쥐고 있으므로 함께 넘긴다 — 도메인은 여전히 저장소를 모른다(숫자 하나다):

```ts
// replicator.ts
stash?: (body: string, at: string, incomingChars: number) => boolean
...
stashed = this.stash?.(mine, at, remote.body.length) === true

// bootstrap.ts — 보관 직후의 로컬은 원격 본문이다. 둘 중 큰 쪽으로 잰다.
export function stashBudget(platform: PlatformService, incomingChars = 0): number {
  const u = platform.storageUsage()
  const after = Math.max(u.chars, Math.max(0, incomingChars))
  return Math.max(0, Math.min(OVERWRITTEN_BUDGET, u.limit - after))
}
```

## 28-75-02 (상) 부팅 때 한 번 보관함을 예산에 맞춘다 — 이미 막힌 기기를 실제로 푸는 조치

28-74는 프로덕션에 나갔고, 그때 고정 예산으로 쓰인 보관함이 실제 기기에 남아 있다. `stashOverwritten`은
예산에 안 들어가면 **아무것도 쓰지 않고** 돌아가므로, 이미 쓰인 초과분은 다음 conflict에서 새 본문이 들어갈
때만 줄어든다 — 그런데 저장이 막힌 기기가 바로 그 조건이 안 맞는 기기다.

```ts
export function trimOverwritten(storage, budget): number   // 지운 개수를 돌려준다
// initPlatform() 끝:
trimOverwritten(storage, stashBudget(service))
```

하나도 안 들어가면 **비운다**(키를 지운다 — 용량이 실제로 돌아온다). 근거: 보관함은 "잃지 않기"를 위한
것인데, 저장이 막히면 그때부터는 보관함이 **잃게 만든다**. 꺼낼 수 없는 1MB보다 쓸 수 있는 1MB가 낫다.

## 28-75-03 (중) 신뢰 IP 스윕에 시간 게이트

28-74-02는 `login()`마다 **모든 계정 × 모든 IP**를 훑었다. 계정 1만이면 로그인 시도 한 번에 5만 번의
Map 연산이고, 무차별 대입은 정확히 그 시도를 많이 만든다 — 막으려는 공격이 CPU를 계정 수만큼 증폭해 먹는다.
28-72 리뷰가 같은 모양(중복 prune)을 지적했고 28-73이 없앴다. 같은 잣대를 적용한다.

```ts
export const TRUSTED_IP_SWEEP_MS = 60 * 60 * 1000
private pruneTrustedIps(now: number): void {
  if (now - this.trustedSweptAt < TRUSTED_IP_SWEEP_MS && this.trustedSweptAt <= now) return
  this.trustedSweptAt = now
  ...
}
```

게이트 시각은 **스냅샷에 남긴다**(`trustedSweptAt`). 서버 모드는 요청마다 `AuthService`를 새로 만들어서,
메모리에만 두면 게이트가 없는 것과 같다. 늦게 지워지는 동안에도 `isTrustedIp`가 TTL을 직접 보므로
**면제가 새지 않는다** — 그 사실을 회귀로 고정했다.

## 28-75-04 (중) 보관함을 역할 무관 자리로 + 주석·문구·개행

**(a) 부품으로 뺐다.** `src/ui/OverwrittenBox.tsx` — 관리자 설정·파트너 마이페이지·고객
마이페이지가 **같은 것**을 쓴다. 보관은 모든 기기에서 일어나는데(conflict는 파트너 기기에서도 난다)
꺼내는 화면은 관리자뿐이었다. 보관함은 그 브라우저의 것이라 서버로 올라가지 않으므로 관리자가 남의 기기
것을 꺼내 줄 수도 없다 — **그 자리의 사람만 꺼낼 수 있다.** 안내 문구도 그렇게 바꿨다.

**(b) 보관 기능이 없으면 보관 이야기를 꺼내지 않는다.** `stash`를 넘기지 않은 앱(저장소 없음)에
"보관하지 못했습니다"라고 말하면 사용자는 **없는 것**을 찾으러 나선다. 이제 그 경우엔 덮였다는 사실만 말한다.

**(c) `purgeAccount`의 docstring이 제자리로.** 28-75가 새 private 메서드를 기존 설명과 그 함수 **사이**에
끼워 넣어, `forgetAccountKeys`가 "기록 파기 — 관리자, 탈퇴 계정만"이라는 틀린 설명을 이고 있었고
`purgeAccount`는 설명을 잃었다. 이 저장소의 규율이 "주석이 사실을 말한다"이므로 형식이 아니라 내용 문제다.

**(d) `_원바이원_감사대기_상태.json`의 끝 개행 복구.** GPT 감사자가 읽는 파일이라 형태가 조용히 바뀌면 안 된다.

## CI가 잡아낸 것 — 단언 앞의 고정 sleep 여섯 곳

첫 판의 `server` 잡이 **내 변경과 무관한 기존 단계**에서 넘어졌다(`A: 사업자 정보 조회 실패`).
원인은 flake가 아니라 그 단언 앞의 `sleep(300)`이다 — 서버 응답이 300ms 안에 오지 않으면 아직 없는 문구를 읽는다.
28-74가 **바로 앞 단계**를 `waitForText`로 고치면서 이웃을 남긴 자리이고, 같은 모양이 파일에 여섯 곳 있었다.

하나만 고치면 다음 라운드가 또 다른 자리에서 넘어지므로 여섯 곳을 전부 결정적 대기로 바꿨다 —
문구는 `waitForText`, 조건(행 수·DB 행·배너 사라짐)은 새 `waitFor` 헬퍼. 남은 `sleep(1500)` 하나는
단언용이 아니라 설정용 지연이라 그대로 뒀다(주석이 이유를 적고 있다). 자세한 것은 `28-76/검증결과.md` §5-1.
