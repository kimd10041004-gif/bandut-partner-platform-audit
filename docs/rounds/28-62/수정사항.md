# 28-62 수정사항 — 가명본 안전장치·열람권 대칭 (28-61 감사 4건 반영)

원본 `28-61`은 건드리지 않고 스크래치 복사본에서 작업한 뒤 `28-62`로 물질화했다 (해시 기준선 v59 검증 통과).

## 28-61-01 (상) 가명본을 복원할 수 있던 문제
- `PlatformSnapshot.pseudonymous`를 타입·`parseSnapshot` 검증에 정식 편입(불리언만).
- `restoreBackup`이 **상태를 건드리기 전에** 가명본을 거부한다 — `PlatformService.isPseudonymousBackup(json)`.
  거부는 예외로 중단이며 부분 적용이 아니다.
- 관리자 카드도 같은 함수로 미리 걸러, 가명본이면 **직전 상태 백업조차 만들지 않고** `[data-backup-error]`로 알린다.
- 가명본 모드 안내에 "복원에는 쓸 수 없습니다"를 명시했다.

## 28-61-02 (상) 가명 처리가 열거 방식이라 이름이 계속 새던 문제
- **허용 목록 방식으로 뒤집었다.** `PSEUDONYMOUS_REQUEST_KEYS`·`REVIEW`·`CLAIM`·`NOTIFICATION`·`AUDIT`·`JOB`·`PAYOUT`
  상수가 내보낼 필드를 고르고 나머지는 버린다. 자유 서술 필드는 목록에 없다.
- 이번에 막은 경로: **감사 로그 상세·행위자**(회원 이름이 들어 있었다), **클레임 처리 내용**(`resolution`),
  **파트너 프로필**(상호 → `파트너 A`, 소개 제거), **`customerId`**(가명 키로 치환, 계정 저장소와의 재식별 차단).
- **자체 검사 `assertNoRealNames`**: 가명본 생성 직후 스냅샷에 실제로 있는 사람·업체 이름이 결과에 남아 있으면
  `PlatformError`로 내보내기를 실패시킨다. 두 글자 미만은 오탐이라 제외.
- **이 검사가 다섯 번째 경로를 실제로 잡았다** — `CompletedJob.payout.account`(지급 계좌 표기)에 예금주 업체명이
  들어 있었다. e2e에서 내보내기가 실패하며 드러났고, `PSEUDONYMOUS_JOB_KEYS`/`PAYOUT_KEYS`로 막았다.
- 구조 식별자(`requestId`·`partnerId`)와 운영 지표(상태·일정·금액·`specialties`)는 유지해 분석에 쓸 수 있다.

## 28-61-03 (중) 열람권이 고객에게만 있던 문제
- `exportPartnerData(partnerId)` — 내가 입찰했거나 낙찰받은 요청 범위만(`bidsOf`로 판정).
  일감 요약·내 견적·방문·완료 작업·리뷰·A/S 답변. **고객 이름·요청 내용은 담지 않는다.**
- 파트너 마이 탭 `PartnerDataCard`(`[data-export-partnerdata]`, `my-partner-data-*.json`) — 고객 카드와 같은 모양.
- 두 경로 모두 `내 데이터 내보내기`로 기록된다(주체 시스템).
