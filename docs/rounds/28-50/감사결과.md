# 28-50 감사결과 (GPT 역할 — Claude 세션 대리 수행)

감사 범위: `28-50` 전체 — 저장 용량·완료 사진 반영 후, **낙찰 이후 파트너 쪽 이탈 경로** 점검.
사전 확인: `npm run check` exit 0 (vitest 210/210), e2e 112/112 PASS, visual-check 전 항목 PASS, `npm audit` 0건, 프로덕션 배포 그린(PR #130 머지). 28-49 감사 4건 전부 수정 확인됨.

핵심 지적: 취소는 지금 **고객만** 할 수 있다(28-46). 파트너가 낙찰 후 사정이 생기면(일정 충돌·자재 수급·사고) 할 수 있는 일이 없다 — 상태 전이표에 `accepted/scheduled → (파트너 사유) 재오픈`이 없고, 결국 채팅으로 고객에게 "취소해 달라"고 부탁해 고객이 취소 버튼을 누르게 되는데, 그러면 **파트너 귀책이 고객 취소로 기록**되고 파트너 신뢰 지표에는 아무 흔적이 남지 않는다. 시안 3의 업체 상세는 "취소율"을 전제로 한다. 또 이 경우 고객은 요청을 처음부터 다시 올려야 한다(사진·답변 유실).

## 상 (High)

### 28-50-01 · 파트너 낙찰 철회 + 재오픈 도메인
→ 요구: `PartnerCancel { id, requestId, partnerId, reason, date }`(스냅샷 `partnerCancels`). `withdrawAward(requestId, partnerId, reason, today)`: 낙찰 파트너만, `accepted`/`scheduled`에서만(시공 시작 후 불가), 사유 필수. 효과 — 그 파트너 입찰 제거, 방문 슬롯 해제, `acceptedPartnerId` 해제, 체크리스트 초기화, 상태를 다른 입찰이 남아 있으면 `estimated` 아니면 `requested`로 **재오픈**(전이표 밖의 관리 전이이므로 스토어에 `reopen` 전용 메서드), 입찰 마감을 오늘 기준 기본값으로 재설정(알림 플래그 초기화), 예약금이 결제돼 있으면 **전액 환불 대기** 생성(고객 취소와 같은 Refund 경로, 사유에 "파트너 철회"), 고객·관리자·다른 입찰자 알림. 재낙찰 후 예약금 재결제가 가능해야 한다(환불된 예약금은 결제 이력에서 제외). `partnerCancels(partnerId?)`, `partnerCancelCount(partnerId, sinceDays=90, today)`. **도메인 테스트 필수**(권한·상태·환불·재입찰·스냅샷 왕복).

### 28-50-02 · 신뢰 지표 + 운영 큐
→ 요구: `partnerSummary`에 `cancelCount`(최근 90일) 추가 → 고객 `PartnerCard`에 "낙찰 후 취소 n회 (90일)" 경고 태그(`[data-cancel-count]`, 0이면 표시 없음). 관리자 회원 탭 파트너 행에 철회 횟수. `opsQueue.frequentCancellers`(90일 내 2회 이상, 파트너·횟수·최근 일자) + 현황 조치 필요 카드 그룹(`data-ops="cancels"`, 회원 탭 정지 검토 안내).

## 중 (Medium)

### 28-50-03 · 파트너·고객 화면
→ 요구: 파트너 내 작업 카드(`accepted`/`scheduled`)에 "낙찰 철회" 위험 버튼 → 사유 입력(`aria-label="철회 사유"`) + "철회 확정" 2단계. 철회 후 그 일감은 일감 탭에 다시 입찰 가능으로 노출. 고객 거래 상세: 철회 이력이 있고 낙찰 전 상태면 재오픈 배너(`[data-reopen-banner]`: "파트너 사정으로 낙찰이 철회돼 다시 입찰을 받고 있어요 — 마감 …"), 예약금 환불은 기존 환불 카드로 표시.

### 28-50-04 · e2e + 실측
→ 요구: e2e — 낙찰 건에서 파트너 철회(사유) → 고객 거래 상세 재오픈 배너 → 파트너 일감 탭에 다시 입찰 가능(입찰 0건) → 재입찰 후 고객 견적함 파트너 카드에 "취소 1회". 환불·운영 큐 규칙은 vitest. 실측: 철회 UI·재오픈 배너·파트너 카드 경고.
