# 28-60 수정사항 — 감사 로그 신뢰성·복원 안전망 (28-59 감사 4건 반영)

원본 `28-59`는 건드리지 않고 스크래치 복사본에서 작업한 뒤 `28-60`으로 물질화했다 (해시 기준선 v57 검증 통과).

## 28-59-01 (상) 데이터 반출이 기록되지 않던 문제
- `platform.exportBackup(): { json, chars }` — 반출을 `백업 내보내기`(대상 `rev N`, 상세 `요청 n건 · kKB`)로 기록하고 JSON을 돌려준다. 기록의 `rev`는 저장 전 리비전이라 **내려준 파일의 rev와 일치**한다.
- 관리자 백업 카드가 `exportData()` 직접 호출 대신 이 메서드를 쓴다. 내려받은 파일이 평문이라는 경고를 화면에 명시했다.

## 28-59-02 (상) 감사 로그가 로그인 실패에 밀려나던 문제
- `AuditEntry`에 `count?`(2 이상)·`firstAt?` 추가 + 스냅샷 검증. `record()`가 `AUDIT_COLLAPSE_MS = 5분` 창 안의 같은 주체·행위·대상 반복을 마지막 줄에 접는다 — `at`은 마지막 발생, `firstAt`은 첫 발생, `count`는 횟수. 정보 손실 없이 줄 수만 줄인다.
- `pruneAuditLog()`가 상한 초과 시 **시스템 기록을 오래된 것부터 먼저** 버리고, 그래도 넘칠 때만 관리자 행위 기록을 버린다. 양이 아니라 가치 순으로 버린다.
- 화면은 `행위 ×n`(`[data-audit-count]`)과 `첫시각 ~ 시각`으로, CSV는 `첫 시각`·`횟수` 열로 보인다(기존 헤더 접두사는 그대로라 기존 단언과 호환).

## 28-59-03 (중) 복원을 되돌릴 수 없던 문제
- 복원 직전 상태를 `banded-before-restore-YYYY-MM-DD.json`으로 **자동 내려받는다**.
- `restoreBackup`이 직전 스냅샷을 메모리에 잡아두고(`canUndoRestore`), `undoRestore()`가 직전 상태로 되돌린 뒤 `복원 되돌리기`를 기록한다. 되돌리기 지점은 한 번 쓰면 사라진다(연쇄 되돌리기 없음). 메모리에만 두어 저장 용량을 늘리지 않는다.
- **e2e에서 발견한 실제 UI 결함도 함께 고쳤다**: 복원·되돌리기는 설정을 통째로 바꾸는데 `AdminSettings`의 폼 상태는 마운트 때 값을 그대로 들고 있어 복원 후에도 옛 값(보증 일수 등)이 남았다. `BackupCard`에 `onRestored` 콜백을 두어 저장된 설정으로 폼을 다시 채운다.
