# 29-29 — 도메인 공개 전 손볼 것 여섯 (29-28 실사용·보안 점검)

## 1. 왜 이 라운드인가

사장님 지시: **"병합 전 실사용자 입장 정밀 체크 및 보안 체크"**, 그리고 **"손볼 거 먼저 보고 하자."** 29-28 을 병합하기 전에
프리뷰 배포 검사(브라우저 24 + 가입 왕복 16), 로컬 실사용 걷기(고객·파트너·관리자 39화면 × 폰·PC), 코드 보안 감사(15건)를
했다. 실사용자가 바로 마주치는 것 셋과 도메인 공개 전에 막아야 할 것 다섯이 나왔고, 그중 뿌리가 같은 것을 묶어 여섯으로 고친다.

## 3. 세션 쿠키 — 설계

```
로그인 → 서버: Set-Cookie: bandut_session=<토큰>; Path=/; HttpOnly; SameSite=Lax; Max-Age=<만료까지>; Secure(Vercel)
요청   → 브라우저가 쿠키를 싣는다 (fetch·<img>·EventSource 모두)
서버   → tokenOf(headers, method): Bearer 있으면 Bearer, 없으면 쿠키 —
         단 쓰기(POST)는 Origin == Host 이거나 Sec-Fetch-Site: same-origin 일 때만 쿠키를 믿는다 (CSRF)
로그아웃 → 세션 폐기 + Max-Age=0 쿠키
```

- **Bearer 는 그대로 받는다.** 옛 SPA(서버 모드, `e2e:server`)·테스트·봇이 쓴다. 두 길이 같은 세션 표를 본다.
- **브라우저 쪽**(`lib/session.ts`)은 토큰을 저장하지 않는다. 29-6~29-28 사이에 저장된 옛 토큰은 발견 즉시 지운다 — 그 토큰은
  서버에서 여전히 유효하므로 남겨 두면 노출면이 그대로다.
- **대가:** 배포 직후 로그인돼 있던 사람은 한 번 다시 로그인한다(옛 토큰은 지워지고 쿠키는 아직 없다). `Secure` 는 `VERCEL_ENV`
  가 있을 때만 — 로컬·CI 는 http 라 붙이면 브라우저가 쿠키를 버린다.
- 서버 컴포넌트가 쿠키를 읽어 서버 렌더에 로그인 상태를 반영하는 것은 **이 라운드가 아니다** — 화면은 여전히 브라우저에서
  `/api/me` 를 한 번 더 묻는다(29-6 의 방식 그대로).

## 4. scrypt — 설계

도메인(`server/domain/hash.ts`)은 브라우저에도 번들되므로 `node:crypto` 를 직접 못 쓴다. 그래서 **끼워 넣는 구조**로 갔다:
`installPasswordHasher()` 로 구현을 주면 `hashPassword` 는 그 형식으로 저장하고, `verifyPassword` 는 저장 형식의 접두사로
구현을 고른다(`scrypt$` → scrypt, `s256$` → 옛 구현). 서버 핸들러 모듈이 로드될 때 scrypt 를 끼운다. 로그인에 성공하면 —
비밀번호를 아는 유일한 순간 — `needsRehash` 인 해시를 새 형식으로 다시 저장한다. 사장님도 파트너도 아무것도 안 해도 된다.

## 5. 솔직하게 — 사진·실시간 상담은 반만 고쳐졌다

29-28 보고에서 "쿠키로 바꾸면 사진·실시간 상담이 함께 풀린다" 고 했다. 쿠키로 바꾸자 401 은 사라졌지만 그 자리에서 **503** 이 나왔다 —
Next 어댑터(`server/marketplaceApi.ts` `needsBucket`)가 사진 올리기·내려주기와 SSE 를 29-5 부터 "저장소가 생기면 잇는다" 며 막아 둔 것이다.
즉 벽이 둘이었고 이 라운드는 첫 벽만 허물었다. 두 번째 벽은 저장소 포트(`server/storage.ts`, 서류가 이미 쓰는 것)로 사진을 올리고
내려주는 라우트와 SSE 라우트를 실제로 만드는 일이라 라운드 하나 크기다 — **29-30** 으로 잡는다. 그 전까지 운영 화면은 지금과 같다
(사진 자리는 비고, 상담은 10초 폴링). 사장님이 보시던 것과 달라지는 것은 없고, 나빠지는 것도 없다.
