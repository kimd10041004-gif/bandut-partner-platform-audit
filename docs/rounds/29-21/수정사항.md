# 29-21 — 가입 코드를 없앤다

## 1. 왜 없애나

가입 코드는 28-70-01에서 들어왔다. 그때의 전제는 하나였다 — **가입이 곧 마켓플레이스 전체
스냅샷의 읽기·쓰기 권한**이었다. 아무나 가입하면 아무나 남의 주문을 읽었으므로, 코드를 아는
사람만 들어오게 막을 이유가 있었다.

29-1이 v17 마켓플레이스를 Postgres로 옮기면서 그 전제가 사라졌다. 지금은 권한이 역할로 갈린다.

```ts
// lib/service.ts
async function approved(u:User){ role(u,'PARTNER');
  const p=await stmt('SELECT * FROM partners WHERE user_id=?',u.id).first<Partner>();
  if(p?.status!=='APPROVED')fail(403,'관리자 승인 후 견적을 제출할 수 있습니다.'); return p; }
```

승인되지 않은 파트너는 견적을 낼 수 없고(`approved()`), 남의 주문은 주소·연락처가 지워진 채로만
보인다(`view()`). 가입은 더 이상 전체 권한이 아니다.

남은 자물쇠는 **운영자 승인**이고 그것은 서버가 건다. 가입 코드는 이미 잠긴 문에 덧댄 두 번째
자물쇠이면서, 값이 어긋나면 아무도 못 들어오는 고장점이었다 — 29-20-3에서 실제로 그렇게 막혔다.

## 2. 없애도 운영이 열리지 않는다

이것을 먼저 확인했다. 운영의 가입을 막는 것은 가입 코드가 아니다.

```ts
// server/authSafety.ts
export function devOtpAllowed(env) {
  if (isProduction(env)) return false        // 운영은 첫 줄에서 끝난다
  ...
}
export function otpDeliverable(env) { return devOtpAllowed(env) || smsConfigured(env) }
```

운영에서는 개발용 인증번호가 첫 줄에서 거부되고, 문자 발송사도 없어 `smsConfigured`가 false다.
그래서 운영의 가입 요청은 503으로 끝난다 — **가입 코드가 있든 없든 같다.**

느슨해지는 곳은 프리뷰 하나다. 프리뷰는 `AUTH_DEV_OTP=on`이라 인증번호가 화면에 뜬다. 그 DB가
운영과 갈라져 있다는 것은 29-17에서 확인했다.

## 3. 열여섯 곳을 게이트가 센다

한 곳이라도 남으면 가입이 조용히 막힌다. 29-20-3이 정확히 그 모양이었다. 손으로 세는 대신
게이트가 세게 했다(29-17-3 `lib/adminRoutes.test.ts`와 같은 방식).

```
+ [
+   "server/handlers/adminGrade.test.ts",
+   "server/handlers/auth.test.ts",
+   "server/handlers/auth.ts",
+   ... (16개)
+ ]
```

이 목록을 빈 배열로 만드는 것이 이번 라운드의 작업 목록이었다. **그리고 그 열여섯이 전부가
아니었다** — 스캔이 `SIGNUP_CODE`·`signupCode`만 찾는데, 화면 쪽은 `data-signup-code`와 한국어
문구("가입 코드를 받으신 분만…")로 남아 있었다. 그 열 곳을 따로 훑어 지웠다.

## 4. 가입 코드가 하던 다른 일 하나를 대신 세운다

`verifyOtp`도 가입 코드를 물었는데 이유가 달랐다(28-71-03b) — 남의 번호로 인증번호를 5번 틀려서
**대기 중인 가입을 지워 버리는** 것을 막기 위해서였다.

```ts
if (rec.attempts >= OTP_MAX_ATTEMPTS) {
  this.otps.delete(key)                                   // ← 남이 내 가입을 끝낸다
  throw new AuthError(`인증 시도 ${OTP_MAX_ATTEMPTS}회를 초과했습니다 — 다시 가입해 주세요`)
}
```

코드를 없애면 그 문이 다시 열린다. 그래서 **지우는 대신 쉬게** 했다.

```ts
export const OTP_LOCK_MS = 60 * 1000
...
if (rec.attempts >= OTP_MAX_ATTEMPTS) {
  rec.lockedUntil = now + OTP_LOCK_MS                     // 지우지 않는다
  throw new AuthError(`인증 시도 ${OTP_MAX_ATTEMPTS}회를 초과했습니다 — 잠시 뒤 다시 시도해 주세요`)
}
```

무차별 대입은 여전히 창당 5회로 막힌다. 인증번호 자체의 5분 만료도 그대로다. 달라지는 것은
하나다 — 정당한 사용자가 **가입을 처음부터 다시 하지 않는다.**

## 5. 검사도 함께 바꿨다

거절돼야 할 길을 재던 검사들이 가입 코드에 기대고 있었다. 없앤 뒤에도 "막혀야 할 것이 막힌다"를
재도록 옮겼다.

| 검사 | 전 | 후 |
|---|---|---|
| `e2e:signup` 1번 | 가입 코드가 틀리면 거절한다 | 가입 화면에 가입 코드 칸이 없다 |
| `e2e:live-ui` | 틀린 가입 코드는 거절한다 | 필수 동의 없이는 가입이 넘어가지 않는다 |
| `e2e:next` | 가입 코드 칸이 있다 | 가입 코드 칸이 없다 |
| `deploy-check` HTML | 칸이 없으면 실패 | 칸이 **있으면** 실패 |
| 계약 테스트 | 코드 없이는 400 | 코드 없이도 200 |

`deploy-check`의 환경변수 분류도 "세 값"에서 "두 값"으로 줄였다. 핸들러의 가드가 셋에서 둘이
됐으므로 보고 문구가 코드와 어긋나지 않게 맞췄다.

## 6. 하지 않은 것

- **문자 발송.** 고객의 휴대폰 인증은 아직 인증이 아니다. 발송사 값 셋(`SMS_*`)이 필요하고
  그것은 사장님이 계정을 만드셔야 한다. 29-23.
- **사업자 서류 업로드.** 파일 저장소가 아직 없다 — `server/marketplaceApi.ts`의 사진 경로는
  전부 503이다. 저장소를 붙이는 것이 먼저다. 29-22.
- **인증 쪽 `approval`과 마켓플레이스 `partners.status`의 통합.** 승인 상태가 두 군데에 있다.
  살아 있는 화면은 후자를 쓰고 전자는 지워질 SPA만 쓴다 — 기록만 남기고 넘긴다.
