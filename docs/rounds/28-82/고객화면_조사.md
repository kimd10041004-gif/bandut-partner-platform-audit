# 고객에게 보이는 숫자 — 전수조사 (28-82)

28-79·80·81은 **랜딩 히어로** 한 자리에서 시연 시드를 걷어내는 데 세 라운드를 썼다. 그런데 28-81 감사가
바로 옆에서 같은 결함을 찾았다 — 고객이 견적을 비교해 업체를 고르는 화면의 업체 카드가 시드로 만든
"완료 3건 · 낙찰률 100%"를 그대로 보여주고 있었다. **한 자리씩 고치는 방식으로는 끝나지 않는다.**

그래서 이번에는 고객에게 보이는 화면을 **전부** 훑고, 결과를 테스트로 고정했다.

## 조사 방법

고객이 실제로 보는 파일 = `src/features/landing/**` + `src/features/customer/**` + **그 화면들이 가져다
쓰는 `src/ui/` 부품**(부품 안에서 부른 것도 화면에 그대로 나온다). 거기서 `platform.*` 호출을 모두 뽑았다.

```
$ grep -rn 'platform\.[a-zA-Z]*(' src/features/landing src/features/customer src/ui/PartnerCard.tsx src/ui/ChatBox.tsx
```

## 결과 — 39개 호출을 세 갈래로 나눴다

### (ㄱ) 요청 단위 — 시드가 섞일 수 없다 (조치 없음)

고객은 28-33부터 **자기 요청만** 본다(`customerId` 스코프). 아래는 전부 "이 요청 하나"에 대한 조회라,
시드 요청이 끼어들 자리가 없다.

`bidCount` · `bidClosed` · `bidsFor` · `getEstimate` · `extraWorksFor` · `claimsFor` · `paymentsFor` ·
`refundFor` · `reviewFor` · `requestTimeline` · `warrantyStatus` · `partnerCancels(파트너, 요청)` ·
`chatFor` · `markRead` · `sendMessage`, 그리고 쓰기 계열(`addRequest` · `acceptBid` · `payDeposit` ·
`payFinal` · `writeReview` · `fileClaim` · `updateRequest` · `rescheduleVisit` · `decideExtraWork` ·
`extendDeadline` · `transitionRequest` · `sweepPaymentReminders`).

### (ㄴ) 운영 설정 — 활동 지표가 아니다 (조치 없음)

`getSettings` · `enabledCategories` · `activePackages` · `questionsFor`.
관리자가 CMS로 정한 내용이고, 시드가 만든 "실적"이 아니다.

### (ㄴ-2) 파트너가 직접 쓴 내용 — 시드도 아니고 CMS도 아니다 (이번 라운드는 조치 없음)

`getProfile`. **28-83-04 정정**: 28-82는 이것을 (ㄴ)에 넣고 "관리자가 CMS로 정한 내용"이라고 적었는데
틀렸다. `getProfile`이 돌려주는 것은 파트너가 자기 마이페이지에서 `updateProfile`로 쓴 상호·전문 분야·
지역·소개이고, 없으면 `DEFAULT_PARTNER_PROFILE`(상호 "반듯 파트너")로 떨어진다. 관리자는 이 내용을
정하지 않는다.

조치가 없다는 **결론은 그대로**다(숫자가 아니라 신원이고, 시드 집계와는 다른 문제다). 다만 이유가
달라지므로 갈래를 나눠 둔다 — 「남은 경계」의 "시드 파트너의 프로필 문구"와 같은 사안이고, 파트너가 쓴
자유 서술이 고객에게 어떻게 보이는지는 아직 아무도 검토하지 않았다.

### (ㄷ) **여러 요청을 가로지르는 집계 — 여기가 새는 자리다** (조치함)

| 호출 | 어디서 | 무엇이 새나 | 조치 |
|---|---|---|---|
| `publicStats()` | `Landing` | — | 28-80·81에서 이미 닫힘 |
| `partnerSummary()` | `PartnerCard` → `CustomerHome`·**`CustomerEstimates`(견적함)** | 완료 건수 · 낙찰률 · 리뷰 수 · 평점 · 낙찰 후 취소 횟수 | → `publicPartnerSummary()` |
| `allReviews()` | `PartnerCard` 최근 리뷰 3건 | 시연 요청에 달린 리뷰 | → `publicReviews()` |

즉 **집계는 세 개뿐이고, 그중 둘이 새고 있었다.** 부팅 경로를 태워 확인한 값:

```
랜딩 공개 지표 — {"totalRequests":0,"completedOrSettled":0,"winRate":null,"average":null,"reviewCount":0}
업체 카드     — 완료: 3 건 / 낙찰률: 100 % / 리뷰: 0 건 / 평점: null
```

## 조사를 테스트로 고정했다

`src/ui/customerSurfaces.test.ts` — 고객이 보는 파일(디렉터리에서 유도 + `ui/` 부품까지 따라감)에서
**시드를 포함한 집계 API**(`adminOverview` · `bidStats` · `reviewStats` · `statusCounts` ·
`partnerSummary` · `allReviews` · `partnerCancelCount`)를 부르면 실패한다.

- 목록을 **하드코딩하지 않는다**: 대상 파일은 디렉터리를 훑어 만들고, 화면이 `import`한 `ui/` 부품을
  따라간다. 새 고객 화면·새 부품은 자동으로 검사 대상이 된다.
- **빈 목록을 훑고 통과하는 것**도 막는다(28-78-04의 교훈): 두 번째 테스트가 대상 목록에
  `Landing.tsx` · `CustomerEstimates.tsx` · `PartnerCard.tsx`가 실제로 들어 있는지 확인한다.

## 남은 경계 — 이 조사가 다루지 **않은** 것

- **파트너 자신의 화면·관리자 화면**은 그대로 둔다. 그 사람들은 기기에 실제로 무엇이 있는지 봐야 한다
  (28-80이 세운 구분과 같다).
- **시드 파트너의 프로필 문구**(상호·소개·지역)는 숫자가 아니라 신원이다. 시연 데이터 지우기로 함께
  사라지지 않으며(프로필은 요청에 딸리지 않는다), 그것이 맞는지는 별개의 판단이라 건드리지 않았다.
- **서버 모드에서 익명 방문자는 스냅샷을 못 받는다**는 사실을 이번 구현 중에 발견했다 —
  `28-82/수정사항.md`의 「하지 않은 것」에 적었다. 조사 범위 밖이지만 히어로 지표의 도달 가능성과
  직결되므로 남겨 둔다.
