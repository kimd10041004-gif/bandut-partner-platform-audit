## 28-69-01 (상) 읽기 경로가 첫 동기화 뒤에 죽는다 — 보기만 하는 기기는 남의 변경을 영원히 못 본다

`replicator.ts:235` `if (!this.needsRead && this.pushedLocalRev === localRev) { setStatus('synced'); return }`.
`needsRead`는 `:244`에서 false가 된 뒤 **실패 경로에서만**(`:308` fail, `:278` conflict+null, `:296` accept 실패)
다시 true가 된다. 성공 경로에는 true로 되돌리는 곳이 없다. 그래서 `PlatformContext.tsx:106`의 focus·visibility
`sync()`는 GET 한 번 없이 `'synced'`를 답한다.

```
1. 관리자 기기 B: 첫 sync → read → needsRead=false, pushedLocalRev=revision
2. 고객 기기 A: 요청 등록 → push → 원격 rev 2
3. B: 탭 복귀 → sync() → :235 조기 반환 → 'synced'. 원격을 보지 않았다
4. B는 새로고침(새 Replicator)하거나 **자기가 뭔가 써서 conflict를 맞을 때까지** A의 요청을 못 본다 —
   그리고 그때는 B의 변경이 덮인다(규칙 3)
```

독스트링 `:75` 규칙 3("원격 rev가 내가 마지막으로 본 값과 다르다 ⇒ 받아들인다")은 `:241 if (this.needsRead)`
안에서만 평가된다 — **쓰기 직전에만** 남의 변경을 본다. `28-68/서버_연결.md:56-60` "붙인 뒤 누가 이기는가"는 코드가
쓰기 경로에서만 적용하는 규칙을 일반 규칙처럼 적었다. 테스트 `replicator.test.ts:384` "변경이 없으면 focus sync는
직렬화하지 않는다"는 "직렬화 안 함"을 "읽지도 않음"으로 고정했다 — 28-68-02(a)가 없애라고 한 것은 **직렬화**였지
읽기가 아니다.

근본 수정: focus 경로는 **rev만 확인**한다(본문 4MB를 매번 받지 않는다). 포트에 `head()`(rev만), 복제기에
`sync({ checkRemote: true })`. rev가 `remoteRev`와 다르면 `needsRead = true` → 기존 read 경로.

## 28-69-02 (상) 같은 브라우저의 두 탭이 서버를 사이에 두고 서로 conflict를 만든다 — 헛 업로드, 거짓 배너, 그리고 진짜 변경 되돌림

복제기 인스턴스는 **탭마다** 하나(`PlatformContext.tsx:42`)이고 `remoteRev`·`pushedLocalRev`는 인스턴스 필드다.
그런데 로컬 진실(도메인 스냅샷·`revision`)은 **브라우저 하나에** 있고 `syncFromStorage()`가 탭 사이를 맞춘다
(`platform.ts:3323` rev 다르면 `applySnapshot` → `:2501 this.rev = snapshot.rev`). 두 상태의 범위가 다르다.

```
탭1 저장(rev 6) → push → 원격 rev 2. 탭1: remoteRev=2, pushedLocalRev=6
탭2 storage 이벤트 → syncFromStorage(rev 6) → replication.sync() (:106)
     → pushedLocalRev(5) ≠ 6 → write(body, expectedRev=1) → 409 {rev 2, 같은 본문}
     → acceptRemote → importSnapshot → save() (:2566 → rev 7, storage 이벤트) → 'conflict'
     → 배너 "이 기기에서 반영되지 않은 변경은 덮였습니다"  ← 거짓. 아무것도 덮이지 않았다
탭1 storage 이벤트(rev 7) → syncFromStorage → sync → pushedLocalRev(6) ≠ 7
     → write(같은 본문, expectedRev 2) → 원격 rev 3  ← 4MB까지의 헛 업로드
탭2 사용자가 진짜 변경(rev 8) → write(expectedRev 2 — 낡음) → 409 {rev 3, 옛 내용}
     → acceptRemote → **사용자의 변경이 되돌려진다**, 배너는 "다른 기기의 변경"이라 한다
```

같은 사람이 탭 둘을 열어 둔 것만으로 매 저장이 conflict·헛 업로드·되돌림이 된다. 28-68 감사가 "OK"로 둔
되쓰기 방지(`pushedLocalRev = revision()` after accept)는 **한 탭 안에서만** 성립한다.
근본 수정: 복제기 커서 `{ remoteRev, localRev }`를 도메인 키 옆(`banded-platform-v1:remote`)에 **저장**하고
매 `run()` 앞에 읽는다(`syncFromStorage`가 `:rev`를 읽는 것과 같은 모양). 그리고 conflict의 `remote.body`가
방금 보내려던 본문과 같으면 accept 없이 rev만 채택한다(안전망).

## 28-69-03 (중) `stop()`→`start()` 뒤의 offline은 되살아나지 않고, 테스트 (a-2)는 아무것도 확인하지 않는다

**(a)** `stop()`(`:134`)이 재시도 예약을 취소하고 `cancelRetry = null`. `start()`(`:143`)는 `stopped`만 되돌린다.
상태가 `'offline'`이었다면 `markChanged()`(`:194`)가 "예약된 재시도가 보낸다"(`:193`)며 아무것도 안 하는데
**그 예약은 없다.** focus 이벤트까지 영원히 offline. 28-68-02(b)의 굶김 수정이 기댄 불변식 "offline ⇒ 재시도가
예약돼 있다"를 `start()`가 깬다. 곁들여: stopped 중에 `fail()`이 닿으면 `setStatus`(`:148`)가 조기 반환해 상태가
`'syncing'`에 **얼어붙고** `lastProblem`은 그 실패를 영영 모른다.

**(b)** `replicator.test.ts:305-315` (a-2): 단언이 `≤ 1500`과 `≥ 0`뿐이다. 수정 전 값 0도, 어떤 구현도 통과한다.
`Date.now()`를 주입할 수 없어 `firstChangeAt + maxPushWaitMs - now`를 진행시킬 방법이 없다 — **공허한 테스트**를
"대기 상한 1건"으로 셌다(`28-69/수정사항.md:59`).

**(c)** `fakeScheduler.fire()`(`:63`)가 실제 5ms `setTimeout`으로 기다린다 — `latencyMs: 20`인 포트와 섞이면
sync가 끝나기 전에 단언한다(지금은 (d)만 latencyMs를 쓰고 fire를 안 써서 살아 있다).

## 28-69-04 (중) 검증 공백과 어긋난 문서 — "붙여도 안 깨진다"의 합성은 CI가 한 번도 돌리지 않았다

**(a)** 복제기 테스트는 전부 `MemoryRemotePort`, 계약 테스트는 포트 단독이다. **`Replicator × HttpSnapshotPort ×
Postgres`** 합성 — 409 본문의 `remote`를 복제기가 받아들이는 경로, 401을 `rejected`로 올리는 경로 — 는 CI 어디에도
없다. 이 라운드의 주장 자체가 그 합성에 관한 것이다.

**(b)** `rejected` 뒤 `needsRead = true`(`:308`)라 다음 변경마다 **전체 본문 GET**(최대 4MB) 뒤 PUT을 한다.
413이면 "너무 커서 거부된 본문"을 저장 묶음마다 다시 올린다 — 413은 원격이 바뀌었다는 뜻이 아니다.

**(c)** 같은 커밋 안의 모순: `api/snapshot.ts:19` *"사용자별 진짜 분리는 28-69의 일이다"*(28-69는 하지 않았고
그 뜻을 인증으로 정정했다), `db/schema.sql:11` *"28-69에서 사용자별 분리가 들어오면 이 열이 테넌트 경계가 된다"*
— `28-68/서버_연결.md:9` *"워크스페이스는 하나다"*와 반대다.

  충돌은 프로덕션 배선이 없어 잠재적이다(독스트링이 이미 적었다). 200KB 한글 왕복·413·`CONTRACT_REQUIRE_HTTP`
