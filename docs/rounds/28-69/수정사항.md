# 28-69 수정 사항 — 「서버를 붙여도 데이터가 안 깨지게」

**사용자 결정: 감사 4건만.** 서버 계정·세션(인증)은 28-70, 프로덕션 DB 연결은 그 뒤.

28-68이 놓은 서버 계층은 **지금 붙이면 데이터가 깨지는** 상태였다. 두 갈래 감사(복제기·서버)가 같은 근본
원인을 짚었다 — `rev`가 기기별 카운터라 두 기기의 rev가 같으면 conflict 없이 조용히 덮어썼다(01).
그리고 28-67-03의 "죽은 배선 살리기"가 새 결함 넷을 만들었고, 그 라운드의 테스트가 정확히 그 메커니즘을
꺼 놓았다(02). 이 라운드는 그 넷을 고쳐 **서버를 붙일 수 있는 상태**로 만든다. 붙이지는 않는다.

계획을 세우다 전제도 하나 정정했다: **스냅샷은 마켓플레이스 전체**라 "사용자별 워크스페이스"는 성립하지
않고, 가능한 것은 인증뿐이다(`28-68/감사결과.md`·`28-68/서버_연결.md`).

---

## 28-68-01 (상) rev를 저장소가 발급한다

**계약** (`src/domain/ports.ts`): `write(body, expectedRev)` — 본문만 주고 rev를 **돌려받는다**.
`SnapshotRecord.rev`는 "그 저장소에 몇 번째로 쓰였는가"라 기기와 무관하게 비교할 수 있다.

- `api/snapshot.ts`: `insert … values ($1, 1, $2)` / `update … set rev = rev + 1 … where rev = $3 returning rev`.
  클라이언트 rev를 **받지 않는다** — 옛 계약의 `rev` 필드가 오면 400(조용히 무시하지 않는다).
  되감기·불변식이 SQL 자체가 됐다.
- `LocalSnapshotPort`·`MemoryRemotePort`: `rev = (current?.rev ?? 0) + 1`. Local 어댑터의 `<key>:rev`가
  도메인의 `revision`과 **다른 숫자**라는 것을 독스트링에 적었다(프로덕션에서 같은 키에 붙지 않는다).
- `HttpSnapshotPort`: `{ body, expectedRev }`를 보낸다.

**복제기** (`src/domain/replicator.ts`) — 두 종류의 숫자를 섞지 않는다:

| 필드 | 뜻 |
|---|---|
| `remoteRev` | 마지막으로 본 **저장소** rev. 되돌리지 않는다 |
| `needsRead` | 첫 동기화·재접속·거부 뒤 — write 전에 read |
| `pushedLocalRev` | 마지막으로 밀어 올린(또는 받아들인) **도메인** revision |

조기 반환은 `pushedLocalRev === revision()`("로컬이 안 바뀌었다")로 — 28-68의
`knownRemoteRev === revision()`은 종류가 다른 두 숫자를 비교해 저장 경로에서 도달 불가였다.

누가 이기는가 — 규칙 하나: 원격이 비었으면 밀어 올린다 / 원격이 있고 이 기기가 한 번도 밀어 올린 적
없으면 받아들인다 / 그 뒤로는 "원격 rev가 내가 마지막으로 본 값과 다르면 남이 썼다 → 받아들인다".
read 경로와 conflict 경로가 **같은 규칙**을 쓴다(28-68은 둘이 달랐다). **마지막 반영 이후의 로컬 변경은
덮인다** — 통째 스냅샷은 병합할 수 없다. 숨기지 않고 `'conflict'`로 올려 화면이 알린다(04a).

회귀: 계약 테스트 "같은 기대값을 든 writer 둘 — 두 번째는 conflict", 복제기 테스트 "로컬 revision이 같은
두 기기 — 두 번째가 conflict 없이 덮지 않는다"(감사의 5단계 시나리오 그대로). 수정 전 출력은 검증결과.md.

## 28-68-02 (상) 타이머 둘, 끈적한 stop, 켜진 테스트

- **(a) 디바운스.** `pushTimer`(변경 뒤 1.5초 조용하면 push, 첫 변경으로부터 10초 안에는 반드시 한 번)와
  `retryTimer`(실패 뒤 지수 백오프)를 분리했다. 한 조작이 낸 여러 save가 **한 번의 직렬화**로 합쳐진다 —
  28-67 주석의 "합친다"가 처음으로 참이 됐다. 28-68은 저장마다 0ms 뒤 전체 스냅샷을 직렬화했다.
- **(b) 굶김.** `armRetry()`는 **이미 예약이 있으면 건드리지 않는다.** `markChanged()`는 offline이면
  아무것도 안 한다 — 예약된 재시도가 최신 상태를 보낸다.
- **(c) 스핀.** conflict + `remote === null`도 `failures += 1` — 백오프가 붙는다. `'pending'`은
  `armRetry`를 부르지 않는다.
- **(d) 끈적한 stop.** `stopped` 플래그. `setStatus`·`armRetry`·`armPush`가 stopped면 no-op.
  `start()`로 되돌리고 `PlatformContext`의 effect가 본문에서 `start()`, cleanup에서 `stop()`.
- **(e) 테스트.** `replicator.test.ts`의 헬퍼가 `scheduleRetry: null`로 끄던 것을 **가짜 스케줄러**
  (예약 목록 + `fire()`)로 바꿨다. `markChanged → 타이머 → 원격에 실제로 써진다`가 **프로덕션 트리거를
  태우는 첫 테스트**다. 회귀 5건(디바운스·굶김·스핀·stop·트리거) + 대기 상한 1건.

## 28-68-03 (중) 비재시도 오류, CI 서버의 본문

- **(a)** `ReadResult`·`WriteResult`에 `{ reason: 'rejected', status, detail }` 갈래. `httpPort.ts`:
  400·401·403·404·405·413·415·422 → `rejected`; 408·429·5xx·네트워크·파싱 실패 → `unavailable`.
  복제기는 `rejected`를 새 상태 `'rejected'`로 올리고 **재시도하지 않는다** — 다음 변경에서 한 번은
  다시 시도한다(토큰이 갱신됐을 수 있다). 28-68은 401·413을 "오프라인"으로 보이게 하고 30초마다
  영원히 다시 보냈다.
- **(b)** `scripts/api-server.mjs`: `Buffer.concat` 뒤 **일괄** 디코드. 28-68은 청크마다 `toString`해서
  한글이 64KB 경계에서 U+FFFD로 깨졌고 `JSON.parse`가 그것을 통과시켰다.
- **(c)** 같은 파일: **인증·파싱 전에** `MAX_BODY_BYTES`(≈12MB) 검사 → 넘으면 `req.destroy()` + 413.
  리스너 전체를 try로 감싸 어떤 요청도 프로세스를 죽이지 못한다.
- `MAX_BODY_CHARS`를 **4MB**로 내렸다 — Vercel Functions 본문 상한(4.5MB급)이 28-68의 8MB보다 작아
  프로덕션에서는 8MB 검사에 닿기도 전에 플랫폼이 413을 냈다. 인증된 GET에 `Cache-Control: no-store`.
- 계약 테스트에 "200KB 한글 본문 왕복"(세 구현 공통)과 API 규약 "인증 없이 상한 초과 → 413, 서버 생존".
  `MAX_BODY_CHARS`의 첫 테스트다.

## 28-68-04 (중) 배너·게이트·e2e·문서

- **(a) 배너.** `PlatformContext`에 `lastProblem` — `offline`·`rejected`는 여기 남고 **`synced`에서만**
  내려간다. 저장 한 번(`pending`)에 사라지지 않는다. `conflict`는 4초 안내로 올린다:
  *"다른 기기의 변경을 받아들였습니다 — 이 기기에서 반영되지 않은 변경은 덮였습니다"*. 28-68은
  복제기가 로컬을 통째로 갈아치우는 유일한 상태를 어디에도 표시하지 않았다.
- **(b) 게이트 자기참조.** `gates.yml` server job에 `CONTRACT_REQUIRE_HTTP: '1'`. 계약 테스트 최상위에서
  그 값이 있는데 URL이 없으면 **throw** — 파일 전체 실패. env 두 줄을 지우면 이제 빨갛다.
- **(c) e2e.** 예금주를 상호·고객명과 다른 실명(`김파트너`)으로. 파트너 열람권 JSON에 그 이름이 **없고**
  `accountMasked`가 `(김**)`로 있는지, 정산 CSV `계좌` 열이 마스킹본인지 단언. 28-67-01을 실사용 여정이
  처음으로 지킨다.
- **(d) 문서.** `types.ts` `account` 주석을 사실대로(관리자 원장·운영 기록 CSV에는 실명 포함으로 나간다).
  `28-67/서버_경계.md`·`수정사항.md` 머리에 정정 블록(본문은 역사로). `28-68/서버_연결.md`를 다시 썼다 —
  워크스페이스는 하나, 4단계는 28-70 전에는 수행 불가, `-pooler`, 4MB. README에 `api/`·`db/`·
  `api:dev`·`test:contract`·`server` job·서버 절. `bootstrap.ts` 독스트링, `package.json` description,
  계약 테스트 헤더 정정.
