대상: `3503565`(#235) + `3c4ae67`(#236) + `c3e585a`(#237).
28-85 감사 4건을 고치고, **정규식 텍스트 검사를 버리고 TypeScript 컴파일러 API로 간** 라운드다.

**방향은 옳다.** 세 라운드 연속으로 손으로 쓴 렉서가 뚫린 뒤 "파서를 직접 쓰지 말고 컴파일러에게
묻자"로 간 것은 이 저장소가 내린 판단 중 가장 잘한 축이다. 28-85가 뚫린 아포스트로피는 물론
28-83·84의 구조 분해·대괄호까지 **한 번에** 사라졌고, `guard-ok` 면제 장치를 고치는 대신 **없앨 수
있었던 것**(03)이 그 증거다. 02가 위험의 이름을 스스로 고쳐 적은 것도 좋다.

그런데 **네 라운드 연속으로 같은 두 가지가 되풀이됐다.**

- 가드에 **여전히 정적으로 뚫리는 구멍이 있고**(01), 문서는 "못 잡는 것은 런타임 이름뿐"이라고
  **한계를 실제보다 좁게** 적었다 — 28-85 감사 02가 지적한 바로 그 실패다.
- 새 방식이 실제로 작동하는지 확인하는 테스트가 **자기 이름이 말하는 것을 확인하지 않는다**(02).
  Copilot이 #229·#232·#235에서 세 번 지적한 그 패턴이, 이번에는 **그 패턴을 막으려고 쓴 테스트
  자체에서** 나왔다.

아래 넷은 전부 병합된 `main`(`c3e585a`)에서 실행해 확인했고, 명령과 출력을 그대로 인용한다.

## 01 (상) 타입 가드도 정적으로 뚫린다 — 그리고 문서가 한계를 좁게 적었다

`customerSurfaces.test.ts`의 문서 블록은 못 잡는 것을 이렇게 적어 뒀다:

> *못 잡는다* — 이름을 런타임에 만들어 부르는 것(`platform[key]`에서 `key`가 변수).
> 그런 접근은 타입도 `any`가 되기 쉬워 컴파일러도 모른다.

**틀렸다.** 이름이 소스에 그대로 적혀 있고 컴파일러가 타입을 온전히 아는데도 빠져나가는 형태가
최소 둘 있다. `PartnerCard.tsx`(고객이 업체를 고르는 자리)에 하나씩 심어 확인했다:

```tsx
// (가) 좁힌 타입으로 받는다 — 테스트 편의로 흔히 쓰는 모양
const narrow: Pick<PlatformService, 'partnerSummary'> = platform
void narrow.partnerSummary(partnerId)
```
```
=== pick ===
      Tests  8 passed (8)          ← 조용히 통과
```

```tsx
// (나) 나머지 스프레드
const { ...rest } = platform
void rest.partnerSummary(partnerId)
```
```
=== rest ===
      Tests  8 passed (8)          ← 조용히 통과
```

대조군으로 옵셔널 체이닝은 **잡힌다**:

```tsx
const maybe: PlatformService | undefined = platform
void maybe?.partnerSummary(partnerId)
```
```
=== optional ===
+   "src/ui/PartnerCard.tsx → partnerSummary (속성)",
      Tests  1 failed | 7 passed (8)
```

**원인은 `isPlatform`의 판정이다.** 수신자 타입의 심볼 이름이 정확히 `PlatformService`일 때만
참이다. `Pick<...>`은 매핑 타입이라 심볼 이름이 다르고, 스프레드 나머지는 익명 객체 타입이라
심볼이 아예 없다. 둘 다 **`partnerSummary`라는 같은 메서드를 같은 객체에서 부르는데** 가드는 못 본다.

**이것이 왜 심각한가.** 구멍이 하나 더 있다는 사실보다, **문서가 그 구멍을 없다고 적었다**는 것이
문제다. 이 저장소는 28-85 감사 02에서 정확히 같은 실패를 지적했다 — "적어 둔 한계가 실제보다
좁았다". 28-86은 그 지적을 받아 02에서 위험의 이름을 고쳤으면서, **01에서 같은 실수를 다시 했다.**
한계를 좁게 적은 문서는 없는 문서보다 나쁘다. 다음 사람이 "컴파일러가 보니까 괜찮다"고 믿는다.

정직하게 덧붙이면 (가)·(나) 둘 다 **일부러 써야 나오는 모양**이다. 28-85의 아포스트로피처럼
실수로 일어나지는 않는다. 그래서 **상**이지만 "지금 새는 중"은 아니다.

## 02 (상) 「세 가지 접근 방법을 모두 같은 것으로 본다」가 세 가지를 보지 않는다

새 방식이 실제로 작동하는지 확인하는 테스트다:

```ts
it('세 가지 접근 방법을 모두 같은 것으로 본다 (28-86-01)', () => {
  const admin = violationsIn('src/features/admin/AdminOverview.tsx')
  expect(admin.length, ...).toBeGreaterThan(0)
  expect(admin.every((v) => v.includes('(속성)') || v.includes('(대괄호)') || v.includes('(구조 분해)'))).toBe(true)
})
```

`AdminOverview.tsx`가 실제로 무엇을 내놓는지 찍어 봤다:

```
AdminOverview 위반 라벨 분포: ["adminOverview (속성)","statusCounts (속성)","bidStats (속성)"]
대괄호 포함? false / 구조 분해 포함? false
```

**셋 다 `(속성)`이다.** `every(속성 || 대괄호 || 구조 분해)`는 전부 `(속성)`이어도 참이므로,
이 단언은 대괄호·구조 분해 경로를 **한 번도 태우지 않는다.** 두 경로를 통째로 지워도 이 테스트는
초록이다. 이름은 "세 가지를 모두 같은 것으로 본다"인데 확인하는 것은 "속성 하나가 잡힌다"뿐이다.

수정사항 문서에는 네 형태를 심어 확인한 출력이 인용돼 있다 — **그때는 실제로 확인했다.**
문제는 그 확인이 **커밋에 남지 않았다**는 것이다. 손으로 심어 본 것은 다음 사람에게 남지 않는다.
회귀 테스트로 남겨야 회귀 테스트다.

**그리고 이것이 네 라운드 연속이다.** Copilot이 #229(컨텍스트 값)·#232(`guard-ok` 주석)·
#235(타임아웃 stub)에서 같은 것을 지적했고, 28-84-02는 **바로 그 문제를 고치려던 항목**이었다.
이번에는 그 패턴을 막으려고 새로 쓴 테스트 안에서 나왔다. 개별 수정으로는 안 잡힌다는 뜻이다 —
**"이 단언은 무엇을 지워도 실패하는가"를 테스트마다 적는 규율**이 필요하다.

## 03 (중) rev 캐시가 파싱은 줄였지만 커넥션은 그대로다 — 익명 요청이 로그인을 굶긴다

28-86-02는 인증 없는 경로의 위험을 **자원 소모**라고 옳게 이름 붙이고 rev 캐시를 넣었다.
그런데 `handlePublicStats`는 캐시 적중 여부와 무관하게 **매 요청 먼저 DB를 친다**:

```ts
const head = await db.query('select rev from snapshots where workspace_id = $1', [workspaceId])
const hit = memo.get(workspaceId)
if (hit !== undefined && hit.rev === rev) return { status: 200, body: { stats: hit.stats }, headers }
```

그리고 그 풀은 이렇다 (`server/db.ts`):

```ts
if (pool === null) pool = new Pool({ connectionString: databaseUrl, max: 3 })
```

**커넥션 3개짜리 풀 하나를 `/api/public-stats`(세션 없음)·`/api/snapshot`·`/api/auth`가 나눠 쓴다.**
레이트리밋이 없으므로 익명 요청을 쏟아부으면 3개가 전부 공개 지표 조회에 물리고, **로그인과
스냅샷 저장이 대기한다.** 즉 이 라운드가 줄인 것은 요청당 CPU·메모리이지 **병목 자체가 아니다.**

28-86의 문서는 "요청당 CPU·메모리"라고 적었는데, `max: 3`에서 실제로 먼저 마르는 자원은
**커넥션**이다. 위험의 이름을 한 번 고쳤지만 **아직 한 칸 덜 갔다.**

고칠 방법은 여럿이고 전부 이 저장소 크기에 맞는다: 캐시 적중 시 rev 조회도 건너뛰는 짧은 TTL
(예: 5초) · 공개 경로 전용 풀 분리 · 엣지 레이트리밋(계속 이월 중). **엣지 레이트리밋이 없어도
앞의 둘은 지금 할 수 있다** — "그다음"으로 미룰 이유가 없다.

## 04 (중) 프로그램에 없는 파일은 `조용히` 빈 배열이 된다

```ts
function violationsIn(file: string): string[] {
  const sf = p.getSourceFile(file)
  if (sf === undefined) return []          // ← 검사하지 않았는데 "위반 없음"과 구별되지 않는다
```

`tsconfig.json`의 `include`는 `["src", "vitest.config.ts", "vite.config.ts"]`다. 오늘은
고객 도달 파일이 전부 `src` 아래라 확인해 보니 모두 해석된다:

```
src/ui/PartnerCard.tsx → getSourceFile: ok
src/App.tsx → getSourceFile: ok
src/features/customer/CustomerEstimates.tsx → getSourceFile: ok
src/features/admin/AdminOverview.tsx → getSourceFile: ok
```

**그러니 지금 새고 있는 것은 아니다 — 잠재다.** 그래도 적어 두는 이유는, 이 저장소가
28-78-04에서 "대상이 비면 테스트는 아무것도 검사하지 않고 통과한다"고 이름 붙였고 그 뒤로
**세 번 그 실패를 겪었기 때문이다**(28-83 감사 01, 28-84 감사 01, 그리고 위 02). 같은 모양의
침묵이 새 가드 안에 하나 더 들어와 있다.

`customerReachableFiles()`가 `src/` 밖을 잘라내므로 `shared/`·`packages/` 같은 디렉터리가
생기거나 `tsconfig`의 `include`가 바뀌면 그 순간부터 조용히 초록이다. 두 줄이면 막는다 —
도달 파일마다 `getSourceFile`이 있는지 단언하고, 없으면 **실패**로 만든다.

## 잘한 것 (기록)

- **접근 방식을 바꾼 판단.** 세 번 뚫린 뒤 스캐너를 고치는 대신 버렸다. 28-84·85가 두 번 미룬
  결정이고, 미룬 대가를 두 번 치른 뒤에 내렸지만 결국 옳게 내렸다.
- **03이 "고칠 것"이 아니라 "없앨 것"이 됐다.** 면제 장치가 필요했던 이유가 사라졌으므로 장치를
  없앴다. 기능을 더하지 않고 빼서 문제를 없앤 라운드는 드물다.
- **02가 자기 문서의 틀린 문장을 스스로 고쳤다.** "유출 가치가 낮아서"를 "비용은 요청당 자원"으로
  바꿨다. (다만 아직 한 칸 덜 갔다 — 위 03.)
- **#237에서 "살아 있는 버그가 아니다"라고 적었다.** `tsc`가 실제로 통과하는 것을 확인하고,
  그럼에도 바꾸는 이유(설정 의존 제거)를 따로 적었다. 지적을 받았다고 없는 버그를 만들지 않았다.
