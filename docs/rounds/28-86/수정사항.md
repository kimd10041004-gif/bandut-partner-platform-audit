28-85 감사 4건을 전부 고쳤다. 01은 **접근 방식을 바꾼 것**이고, 그 결과 03은 고칠 것이 아니라

## 01 (상) 정규식을 버리고 TypeScript 컴파일러로

**원인.** 28-85-02가 `stripNonCode`를 손으로 쓴 스캐너로 다시 만들었는데, TSX의 **JSX 본문에 있는
아포스트로피는 문자열이 아니다.** `It's`의 `'`가 문자열 시작으로 읽혀 그 뒤 줄 끝까지가 지워졌고,
그 안의 집계 호출이 검사 대상에서 사라졌다.

**그리고 이것이 세 라운드 연속이었다:**

| 라운드 | 방식 | 뚫린 방법 | 성격 |
|---|---|---|---|
| 28-83 | `.이름(` 호출 형태 | 구조 분해 | 일부러 |
| 28-84 | 식별자 + 문자열 통째 제거 | 대괄호 · 템플릿 리터럴 | 템플릿은 실수로 |
| 28-85 | 문자열 경계를 직접 판단 | **JSX 본문의 아포스트로피** | **실수로** |

손으로 쓴 렉서는 언어의 모서리를 다 알지 못한다. 28-84·28-85가 두 번 미룬 판단을 이번에 한다.

**수정.** `typescript`(이미 devDependency)의 컴파일러 API로 프로그램을 만들고 **타입 검사기에게 묻는다**:

```ts
function isPlatform(checker, node) {
  const t = checker.getTypeAtLocation(node)
  const sym = t.getSymbol() ?? t.aliasSymbol
  return sym !== undefined && sym.getName() === 'PlatformService'
}
```

세 형태를 **같은 것**으로 본다 — 28-83~85가 하나씩 뚫린 그 셋이다:
`platform.partnerSummary`(속성) · `platform['partnerSummary']`(대괄호) · `const { partnerSummary } = platform`(구조 분해).
주석·문자열·JSX 본문은 애초에 표현식이 아니라 **후보가 되지 않는다.**

**수정 전 실패 인용.** 네 가지를 `PartnerCard.tsx`에 심어 확인했다:

```
아포스트로피  `<span>It's ready</span>; platform.partnerSummary(id)`
  28-85 → Tests 7 passed (7)          ← 조용히 통과 (28-85 감사 01)
  28-86 → + "src/ui/PartnerCard.tsx → partnerSummary (속성)"

대괄호       platform['partnerSummary'](id)      → + "… (대괄호)"
템플릿       `완료 ${platform.partnerSummary(id).done}건`  → + "… (속성)"
구조 분해     const { partnerSummary } = platform → + "… (구조 분해)"
```

넷 다 **어떤 방법으로 닿았는지까지** 이름 붙여 실패한다.

**값**: 프로그램을 한 번 만드는 데 ~2초. 가드 전체가 4초 안쪽이고, 한 번만 만들어 캐시한다.

## 02 (상) 인증 없는 경로에 rev 캐시 + **위험의 이름을 고쳤다**

**원인 둘.**
1. 요청마다 최대 4MB를 읽고 파싱했다. `cache-control`은 클라이언트·CDN에게 주는 **힌트**라
   캐시를 우회한 요청은 그대로 원본에 닿는다 — **세션 없이 아무나** 그 비용을 유발할 수 있었다.
2. 문서가 레이트리밋 부재를 "집계 다섯 개라 **유출 가치가 낮아**서"라고 적었다. **위험의 이름이 틀렸다** —
   여기서 비용은 응답 크기가 아니라 **요청당 CPU·메모리**이고, 데이터가 얼마나 민감한가와 무관하다.

**수정.** 먼저 `rev`만 읽고, 캐시된 rev와 같으면 **본문을 아예 가져오지 않는다.**

```
첫 요청      select rev → select body → 파싱 → 기억
같은 rev     select rev → 끝            ← 4MB를 읽지도 파싱하지도 않는다
rev 바뀜     select rev → select body → 다시 파싱
```

깨진 본문도 결과(`null`)를 기억한다 — 매 요청 재파싱하지 않으려고. 문서의 위험 서술도
**자원 소모**로 고쳤다(유출 가치 이야기는 근거로 쓰지 않는다). 엣지 레이트리밋은 계속 이월이다.

**수정 전 실패 인용.** 가짜 풀로 쿼리 순서를 고정했다:

```
수정 전 → × 첫 요청은 rev와 body를 읽고, 두 번째 요청은 rev만 읽는다
          × rev가 바뀌면 다시 읽는다 — 낡은 값을 내밀지 않는다
수정 후 → Tests 9 passed (9)
```

## 03 (중) `guard-ok` 면제 장치를 **없앴다**

28-85 감사는 면제가 파일 전체를 열고, 문자열 어디에 있어도 걸리며, 목록이 없다고 지적했다.
범위를 좁히는 대신 **장치 자체를 제거했다** — 면제가 필요했던 이유는 문자열 검사의 거짓 경보였고,
01이 문자열을 검사 대상에서 없앴으므로 **면제할 것이 남지 않는다.**

고칠 것보다 없앨 것이 있으면 없애는 쪽이 낫다. 관리되지 않는 면제 장치를 관리하려 애쓰는 것보다.

## 04 (중) 공개 집계 요청에 5초 타임아웃

**원인.** `fetchPublicStats`에 `AbortController`도 `signal`도 없었다. 28-85는 실패를 안전하게
(지표를 접는 쪽으로) 처리했지만 **응답이 없는 경우는 실패로도 처리되지 않았다** — `catch`에
들어가지 않고 계속 기다렸고, 그 페이지 뷰에서는 지표가 영영 뜨지 않았다.

**수정.** `signal: AbortSignal.timeout(5000)`. 타임아웃도 `catch`로 떨어져 `null`이 된다.

**수정 전 실패 인용.**

```
수정 전 → × 응답이 없으면 타임아웃으로 끊고 null — 영영 기다리지 않는다 (28-86-04)
수정 후 → Tests 6 passed (6)
```

**덧붙여 고친 것**: 기존 테스트가 "인증 헤더를 붙이지 않는다"를 `expect(calls[0][1]).toBeUndefined()`
(= 두 번째 인자 자체가 없다)로 적어 두어, `signal` 하나 붙이자 **의미 없이 깨졌다.**
단언이 말하려던 것(헤더가 없다)을 그대로 적도록 고쳤다 — 테스트가 의도가 아니라 형태를 잡고 있었다.
