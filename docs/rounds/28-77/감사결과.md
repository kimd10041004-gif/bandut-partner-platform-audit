# 28-77 감사결과 (GPT 감사자 역할)

**대상**: `567eb36`(#213) + `e0c894e`(#214) — 28-77이 **새로 넣은 것**만 본다.

라운드는 자기 몫을 했고, 특히 자기 감사의 과장 두 건(증폭 부활·백업 노출)을 스스로 확인해 정정한 것은
이 시리즈가 지켜 온 규율대로다. 아래 4건은 **그 수정들이 새로 만든 자리**다.

먼저, 확인해 보고 **문제가 아니었던 것**을 적어 둔다(감사자가 헛다리를 짚었다는 기록도 자산이다):

- 28-77-01의 `save()`가 서버 모드까지 도달하는가 → **도달한다.** `api/auth.ts`의 `DomainError` 경로가
  `saveAuth(c, workspaceId, loaded)`를 부르고, `saveAuth`는 `exportState()` 전후 비교로 바뀐 것만 쓴다.
  정지·미인증 계정 경로는 `AuthError extends DomainError`라 여기에 걸린다.
- 인증 상태 동시 쓰기 경쟁 → `select … for update` 행 잠금이 있다. 이번 라운드가 쓰기를 늘렸지만
  경쟁은 새로 생기지 않는다.
- `maskLabel` 배선 → 기존 회귀(`target: '고객 010****5678'`)가 이미 지키고 있다.

## 01 (중) 보관함 정리는 **부팅에만** 돈다 — 세션 중에 넘치면 새로고침 전까지 안 풀린다

`trimOverwritten`을 부르는 곳은 지금도 하나뿐이다:

```
src/app/bootstrap.ts:273:  const trimmedStash = trimOverwritten(storage, stashBudget(service))
```

28-75-02가 "이미 쓰인 초과분을 푸는 유일한 조치"로 부팅 정리를 넣었고, 28-77은 거기에 **안내**를 붙였다.
그런데 예산을 넘기는 사건은 **부팅 때가 아니라 쓰는 중에** 일어난다: 스냅샷이 커지면(사진 첨부, 요청 누적)
`stashBudget = 한도 − 스냅샷`이 줄어들어, 어제까지 예산 안이던 보관함이 오늘 예산 밖이 된다.
그 순간부터 `assertCapacity`가 저장을 막고, **탭을 새로 열기 전까지 아무것도 풀리지 않는다.**

- `stashOverwritten`은 **새 보관이 생길 때만** 예산에 맞춘다 — conflict가 나야 돈다.
- 관리자·마이페이지의 "보관함 비우기"는 있지만, 사용자가 **저장 실패 메시지를 읽고 스스로 찾아가야** 한다.

즉 28-75-02가 고친 "막힌 기기는 영영 막혀 있다"가, 시간 축을 바꾸면 "막힌 **세션**은 새로고침까지 막혀
있다"로 남아 있다. 안내 문구가 붙은 만큼 이 자리는 더 눈에 띈다.

**고치는 방향**: 저장이 용량으로 실패했을 때(`assertCapacity`가 던지는 자리) 한 번 `trimOverwritten`을
돌리고 재시도한다 — 보관함은 "잃지 않기"의 장치지 저장을 막는 장치가 아니므로, 둘이 부딪히면 보관함이
양보하는 것이 이미 정해진 순서다(28-75-02가 같은 이유로 "하나도 안 들어가면 비운다"를 택했다).
회귀: 스냅샷을 키워 예산 밖으로 만든 뒤 저장하면, 실패가 아니라 보관함이 줄고 저장이 성공한다.

## 02 (중) 정리는 **말하고 남기지는 않는다** — 다른 세 정리와 어긋난다

28-77-03은 부팅 정리를 4초짜리 안내로 알린다. 그런데 같은 부팅에서 도는 다른 정리들은 **운영 기록에
남는다**:

```
src/domain/platform.ts:  this.record('system', '알림 정리', String(n))
src/domain/platform.ts:  this.record('system', '채팅 정리', String(n))
src/domain/platform.ts:  this.record('system', '사진 정리', String(n))
```

보관함만 `record`가 없다(`grep -rn "record(" src/app/`은 주석 한 줄뿐이다). 그래서 4초가 지나면
**무엇이 언제 얼마나 지워졌는지 아무 데도 없다.** 하필 보관함은 넷 중 유일하게 "사용자가 잃은 것"이고,
나머지 셋은 정책상 만료된 파생 데이터다 — 기록이 가장 필요한 것이 기록되지 않는다.

덧붙여 안내 문구는 **몇 건**만 말하고 **언제 것**인지는 말하지 않는다. 보관 항목은 `at`(ISO 시각)을
갖고 있으므로 "9월 1일자 1건"까지 말할 수 있다.

**고치는 방향**: `initPlatform`이 지운 수를 돌려줄 때 `record('system', '보관함 정리', …)`도 남긴다
(부팅 중 record 호출은 이미 다른 정리들이 하고 있고, `PlatformContext`의 주석이 그 순서를 설명한다).
회귀: 예산 밖 보관함으로 부팅하면 운영 기록에 '보관함 정리' 행이 생긴다.

## 03 (중) 가명 키에 **설치별 소금이 없다** — 배포가 달라도 같은 사람은 같은 해시다

28-77-02는 막는 것과 막지 못하는 것을 정직하게 적었다(목록화는 막고, 지목 확인은 못 막는다).
그런데 **적히지 않은 잔여물**이 하나 있다:

```ts
function keyDigest(value: string): string {
  return sha256Hex(value).slice(0, KEY_DIGEST_LEN)   // 소금 없음
}
```

소금이 없으므로 `sha256('customer:01012345678')`은 **어느 배포에서나 같은 값**이다. 스테이징·프로덕션,
또는 서로 다른 워크스페이스의 `auth_state`를 나란히 놓으면 "같은 사람이 두 곳에 있다"가 **전화번호를
몰라도** 바로 읽힌다. 지목 확인(한 번의 해시)과 달리 이것은 **대상을 특정하지 않고도** 얻어지는 정보라
성격이 다르다.

**고치는 방향**: 설치마다 한 번 만드는 임의 소금을 스냅샷에 두고(`keySalt`) `sha256(salt + value)`로
바꾼다. 같은 행 안에서의 조회는 그대로 동작하고, 행을 가진 사람에 대한 방어는 원래도 아니었으므로
잃는 것이 없다. 옛 키는 지금처럼 버리면 된다. 문서의 "막는 것/막지 못하는 것" 표에 **상호 대조**도 적는다.

## 04 (하) 구조 테스트의 **소비자 목록이 하드코딩**이다 — 규칙은 전역인데 검사 범위는 네 곳

```ts
for (const file of [...walk(FEATURES), ...walk(UI), ...walk('src/app'), 'src/App.tsx']) {
```

`ui/` 조각의 사용처를 셀 때 보는 곳이 `features/` · `ui/` · `app/` · `App.tsx` 넷으로 고정돼 있다.
`src/` 아래에 다른 디렉터리가 생기면(예: 서버와 공유하는 어댑터) 거기서만 쓰이는 조각이 **"한 곳에서만
쓰인다"로 오탐**되어 CI가 빨개진다. 규칙("공용으로 두 번 쓰이는")은 저장소 전체에 대한 것이므로,
검사도 `src/` 전체를 걸어야 한다(테스트 파일만 제외).

**고치는 방향**: `walk('src')` 한 번으로 소비자를 모으고, 대상만 `ui/`로 좁힌다. 앞 방향 검사
(`features/` 안의 공용 조각)도 같은 그래프에서 나온다 — 두 검사가 한 번의 순회를 나눠 쓰면 규칙이
한 곳에 모인다.
