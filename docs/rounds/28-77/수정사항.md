# 28-77 수정사항 — 게이트가 실제로 남게 · 키에 식별자를 남기지 않게

**대상**: `28-76/감사결과.md` 4건. 범위는 사용자가 정한 **"감사 4건만"**이다.

---

## 28-77-01 (중) 스윕은 **훑었으면 남긴다**

`login()`은 `pruneTrustedIps(now)`를 먼저 부르고, 그 함수는 게이트를 통과하면 `trustedSweptAt`을 올리고
만료 항목을 지운다 — **둘 다 메모리에서만**. 저장은 호출자 몫인데 `login()`에는 저장 없이 던지고 끝나는
경로가 있다(정지된 계정·미인증 계정). 거기서 끝나면 지운 항목이 되살아나고 게이트 시각도 남지 않는다.
서버 모드는 요청마다 인스턴스를 새로 만들므로, 다음 요청이 또 훑는다.

```ts
    // 28-77-01: **훑었으면 남긴다.** 호출자(`login`)에는 저장 없이 던지고 끝나는 경로가 있다 …
    this.save()
```

> **감사의 정정**: 초안은 이것을 "잠긴 계정 반복 시도에서 증폭이 되살아난다"고 (상)으로 적었다가,
> 확인 후 (중)으로 고쳤다. 실패는 `recordFail`이 저장하고 잠금은 15분인데 게이트는 1시간이라
> **잠겨 있는 동안에는 게이트가 이미 닫혀 있다.** 무차별 대입 경로에서 증폭은 되살아나지 않는다.
> 남는 문제는 "계약이 일부 경로에서만 참"이라는 것이고, 그것만 고쳤다.

## 28-77-02 (중) 잠금·신뢰 IP 키에 **원문 전화번호와 IP를 담지 않는다**

키가 `acct|customer:01012345678` → `203.0.113.5`였다. 인증 스냅샷(서버 모드의 `auth_state` 행, 로컬
모드의 브라우저 저장소)을 **열어 보는 것만으로** "이 번호가 어디서 접속했는지"가 목록으로 읽혔다.
같은 파일이 감사 로그에는 `maskKey`로 가려서 남긴다 — 로그에는 가리고 상태에는 그대로 두고 있었다.

`failKey`가 번호와 스코프(IP)를 각각 `sha256` 앞 32자로 넣는다. 구조(`role:번호[:IP]`)는 그대로라
접두 일치(`forgetAccountKeys`)와 `acct|` 표식이 산다. `loginFails`와 `trustedIps`가 **한 번에** 바뀐다 —
두 곳 다 이 함수를 지난다(이웃을 남기지 않는다).

**막는 것과 막지 못하는 것을 분명히 적었다**(코드 주석에도 같은 내용이 있다):

- 막는다: **목록화.** 행을 읽어도 계정별 접속 IP 목록이 나오지 않는다.
- 막지 못한다: **지목 확인.** "이 번호가 이 IP에서 접속했나"는 해시 한 번이면 확인된다. 전화번호 자체는
  로그인 식별자라 `accounts`에 원문으로 남아 있다 — 없애는 것은 그 번호와 **IP의 결합**이 눈에 보이는 것이다.

곁들여 바뀐 것:
- **감사 로그 라벨**: 키가 가명이라 `maskKey`로는 사람이 못 읽는다. 부르는 자리가 역할·번호를 쥐고 있으므로
  `maskLabel(role, phone)`을 만들어 넘긴다 — 운영 기록에 남는 형태는 예전 그대로(`고객 0101***5678`)다.
- **옛 평문 키는 불러올 때 버린다**(`isPseudonymKey`). 버리는 방향이 안전하다: 실패 기록이 사라지면 잠금이
  풀릴 뿐이고(15분짜리다), 신뢰 IP가 사라지면 면제가 없어져 잠금이 그대로 걸린다.

> **감사의 정정**: 초안은 "관리자 백업 JSON에도 실린다"고 적었다. 틀렸다 — 백업은 `platform.exportBackup()`
> (플랫폼 스냅샷)이고 인증 상태는 별도 키라 백업에 들어가지 않는다. 확인하고 감사 문서도 고쳤다.

## 28-77-03 (중) 부팅 정리는 **조용하지 않다**

`trimOverwritten`은 지운 개수를 돌려주는데 `initPlatform`이 그것을 버리고 있었다. 어제 "덮인 내용은
보관했습니다"를 본 사람이 오늘 앱을 열면 보관함이 비어 있고, 화면 어디에도 이유가 없었다.

`InitializedPlatform`에 `trimmedStash`를 싣고, `PlatformProvider`가 0보다 크면 한 번 안내한다:

```
저장 공간을 확보하려고 덮인 변경 보관함 N건을 정리했습니다
```

같은 채널(`data-sync-notice`)을 쓰므로 다른 1회성 안내와 같은 자리에 뜬다. 서버 e2e에 단계를 더해
**화면까지** 확인한다(예산 밖 보관함을 심고 새로 고치면 안내가 뜨고 보관함이 비어 있다).

## 28-77-04 (중) 부팅 **배선**에 회귀를 걸었다 + 구조 규칙의 반대 방향

- `src/app/bootstrap.test.ts`: `window.localStorage`에 가짜를 세우고 **`initPlatform()`을 그대로 태운다**.
  예산 밖 보관함이 실제로 줄고 `trimmedStash`가 1이다. 28-76까지는 그 호출을 지워도 448건이 전부 초록이었다.
- `src/ui/structure.test.ts`: `UI_가이드.md` 3절의 **뒤 문장**("화면 전용 조각은 해당 feature 파일 안에")도
  검사한다 — `ui/`의 조각이 한 곳에서만 쓰이면 실패한다. `App.tsx`가 화면을 조립하는 것은 셸의 일이라 규칙 밖이다.

## 이 라운드에서 하지 않은 것 (조용히 빼지 않는다)

### ⚠ 시연 데이터 시드가 **실제로 터지고 있다** — 결정이 필요하다

28-77-04의 배선 테스트를 쓰다가 발견했다. **빈 저장소로 부팅하면**(=로컬 모드 첫 방문) `seedPlatform`이
던진다:

```
PAGE ERRORS: [ 'PlatformError: 고객 결제 완료 후 정산할 수 있습니다' ]
요청 수: no snapshot
```

시드가 `completed` 다음 바로 `settled`로 보내는데, 28-28-01 불변식이 **최종 결제 없이는 정산을 막는다**.
그래서 부팅이 통째로 실패하고 스냅샷이 저장되지 않는다 — 첫 방문자에게 시연 데이터(일감 3건 + 정산 이력
3건)가 **하나도 보이지 않는다**. 라이브(`bandut-partner-platform.vercel.app`, 로컬 모드)가 지금 그 상태다.

패치는 한 줄이고 검증도 했다(고친 뒤 브라우저에서 `요청 6건 · settled 3건`, 페이지 오류 없음):

```ts
    p.transitionRequest(r.id, 'completed', { completedDate: h.date })
    p.payFinal(r.id, 'card')                     // ← 이 한 줄
    p.transitionRequest(r.id, 'settled')
```

**그런데 이 라운드에 넣지 않았다.** 고치면 첫 화면에 시연 데이터 6건이 새로 보이게 되고, `e2e-journey`의
단언 **10곳**이 그 부재를 전제로 쓰여 있어 함께 고쳐야 한다(지급 대기 1건 → 4건 등). 제품이 달라지는
변경이라 "감사 4건" 라운드에 조용히 끼워 넣을 일이 아니다. 배선 테스트는 시드 경로를 타지 않도록
스냅샷을 미리 심어 통과시켰고, 코드에는 경위를 주석으로 남겼다.

### 그 밖(이월 그대로)

- `scripts/api-server.mjs`의 포트 인자가 `--static` 없이 무시되는 것.
- `clientIpOf`의 `trusted`가 "프록시를 검증했다"가 아니라 "헤더가 있다"는 뜻이라는 사실의 문서화.
- `otps` 맵의 키는 아직 평문(`role:phone`)이다 — 5분짜리이고 번호 자체는 `accounts`에 있으므로 이번 항목
  (번호↔IP 결합)의 대상이 아니다.
- 병합(엔티티 단위 인가), 보관함 서버 업로드·자동 복원, SMS OTP, 쿠키 세션·CSP, scrypt, 엣지 레이트리밋.
