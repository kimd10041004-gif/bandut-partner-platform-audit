# 28-41 감사결과 (GPT 역할 — Claude 세션 대리 수행)

감사 범위: `28-41` 전체 — 의존성·보안 위생 반영 후, **플랫폼의 구조적 전제** 점검: 파트너가 여럿일 때 데이터가 분리되는가.
사전 확인: `npm run check` exit 0 (vitest 189/189), e2e 68/68 PASS, visual-check 전 항목 PASS, `npm audit` 0건, 프로덕션 배포 그린(PR #94 머지). 28-40 감사 4건 전부 수정 확인됨.

핵심 지적: 파트너 센터는 여전히 **단일 파트너 상수 `PARTNER_ID = 'P-001'`** 로 동작한다. 파트너 계정(가입·승인·계좌)은 여럿 만들 수 있지만, 로그인한 파트너가 누구든 대시보드·내 작업·일정·정산·프로필·리뷰가 **모두 같은 데이터**를 보여준다 — 두 번째 파트너가 가입하면 첫 파트너의 낙찰 작업·정산금·리뷰·프로필을 그대로 보게 되고, 견적도 `P-001` 이름으로 제출된다. 관리자 지급 처리도 "첫 번째 파트너 계정"의 계좌를 쓴다. 중개 플랫폼에서 파트너 간 데이터 분리는 기능이 아니라 전제이며, 이 상태로는 두 번째 파트너를 받을 수 없다.

## 상 (High)

### 28-41-01 · 파트너 식별 = 계정, 도메인 범위 분리
→ 요구: 견적·슬롯·작업의 `partnerId`는 **로그인한 파트너 계정 id**(`AuthSession.accountId`)여야 한다(시드 데이터만 `P-001` 데모 파트너 유지). `PlatformService`에 파트너 범위 조회 도입: `partnerRequests(partnerId)`(내 견적이 있는 요청), `bidStats(partnerId)`, `statusCounts(partnerId)`, `settlements(filter, partnerId)`, `unsettledPayout(partnerId)`, `monthlyReport(partnerId)`/`monthSummary(month, partnerId)`, `completedJobsOf(partnerId)`, `reviewStats(partnerId)`/`allReviews(partnerId)`, `upcomingSlots(today, n, partnerId)`, `partnerHasOpenWork(partnerId)`, `partnerOf(requestId)`. **파트너 알림도 계정 범위**(요청의 견적 파트너 = 계정). 인자 생략 시 전체(관리자·랜딩 지표) — 기존 호출 하위 호환. **도메인 테스트 필수**(두 파트너 데이터 교차 없음).

### 28-41-02 · 파트너 프로필 다중화 + 고객 업체 카드 연결
→ 요구: 프로필을 `profiles: Map<partnerId, PartnerProfile>`로. `getProfile(partnerId)`/`updateProfile(partnerId, …)`/`partnerSummary(partnerId)`. 구 스냅샷의 단일 `profile`은 `P-001`로 이전(하위 호환). 고객 견적함·거래 상세의 업체 카드는 **그 요청의 견적 파트너** 프로필·실적을 보여준다.

### 28-41-03 · 파트너 센터·관리자 UI 범위 적용
→ 요구: 대시보드·일감·내 작업·일정·정산·마이 탭이 세션의 `accountId`로 범위 조회. 일감 탭은 "입찰 가능(requested)" + "내 입찰" 만 표시(타 파트너 견적 건 제외). 관리자 정산 감독 지급 처리는 `job.partnerId`로 파트너 계정을 찾아 계좌 사용, 파트너명 표기. 회원 탭 파트너 행에 파트너 id 표시.

## 중 (Medium)

### 28-41-04 · e2e + 실측
→ 요구: e2e — 두 번째 파트너 가입·승인 → 대시보드/내 작업/정산이 비어 있음(첫 파트너 데이터 미노출) → 두 번째 파트너가 새 요청에 입찰 → 첫 파트너 일감 탭에 그 요청이 "타 파트너 입찰"로 제외 → 관리자 지급 처리가 낙찰 파트너 계좌를 사용. 두 파트너 대시보드 스크린샷.
