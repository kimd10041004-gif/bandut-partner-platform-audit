# 28-78 감사결과 (GPT 감사자 역할)

**대상**: `83ef265`(#215) + `ae0fa2a`(#216) + `decfa74`(#217) — 28-78이 새로 넣은 것.

라운드는 오래 죽어 있던 첫 화면을 되살렸고, 리뷰 지적(포트 예외 방어)도 회귀와 함께 닫았다.
**그런데 되살린 것이 무엇인지 화면이 말하지 않는다** — 01이 그것이고, 이번 감사에서 가장 급한 항목이다.

---

## 01 (상) 시연 데이터가 **시연이라고 말하지 않는다** — 첫 화면 지표가 실적처럼 읽힌다

`Landing.tsx`의 히어로는 플랫폼 데이터를 그대로 지표로 쓴다:

```tsx
<div className="hero-stats">
  <div><strong>{ov.totalRequests}</strong><span>누적 요청</span></div>
  <div><strong>{ov.completedOrSettled}</strong><span>완료된 수리</span></div>
  <div><strong>{stats.winRate === null ? '—' : `${stats.winRate}%`}</strong><span>파트너 낙찰률</span></div>
  <div><strong>{rstats.average === null ? '—' : `★${rstats.average}`}</strong><span>평균 만족도</span></div>
</div>
```

28-78 이전에는 시드가 던져서 스냅샷이 비어 있었고, 그래서 이 자리는 **0 · 0 · — · —**였다. 비어 있는 것은
정직했다. 복구 뒤 첫 방문자가 보는 값은(부팅 경로를 그대로 태워 확인했다):

```
누적 요청 6 | 완료된 수리 3 | 낙찰률 100 | 평균 만족도 null
```

즉 라이브 랜딩이 지금 **"누적 요청 6건 · 완료된 수리 3건 · 파트너 낙찰률 100%"**를 내건다. 전부 시연
데이터에서 계산된 숫자이고, **"시연"이라는 표시는 랜딩 어디에도 없다**(`grep -rn "시연\|데모\|demo\|샘플"
src/features/landing/Landing.tsx src/App.tsx` → 없음). 관리자 화면의 시연 계정 안내와 달리, 고객이 처음
보는 화면에는 아무 단서가 없다.

이것은 이 저장소가 스스로 세운 잣대("말과 사실을 맞추는 것")를 정면으로 어긴다. 게다가 **낙찰률 100%**는
시드가 만든 우연(입찰 3건이 전부 낙찰)인데 마케팅 문구처럼 읽힌다. 사업 홍보용 수치를 사실과 다르게
내거는 것은 기술 문제가 아니라 **신뢰 문제**이고, 28-78이 복구하면서 만든 것이다.

**고치는 방향**(택일이 아니라 조합 가능):
1. 시연 데이터일 때 히어로 지표를 **숨긴다** — 실적이 쌓이기 전에는 지표 대신 서비스 설명을 둔다.
2. 지표를 남긴다면 **"시연 데이터"라고 붙인다**(배지 한 줄). 관리자 시연 계정 안내와 같은 자리·같은 톤.
3. 시드에 표식을 남긴다(`seeded: true`) — 도메인이 "이 데이터는 시연"임을 알면 화면마다 판단할 수 있다.

회귀: 시연 시드만 있는 상태의 랜딩에 실적 수치가 **그대로 노출되지 않는다**(숨김 또는 표기).

## 02 (중) 보관함 정리 정책이 **두 개**다 — 같은 것을 다르게 판단한다

부팅과 런타임이 서로 다른 기준으로 보관함을 줄인다:

```ts
// 부팅 (bootstrap.ts) — 예산: 한도 − 스냅샷, 최대 1MB
const trimmedStash = trimOverwritten(storage, stashBudget(service))

// 런타임 (platform.ts assertRoom) — 딱 모자란 만큼만
const need = usage.totalChars + extraChars - usage.limit
freed = this.trimExternal(need)
```

부팅은 "예산 안으로", 런타임은 "이번 저장이 되는 만큼만"이다. 그래서 런타임에 간신히 통과한 기기는
**다음 저장에서 또 걸리고**, 그때마다 조금씩 더 지운다 — 사용자에게는 "왜 자꾸 줄어들지?"가 되고,
지운 것은 28-78-02의 기록에도 남지 않는다(그 기록은 부팅 경로에만 있다).

**고치는 방향**: 런타임도 예산(`stashBudget`) 기준으로 한 번에 맞춘다. 그리고 런타임에서 지운 것도
`recordExternalTrim`으로 남긴다 — 부팅에만 기록을 남기는 것은 절반이다.

## 03 (중) `recordExternalTrim`이 **임의 문자열**을 받는 공개 API다

```ts
recordExternalTrim(action: string, count: number): void
```

앱 계층이 아무 행위명이나 감사 로그에 넣을 수 있다. 28-59·28-60이 감사 로그의 **무결성**(누가 무엇을
남기는가)을 다룬 저장소에서, 도메인이 이름 검증 없이 통로를 열어 준 셈이다. 지금 부르는 곳은 한 곳이고
문자열도 하나(`'보관함 정리'`)뿐이라 **지금은** 문제가 없지만, 통로가 넓은 것 자체가 다음 라운드의 함정이다.

**고치는 방향**: 인자를 좁힌다 — `recordExternalTrim(kind: 'stash', count: number)`처럼 유니온으로 두거나,
아예 `recordStashTrim(count)`로 이름을 고정한다. 도메인이 남기는 행위명은 도메인이 정한다.

## 04 (하) `assertRoomForTest`가 **프로덕션 표면**에 남았다

```ts
/** 용량 가드를 테스트에서 직접 태운다 (28-78-01) */
assertRoomForTest(extraChars: number): void { this.assertRoom(extraChars) }
```

테스트를 위해 공개 메서드를 하나 늘렸다. 이름이 정직한 것은 좋지만, 도메인 표면은 화면이 쓰는 계약이라
테스트 편의로 넓히면 다음 사람이 그것을 계약으로 오해한다.

**고치는 방향**: 사진 첨부 등 **실제 경로**로 가드를 태우거나(그쪽이 진짜 회귀다), 그게 번거로우면
테스트에서 `service['assertRoom']`으로 접근하고 공개 메서드는 지운다.

## 확인해 보고 문제가 아니었던 것

  겹치지 않는다.
