# 29-26 — 같은 스위트를 Postgres 로도 돌린다

## 1. 왜 이 라운드인가

29-25 가 찾은 넷은 모두 같은 모양이었다. **단위 테스트는 SQLite 로 돌아 초록이고, 운영은 Postgres 라서
죽어 있었다.** 넷을 고치고 나니 물음이 남았다 — 그 모양의 결함이 넷뿐인가.

하나씩 찾아 고치는 것으로는 답이 안 나온다. 도메인 규칙을 증명하는 통합 스위트 셋(접수 40 · 거래 42 ·
작업공간 15 — vitest 출력 기준 97건)이 전부 SQLite 로만 돈다. **같은 97건을 Postgres 로 돌리면** 방언
차이는 한 번에 드러난다.

그렇게 했다. 고치기 전 **15건이 실패**했다.

## 2. 찾은 것 — 셋

| | 무엇이 | 사용자가 보던 것 |
|---|---|---|
| **01** | `COUNT`·`SUM` 이 Postgres 에서 **문자열**로 온다 | **관리자가 정산을 승인할 수 없다.** `계약·승인된 추가 작업의 최초 결제액이 일치해야 합니다.` 로 항상 거절 |
| **02** | `AVG(rating)` 이 문자열로 온다 | 후기가 하나 생기는 순간 **업체 찾기와 업체 페이지가 하얗게 빈다** (`rating.toFixed` 가 던진다) |
| **03** | `EXISTS(...)` 가 Postgres 에서 boolean 이다 | 화면은 안 죽지만 `Visit.pending:number` 타입이 거짓말이다 |

셋 다 29-25 와 같은 뿌리다 — 도메인이 SQLite 에서 자랐다.

### 01·02 — `pg` 는 큰 수를 문자열로 준다

`pg` 는 `bigint`(int8)와 `numeric` 을 기본으로 **문자열**로 돌려준다. 자바스크립트 숫자로 바꾸면 정밀도를 잃을
수 있어서다. `COUNT(*)` 는 int8 이고, `SUM(integer)` 도 int8 이고, `AVG` 는 numeric 이다. SQLite 는 셋 다
숫자로 준다.

그 차이가 어디서 터지는지는 코드가 `+` 를 쓰는지 `-` 를 쓰는지에 달려 있었다.

```ts
// lib/trade.ts financials()
return { expected: c.total + (ex?.total ?? 0), gross, refunded, fee, payable: gross - refunded - fee }
```

`ex.total` 이 `"0"` 이면 `198000 + "0"` 은 **`"1980000"`** 이다 — 이어붙이기. `gross - refunded` 는 `-` 라서
우연히 숫자다. 그래서 정산 승인의 `if (f.gross !== f.expected)` 는 `"198000" !== "1980000"` 으로 **언제나**
거절했다. 관리자가 보는 문구는 "최초 결제액이 일치해야 합니다" — 일치하고 있었다.

`companies.tsx` 의 `c.rating.toFixed(1)` 은 `"4.0000000000000000".toFixed` 라서 던진다. 후기가 없을 때는
`null` 이라 안 던진다. **후기가 처음 생기는 날 업체 찾기가 죽는** 구조다.

`unread > 0`, `n >= 20`, `Number(c?.n ?? 0)` 같은 자리는 비교라서 우연히 맞았다(마지막 것은 누군가 한 번
데인 흔적이다).

**포트가 흡수한다** (`server/pgPort.ts`, `numericTypes`). int8 과 numeric 을 숫자로 읽는 파서를 **문장마다**
붙인다 — 풀 설정이 아니다. 운영·CI·테스트가 풀을 제각기 만들기 때문에, 어떤 풀을 받아도 도메인이 보는 값이
같아야 한다. 이 플랫폼의 정수는 원 단위 금액과 일련번호라 2^53 안에 있다.

도메인 코드는 손대지 않았다. 도메인이 SQLite 로 증명한 규칙이 그대로 Postgres 의 규칙이 되는 것이 포트의
일이다.

### 전역 파서가 가리고 있었다

`tests/pg.port.test.ts` 는 `beforeAll` 에서 `pg.types.setTypeParser(20, Number)` 를 **전역으로** 걸고 있었다.
그래서 29-25 가 넣은 지표 테스트(`m.orders > 0`)도 초록이었다 — 운영 풀에는 그 설정이 없다. 걷어냈다. 이제 그
파일은 운영과 같은 풀로 포트를 본다. 걷어내자 29-25 의 그 테스트가 바로 넘어졌다(`검증결과.md` §1-3).

### 03 — `EXISTS` 는 두 방언에서 다른 타입이다

`workspace-service.ts` 의 방문 일정이 `EXISTS(...) pending` 을 그대로 열로 내보냈다. SQLite 는 `0/1`,
Postgres 는 `true/false`. 화면(`calendar-hub.tsx`)은 truthy 로만 봐서 안 죽지만 `Visit.pending:number` 는
거짓이 된다. `CASE WHEN EXISTS(...) THEN 1 ELSE 0 END` 로 바꿨다 — 두 방언에서 같은 정수다.

## 3. 하네스 — `npm run test:pg:suite`

`tests/support/testDatabase.ts` 가 파일마다 저장소를 연다. `TEST_DIALECT=postgres` 와 `DATABASE_URL` 이
있으면 Postgres 에 **파일마다 제 스키마**(`it_trade` 같은)를 세우고 테스트 사이에는 표만 비운다. 아니면
지금까지처럼 메모리 SQLite 다. `vitest.pg.config.ts` 가 그 환경변수를 주고, CI 의 server job 에 한 단계로
들어갔다.

세 파일에서 손댄 것은 **SQLite 를 직접 만지던 자리**뿐이다 — `sqlite.prepare(...).run()` 을 `await t.run(...)`
으로. 같은 포트를 지나가므로 두 방언에서 같은 문장이다. SQLite 가 동기라 바로 던지던 단언은
`await expect(t.run(…)).rejects.toThrow()` 가 됐다. 단언의 내용은 바꾸지 않았다.

한 곳만 순서를 바꿨다. 접수 스위트의 "빈 데이터베이스의 첫 가입자" 는 새 저장소를 열었다가 **옛 저장소로
돌아가** 관리자 역할을 확인했다. Postgres 는 표를 비우므로 돌아갈 곳이 없다. 관리자 확인을 먼저 하고 새
저장소를 연다 — 두 단언은 서로를 모르므로 뜻은 같다.

## 4. 봇 — `e2e:trade` 세 걸음

02 는 화면이 죽는 결함이라 브라우저로도 봤다. 작업 완료 뒤에 세 걸음을 더했다.

- 완료한 고객이 후기를 남길 수 있다
- 후기가 생긴 업체가 업체 찾기에 평점과 함께 나온다 (`후기 1건 · 평점 5.0`)
- 업체 페이지가 평점을 숫자로 그린다 (`5.0 / 5 · 후기 1건`)

고치기 전 빌드에서는 두 번째 걸음에서 넘어진다 — 업체 찾기 본문이 스크립트 페이로드뿐이고 목록도 빈 안내도
뜨지 않는다(`검증결과.md` §3).

  같은 코드를 로컬 Postgres 로 돌린 것이다.

  문장에만 붙는다 — 그쪽 동작은 바뀌지 않았다.
