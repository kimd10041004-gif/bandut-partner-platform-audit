# 29-23 검증결과

## 1. 승인 게이트 — 수정 전 실패를 먼저 냈다

`tests/marketplace.integration.test.ts` 에 두 줄을 더했다. 게이트 코드를 빼고 돌린 결과:

```
× 서류가 하나도 없으면 승인이 막히고, 둘 다 내면 열린다
  AssertionError: promise resolved "{ ok: true }" instead of rejecting
  - Error { "message": "rejected promise" }
  + { "ok": true }
```

서류를 하나도 안 낸 사업자 파트너가 **승인됐다.** 게이트를 되돌리자 통과한다.

이 줄은 **한 장만 냈을 때도** 막히는지 본다. "둘을 요구한다"고 적어 놓고 하나에서 열리면
요구한 것이 아니다.

```
✓ 서류가 하나도 없으면 승인이 막히고, 둘 다 내면 열린다
✓ 개인 파트너는 서류 없이 그대로 승인된다
```

둘째 줄이 짝이다. 게이트가 **사업자에게만** 걸리는지 확인한다 — 안 그러면 개인 파트너가
영원히 대기에 갇힌다.

## 2. 저장소 포트 — 여덟 줄

`server/storage.test.ts`. 셋으로 나뉜다.

| 갈래 | 재는 것 |
|---|---|
| 백엔드 선택 | `BLOB_STORE_ID` 가 `LOCAL_STORAGE_DIR` 을 이긴다 · **빈 문자열은 "설정됨"이 아니다** · 둘 다 없으면 `null` |
| 키 탈출 | `..`, `//`, 절대경로, 빈 값, 200자 초과를 거부하고 **파일을 만들지 않는다** |
| 로컬 계약 | 넣고 꺼내면 바이트가 같다 · 없는 키는 `throw` 가 아니라 `null` · 덮어쓰기가 된다 · 지운 뒤에는 `null` |

"거부하고 파일을 만들지 않는다"를 따로 잰다. 예외를 던지고 나서 파일이 이미 생겼으면
막은 것이 아니다.

## 3. 봇이 서류 흐름을 끝까지 걸었다

`e2e:roles` 에 일곱 줄이 늘었다. 서류 넷, 관리자 문 셋.

```
✓ 서류를 안 냈으면 승인 화면이 그것을 먼저 말한다
✓ 서류 없이는 승인되지 않는다
✓ 서류 둘이 올라가 목록에 남는다
✓ 운영자 화면에 그 서류가 보인다
✓ 로그인 안 한 관리자를 관리자 문으로 보낸다
✓ 고객 화면은 그대로 고객 문으로 보낸다
✓ 공개 로그인 화면에는 여전히 관리자 선택지가 없다
```

둘째 줄은 **승인을 실제로 눌러 보고** 대기 상태가 그대로인지 센다. 버튼이 비활성인 것을
재는 것이 아니다 — 서버가 막는지를 잰다.

셋째 줄은 파일을 실제로 올린다(`setInputFiles`). 넷째 줄은 **다른 창**(관리자)에서 그것이
보이는지 본다. 같은 창에서 자기가 올린 것이 보이는 것만 재면 아무것도 확인하지 못한다.

마지막 줄은 이번 수정이 **공개 화면을 건드리지 않았다**는 것이다. 문을 하나 열면서 다른 문을
같이 열어 버리는 것이 흔한 실수다.

## 5. 아직 확인되지 않은 것

**Vercel Blob 경로는 한 번도 돌지 않았다.** 여기 적힌 서류 검사는 전부 로컬 파일 백엔드
(`LOCAL_STORAGE_DIR`)에서 잰 것이다. 두 백엔드가 같은 포트를 구현하지만, **구현했다는 것과
돌려 봤다는 것은 다르다.**

확인하려면 프리뷰 배포에서 파트너로 서류 한 장을 올려 보고, 관리자로 그것을 열어 봐야 한다.
`BLOB_STORE_ID` 는 세 환경에 모두 연결돼 있고, 환경변수는 **빌드 시점에 주입되므로** 이
브랜치가 배포된 뒤여야 한다.

그리고 하나 더 — **올라온 서류가 진짜 그 서류인지는 아무도 재지 않는다.** 사람이 본다.
그것이 이 라운드의 설계다.
