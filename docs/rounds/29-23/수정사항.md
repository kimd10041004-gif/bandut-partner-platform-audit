# 29-23 — 사업자 파트너의 확인 서류

## 1. 왜 지금인가

29-21 에서 가입 코드를 없앴다. 그때 적어 둔 대로, 남은 자물쇠는 **운영자 승인** 하나다.

그런데 승인하는 사람이 볼 것이 지금까지 **업체명과 사업자등록번호뿐**이었다. 등록번호는
체크섬만 맞으면 통과한다 — 아무 숫자나 규칙에 맞게 만들면 된다. 즉 승인 화면에 앉은 사람은
"이 사람이 진짜 그 사업자인가"를 판단할 근거가 없는 채로 승인 버튼을 누르고 있었다.

사업자 파트너는 서류 둘을 낸다.

| 종류 | 무엇을 확인하나 |
|---|---|
| `BUSINESS_LICENSE` 사업자등록증 | 그 번호가 **이 사람의** 사업자인가 |
| `TRAVEL_RECORD` 출입국사실증명서 | 지금 이 나라에서 **일할 수 있는** 사람인가 |

개인 파트너는 내지 않는다. 고객과 같은 휴대폰 인증 + 승인이다(사용자 결정).

## 2. 파일 저장소를 도메인에서 떼어 놓는다

서류는 바이트다. DB 에 넣지 않는다 — 백업과 스냅샷에 신분 서류가 섞여 들어가기 때문이다.
표에는 **어디에 있는지만** 남는다(`object_key`).

`server/storage.ts` 가 포트 하나를 정의한다.

```ts
export interface Storage {
  put(key, bytes, contentType): Promise<StoredFile>
  get(key): Promise<{ bytes; contentType } | null>
  remove(key): Promise<void>
}
```

뒤에 둘이 붙는다. `BLOB_STORE_ID` 가 있으면 Vercel Blob, `LOCAL_STORAGE_DIR` 만 있으면
로컬 파일이다. 둘 다 없으면 `null` 이고, 서류 경로는 503 으로 "저장소가 연결되지 않았습니다"를
말한다 — **조용히 성공한 척하지 않는다.**

Vercel 쪽은 `access: 'private'` 을 못박고, `addRandomSuffix: false` 로 키를 우리가 정한
그대로 쓴다. 인증은 `BLOB_READ_WRITE_TOKEN` 이 있으면 그것을, 없으면 OIDC 토큰을 쓴다 —
SDK 소스를 읽어 두 경로가 모두 1급이라는 것을 확인했다.

**키 탈출을 막는 것이 여기서 제일 중요한 줄이다.**

```ts
const KEY_RE = /^[A-Za-z0-9][A-Za-z0-9/_.-]{0,200}$/
export function assertSafeKey(key: string): void   // '..', '//', 절대경로, 빈 값, 200자 초과를 막는다
```

로컬 백엔드는 이것이 없으면 `../../etc` 를 쓴다. 포트 안쪽에 두어 **백엔드를 바꿔도 같은 규칙**이
걸리게 했다.

## 3. 승인 문에 조건을 하나 더 단다

`lib/service.ts` 의 `approve` 안이다.

```ts
if (p.partner_type === 'business') {
  const c = await stmt('SELECT COUNT(*) n FROM partner_documents WHERE partner_id=?', id).first()
  if (Number(c?.n ?? 0) < 2)
    fail(409, '사업자 파트너는 사업자등록증과 출입국사실증명서를 모두 제출해야 승인할 수 있습니다.')
}
```

`(partner_id, kind)` 에 고유 인덱스가 있으므로 **2 는 곧 "두 종류를 다 냈다"**이다. 같은
종류를 두 번 세는 일이 없다.

화면에서 버튼을 감추는 것으로는 부족하다. 승인은 HTTP 한 줄이라, 문은 서버에 있어야 한다.

## 4. `partner_type` 을 `partners` 표로 가져왔다

사업자·개인 구분은 **가입 계정 쪽에만** 있었다(`auth_state`). 승인 화면이 보는 `partners` 표에는
없었다. 그래서 승인 게이트가 판단할 근거가 그 사람이 보는 표에 없는 상태였다.

`db/sqlite/0012_partner_type.sql` 로 칸을 더했다. 두 곳에서 읽어 맞춰 보는 대신 승인이 보는
표에 둔다 — 두 저장소가 다른 말을 하면 그때부터는 분쟁이다.

**기본값을 스키마에만 두고 입력에는 두지 않았다.** `partnerSchema` 의 `partnerType` 은 필수다.

> 기본값은 사람을 조용히 분류한다.

이것 때문에 기존 테스트 95 개가 깨졌고, 기본값을 넣는 대신 **부르는 쪽 네 곳에 실제 값을
적었다.** 이번 라운드에서 HTTP 통합 테스트 여섯 자리가 더 나와 같은 식으로 고쳤다.

## 5. 서류를 미리 그리지 않는다

목록에는 **종류·크기·낸 시각·파기 예정일**만 있다. 실제 내용은 **누른 사람에게만** 나간다.
관리자 화면은 어깨너머로 보이는 자리일 수도 있다.

바이트도 우리 서버를 거쳐 나간다 — 저장소 주소를 브라우저에 주지 않는다. 받은 뒤에는
`URL.revokeObjectURL` 로 60초 뒤 되돌린다. 남겨 두면 그 탭이 서류를 계속 쥐고 있다.

## 6. 파기

신분 서류를 영원히 갖고 있을 이유가 없다. 낼 때 파기 예정일을 함께 적고(180일),
`purgeExpired` 가 지난 것을 **저장소와 표에서 둘 다** 지운다. 관리자가 목록을 열 때 돈다.

지우는 순서가 중요하다. **저장소를 먼저** 지운다.

- 표를 먼저 지우면 → 저장소에 아무도 모르는 신분 서류 파일이 남는다.
- 저장소를 먼저 지우면 → 최악이 "못 여는 줄" 하나다.

## 7. 곁가지로 잡은 것 — 관리자 문 (29-23-3)

사용자가 물었다: 로그인 안 한 채로 `/admin` 을 열면 어디로 가느냐.

`Access` 가 내걸던 로그인 단추는 **언제나 `/login`** 을 가리켰다. 그런데 그 화면에는 29-10 이후
관리자 선택지가 없다 — 일부러 뺐다. 즉 관리자는 안내를 따라가면 들어갈 수 없는 문 앞에 섰다.

주소가 문을 정하게 했다.

```tsx
const door = path.startsWith('/admin') ? '/login/admin' : '/login'
```

**공개 로그인 화면은 그대로다.** 봇이 세 줄로 셋 다 본다 — 관리자 문으로 보내는가, 고객은
고객 문으로 보내는가, 공개 화면에 여전히 관리자 선택지가 없는가.

## 8. 하지 않은 것

- **서류 내용 판독.** 올라온 것이 진짜 사업자등록증인지는 **사람이 본다.** 자동 판독은 틀렸을 때
  통과시키는 쪽으로 틀린다.
- **개인 파트너 신분증.** 받지 않기로 했다(사용자 결정). 받으면 보관 의무가 생긴다.
- **정산 계좌 등록.** 아직이다. 프로필의 안내 문구만 현재 상태에 맞게 고쳤다.
