# 28-97 수정사항 — 결제 멱등 키 · 정산 = 총액 − 환불 − 수수료 (참고 v12 대조 7)

`../28-90/참고_v12_대조.md` "더할 것" 7번. 참고 시안은 결제를 **주문(READY) → 승인(DONE) | 실패**의 수명주기로 두고
승인·취소에 **멱등 키**를 실어 결제사(토스페이먼츠)에 보낸다(`lib/payments.ts`). 정산은 결제 합계에서 환불을 빼고 그 위에
수수료를 매긴다(`settlements.gross/refunded/fee/payable`). 28-96까지 우리는 "버튼을 누르면 곧 결제 기록"이었고, 정산은
**총액 − 수수료**뿐이라 환불이 지급액에 반영되지 않았다.

## A. 도메인 — 결제 수명주기

- `Payment`에 `orderId`(= 멱등 키 `BD-<요청>-<종류>-<번호>`)·`status`(`ready|done|failed`)·`providerKey?`·`failReason?`.
- `preparePayment(requestId, kind, method)`: 금액은 도메인이 정하고(`depositDue`/`finalDue` — 종전 `payDeposit`/`payFinal`의
  규칙을 그대로 분리) 주문번호를 발급한다. 같은 요청·종류·**금액·수단**의 준비가 열려 있으면 그것을 돌려준다(결제창을 다시
  열어도 주문이 늘지 않는다). 금액·수단이 바뀌었으면 옛 주문을 실패로 닫고 새로 발급한다.
- `confirmPayment(orderId, { providerKey, amount })`: **멱등** — 같은 주문에 같은 키로 다시 오면 같은 결제를 돌려준다.
  다른 키·금액 불일치·실패한 주문·다른 주문에 쓰인 키는 거부한다. 준비 뒤 거래가 바뀌어 청구 금액이 달라졌으면
  (예: 그 사이 취소) 주문을 실패로 닫고 거부한다.
- `failPayment(orderId, reason)`: 결제창 닫힘·거절. 승인된 주문은 실패로 되돌리지 않는다. 재기록은 멱등.
- `payDeposit`/`payFinal`은 남는다 — 이제 **준비 + 승인을 한 번에** 하는 기록 결제이고 승인 키는 `local:<주문번호>`다.
  결제사 연결 전(지금)과 로컬 모드가 이 경로를 쓴다.
- 승인된(done) 결제만이 결제다: `paymentFor`·미결제 완료 큐·정산 불변식·타임라인·원장이 전부 `status === 'done'`을 본다.
- 구 스냅샷은 `status: 'done'` · `orderId: 'LEGACY-<id>'`로 올라온다(그때는 기록이 곧 결제였다). 스냅샷 검증에
  상태·주문번호·중복(주문번호·승인 키) 검사를 더했다.

## B. 도메인 — 정산 = 총액 − 환불 − 수수료

- `requestRefund(requestId, { amount, reason })` (관리자): **완료 거래·지급 전**에만, 결제(최종 → 없으면 예약금)의 남은
  금액 안에서. 대기 중에는 `settle`·`markPayout`이 보류된다.
- `settleRefund`가 완료되면 `CompletedJob.refunded`에 누계로 더하고 **수수료를 (총액 − 환불) 기준으로 다시 산정**한다
  (요율은 28-95의 계약 bps).
- `settlementFor(requestId)` → `{ gross, refunded, pendingRefund, fee, bps, payable }`, `PlatformService.payableOf(job)` —
  화면·원장·지급이 같은 식을 쓴다. `markPayout`은 지급액과 함께 **근거**(환불 누계·수수료)를 기록에 남긴다.
- 원장의 수수료 메모가 "총액의 3%" 고정 문구에서 `정산 기준 <총액−환불>원의 <실제 bps>%`로 바뀌었다.
- 부분 환불은 결제를 지우지 않는다 — 전액 환불(취소·철회)만 그 결제를 소진시킨다(`fullyRefunded`).

## C. 서버 — 결제사 어댑터와 API

- `server/toss.ts`: `paymentProvider(env, fetch)` — `confirm`(멱등 키 = 주문번호) · `lookup` · `cancel`(멱등 키 = 환불 id).
  `PAYMENTS_ENABLED=true` + 키 접두사(`test_ck_`/`test_sk_`, 라이브는 `live_ck_`/`live_sk_` + `PAYMENTS_LIVE_APPROVED=true`)가
  갖춰지지 않으면 `ready=false`이고 **어떤 호출도 나가지 않는다**. 응답은 통화·금액까지 검증하고, 못 받으면 503(“다시 결제하기
  전에 상태를 확인”)이다.
- `api/payments.ts`: `config`(공개 키·모드만) · `confirm` · `lookup` · `cancel`(관리자만). 세션 토큰 필수.
- 프로덕션·CI는 결제사 미설정 상태이므로 `config`는 `ready:false`이고 승인·취소는 503이다 — 결제는 지금도 기록 결제로 남는다.
- 남은 연결점과 이 구조가 **지금 지키지 못하는 것**은 `결제_연동.md`에 적었다(주문 단위 인가, 결제창 SDK와 CSP).

## D. 화면

- 고객 거래 상세: 영수증 줄에 **주문번호**(`[data-order-id]`)와 상태 태그(`[data-payment-status]`), 실패한 직전 주문 안내
  (`[data-payment-failed]`), 환불 카드는 **환불 내역**(여러 건)으로.
- 관리자 정산 감독: **정산 내역** 카드(`[data-settlement]`) — `총액 − 환불 − 수수료 = 지급액`과 환불 대기 표시, 그 자리에서
  부분 환불 등록(`aria-label="환불 금액"`·`"환불 사유"`, `[data-add-refund]`).
- 지급 대기·파트너 정산·현황 지급 대기의 지급액이 `settlementFor().payable`을 쓴다(환불이 반영된 금액).
- 현황의 환불 대기 카드 문구가 부분 환불을 포함하도록 바뀌었다("예약금" 고정 표기 제거).

## E. 하지 않은 것

- **결제창(SDK) 연동**: 토스 결제창은 외부 스크립트라 지금 CSP(`script-src 'self'`)에서 막힌다. 가맹점 키·CSP 허용·복귀 처리는
  다음 단계이고, 그때 이 라운드의 `confirm`이 그대로 쓰인다(`결제_연동.md`).
- **주문 단위 인가**: 스냅샷이 마켓플레이스 한 덩어리라 서버가 주문 소유자를 판정하지 못한다 — 로그인 계정이면 남의 주문 승인을
  대신 호출할 수 있다(돈이 새지는 않지만 적어 둔다).
- 자동 환불(결제사 취소를 도메인이 직접 호출)·부분 환불의 세금계산서 반영·환불 사유 유형화.
