# 28-65 감사 결과 (GPT 역할)

> 대상: `28-65/` (main `2c27089`, 라이브 https://bandut-partner-platform.vercel.app)
> 방법: 코드를 직접 읽고, 주장에 대해 **반증 탐침을 실행해** 확인했다. 추정과 실측을 구분해 적는다.

이번 라운드는 "약속과 실제 코드를 맞춘다"를 내걸었다. 그래서 감사도 같은 잣대로 했다 —
**28-65가 주석에 적은 보장이 코드에서 실제로 성립하는가.** 넷 중 셋이 성립하지 않는다.

## 28-65-01 (상) 가명본 구조 검사가 한 겹 아래로 내려가지 않는다

`assertPseudonymousShape`(`src/domain/platform.ts:147`)의 문서 주석은 이렇게 약속한다(`:145`):

> 컬렉션을 통째로 통과시키는 실수 자체를 불가능하게 만든다 — **새 필드가 생기면 기본이 "제외"다.**

**한 겹 아래에서는 거짓이다.** 검사는 각 행의 최상위 키만 허용 목록과 대조하고, 값이 객체여도
그 안으로 들어가지 않는다. 그런데 spec 목록(`:3358`)에는 중첩 객체를 키로 허용하는 항목이 둘 있다:

```ts
['estimates', [...PSEUDONYMOUS_STORED_ESTIMATE_KEYS, 'estimate']],   // estimate 안은 검사 안 함
['jobs',      [...PSEUDONYMOUS_JOB_KEYS,             'payout']],     // payout 안은 검사 안 함
```

**탐침을 실행해 확인했다.** 아래 두 경우가 모두 **통과한다**(`toThrow()` 기대가 2/2 실패):

```ts
// 1) 견적 메모에 실명·전화번호가 들어간 경우
estimates: [['E-1', { breakdown:{}, revision:1, submittedAt:'x',
  estimate: { requestId:'R-1', partnerId:'P-1', memo:'고객 김하늘 010-1234-5678 자택' } }]]
//  → assertPseudonymousShape 통과 ❌

// 2) 지급 계좌에 예금주가 들어간 경우
jobs: [{ requestId:'R-1', partnerId:'P-1', payout:{ paidAt:'x', amount:1, holder:'박준서' } }]
//  → assertPseudonymousShape 통과 ❌
```

`memo`는 28-62-01이 **"자유 서술(memo·reason)은 목록에 없다"**고 명시하며 막았다고 선언한 바로 그 필드다.
`payout`의 예금주는 28-61-02가 **"자체 검사가 잡아낸 경로"**라고 적어 둔 필드다(`:132` 주석).
지금은 조립부가 `pick(...)`을 쓰고 있어 실제로 새지는 않는다 — 그러나 **구조 검사는 그것을 확인해 주지 않는다.**
조립부 한 줄이 전개(`{...b.estimate}`)로 바뀌면 두 겹 중 한 겹이 통째로 침묵한다.

값 대조(`assertNoRealIdentifiers`)가 남지만 그건 **아는 이름만** 잡는다. 파기된 계정의 이름,
제3자 이름, 주소 문구는 목록에 없어 통과한다. 구조 검사는 원래 "이름을 몰라도 막는" 층이었는데
그 층이 중첩 아래에서 없다.

같은 함수의 `:164`도 같은 성격이다:
```ts
if (rec === null || typeof rec !== 'object' || Array.isArray(rec)) continue
```
28-64-02가 없앤 "배열이면 `continue`"가 형태만 바꿔 남아 있다. 조용히 건너뛰는 경로는 검사처럼 보이지만 검사가 아니다.

**상으로 두는 이유**: 이 앱에서 유일하게 브라우저를 떠나는 산출물이 이 파일이고,
"두 겹"이라는 설계 주장이 여기서 한 겹으로 줄어 있다.

## 28-65-02 (중) 열람권 내보내기의 통째 전개가 절반만 끊겼다

`exportCustomerData`(`:3410`)에 28-65가 붙인 주석(`:3417`):

> 28-64-03: **통째 전개를 끊는다** — 새 필드가 조용히 따라오지 않게 담을 것을 고른다.

실제로 필드를 고르도록 바뀐 것은 `requests`와 `claims` **둘뿐**이다. 같은 함수 안에 통째 전개가 셋 남아 있다:

```
:3428  payments: ...map((p) => ({ ...p })),
:3429  refunds:  ...map((f) => ({ ...f })),
:3430  reviews:  ...map((v) => ({ ...v })),
```

`exportPartnerData`도 같다:
```
:3468  jobs:    ...map((j) => ({ ...j })),
:3469  reviews: ...map((v) => ({ ...v })),
```

**지금 새는 값은 확인되지 않았다.** `Payment`·`Refund`·`Review`의 현재 필드를 전부 읽어 봤고
(`receiptNo`·`reason`·`text`·`reply`), 정보주체 본인 범위의 값이라 열람권 대상이 맞다.
그래서 **유출이 아니라 약속 위반**으로 적는다 — 주석은 "끊었다"고 하고 코드는 절반만 끊었다.
`Job`에 필드가 하나 늘면 파트너 내보내기에 조용히 따라 들어가고, 아무도 잡지 않는다.
28-64-02와 정확히 같은 실패 형태다.

## 28-65-03 (중) `isKnownError`가 손으로 유지하는 목록이고, 새로 넣은 테스트가 그 목록을 그대로 베꼈다

`src/ui/format.ts:28`의 `isKnownError`는 도메인 오류를 하나씩 열거한다. 저장소의 도메인 오류 클래스는 **9개**인데
목록에는 **8개**만 있다. 빠진 것은 `PlatformReopenError`(`src/domain/store.ts:15`, `:172`에서 throw).

호출부는 전부 이 모양이다(예: `CustomerHome.tsx:41`):
```ts
catch (err) {
  if (isKnownError(err)) setError(err.message)
  else throw err          // ← 목록에 없으면 ErrorBoundary로 올라가 화면 전체가 교체된다
}
```

**지금은 도달하지 않는다.** `PlatformReopenError`의 두 호출부(`platform.ts:807`, `:1433`)가 모두
앞에서 상태를 검사하고 들어가므로 실제로는 던져지지 않는다. 그래서 중이다.
다만 이 클래스는 도메인의 공개 API이고, 28-66에서 서버 층이 새 호출 경로를 만들면 그날 되살아난다.

**진짜 문제는 목록이 아니라 검사 방식이다.** 28-65가 새로 넣은 테스트(`src/ui/format.test.ts:52`)는
**`isKnownError`가 나열한 것과 똑같은 5개를 다시 나열해** 참을 확인한다. 목록에서 빠진 것을 이 테스트는
영원히 못 잡는다 — 코드가 하는 일을 테스트가 되풀이할 뿐, 해야 할 일을 확인하지 않는다.
**28-64-01(죽은 코드를 검사해 초록을 만들던 게이트)과 같은 실패 형태가, 그 항목을 고친 라운드에서 재발했다.**

같은 성격: `SECURITY_AUDIT_ACTIONS`(`platform.ts:102`)는 `auth.ts`의 `emit(...)` 문자열과 손으로 맞춘다.
지금은 5개가 정확히 일치하는 것을 확인했다(`auth.ts:422,473,478,551,561,688`). 컴파일러가 지켜 주는 것은 없다.

## 28-65-04 (중) 라운드 스냅샷 방식의 비용이 이제 숫자로 나왔다

푸시할 때마다 GitHub이 경고한다: **기본 브랜치 취약점 200건(critical 40 · high 40 · moderate 120).**
어디서 나오는지 직접 셌다.

```
저장소의 package-lock.json  : 65개
그중 내용이 다른 것         : 2개            ← 나머지 63개는 바이트 단위 사본

28-1 ~ 28-40 (40개, 구 락파일)  npm audit → 5 vulnerabilities (3 moderate, 1 high, 1 critical)
28-41 ~ 28-65 (25개, 현 락파일) npm audit → found 0 vulnerabilities
```

40 × (critical 1 + high 1 + moderate 3) = **critical 40 · high 40 · moderate 120.**
GitHub이 세는 200건과 정확히 일치한다.

**즉 이 저장소의 보안 경고 200건은 전부, 40번 복사된 하나의 낡은 락파일에서 나온다.
살아 있는 코드의 취약점은 0이다.** 진짜 경고가 오는 날 그것을 200건의 잡음 속에서 구분할 방법이 없다 —
보안 신호가 기능을 잃었다.

부수 비용도 같은 뿌리다: 추적 파일 4,304개, 라운드마다 +81개.
28-66부터 서버 코드·DB 스키마·마이그레이션이 붙으면 라운드당 복제량이 다시 늘어난다.

## 28-66 권고

사용자 결정 두 가지를 반영한다 — **코드는 하나로, 문서만 라운드별** / **서버 경계부터 먼저**.

1. **01**: 구조 검사를 재귀로. 중첩 spec(`estimates.estimate`·`jobs.payout`)을 명시하고,
   조용한 `continue` 경로를 없앤다(검사 못 하는 형태는 통과가 아니라 실패여야 한다).
   위 탐침 2건을 그대로 회귀 테스트로 넣는다.
2. **02**: 두 내보내기의 남은 통째 전개 5줄을 전부 필드 선택으로. 허용 키를 상수로 빼서
   가명본 허용 목록과 같은 방식으로 관리한다.
3. **03**: 목록을 손으로 유지하지 않게 만든다 — 도메인 오류에 공통 기반(또는 등록부)을 두고,
   **"도메인이 내보내는 모든 Error 하위 클래스가 `isKnownError`에 참이다"**를 목록을 베끼지 않고 확인하는 테스트를 넣는다.
4. **04**: 저장소 재구성. `28-65/`의 소스를 루트로 올리고, `28-N/`에는 문서 3종만 남긴다.
   락파일 1개 → 경고 200건이 실제 신호로 돌아온다. `vercel.json`·`gates.yml`·`deploy-check.yml`·
   `dependabot.yml`·라운드 표기가 전부 여기에 묶여 있으므로, **배포가 끊기지 않는 것을 게이트로 증명**하며 옮긴다.
