# 28-65 수정사항 — 서버로 가기 전 바닥 다지기

28-64 감사 4건을 전부 반영했다. 이번 라운드의 성격은 **약속과 실제 코드를 맞추는 것**이다.
28-59~28-64가 세운 "게이트가 지킨다"·"가명본은 두 겹"·"열람권은 대칭"·"감사 로그는 불변 기록"이
각각 어디서 깨져 있었는지 코드로 확인하고 고쳤다.

사용자 결정으로 다음 방향은 **백엔드 개통(28-66~)** 이다. 그래서 이번 라운드는
"CI 없이 마이그레이션을 시작하지 않는다" + "지금은 무해하지만 서버가 생기는 날 사고가 되는 범위 오류를 먼저 끈다"에 맞췄다.

## 이번 라운드가 전제로 확인한 사실 — 서버가 없다

소스 전체에 `fetch`·XHR·WebSocket이 0건이고, 모든 상태는 브라우저 `localStorage`에만 있다.
그래서 역할(고객/파트너/관리자) 분리는 **한 브라우저 안의 화면 분리**이지 테넌트 경계가 아니다.
28-64-03(열람권 범위)을 "교차 유출(상)"이 아니라 **중**으로 매긴 근거이며, 그럼에도 서버 전에 반드시 고쳐야 하는 이유다.

## 28-64-01 (상) 게이트가 거짓 초록이라 실제 버그가 배포됐다

**원인.** `test:node` 게이트가 도는 유일한 파일이 `scripts/format.mjs`를 검사했는데, 그 파일을 쓰는 앱 코드가 없었다.
`# pass 7`은 전부 죽은 코드에서 나왔다. 하필 그 파일이 28-1-04(달력에 없는 날짜 거부)를 구현·검증하고,
실제 배포되는 `src/ui/format.ts`에는 그 가드가 없었다.

**수정.**
- `scripts/format.mjs`·`tests/node/format.test.mjs` 삭제, `package.json`에서 `test:node` 제거(`check`에서도).
- `src/ui/format.ts`의 `koreanDate`가 도메인의 `isValidDateStr`(`src/domain/date.ts`)를 쓰게 했다 — 중복 구현 제거.
- `src/ui/format.test.ts`에 옮겨온 케이스 + `krw`·`isKnownError` 테스트 추가(둘 다 그전까지 테스트 0건이었다).
- `vitest.config.ts`의 `include`를 `src/**/*.test.{ts,tsx}`로 넓혀 `.tsx` 테스트가 조용히 사라지지 않게 했다.
- **`.github/workflows/gates.yml` 신설** — push/PR에서 `check` → `npm audit` → `e2e` → `visual-check`를 전부 돌린다.
  넷 다 차단(blocking)이고 `continue-on-error`는 쓰지 않는다. 라운드 폴더는 `vercel.json`에서 읽어 라운드마다 고칠 필요가 없다.
- `scripts/e2e-journey.mjs`·`scripts/visual-check.mjs`에 **dist 신선도 가드** — `src/` 최신 mtime이 `dist/index.html`보다
  새로우면 exit 2. 옛 빌드에 초록을 주지 않는다.

**회귀 증명(수정 전).**
```
FAIL  src/ui/format.test.ts > 달력에 없는 날짜는 롤오버하지 않고 원문을 돌려준다 (28-1-04)
AssertionError: expected '3월 3일 화요일' to be '2026-02-31'
```
**신선도 가드 증명.** 소스를 건드린 뒤 실행 → `e2e 실제 종료 코드: 2`, `visual-check 실제 종료 코드: 2`.

## 28-64-02 (상) 가명본 구조 검사가 요청 컬렉션에 닿지 못했다

**원인.** `assertPseudonymousShape`가 `out[path]` 단일 조회라 경로 탐색이 없었다. 요청은 `out.store.requests`에
중첩돼 있어 `out['store.requests']`가 `undefined` → 검사를 통째로 건너뛰었다. `photoCount`가 허용 목록 밖인데
아무도 잡지 못하고 있던 것이 그 증거다. `[id, obj]` 쌍 컬렉션(`estimates`·`profiles`)은 "배열이면 continue"에 걸려
영영 검사되지 않았고, `settings`는 객체라 건너뛰었고, `daysOff`는 통째로 통과했다.

**수정.**
- `assertPseudonymousShape`에 **점 경로 탐색** + `[id, obj]` 두 번째 원소 검사 + 단일 객체 검사를 넣었다.
- spec 목록에 `store.requests`·`profiles`·`settings`를 추가하고 `estimates`의 빈 목록을 실제 허용 키로 채웠다.
- `PSEUDONYMOUS_REQUEST_KEYS`에 실제 방출 키(`customerId`·`customerName`·`region`·`description`·`photoCount`)를 명시.
- `PSEUDONYMOUS_PROFILE_KEYS` 신설. `daysOff`는 `[partnerId, string[]]` 형태로 재조립(통째 통과 제거).
- `assertNoRealNames` → **`assertNoRealIdentifiers`**로 넓혔다: 이름 + 전화번호 + 사업자등록번호.
  숫자 식별자는 구분자를 지운 형태로도 대조한다(`010-1234-5678` ↔ `01012345678`). 2자 이하 토큰은 오탐 방지로 제외.
  기존 `assertNoRealNames`는 호환 래퍼로 남겼다.
- `PlatformContext`가 `a.phone`·`a.bizNo`도 넘기고, **effect가 아니라 렌더 중에 대입**한다 —
  `initPlatform`이 첫 렌더 중 돌리는 sweep/prune이 `record()`를 부를 때 식별자가 비어 있던 문제를 없앤다.
- `city()`를 **실패 시 닫히는** 방식으로: 알려진 시/도로 시작하고 숫자가 없을 때만 `시/도 + 시군구`를 남기고,
  그 외에는 `'[가명 처리] 지역'`으로 떨어뜨린다.

**회귀 증명(수정 전).** 신규 12건 중 10건이 빨간불이었다. 대표:
```
× 중첩 경로(store.requests)의 허용 밖 키를 잡는다 — 이전에는 통째로 건너뛰었다
× 공백 없이 입력한 상세 주소는 그대로 남지 않는다
× 전화번호가 결과에 남으면 실패시킨다 — 구분자가 달라도 잡는다
```

## 28-64-03 (중) 열람권 범위 — 서버가 생기는 날 사고가 될 것을 지금 끈다

**원인.** `exportPartnerData`에서 `visits`·`jobs`·`reviews`는 전부 파트너로 좁히는데 `claims`만 안 좁혔다.
`ids`는 "입찰했거나 철회한" 요청 전부라, 낙찰 실패한 파트너가 낙찰 파트너의 자유 서술 `partnerReply`를 받았다.
대칭으로 `exportCustomerData`는 자체 검사가 없고 `{...r}`/`{...c}` 통째 전개라 관리자 내부 메모 `Claim.resolution`이
정보주체에게 그대로 갔다.

**수정.**
- `claims`를 `reviews`와 동일하게 수행 파트너 기준으로 좁혔다(`Claim`에 `partnerId`가 없다).
- `exportCustomerData`를 필드 선택 방식으로 바꿨다. `resolution`은 담지 않고, 사진은 데이터 URL 대신 개수만.
  `customerId`는 정보주체 본인 식별자라 남겨 범위가 좁혀졌음을 결과에서 확인할 수 있게 했다.
- `exportCustomerData`에도 `assertNoRealIdentifiers`를 걸었다(본인 이름은 제외 목록).

**회귀 증명(수정 전).**
```
× 낙찰 실패한 파트너의 내보내기에 남의 분쟁 기록이 들어가지 않는다
    expected [ { id: 'CL-0001', …(5) } ] to have a length of +0 but got 1
× 고객 내보내기에 관리자 내부 처리 메모가 들어가지 않는다
    expected '{"exportedAt":…' not to contain '관리자 내부 처리 메모입니다'
```
> 첫 시도에서 `customerId` 자리에 이름을 넣어 **0건을 검사하는 공허한 통과**를 만들었다.
> 탐침으로 확인해 실제 데이터를 보도록 고친 뒤에야 위 실패가 드러났다.

## 28-64-04 (중) 감사 로그가 남겨야 할 것을 지웠다

**원인 1 — 병합이 내용을 덮어썼다.** 병합 키는 `actor/action/target/by`인데 `detail`은 키가 아니면서 최신 값으로
덮어썼다. `설정 변경`은 target이 상수 `'settings'`이고 바뀐 필드 목록이 `detail`에 들어가, 5분 안 두 번의 설정 변경이
한 줄로 접히며 **첫 변경 내역이 사라졌다.**

**원인 2 — 상한 축출이 보안 이력을 먼저 버렸다.** `actor === 'system'`을 먼저 버렸는데 인증 보안 이벤트가
전부 `system`이라, 주석의 의도와 반대로 평범한 관리자 작업 폭주가 잠금 이력을 지웠다.

**수정.**
- 병합에서 `detail`이 다르면 접지 않는 것을 **기본값**으로 삼되, `PROGRESS_DETAIL_AUDIT_ACTIONS`(현재 `로그인 실패`)에
  한해 진행 표시 detail을 무시하고 접는다. 기본이 "접지 않음"이라 새 행위가 생겨도 내용을 잃지 않는다(안전한 방향으로 실패).
- 축출을 순수 우선순위가 아니라 **등급별 예약분**으로 바꿨다(`AUDIT_RESERVE = 200`).
  관리자 기록과 보안 이벤트에 각각 예약분을 주고 **예약분을 넘긴 쪽에서 오래된 것부터** 버린다.
  순수 우선순위는 어느 방향이든 반대 사고를 낳는다 — 이건 검증에서 실제로 확인했다(아래).
- 보관 정책에서 파싱 불가 `at`을 제거한다(이전에는 `true`를 돌려줘 영구 잔류 + 병합 영구 차단).
- `auditWithMeta()`를 더해 병합 여부를 호출자가 구분할 수 있게 했다. `audit()`는 그 위의 얇은 래퍼다.

**중간에 스스로 잡은 과잉 교정.** 처음엔 `detail`을 무조건 병합 키에 넣었는데, e2e가 지적했다:
```
FAIL  로그인 실패 4회가 한 줄 ×4로 접힘
```
로그인 실패의 `남은 시도 N회`는 내용이 아니라 진행 표시라 접히는 게 맞다. 규칙을 좁혀 둘 다 만족시켰다.

**축출 정책은 양방향으로 검증했다.**
- 분산 무차별 로그인(대상을 매번 바꿔 접기를 회피) → 관리자 기록 10건 전부 생존.
- 평범한 관리자 작업 폭주 → `로그인 잠금`·`비밀번호 변경` 생존.
