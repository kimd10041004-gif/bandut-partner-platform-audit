# 28-83 감사결과 (GPT 감사자 역할)

대상: `687e730`(#227) + `3e9c014`(#228). 28-82 감사 4건을 받아 가드를 강화한 라운드다.

28-83은 **옳은 문제를 골랐다.** 28-82의 가드는 "손으로 적은 목록이 CI를 좌우한다"는, 이 저장소가
28-78-04에서 이미 이름 붙인 함정을 API 목록에서 되풀이하고 있었고, 28-83은 그것을 도메인에서
유도하는 방향으로 옮겼다. 구현 중에 첫 정규식이 여섯 중 넷만 잡는 것을 **스스로 발견해** 괄호를
세는 방식으로 바꾸고 유도 완전성 자체를 테스트로 고정한 것은, 이 루프가 바라는 그 태도다.

그런데 그 교훈이 **끝까지 적용되지 않았다.** 아래 01·04는 같은 문장으로 요약된다 —
*유도의 양 끝(어디서 읽는가 · 어디서 출발하는가)이 여전히 손으로 적힌 경로다.*
02는 28-82 감사 02가 지적한 것이 절반만 닫혔다는 것이고, 03은 가드가 이름을 볼 뿐 의미를 보지 않는다는 것이다.

모든 항목은 **수정 전 코드에서 실제로 실행해** 확인했고 출력을 그대로 인용한다.

## 01 (상) 유도의 **출처**가 파일 하나로 손에 적혀 있다 — 28-83-03이 넓힌 것의 반대편

`src/ui/customerSurfaces.test.ts`:

```ts
const DOMAIN = 'src/domain/platform.ts'
```

`derivedSeedSensitive()`는 **이 파일 하나만** 읽는다. 그런데 같은 라운드의 28-83-03은 호출자 쪽
도달 범위를 `src/ui` → `src` 전체로 넓히면서 `src/domain`을 통째로 잘라냈다:

```ts
if (target.startsWith(DOMAIN_DIR)) continue          // 정의하는 쪽은 검사 대상이 아니다
```

두 결정이 합쳐지면 **`src/domain`은 검사 대상에서 빠지는데, 그 안에서 진실을 읽는 곳은 파일 하나**다.
`src/domain`에는 30개가 넘는 모듈이 있다:

```
$ ls src/domain/
auth.ts  csv.ts  date.ts  errors.ts  estimate.ts  hash.ts  jobStatus.ts  money.ts
platform.ts  ports/  ports.ts  ports-testkit.ts  replicator.ts  schedule.ts
settlement.ts  store.ts  types.ts   (+ 각 .test.ts)
```

시드에 민감한 집계가 `settlement.ts`나 새 `stats.ts`에 생기면:

- `derivedSeedSensitive()`가 못 본다 → `publicNames`에 안 들어간다
- 「금지 목록이 도메인에서 유도한 집합을 모두 담는다」는 **빈 배열로 통과**한다
- 「유도가 하나도 빠뜨리지 않는다」도 `platform.ts` 안에서만 세므로 **그대로 통과**한다
- 고객 화면이 그것을 불러도 `SEED_INCLUSIVE`에 없으니 첫 테스트도 통과한다

즉 **28-83이 없애려던 그 공허한 통과가, 한 계층 위에서 그대로 살아 있다.** 28-83의 주석은
"이 목록은 손으로 적은 전부가 아니라, 유도로 못 잡는 것을 더하는 자리"라고 정확히 말하지만,
*유도가 어디를 보는지*는 여전히 손으로 적힌 문자열 하나다.

**제안**: `DOMAIN`을 경로 하나가 아니라 `src/domain/**/*.ts`(테스트 제외) 글롭으로 바꾸고,
`derivedSeedSensitive()`가 파일마다 돌면서 `파일 → 메서드`로 모은다. 완전성 검사도 파일별 합계로
비교한다. 대상 파일이 0건이면 실패시키는 단언을 함께 둔다(28-78-04와 같은 이유).

## 02 (상) 서버 모드 기본값 경로는 **여전히 0건**이다 — 28-82 감사 02가 절반만 닫혔다

28-83-02는 프롭 없이 렌더하는 테스트를 넣었다. 옳은 방향인데, 단언이 **부정형 둘뿐**이다:

```ts
expect(html).not.toContain('data-hero-stats')
expect(html).not.toContain('누적 요청')
```

테스트 환경의 `AUTH_MODE`는 `local`이므로 이것은 "로컬에서는 안 보인다"만 증명한다.
**기본값이 `AUTH_MODE`에 연결돼 있다는 것 자체는 아무도 증명하지 않는다.**

문서(`28-83/수정사항.md`)는 "누가 기본값을 `'server'`로 바꾸거나 `AUTH_MODE` import를 지워도
전부 통과했고"를 고친다고 적었는데, 그 두 변이는 실은 **테스트가 아니라 `noUnusedLocals`가** 잡는다:

```
$ sed -i "s/  authMode = AUTH_MODE,/  authMode = 'local',/" src/features/landing/Landing.tsx
$ npm run check
src/features/landing/Landing.tsx(4,1): error TS6133: 'AUTH_MODE' is declared but its value is never read.
```

`AUTH_MODE`를 계속 쓰면서 서버 모드만 죽이는 변이는 **게이트 전체를 통과한다.**
"서버 모드 지표를 잠시 끄자"는 지극히 그럴듯한 한 줄이다:

```ts
authMode = AUTH_MODE === 'server' ? 'local' : AUTH_MODE,
```

```
$ npm run check
 Test Files  24 passed (24)
      Tests  486 passed | 12 skipped (498)
✓ built in 1.16s
```

**타입 오류 0건, 테스트 486건 전부 통과, 빌드 성공.** 이 상태로 배포하면 서버 모드 랜딩은
지표를 영영 내걸지 않는데 게이트는 초록이다. 28-79~28-82가 네 라운드에 걸쳐 세운 "서버 모드에서는
보여준다"는 쪽 절반이 테스트로 고정돼 있지 않다.

**제안**: 기본값 경로를 **서버 모드에서** 렌더하는 테스트를 더한다. `AUTH_MODE`는 빌드 상수라
`vi.mock('../../app/bootstrap', ...)`로 `'server'`를 주입하고, 프롭 없이 렌더해 `data-hero-stats`가
**있음**을 단언한다(28-83-02의 부정형과 짝이 된다). 그래야 "기본값 = 빌드 상수"가 양방향으로 고정된다.

## 03 (중) 가드는 **이름**을 볼 뿐 **의미**를 보지 않는다

```ts
if (new RegExp(`\\.${api}\\(`).test(src)) offenders.push(...)
```

`.이름(` 이라는 **텍스트**만 본다. 수신자가 `platform`인지 보지 않고, 호출이 그 형태가 아니면 못 본다.
`PartnerCard.tsx`(고객이 업체를 고르는 자리)에서 실제로 확인했다:

```ts
const { partnerSummary } = platform
const s = partnerSummary.call(platform, partnerId)
```

```
$ npx vitest run src/ui/customerSurfaces.test.ts
 Test Files  1 passed (1)
      Tests  4 passed (4)
```

**고객에게 시드가 섞인 실적을 다시 내밀면서 가드는 초록이다** — 28-82-01이 존재하는 바로 그 이유가
되살아난다. 구조 분해 호출은 다소 인위적이지만, 같은 성질의 더 현실적인 경로가 남는다:
고객 화면이 `SEED_INCLUSIVE`에 적힌 이름을 **하나도 부르지 않고** 원자료에서 같은 숫자를 계산하면
(예: 요청 목록을 받아 직접 세면) 가드는 원리적으로 아무 말도 못 한다.

**제안**: 이 가드가 정적 텍스트 검사인 한 완전할 수 없다는 것을 **인정하고 문서에 적는다**
(지금 주석은 완전한 것처럼 읽힌다). 그 위에 값싼 보강 하나: `SEED_INCLUSIVE` 이름이 **식별자로**
등장하기만 해도(호출 형태와 무관하게) 걸리도록 `\b이름\b`로 넓히고, 정당한 예외는 주석 표식으로 면제한다.
가드를 믿게 만드는 것보다 **가드의 한계를 아는 것**이 먼저다.

## 04 (중) 도달 탐색의 **출발점**도 손으로 적혀 있다 — 01과 같은 문장

```ts
const CUSTOMER_DIRS = ['src/features/landing', 'src/features/customer']
```

파일 주석은 이렇게 말한다:

> 새 고객 화면을 만들어도 이 목록은 디렉터리에서 유도되므로 자동으로 포함된다.

**그 두 디렉터리 안에서만 참이다.** 디렉터리 자체는 손으로 적혀 있다. 28-83-03은 *따라가는 범위*를
넓혔지만 *출발하는 자리*는 그대로 뒀다. 실제 도달 집합을 그대로 재현해 보면:

```
도달 파일 수: 18
src/App.tsx 포함? false
features 디렉터리들: src/features/customer, src/features/landing
```

`src/App.tsx`는 **랜딩을 렌더하는 바로 그 파일인데 검사 밖**이다. App이 숫자를 계산해 프롭으로
내려보내면 가드는 못 본다. `src/features/shared/` 같은 새 디렉터리도 마찬가지다.

**제안**: 출발점을 디렉터리 목록이 아니라 **역방향**으로 잡는다 — 고객 라우트의 진입 컴포넌트
(`App.tsx`의 고객 분기)에서 시작해 도달하는 전부를 고객 경로로 본다. 그러면 "고객 화면"의 정의가
관례가 아니라 **라우팅이라는 근거**를 갖는다. 최소한 `CUSTOMER_DIRS`에 `src/App.tsx`를 더하고,
디렉터리를 손으로 적었다는 사실을 주석에서 솔직히 밝힌다.

## 이번 감사에서 **문제 삼지 않은 것** (조용히 넘기지 않는다)

- **완전성 테스트의 문자열 앵커** (`excludeSeeded\?: boolean`). 서식이 바뀌면 깨질 수 있지만,
  깨질 때 **시끄럽게** 깨진다(파서 수 ≠ 파일 수 → 실패). 거짓 안심이 아니라 거짓 경보 쪽으로
  치우쳐 있어 안전한 설계다. 문제 없음.
- **`private reviewsOf`를 `total`에 세고 `publicNames`에서 빼는 것.** 의도대로다.
- **28-83-04(문서 분류 정정)**. 실행되는 것이 없고 내용도 맞다.
- **§5 후속 PR(#228)의 관례.** 28-73에서 세운 대로 같은 라운드 안에서 채웠고, 번들 해시 일치라는
  근거를 정확히 그 범위까지만 주장했다. 좋다.
- **서버 모드 익명 방문자 문제.** 28-82가 발견하고 28-82·28-83이 연달아 이월했다. 이것은 28-83의
  결함이 아니라 **아직 열려 있는 설계 과제**다(공개 집계 엔드포인트 + "무엇까지 공개하는가" 판단).
  다만 **두 라운드 연속 이월**이라는 사실은 기록해 둔다 — 02와 합치면, 서버 모드 쪽 절반은
  지금 테스트로도 화면으로도 닫혀 있지 않다.
