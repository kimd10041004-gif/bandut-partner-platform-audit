# 28-83 수정사항 — 가드가 자기 자신을 지키게

**대상 감사**: `28-82/감사결과.md` 4건. 브랜치 `round-28-83`, 라운드 문자열 `28-83`, 버전 `28.83.0`.

28-82는 "고객에게 보이는 숫자"를 전수조사하고 그 결과를 가드 테스트로 고정했다. 좋은 방향이었는데,
**그 가드가 자기 자신을 지키는 방식**이 다시 손으로 적은 목록이었다. 이번 라운드는 가드를 고친다.

---

## 28-83-01 (상) 금지 API 목록을 도메인에서 **유도**해 하한으로 검사한다

### 무엇이 문제였나

`SEED_INCLUSIVE`가 상수 한 줄이라, 시드에 민감한 집계가 새로 생기고 거기 적히지 않으면 고객 화면이
그것을 마음껏 불러도 **가드는 초록으로 남았다**. 28-78-04가 이름 붙인 "규칙이 아니라 목록이 CI를
좌우한다"가, 파일 목록에서는 피해 놓고 API 목록에서 되풀이된 것이다.

재현해서 확인했다 — 도메인에 시드 민감 집계(`categoryCounts`)를 하나 더하고 `CustomerHome`이 그것을
부르게 한 뒤 **28-82의 가드를 돌리면**:

```
Tests  2 passed (2)      ← 새 집계가 고객 화면에서 불리는데 가드는 통과
```

### 무엇을 했나

도메인에는 "시드에 민감한 집계"의 **실제 집합**이 이미 있다 — `{ excludeSeeded?: boolean }`을 받는
메서드들이다. 그것을 뽑아 `SEED_INCLUSIVE`가 **상위집합**인지 검사한다.

**유도로 대체하지 않고 하한으로만 쓴다.** `adminOverview`는 시드를 뺄 방법 자체가 없어 옵션을 받지
않으므로, 유도 목록으로 갈아치우면 오히려 놓친다. 손으로 적은 목록은 "유도로 못 잡는 것을 더하는
자리"로 줄었다.

### 유도가 **덜 잡는 것**까지 막는다

처음 구현한 정규식은 여섯 중 **넷만** 잡았다. `today: string = todayUTC()`의 괄호가 `[^)]*`를 끊어
`partnerSummary`와 `partnerCancelCount`의 시그니처가 잘렸기 때문이다. 유도가 조용히 덜 잡으면
하한 검사가 빈 배열로 통과하고, **고치려던 실패로 그대로 돌아간다.**

그래서 두 가지를 했다: 인자 목록을 정규식이 아니라 **괄호를 세어** 끝을 찾고, 파일에 적힌
`excludeSeeded?: boolean` 개수와 파서가 센 개수가 같은지 별도 테스트로 확인한다.

```
유도(공개): ['allReviews', 'bidStats', 'partnerCancelCount', 'partnerSummary', 'reviewStats', 'statusCounts']
유도 전체: 7 / 파일의 excludeSeeded?: boolean 개수: 7
```

### 회귀 (수정 전 실패 인용)

같은 재현 상태에 **28-83의 가드**를 얹으면:

```
× 금지 목록이 도메인에서 유도한 집합을 모두 담는다 (28-83-01)
  AssertionError: 시드에 민감한 집계가 새로 생겼습니다 — SEED_INCLUSIVE에 더하고,
  고객 경로에는 public* 대응물을 만드세요: expected [ 'categoryCounts' ] to deeply equal []
      Tests  1 failed | 3 passed (4)
```

가드가 **새 집계를 이름으로 지목한다.**

## 28-83-02 (중) 기본값 경로를 **실행하는** 테스트

28-82의 SSR 테스트 세 개는 언제나 `authMode`를 넘겼다. 그런데 프로덕션(`App.tsx:206`)은 프롭을 넘기지
않고 **기본값에 의존한다** — 즉 기본값 경로를 실행하는 테스트가 0건이었다.

프롭 없이 렌더하는 테스트를 더했다(`App.tsx`가 하는 그대로). 테스트 실행 시 `AUTH_MODE`는 `local`이므로
지표가 없어야 한다.

### 회귀 (수정 전 실패 인용)

기본값을 `'server'`로 뒤집어 확인했다:

```
× 프롭 없이 렌더하면 기본값(AUTH_MODE)을 따른다 — 로컬 빌드에서는 지표가 없다 (28-83-02)
  AssertionError: expected '<div class="landing">…' not to contain 'data-hero-stats'
      Tests  1 failed | 3 passed (4)
```

**28-82의 세 테스트는 그대로 통과한다**(`3 passed`) — 자기 값을 넘기니 기본값이 무엇이든 상관없다.
그 대비가 이 항목이 메우는 구멍이다.

## 28-83-03 (중) 가드의 도달 범위를 `src` 전체로 (도메인만 잘라낸다)

28-82는 `src/ui`만 따라갔다. 규칙이 아니라 관례였고, `src/app`이나 다른 feature에 "요약 숫자를 만들어
주는 헬퍼"를 두면 시야 밖이었다 — `Landing`부터가 `app/bootstrap`에서 `AUTH_MODE`를 가져온다.

이제 상대 경로 import를 **전부** 따라가고 `src/domain`만 잘라낸다. 도메인은 이 집계들을 **정의하는**
쪽이지 화면을 대신해 **부르는** 쪽이 아니므로, 따라가면 정의부가 통째로 위반으로 잡힌다 — 잘라내는
이유가 관례가 아니라 근거다.

## 28-83-04 (하) 전수조사 문서의 `getProfile` 분류 정정

28-82는 `getProfile`을 "(ㄴ) 운영 설정 — 관리자가 CMS로 정한 내용"에 넣었는데 틀렸다. 파트너가 자기
마이페이지에서 `updateProfile`로 쓴 내용이고, 없으면 `DEFAULT_PARTNER_PROFILE`로 떨어진다. 관리자는
이 내용을 정하지 않는다.

**조치가 없다는 결론은 그대로**이고 이유만 고친다 — (ㄴ-2) "파트너가 직접 쓴 내용 — 시드도 아니고
CMS도 아니다"로 갈래를 나누고, 「남은 경계」의 프로필 항목과 같은 사안임을 밝혔다. 조사 문서가 다음
라운드의 지도라 분류가 맞아야 한다.

## 하지 않은 것 (조용히 빼지 않는다)

- **서버 모드 익명 방문자 문제** — 28-82가 발견해 넘긴 것. 세션 없이 읽는 공개 집계 엔드포인트가
  필요하고 "무엇을 공개할 것인가"라는 보안 판단이 따른다. 이번 범위(감사 4건) 밖이고 여전히 열려 있다.
- **`authMode` 프롭 자체를 없애는 것** — 없애면 렌더링 테스트가 두 모드를 볼 수 없다. 28-83-02가
  기본값 경로를 덮으면서 프롭의 대가는 갚았다고 본다.
- **가드가 "public\* 대응물이 실제로 있는지"까지 확인하는 것** — 지금은 금지만 한다. 대응물 없는
  금지는 막다른 길이 될 수 있지만, 그 검사는 이름 규칙에 기대야 해서 또 다른 목록이 된다. 남겨 둔다.
