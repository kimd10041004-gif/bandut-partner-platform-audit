# 29-19 — 배포된 주소를 브라우저로 연다 · 배포 확인의 오분류

## 0. 개발 컨테이너는 프리뷰로 나갈 수 없다

사장님이 "너는 검증할 수 있어"라고 하셔서 프록시부터 제대로 확인했다. 정책 거부가 맞다.

```
curl: (56) CONNECT tunnel failed, response 403

recentRelayFailures:
  kind: connect_rejected
  detail: gateway answered 403 to CONNECT (policy denial or upstream failure)
  host: bandut-partner-platform-git-r-fe6a07-...vercel.app:443
```

`/root/.ccr/README.md` 는 이 경우를 "조직 정책이 막은 것 — 우회하지 말고 보고하라"로 적어 뒀다.
Vercel MCP 의 `web_fetch_vercel_url` 도 이 프로젝트를 못 본다(계정이 이 팀에 연결돼 있지 않다).

**그런데 GitHub 러너는 그 밖에 있다.** 28-63 이 `deploy-check` 를 만든 이유가 정확히 그것이었고,
29-5 가 거기에 `base_url` 을 열어 뒀다. 그 길로 쟀다.

## 1. 배포 확인이 틀린 답을 내고 있었다

`deploy-check` 를 프리뷰 주소로 돌린 결과다.

```
서버 환경변수 준비: no — DATABASE_URL 없음 (HTTP 503)
{"ok":false,"error":"문자 발송이 아직 연결되지 않아 가입과 비밀번호 찾기를 받을 수 없습니다."}
```

판정과 응답 본문이 어긋난다. 분류가 이렇게 돼 있었다.

```bash
if [ "$code" = "503" ] && printf '%s' "$body" | grep -q '아직 연결되지'; then
  ready=no; detail="DATABASE_URL 없음"
```

`아직 연결되지` 가 **두 문구에 다 들어 있다.**

```
"서버 저장소가 아직 연결되지 않았습니다"     ← DATABASE_URL 없음
"문자 발송이 아직 연결되지 않아 …"           ← 인증번호 전달 불가
```

프리뷰는 뒤엣것으로 답했는데 앞엣것으로 읽혔다. **설정이 멀쩡한데 없다고 말한 것**이라, 사람을
엉뚱한 곳으로 보내는 종류의 오류다. 29-17-2(화면이 운영과 비교했다고 말한 것)와 같은 급이다.

각 문구의 고유한 부분으로 가르고, 인증번호 전달 불가를 **따로 된 한 줄**로 뒀다.

## 2. 그 오분류가 가리고 있던 사실

핸들러는 이 순서로, **DB 에 닿기 전에** 본다(`server/handlers/auth.ts`).

| 순서 | 검사 | 프리뷰에서 |
|---|---|---|
| 1 | `DATABASE_URL` 없음 | 안 걸렸다 → **설정돼 있다** |
| 2 | `ADMIN_PASSWORD` 없음·8자 미만·시연값 | 안 걸렸다 → **제대로 있다** |
| 3 | `SIGNUP_CODE` 없음·12자 미만 | 안 걸렸다 → **제대로 있다** |
| 4 | 인증번호 전달 불가 | **여기서 걸렸다** |

세 값은 전부 제대로 설정돼 있다. 막힌 것은 인증번호를 전달할 방법 하나다.

`server/authSafety.ts` 가 프리뷰에서 `AUTH_DEV_OTP === 'on'` 일 때만 화면에 번호를 띄운다.
그 값이 없다. **이것이 프리뷰에서 가입 왕복을 못 하던 이유다** — 주소도 계정도 아니었다.

사장님이 Vercel 의 **Preview 환경에만** `AUTH_DEV_OTP=on` 을 넣으시면 열린다. 비밀값이 아니다.
운영에는 넣지 않는다 — 운영에서는 `devOtpAllowed` 가 그 값을 아예 보지 않는다(`isProduction`
에서 먼저 false 를 준다).

## 3. 배포된 화면을 브라우저로 연다

`scripts/e2e-live-ui.mjs`.

| 있던 것 | 무엇을 보나 | 무엇을 못 보나 |
|---|---|---|
| `deploy-check` | 배포된 주소, HTTP 로 | 브라우저에서 어떻게 보이는지 |
| `e2e:layout` · `e2e:next` | 브라우저로 | **로컬 서버**다. 배포된 인스턴스가 아니다 |

그 사이가 비어 있었다. 배포 자체가 어긋나는 것(빌드 산출물, 자산 경로, CSP)은 아무도 못 잡는다.
29-16-1 이 그 부류였다 — 200 이고 HTML 도 맞는데 아이콘이 글줄을 밀어냈다.

**로그인하지 않고 쓰지도 않는다.** 비밀번호와 가입 코드는 Vercel 환경변수에만 있고 여기 없다.
배포된 DB 에 아무것도 남기지 않는다. 가입 코드 거절은 **틀린 코드**로 잰다 — 맞는 코드를 몰라도
"아무 코드나 통과하지는 않는다"는 확인되고, 그것이 여기서 재고 싶은 것이다.

공개 화면 일곱 장을 열어 아이콘 배치(1280px·390px), 관리자 문이 공개 화면에 없는지, 진단 화면이
로그인 없이 내용을 내주지 않는지, 깨진 자산과 화면 오류가 없는지 본다.

## 4. 새 워크플로는 병합 전에 부를 수 없었다 (29-19-1)

`live-ui-check.yml` 을 만들고 부르려 했더니 이랬다.

```
POST .../workflows/live-ui-check.yml/dispatches: 404 Not Found
```

`workflow_dispatch` 는 워크플로 파일이 **기본 브랜치에 있어야** 부를 수 있다. 이 파일은
`round-29-5` 에만 있고 `main` 은 29.4.0 이다. 병합 전에는 영영 못 돈다.

`deploy-check.yml` 은 이미 `main` 에 있다. 그래서 브라우저 단계를 **거기에** 넣었다 — 부를 때
`ref` 로 이 브랜치를 주면 브랜치 버전의 파일이 돈다. `browser` 입력이 참이고 `base_url` 이 있을
때만 돌게 막았다. 프로덕션은 아직 옛 SPA 라 어떤 경로든 `index.html` 을 주고, 그 위에서는 이
검사가 뜻이 없다. 전환 뒤에 조건을 푼다.

`live-ui-check.yml` 은 그대로 둔다 — 병합 뒤에는 그쪽이 제자리다.

## 5. 내가 CI 를 빨갛게 만들었다 (29-19-2)

판번호를 29.19.0 으로 올리면서 `docs/rounds/29-19/` 를 만들어 놓고 **문서를 안 썼다.**
빈 디렉터리는 git 이 추적하지 않아 커밋에 들어가지 않았고, CI 의 라운드 확인이 걸렸다.

```
- 대상 라운드: ``
- 결과: failure
```

`test -d "docs/rounds/$r"` 가 첫 줄에서 막은 것이다. 게이트가 제 일을 했다 — 라운드 문서 없이
판번호만 올라가는 것을 막으려고 28-64 가 넣은 줄이다. 이 문서가 그 수정이다.
