핵심 지적: 거래 수명주기에서 **돈이 실제로 움직이는 지점이 없다**. 지금은 파트너가 "→ 정산 완료"를 누르면 고객이 한 푼도 내지 않았는데 정산이 끝난다 — 상용 서비스에서 있을 수 없는 흐름이다. 시안의 결제 계층(예약금 → 시공 → 최종 결제 → 영수증 → 정산)을 도메인 규칙으로 강제해야 하고, 실제 PG(토스페이먼츠 등) 연동은 서버가 필요하므로 **PG 연동 지점을 명확히 분리한 시뮬레이션 게이트웨이**로 구현한다(연동 지점 문서화 필수).

## 상 (High)

### 28-28-01 · 결제 도메인 부재
→ 요구: `Payment { id, requestId, kind('deposit'|'final'), amount, method('card'|'transfer'), receiptNo, paidAt }`.
- `payDeposit(requestId, method)`: **accepted 상태에서만**(낙찰 직후 예약금), 금액 = 낙찰가의 10%(정수 내림, 최소 10,000원), 중복 결제 거부.
- `payFinal(requestId, method)`: **completed 상태에서만**, 금액 = 최종 금액(기본 견적 + 승인 추가 작업) − 기결제 예약금, 중복 거부.
- `paymentsFor(requestId)` / `paymentFor(requestId, kind)` / 영수증 번호 `RCT-####`.
- **정산 차단 규칙**: `settle()`는 최종 결제가 없으면 거부("고객 결제 완료 후 정산할 수 있습니다") — 상용화의 핵심 불변식.
- 스냅샷 `payments?`+`paymentSeq?` 하위 호환 + 요소 검증 + **도메인 테스트 필수**.

### 28-28-02 · 고객 결제 UI (시안 "결제 및 예약"·"계산서/영수증")
→ 요구: 고객 거래 상세 —
- accepted: "예약금 결제" 카드(금액·수단 선택 카드/계좌이체·결제하기).
- completed: "최종 결제" 카드(금액 분해: 기본 견적 + 추가 작업 − 예약금).
- 결제 후: **영수증 카드**(영수증 번호·일시·수단·금액, 공급가/부가세 분리 표기). 타임라인에 결제 이벤트 표시.

### 28-28-03 · 파트너·관리자 반영
→ 요구: 파트너 내 작업 카드에 결제 상태 표기(예약금 결제됨 / 결제 대기 / 결제 완료), 결제 전 정산 시도 시 도메인 오류 그대로 노출. 관리자 정산 탭에 결제 현황(결제 완료/대기) 컬럼.
