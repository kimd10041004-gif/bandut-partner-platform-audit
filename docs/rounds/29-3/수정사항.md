# 29-3 — Next.js 앱 셸이 선다 (배포는 아직 SPA)

29-2가 v17 도메인을 우리 세션으로 HTTP에 올렸다. 이번에는 그 위에 **v17 화면과 디자인**을 세운다.
**라이브는 바뀌지 않는다** — 새 셸은 저장소 안에서 빌드되고 검사받지만, 배포 전환은 29-4다.

## 1. 먼저, 지난 라운드의 판단이 틀렸다

29-2 문서와 PR에 이렇게 적었다:

> 한 `package.json`에 React 두 개를 둘 수 없으니 프레임워크를 바꾸는 순간 SPA·`vite build`·`e2e`·
> `visual-check`가 **동시에** 깨진다. 화면 전환은 쪼갤 수 없는 덩어리다.

**해 보니 아니었다.** React 19 하나로 올린 뒤에도 옛 SPA는 그대로 빌드되고, 브라우저 여정도 전부 통과한다:

```
dist/assets/index-sY1nT7Zb.js   555.99 kB   (React 18일 때 505.27 kB)
E2E-JOURNEY OK
```

우리 SPA가 React 19에서 사라진 API를 쓰지 않기 때문이다. 번들이 50KB 커진 것 말고는 달라진 게 없다.

그래서 이 라운드는 **셸을 세우기만** 하고, 배포 전환과 SPA·스냅샷 스택 삭제는 29-4로 미뤘다. 되돌리기 쉬운
쪽으로 한 칸씩 가는 편이 낫고, 무엇보다 **라이브를 건드리지 않고** 새 셸을 CI가 지키게 할 수 있다.

`docs/참고_v17_대조.md`의 그 문단에 정정을 달아 두었다. 틀린 가정이 라운드 계획을 어떻게 좁혔는지가 남아야
다음에 같은 방식으로 좁히지 않는다.

## 2. 화면은 한 줄도 고치지 않았다

v17 화면이 API를 부르는 방법은 `lib/client.ts`의 함수 하나다:

```ts
export async function api<T>(path:string, ...) { fetch('/api/' + path, ...) }
```

그래서 우리 핸들러를 **v17과 같은 자리**에 붙였다. `app/api/[...path]/route.ts`가 마켓플레이스를 받고,
우리 것인 `/api/auth`·`/api/payments`는 형제 폴더에 정적 세그먼트로 둔다 — Next.js는 catch-all보다 그쪽을
먼저 고른다. 29-2에서 쓰던 `/api/mp` 접두사는 옛 SPA의 정확 경로 라우터를 피하려던 것이라 이제 없앴다.

결과: `components/`(79개)·`app/[...slug]/page.tsx`·`app/layout.tsx`가 **원본 그대로**다.

## 3. 프레임워크 어댑터는 파일 하나였다

28-68부터 API 핸들러를 `(req, env) => res` 순수 함수로 유지해 온 값이 여기서 나왔다. Vite에서 Next.js로
옮기면서 고친 것은 `server/nextAdapter.ts` 하나이고, `api/auth.ts`·`api/payments.ts` 본체는 한 줄도
바뀌지 않았다.

| 새 파일 | 하는 일 |
|---|---|
| `app/api/[...path]/route.ts` | 마켓플레이스 — 29-2의 `handleMarketplace`를 그대로 부른다 |
| `app/api/auth/route.ts` · `app/api/payments/route.ts` | 우리 핸들러 (catch-all보다 우선) |
| `server/nextAdapter.ts` | `Request` ↔ 우리 핸들러 모양. 본문 상한도 여기서 건다 |
| `scripts/e2e-next.mjs` | 셸 연기 검사 8건 |

## 4. Cloudflare 결합 두 곳을 더 걷어냈다

- `lib/presentation-server.ts` — 화면이 서버에서 프레젠테이션을 읽는 자리다. `env.DB`(D1)를 우리 풀로
  바꿨다. 저장소가 없으면 `null`을 주고 화면이 다시 시도 상태를 보인다는 v17의 계약은 그대로다.
- `db/schema.drizzle.ts` — v17이 마이그레이션을 뽑을 때 쓴 원본이다. 우리는 `db/sqlite/*.sql`을 직접 읽고
  drizzle을 설치하지 않으므로, 아무도 import 하지 않으면서 빌드만 막고 있었다. 지웠다.

## 5. 엄격함은 우리 코드에만

v17 원본(`app/`·`components/`)을 우리 `exactOptionalPropertyTypes` 아래 두면 수백 건이 터진다. 29-1에서
prettier를 나눈 것과 같은 이유로 나눴다:

| 무엇이 본다 | 무엇을 |
|---|---|
| `tsconfig.json` | 옛 SPA(`src/`) — 28-41까지 쓰던 그대로 |
| `tsconfig.next.json` | Next 앱(`app/`·`components/`) — v17의 설정 |
| `tsconfig.api.json` | `api/`·`server/` — 우리 설정(`exactOptionalPropertyTypes` 등) |

Next.js는 기본으로 루트 `tsconfig.json`을 자기 것으로 **정규화한다**. 프로젝트가 셋인 이 저장소에서는 그러면
서로의 설정을 덮어써서, 실제로 우리 서버 테스트가 Next의 타입 환경에서 `ProcessEnv` 불일치로 무더기로 터졌다.
`next.config.ts`의 `typescript.tsconfigPath`로 Next에게 전용 파일을 줘서 각자 자기 것만 보게 했다.

## 6. 이번에 바뀌지 않는 것

`vercel.json`·`index.html`·`src/`의 화면 코드는 그대로다(`src/App.tsx`의 라운드 표기 한 줄 제외).
라이브는 여전히 SPA이고, 배포 확인도 여전히 SPA 번들에서 `29-3`을 찾는다.

29-4에서 배포를 Next.js로 전환하고, 그때 SPA·스냅샷·보관함·가명본·용량 가드를 함께 지운다.
사진 저장소는 그다음(29-5)이라 사진 경로는 아직 503이다.

## 7. 새 의존성이 감사를 깨뜨렸다 — 올려서 되돌렸다

Next.js를 v17이 쓰던 16.2.6으로 넣었더니 `npm audit`이 **critical**을 물어 왔다(미들웨어 우회, 이미지
최적화 API의 원격 코드 실행 등 11건). 28-41 이후 이 저장소는 0을 유지해 왔으므로 그대로 둘 수 없다.
16.3.4로 올려 **0 vulnerabilities**로 되돌렸다. v17의 핀을 그대로 따르지 않은 첫 자리다.
