| # | 확인 |

| 1 | 앱 셸이 200을 준다 |

CI에서는 Postgres가 있는 `server` job에 넣었다(단계 12). `gates` job에는 DB가 없어 401 대신 503이 나온다.

## 3. 지난 라운드의 판단을 정정했다

29-2 문서와 PR에 "React 두 개를 둘 수 없으니 화면 전환은 쪼갤 수 없는 덩어리"라고 적었다. 실제로 해 보니
아니었다 — React 19 하나로 올려도 옛 SPA가 그대로 빌드되고 여정도 전부 통과한다.

```
dist/assets/index-sY1nT7Zb.js   555.99 kB   (React 18일 때 505.27 kB)
E2E-JOURNEY OK
```

그래서 이 라운드는 셸만 세우고 배포 전환·삭제를 다음으로 미룰 수 있었다. `docs/참고_v17_대조.md`에 정정을
달았다. 틀린 가정이 라운드 계획을 어떻게 좁혔는지가 남아야 다음에 같은 방식으로 좁히지 않는다.

## 4. 새 의존성이 감사를 깨뜨렸다

Next.js를 v17의 핀(**16.2.6**)으로 넣었더니 `npm audit`이 **critical 11건**을 물어 왔다 — 미들웨어 우회,
이미지 최적화 API의 원격 코드 실행, 서버 액션 SSRF 등. 이 저장소는 28-41 이후 0을 유지해 왔다.

**16.3.4**로 올려 0으로 되돌렸다. v17의 핀을 그대로 따르지 않은 첫 자리다 — 참고본을 따르는 것보다
우리 게이트를 지키는 쪽이 먼저다.

## 5. 배포 확인

병합 커밋 `a15673a`의 deploy-check(run 81)가 첫 시도에 통과했다.

```
시도 1/12 — 서빙 번들 /assets/index-BIRJHrwZ.js 에 라운드 29-3 확인, 배포 반영됨
서빙 인증 모드: local
```

| 항목 | 값 |
|---|---|
| 서빙 번들 | `index-BIRJHrwZ.js` (**옛 SPA**) |
| 라운드 표기 | `29-3` |
| 서빙 인증 모드 | `local` |

**이 라운드에서는 이것이 정답이다.** 라이브가 여전히 SPA 번들을 내려 주는 것이 "배포를 안 바꿨다"는 증거다.
새 셸은 저장소 안에서 빌드되고 CI가 지키지만, 아직 아무에게도 보이지 않는다.

`local` 경고도 그대로다 — 배포를 Next.js로 옮길 때 함께 해소된다.

다음 라운드는 배포 전환과 삭제인데, 준비를 하다가 **혼자 결정하면 안 되는 것**이 나왔다.

  지운다. `src/`의 28,730줄 중 로그인 도메인 3,160줄만 옮겨 살아남고 **약 25,500줄이 사라진다.**
