그대로 배포를 옮겼다면 게이트가 아무것도 못 읽고 실패했을 것이다.

## 3. 과도기 분기를 양쪽으로 확인

배포 확인이 옛 SPA와 새 셸을 둘 다 판정할 수 있어야 29-5에서 `vercel.json`만 바꿔도 게이트가 안 깨진다.

| 분기 | 확인 방법 | 결과 |
|---|---|---|
| Next 셸 | 로컬 `next start`의 HTML을 받아 봄 | `/assets/index-*.js` 패턴 **없음**(Next는 `/_next/static/`) · `29-4` 있음 · `bandut-auth-mode:server` 있음 |
| 옛 SPA | **병합 뒤 배포 확인(run 84)이 라이브 응답으로 직접 판정** | 아래 §3-1 |

로컬에서는 SPA 분기를 직접 태워 볼 수 없었다 — 이 샌드박스에서 라이브 주소로 나가는 연결이 프록시에
막힌다(`CONNECT tunnel failed, 403`). 그래서 병합 전에는 "코드가 안 바뀌었다 + 지난 로그"까지가 근거였고,
그 한계를 그대로 적어 두었다. run 84가 그 자리를 메웠다.

### 3-1. run 84 (`main` `3f35afc`, job `live`)

```
시도 1/12 — 옛 SPA 번들 /assets/index-yIcYHjl-.js 에 라운드 29-4 확인, 배포 반영됨
서빙 인증 모드: local
```

읽을 것이 세 가지 있다.

- **첫 시도에 통과했다.** 새로 넣은 `grep -oE '/assets/index-...'` 분기가 라이브 HTML에서 번들 이름을
  실제로 뽑아냈다는 뜻이다. 못 뽑았다면 `else`로 빠져 HTML에서 라운드를 찾다가 12번 재시도하고 실패했을
  것이다. **과도기 분기의 SPA 쪽이 라이브 응답으로 증명됐다.**
- **번들 이름이 바뀌었다** — 29-3의 `index-BIRJHrwZ.js` → 29-4의 `index-yIcYHjl-.js`. 이번 라운드가
  `App.tsx`의 라운드 문자열을 건드렸으니 해시가 바뀌는 것이 맞다. 배포가 이 커밋의 것임을 이름이 말한다.
- **모드는 여전히 `local`이고 경고도 그대로다.** 이것이 이번 라운드의 정답이다. 라이브는 안 건드렸고,
  그 경고는 29-5에서 전환할 때 사라진다.

양쪽 분기가 이제 각각 실제 응답으로 확인됐다 — Next 셸은 로컬 `next start` HTML로, 옛 SPA는 run 84로.
29-5는 `vercel.json`만 바꾸면 되고 이 게이트는 손대지 않는다.

## 4. 라이브는 안 건드렸다

`vercel.json`은 그대로다. 라이브는 여전히 옛 SPA를 서빙하고, 배포 확인은 SPA 번들에서 `29-4`를 찾을 것이다.
`local` 모드 경고도 그대로 — 전환할 때 함께 해소된다.

## 5. 남는 것 — 29-5는 사용자 확인이 필요하다

배포를 옮기면 라이브가 서버 렌더링이 되어 Vercel 프로젝트에 `DATABASE_URL`·`ADMIN_PASSWORD`·`SIGNUP_CODE`가
있어야 한다. 없으면 라이브가 500이 된다. Vercel 프로젝트를 읽을 수 없어(404) 확인이 안 되고, 라이브를 내리는
것은 되돌리기 어려우므로 **확인 없이 진행하지 않는다.**

확인되면 29-5에서: `vercel.json` 전환 · 로그인 도메인을 `server/domain/`으로 이사 · SPA와 스냅샷 스택
약 25,500줄 삭제 · 배포 확인에서 `local` 경고가 사라지는지 검증.
