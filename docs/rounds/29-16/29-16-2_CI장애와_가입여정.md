# 29-16-2 — CI가 멈춘 진짜 이유, 그리고 그동안 메운 구멍

## 1. CI는 고장 난 것이 아니라 **거부당한** 것이다

`c62ea3f`(29-13)부터 모든 작업이 2~4초 만에 단계 0개로 끝났다. 재실행으로는 아무것도 알 수 없었다.
실행 로그는 404다 — 로그가 없는 것이 아니라 **아무것도 실행되지 않아서** 생기지 않았다.

답은 check-run 주석에 있었다.

```
GET /repos/kimd10041004-gif/bandut-partner-platform/check-runs/<id>/annotations

"The job was not started because recent account payments have failed or your
 spending limit needs to be increased. Please check the 'Billing & plans'
 section in your settings"
```

`816121c`의 `gates`·`server`, 그리고 `deploy-check`의 `live` — 세 작업 모두 같은 문장이다.

작업 상세가 그것을 뒷받침한다.

| 항목 | 값 | 뜻 |
|---|---|---|
| `runner_id` | `0` | 실행기가 배정된 적이 없다 |
| `runner_name` | `""` | 같은 뜻 |
| `steps` | 없음 | 단계가 만들어지지도 않았다 |
| `billable.UBUNTU.total_ms` | `0` | 청구된 시간이 0 — 아무것도 돌지 않았다 |
| 로그 | HTTP 404 | 남길 것이 없었다 |

저장소는 **비공개**이고 소유자는 개인 계정이다. 비공개 저장소의 Actions 분은 무료 한도가 있고,
그 한도를 넘거나 결제가 실패하면 GitHub는 작업을 **시작조차 하지 않는다.** 지금이 그 상태다.

**이 실패는 코드가 만든 것이 아니다.** 워크플로 파일은 마지막으로 초록이던 실행과 같고, 같은 검사가
로컬에서는 전부 통과한다.

다만 여기서 한 걸음 더 나가면 안 된다 — 검사가 **실행되지 않았으므로** "코드에도 문제가 없다"까지
입증된 것은 아니다. 이 주석이 말해 주는 것은 실패의 원인뿐이고, 우리 코드의 결백은 CI 가 실제로
돌아야 나온다. 로컬 게이트는 그 자리를 대신하지 못한다.

## 2. 우리가 고칠 수 있는 것은 없다

낭비를 줄이는 쪽은 이미 되어 있었다 — `gates`는 `concurrency: gates-${{ github.ref }}` 에
`cancel-in-progress: true` 라, 새 푸시가 이전 실행을 취소한다. 여기서 더 깎을 것이 없다.

한도 자체는 저장소 설정이 아니라 **계정 결제**에 달려 있다. 사장님만 여실 수 있다.

## 3. 그래서 막힌 동안 무엇을 했나 — 비어 있던 이음매를 메웠다

가입부터 승인까지의 여정은 **두 파일로 쪼개져 있었다.**

```
passwordReset.http.test   가입·로그인까지 — 세션이 생기는 것까지
marketplace.http.test     세션이 있다고 가정하고 시작 (issueSession 으로 토큰을 만든다)
```

그 사이가 비어 있었다. 진짜 가입으로 받은 토큰이 v17 `users` 행이 되는지, 업체 신청으로 그 행의
역할이 올라가는지, 관리자 승인이 그 계정의 권한을 **실제로** 여는지 — 아무도 재지 않았다.
사장님이 프리뷰에서 눈으로 보실 항목이 정확히 이 여정이다.

`tests/signupJourney.http.test.ts` 가 그것을 한 줄로 잰다.

```
가입(인증번호 확인) → 재로그인 → me = CUSTOMER → 업체 제출 → me = PARTNER
 → 승인 전 파트너 일감 403 → 손님 목록에 안 보임
 → 관리자 승인 → 같은 요청 200 → 손님 목록에 보임
 → 다시 로그인해도 PARTNER 그대로
```

마지막 줄이 이 검사의 값이다. 우리 세션은 가입 당시의 역할('partner')을 계속 들고 다니는데,
요청마다 v17 행을 그 값으로 덮어썼다면 승인받은 PARTNER 가 다음 요청에 CUSTOMER 로 되돌아간다.
`identityOf` 는 덮어쓰지 않는다 — 이제 그것이 검사로 고정됐다.

### 쓰면서 하나 배운 것

처음에는 "승인 전에는 파트너 일감이 403" 을 가입 직후에 두었다. 200 이 나왔다. 틀린 것은 코드가
아니라 내 가정이었다 — 그 시점의 계정은 아직 평범한 고객이고, `orders` 는 **자기 주문 목록**을
돌려주는 것이 맞다. 승인 게이트는 역할이 PARTNER 가 된 뒤에야 선다. 그 자리에 맞게 옮겼다.

`npm run test:journey` 로 돌리고, CI 의 `server` 작업에도 넣었다 — 게이트 작업에는 DB 가 없어
그 자리에 두면 영영 돌지 않는다(`test:reset` 에서 같은 것을 겪었다).

## 5. 뒤이어 확인한 것 — 고른 주소가 정말 연결에 쓰이는가 (29-16-3)

`DATABASE_URL_PREVIEW` 를 넣는 것만으로 DB 가 분리되지는 않는다. 세 가지가 모두 맞아야 한다.

| 조건 | 지금 상태 | 근거 |
|---|---|---|
| 값이 **다른 DB·브랜치**를 가리킬 것 | 사장님이 만드셔야 함 | 같은 곳을 가리키면 `/admin/diagnostics` 가 "분리되지 않음"으로 표시한다 |
| 프리뷰에서 **그 이름을 고를 것** | 코드로 확인됨 | `resolveDatabaseUrl` — `VERCEL_ENV==='preview'` 일 때만 고른다 |
| 고른 주소가 **실제 연결에 쓰일 것** | 이번에 고쳤다 | 아래 |

세 번째가 가정 위에 서 있었다. `getPool` 은 첫 호출에서 만든 풀 하나를 들고 있다가 이후 호출에는
**주소를 보지 않고** 그것을 돌려줬다. 한 프로세스의 `process.env` 는 바뀌지 않으니 잘못된 DB 에
붙는 일은 없었지만, 그것은 코드가 지키는 보장이 아니라 환경이 안 바뀐다는 가정이었다.
분리를 가정 위에 올려 두지 않는다 — 주소를 열쇠로 두는 `Map` 으로 바꿨다.

`server/db.test.ts` 가 고치기 전 상태에서 두 건 실패한다. 특히 이 줄이 결과를 그대로 보여 준다.

```
× 두 번째 주소의 풀이 그 주소로 만들어진다 — 첫 주소로 붙지 않는다
  expected 'postgres://u:p@host-a.example/db1' to be 'postgres://u:p@host-b.example/db2'
```

DB 를 여는 모든 입구가 `resolveDatabaseUrl` 을 지나는지도 전수로 확인했다 —
`app/api/[...path]`, `app/api/auth`, `app/api/payments`, `lib/presentation-server`, 그리고
핸들러 세 곳. 해석기 밖에서 `DATABASE_URL` 을 직접 읽는 런타임 코드는 없다.
