# 28-90 수정사항 — 참고 v12 대조 정리 라운드

사용자 요청: 참고 프로젝트(`bandeut-marketplace-v12`, 별도 스택으로 이 플랫폼을 "최적화해 다시 만든" 시안)를 보고
**"쓸데없는 부분은 전부 없애고, 이 방향에서 더 추가하자"** · **"이전에 쌓인 쓰레기와 중복, 코드가 한 줄에
말도 안 되게 하드코딩된 부분은 다 정리하자."** 대조표와 라운드 계획은 `참고_v12_대조.md`에 있다.

이번 라운드는 **더하는 라운드가 아니라 빼고 고르는 라운드**다. 사용자가 네 가지를 결정했다:

| 결정 | 선택 |
|---|---|
| A/S 와 분쟁 | **분쟁으로 통합**(+ 열린 분쟁은 정산·지급 보류) |
| 다크 모드 | **제거** |
| 정산 계좌 | **가입한 이름과 예금주가 같은 계좌만, 관리자가 인증한 계좌만 지급** |
| 로컬 모드 | **당분간 유지** — 대신 쌓인 중복·하드코딩 정리 |

## A. A/S → 분쟁 통합 (+ 정산 보류)

28-22부터 클레임은 `kind: 'as' | 'dispute'` 두 갈래였고, 28-54가 A/S 에 **보증 기간**(`warrantyDays`,
`warrantyStatus`)을 붙였다. 참고 v12는 갈래가 하나(분쟁)이고, 분쟁이 열리면 **정산을 붙든다**. 고객이
"이게 A/S 인지 분쟁인지"를 먼저 고르게 하는 것은 고객의 일이 아니라 운영의 일이다 — 그래서 합쳤다.

- `src/domain/types.ts` — `ClaimKind` · `Claim.kind` · `SiteSettings.warrantyDays` 제거.
- `src/domain/platform.ts`
  - `fileClaim(requestId, { detail, createdDate? })` — 갈래 인자가 없다. 접수 알림 문구가 `분쟁 접수 — … · 정산·지급 보류`.
  - `hasOpenClaim(requestId)` 신설. **`settle()`·`markPayout()`이 열린 분쟁이 있으면 거절**한다
    (`분쟁 검토 중인 거래는 정산할 수 없습니다 — 해결 처리 뒤 다시 시도하세요` / `…지급할 수 없습니다…`).
    `resolveClaim()` 뒤에는 다시 풀린다.
  - `WARRANTY_DEFAULT_DAYS` · `warrantyDays` 기본값·검증·`updateSettings` 분기 · `warrantyStatus()` 제거.
    `PSEUDONYMOUS_SETTINGS_KEYS = ['disabledCategories']`, `PSEUDONYMOUS_CLAIM_KEYS`에서 `kind` 제거.
  - 약관 본문(제4조·개인정보 2항)의 "A/S·분쟁" → "분쟁".
  - 옛 스냅샷의 `kind`는 **읽을 때 버린다** — 손상으로 취급하지 않는다(테스트 "옛 스냅샷의 kind는 무시된다").
- `src/ui/constants.ts` — `CLAIM_KIND_LABEL` 제거.
- 화면: 고객 거래 상세 카드 "문제 접수 (분쟁)" 버튼 하나(`[data-file-claim]`, 문구 "문제 신고", 안내
  "해결 전까지 정산·지급 보류"), 파트너 답변 상자 `aria-label="분쟁 답변"` + 태그 "분쟁 접수됨 · 정산 보류",
  관리자 탭 이름 **분쟁**, 현황 카드 "미해결 분쟁", 관리자 설정의 "A/S 보증 기간" 카드 삭제.
  관리자 정산 탭의 지급 대기 행은 열린 분쟁이 있으면 `data-payout-held="dispute"` + "분쟁 보류" 태그.
- CSS: `.claim-tag.as` · `.warranty.*` 제거.

## C. 정산 계좌 — 실명 일치 + 관리자 인증

지급은 돈이 나가는 유일한 지점이다. 참고 v12는 정산 계좌를 **인증된 계좌**로만 다룬다. 사용자 결정은
그보다 한 단계 더 — **예금주가 가입한 이름과 같아야** 하고, **관리자가 인증 기록을 남긴 계좌만** 지급된다.

- `src/domain/auth.ts`
  - `PayoutAccount { bank; number; holder; updatedAt; verifiedAt?; verifiedBy? }`.
  - `setPayoutAccount()` — `normalizeHolder(holder) !== normalizeHolder(account.name)`이면
    `예금주는 가입한 이름과 같아야 합니다: <이름>`. 계좌를 바꾸면 **인증이 초기화**된다.
  - `verifyPayoutAccount(accountId, adminId)` 신설 — 파트너 계정만, 계좌가 있어야, 보안 이벤트 `정산 계좌 인증`.
  - `payoutAccountLabels()`가 `{ label, masked, verified }`를 준다.
- `src/domain/platform.ts` — `markPayout(requestId, account)`가 `verified === false`면
  `인증되지 않은 정산 계좌입니다 — 예금주·계좌를 확인하고 계좌 인증을 기록한 뒤 지급하세요`.
- 서버: `api/auth.ts` `ADMIN_OP_ACTION.verifyPayoutAccount: 'operate'`(매니저 이상, 열람은 403).
  `src/app/authActions.ts`에 `verifyPayoutAccount(id)`(서버 모드는 `call('verifyPayoutAccount', …, 'admin')`).
- 화면: 파트너 정산 카드의 예금주 라벨 "예금주 — 가입한 이름과 같아야 합니다 (이름)", `data-payout-verified="yes|no"`
  + 인증됨/인증 대기 태그. 관리자 정산 탭 계좌 칸에 **계좌 인증** 버튼(`[data-verify-payout]`) 또는 인증됨 태그.
