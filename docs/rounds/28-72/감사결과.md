# 28-72 감사 결과 (`6e5c0a0` 기준)

28-72는 "두 번째 사용자부터" 무너지던 것을 고쳤다 — 로그인이 첫 접촉을 기다리고(01), 잠금이 남의 IP에 열려
있지 않고(02), 가드·OTP가 조여졌다(03). 이번 감사는 그 넷이 **실제로 성립하는지**와, 고치는 과정에서 **새로 열린
문이 있는지**를 봤다. 결론: 01의 수정에는 아직 새는 구멍이 있고(01), 02의 수정은 DoS를 막는 대신 **무차별 대입**을
열었다(02). 28-72가 스스로 기록한 409 데이터 손실은 정식 항목으로 올린다(03).

네 갈래로 봤다 — 배선·복제 / 인증·잠금 / 스크립트·가드 / 검증·문서.

## 28-72-01 (상) 로그인이 기다리는 것이 **자기 첫 접촉이 아닐 수 있다** — 28-71-01의 수정에 난 구멍

`authActions.login()`은 이제 `await settleSession(onSession)`으로 첫 접촉을 기다린다. 그런데 그 `onSession`은
`replication.sync({ checkRemote: true })`이고, `Replicator.sync()`는 **이미 진행 중인 동기화가 있으면 자기 일을
큐에 넣고 그 진행 중인 것을 돌려준다**:

```js
async sync(options = {}) {
  if (this.inFlight) {
    this.queueAgain({ ... })
    return this.inFlight        // ← 남의 sync다. 내 checkRemote는 아직 시작도 안 했다
  }
```

그래서 로그인 순간에 다른 sync가 돌고 있으면(앱 시작 `restore()`의 sync, 다른 탭 storage 이벤트, 디바운스가 만료된
push — 서버 e2e에서 실제로 겹쳤던 그 창이다) 로그인은 **그 남의 sync**가 끝나면 반환한다. 자기 `checkRemote`는
그 뒤에 `again`으로 돈다. 결과는 28-71-01이 고치려던 것과 **같다**: `AuthGate.doVerify`가 로그인 직후 넣는 파트너
프로필 시드가, 뒤늦게 도착한 accept의 `importSnapshot`에 덮인다.

**재현(복제기 수준, 이번 감사에서 실행).** 느린 write로 push를 진행 중으로 만들고, 그 사이 `sync({checkRemote:true})`를
부른 뒤 **그것이 resolve되는 그 순간** 원격 확인(`head`)이 몇 번 완료됐는지 센다:

```
[probe] 두 번째 sync가 resolve된 순간 — 완료된 head 수 = 0
[probe] 모든 동기화가 끝난 뒤 — 완료된 head 수 = 1
```

0이다 — 로그인이 "첫 접촉이 끝났다"고 판단한 시점에 **서버와 한 번도 이야기하지 않았다.**

`authActions.test.ts`가 이것을 못 본 이유는 분명하다: 그 테스트의 `onSession`은 손으로 release하는 빈 Promise라
**진짜 `Replicator`를 태우지 않는다.** 계약("로그인은 첫 접촉이 끝나야 끝난다")을 지키는 주체는 복제기인데
테스트는 복제기를 빼고 확인했다.

근본 수정: `sync()`가 **호출자에게 자기 일이 끝나는 Promise를 돌려준다**. 진행 중이면 `again`에 넣되, 그 큐에
`resolve`를 함께 달아 큐가 소화될 때 풀어 준다(합쳐진 요청은 하나의 Promise를 공유한다). 회귀: 위 probe를 정식
테스트로("진행 중 push가 있을 때 sync가 자기 head 완료 전에 resolve되지 않는다") + `authActions`가 **실제
Replicator**를 쓰는 통합 테스트 1건.

## 28-72-02 (상) (계정, IP) 잠금이 **무차별 대입을 무제한으로 연다** — 28-71-02의 뒷면

28-71-02는 `failKey`에 요청 IP를 넣어 "남의 IP에서 낸 실패가 내 로그인을 잠그지 않게" 했다. 맞는 방향이지만
**잠금이 계정을 지키던 몫까지 같이 없앴다.** 지금 규칙은 `(role, 전화번호, IP)`당 5회/15분이다. 공격자가 IP를
바꾸면 카운터도 바뀐다 — 프록시 200개면 **15분당 1,000회**, 하루 약 9만 6천 회를 한 계정에 시도할 수 있다.
비밀번호 최소 길이는 8자(`auth.ts:468`)이고 사전 단어·전화번호 조합이면 이 정도로 충분히 뚫린다.

IP 실패 제한(`rateLimit.ts`, 60초 20회)은 이것을 막지 못한다 — **IP마다 따로 세는 카운터**이므로 IP를 바꾸는
공격자에게는 제한이 아니다(게다가 서버리스 인스턴스 로컬이다).

그런데 `28-68/서버_연결.md`는 이렇게 적어 두었다:

> 비밀번호 무차별 대입은 (계정, IP)당 5회/15분 + 8자 최소로 막힌다.

**막히지 않는다.** 문서가 실제보다 안전하다고 말하고 있다 — 이 라운드에서 가장 고쳐야 할 문장이다.

근본 수정(2단): (계정, IP) 5회/15분은 그대로 두고, **계정 단위 카운터**를 하나 더 둔다 — IP와 무관하게 한 계정에
15분 안에 실패가 N회(예: 30) 쌓이면 그 계정을 잠근다. DoS 비용이 5회에서 30회로 오르고(28-71-02가 막으려던 것),
무차별 대입은 15분당 30회로 닫힌다(28-71-02가 연 것). 관리자 계정은 `setSuspended`처럼 운영자 경로가 있으므로
잠겨도 복구 수단이 있다. 회귀: "다른 IP 6곳에서 각 5회 실패 → 30회째에 계정이 잠긴다"(수정 전: 영원히 안 잠긴다),
"같은 계정 다른 IP의 실패가 5회까지는 이 IP를 잠그지 않는다"(28-71-02의 회귀가 그대로 살아 있는지).

## 28-72-03 (중) conflict가 **대기 중인 로컬 변경을 영구히 버린다** — 28-72가 스스로 기록한 것

`28-72/수정사항.md`의 "이 라운드에서 새로 드러난 것"에 적혀 있다. 감사 항목으로 정식화한다.

`acceptRemote()`는 원격을 받아들인 뒤 `this.pushedLocalRev = this.source.revision()`으로 커서를 **accept 이후의
revision**에 맞춘다. 그래서 conflict 직전에 이 기기가 만든 변경(아직 원격에 못 올린 것)은 다시 밀어 올릴 경로가
사라진다 — 다음 `run()`은 `pushedLocalRev === localRev`로 조기 반환한다. 화면은 "덮였습니다"라고 **알리기는**
하지만, 덮인 내용은 **어디에도 남지 않는다.**

통째 스냅샷 모델에서 병합은 불가능하다(그건 엔티티 단위 API의 일이다). 하지만 **잃지 않는 것**은 지금도 가능하다:
accept 직전의 로컬 본문을 보관함에 넣고(이미 있는 백업·복원 경로를 그대로 쓴다), 배너에서 "덮인 내용 보기·복원"으로
꺼낼 수 있게 한다. 회귀: "conflict 뒤 덮인 로컬 본문이 보관함에 있다"(수정 전: 없다), "보관은 최근 N개만 남는다"
(저장 용량 상한과 충돌하지 않게).

## 28-72-04 (중) 검증·문서 어긋남

- **(a)** `28-70`·`28-71`·`28-72` 세 라운드의 `검증결과.md` §7(deploy-check)이 전부 **자리표시자**다
  (`## 7. deploy-check (병합 뒤 채운다)` 한 줄). 병합 뒤 브랜치가 닫히면서 아무도 채우지 않았다. 실제 로그는
  세 번 다 초록이었으므로 내용이 틀린 것은 아니지만, **검증 문서가 검증을 안 적고 있다.**
- **(b)** `authActions.test.ts`가 스텁 `onSession`만 태워 01을 못 봤다(위 참조). "복제기가 지키는 계약"을
  복제기 없이 검증한 테스트다.
- **(c)** `clientIp()`는 `x-forwarded-for`도 `x-real-ip`도 없으면 `'unknown'`을 돌려준다. 그러면 28-71-02의
  잠금 범위가 **모든 사용자 공유의 단일 값**으로 무너지고(= 28-71-02 이전과 같다) `isThrottled('unknown')`이
  전원을 함께 막는다. Vercel은 XFF를 넣으므로 프로덕션에서는 안 나지만, 자체 호스팅·프록시 없는 배포에서는 난다 —
  **어디에도 적혀 있지 않다.** 서버 모드 부팅 때 IP를 못 얻으면 경고를 남기는 편이 낫다.
- **(d)** e2e 가드 정규식 `/(^|[^a-z])test([^a-z]|$)/i`는 `bandut_latest`를 제대로 거부하지만 `testdb`처럼
  **진짜 테스트 DB도 거부**한다(안전한 방향의 오탐이므로 순위는 낮다). 문서에 "이름에 `test`가 **단어로** 있어야
  한다"고 적어야 사람이 헷갈리지 않는다.

## 반증한 것 (감사가 의심했다가 코드로 확인한 것)

- `pruneLoginFails`는 이번 라운드의 리뷰 지적대로 `lastAt` 기준으로 고쳐져 있다 — 보관은 실제로 15분이다.
- `verifyOtp`는 서버 모드에서 가입 코드를 **정말로** 요구한다(`api/auth.ts:175`, `safeEqual`).
- `settleSession`은 `onSession`의 예외를 삼키고 로그인은 성공시킨다 — 복제 실패가 로그인 실패가 되지 않는다.
- 서버 e2e의 기기 D는 원격이 비어 있지 않은 상태에서 가입한다 — 28-71-04(a)가 지적한 경로 공백은 메워졌다.
