# 28-72 수정 사항 — 「두 번째 사용자부터」 (28-71 감사 4건)

**사용자 결정: 감사 4건만.**

28-71 감사(`28-71/감사결과.md`)의 기준은 "켠 뒤 두 번째 사용자부터 무슨 일이 나는가"였다. 두 번째 파트너부터 프로필이 사라지고(01),
관리자 잠금이 인터넷의 누구에게나 열려 있었다(02). 이 라운드는 그 넷을 고친다. 배포된 앱은 여전히 로컬 모드라 동작이 바뀌지 않는다.

## 28-71-01 (상) 로그인은 첫 접촉이 끝나야 끝난다

- `authActions.ts`: `onSession`이 `Promise`를 돌려주고 `login()`·`restore()`가 **기다린다**(`settleSession` — 던져도 로그인은 성공, 로그만).
  `PlatformContext`는 `() => replication.sync({ checkRemote: true })`를 넘긴다. 첫 접촉의 accept(원격 통째 교체)가 끝난 뒤에야
  `AuthGate.doVerify`의 프로필 시드가 돈다 — 정상 로컬 변경으로 밀어 올라간다.
- 회귀: `authActions.test.ts` "onSession이 끝나기 전에는 login이 resolve되지 않는다"(수정 전 `done === true`), "던져도 로그인은 성공".
  서버 e2e 기기 D(두 번째 파트너, 원격이 있을 때 가입) — 프로필 시드가 서버 스냅샷 `profiles`에 있다.

## 28-71-02 (상) 잠금 키에 요청 IP

- `auth.ts`: `login(role, id, pw, now, { lockScope })` — `failKey`에 `:${lockScope}`. 범위 없는 호출(로컬 모드)은 예전 키 그대로.
  `pruneLoginFails(now)`가 로그인마다 15분 지난 기록을 지운다(IP별 키가 `auth_state`에 쌓이지 않게, `LoginFailRecord.lastAt`).
- `api/auth.ts`: `login`에 `{ lockScope: ip }`. 가입 코드 오류는 IP 실패 **5회분**(`recordFailure(ip, 5)` — 분당 4회). `SIGNUP_CODE_MIN` 8 → **12**.
- 회귀: `auth.test.ts` "다른 lockScope의 5회 실패는 이 lockScope를 잠그지 않는다 — 관리자도"(수정 전: 잠겼다), "15분 지난 기록 정리"
  (수정 전 30건 잔류); `api/auth.test.ts` 12자 미만 503, 가중치 4회 → 429(수정 전 20회).

## 28-71-03 (중) 가드·OTP

- `e2e-server.mjs` 가드 정규식 `/(^|[^a-z])test([^a-z]|$)/i` — `bandut_latest`로 돌리면 종료 2(확인함).
- `verifyOtp`도 가입 코드 필수(`args[3]`) — 없거나 틀리면 400(IP 실패 5회분). `AuthGate`가 서버 모드에서 상태의 코드를 넘긴다,
  계약 테스트·서버 e2e도. 계약 "코드 없는 verifyOtp → 400"(수정 전 200).
- `SIGNUP_CODE` 12자·무작위 생성 명령을 문서에.

## 28-71-04 (중) 검증·문서

- 서버 e2e에 기기 D(원격이 있을 때 파트너 가입) 3단계. 잠금 뒤 세션 단언은 A의 계정으로 범위를 좁혔다(D의 세션은 살아 있어야 한다).
- `서버_연결.md` 전제 절: 잠금은 (계정, IP) 단위, IP 제한은 인스턴스 로컬, `x-forwarded-for`는 Vercel이 덮어쓰고 로컬 api-server는 스푸핑 가능,
  `SIGNUP_CODE` 생성 명령, `verifyOtp`도 코드, 로그인은 첫 접촉을 기다린다.
- `28-71/감사결과.md` 04(c)에 02-d의 실제 재현 범위(복제기 가드는 첫 save 전, 실제 경로는 `clearStaleCursor`)를 적었다.
- `pruneSessions` 반환값을 로그로(0이면 침묵).

## 이 라운드에서 새로 드러난 것 (다음 감사로 이월)

**push 창 안의 409는 대기 중인 로컬 변경을 영구히 없앤다.** 기기 D의 e2e가 CI에서만 한 번 빨갛게 났고,
로그 타임스탬프를 맞춰 보니 원인은 테스트가 아니라 **복제기**였다: C(관리자)가 승인 직후 감사 로그를 저장해
1.5초 디바운스 뒤 스냅샷을 밀어 올리고, 그것이 D의 첫 push 창에 겹치면 D의 `expectedRev`가 낡아 409가 된다.
그때 D는 규칙대로 원격을 받아들이는데(`acceptRemote → importSnapshot`), **방금 만든 프로필은 다시 밀어 올리지 않는다** —
accept 뒤 `pushedLocalRev === revision()`이라 조기 반환한다. 28-71-01이 고친 것은 "받아들이기 **전에** 저장을
허용한 것"이고, 이것은 "받아들일 때 **대기 중인** 저장을 버리는 것"이다. 같은 뿌리(통째 스냅샷은 병합할 수 없다)의
다른 창이다.

지금 한 것은 **테스트를 결정적으로 만든 것뿐이다**: D 블록 앞에서 B·C를 닫고 2초 기다려 다른 기기를 조용히 시킨 뒤,
28-71-01이 실제로 보려는 것(로그인이 첫 접촉을 기다렸는가 = D **로컬**에 시드가 남았는가)을 먼저 단언하고,
서버 전파는 별도 단계로 뒀다. 경합 자체는 고치지 않았다 — 통째 스냅샷 모델에서 제대로 고치려면 accept 뒤
"내가 만든 미반영 변경"을 다시 적용해야 하고, 그것은 병합이라 엔티티 단위 API가 필요하다.
**운영 함의: 서버 모드에서 두 사람이 같은 몇 초 안에 저장하면 나중 것이 진다.** `서버_연결.md`의
"마지막 반영 이후의 로컬 변경은 덮인다"가 이 경우를 이미 덮지만, 화면의 "덮였습니다" 안내가 **가입 직후**에도
뜬다는 뜻이다.

## PR 리뷰에서 고친 것

**`pruneLoginFails`의 기준 시각** (Copilot 리뷰 지적, PR #204). 28-71-02이 넣은 정리 로직이 잠긴 기록의
기준을 `lockedUntil`로 잡았는데, 그 값은 이미 `lastAt + 15분`이라 삭제가 **30분** 뒤에 일어났다 —
주석("15분 지난 실패 기록")과도, `auth_state`에 IP별 키가 쌓이지 않게 한다는 의도와도 어긋난다.
기준을 `lastAt`으로 바꿨다(없으면 `lockedUntil`로 대비 — 28-71 이전 스냅샷에는 `lastAt`이 없다).
`lastAt + 15분 = lockedUntil`이라 잠금을 일찍 풀지도 않는다. 회귀 1건(수정 전 출력은 검증결과.md §5).
