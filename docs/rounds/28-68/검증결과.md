## 2. 회귀 증명 — 감사 4건 각각 **수정 전 코드에서 실패**

### 28-67-01 — 재현됨

```
$ npx vitest run src/domain/platform.test.ts -t "28-67-01"      # 수정 전
 FAIL  > 예금주가 가입명과 같아도 파트너 본인 열람권이 실패하지 않는다 (28-67-01)
PlatformError: 가명 처리에 실패했습니다 — 결과에 실제 식별자가 남아 있습니다: 김반듯

 ❯ PlatformService.exportPartnerData src/domain/platform.ts:3657:5
```

**감사가 코드를 읽어 내린 결론이 실제로 그대로였다.** 예금주 = 가입명 ≠ 업체명인 계정에서
파트너 본인의 "내 데이터 내보내기"가 `PlatformError`로 실패한다.
수정 후에는 `accountMasked = '국민 123******012 (김**)'`가 담기고 `json`에 `김반듯`이 없다.

### 28-67-02 — 네 결함 전부

`replicator.ts`만 수정 전으로 되돌리고(`git stash`) 새 테스트를 돌렸다:

```
$ git stash push src/domain/replicator.ts && npx vitest run src/domain/replicator.test.ts -t "28-67-02"
     × (a) write가 던져도 offline으로 내려가고 again이 고착되지 않는다 6ms
     × (b) accept가 던지면 원격을 덮지 않고 다음 sync가 다시 read부터 한다 1ms
     × (c) 원격이 사라져도 무한 conflict가 아니라 다시 읽고 새로 쓴다 1ms
     × (d) 오프라인이었다가 돌아오면 stale한 rev로 쓰지 않고 read부터 다시 한다 3ms
      Tests  4 failed | 7 skipped (11)
```

넷 다 빨간불이다. 되돌리면 전부 통과한다. (b)의 가짜 원격은 `write()`가 던지도록 되어 있다 —
**남의 변경을 덮으려는 순간 테스트가 깨진다.**

### 28-67-03 — 죽은 배선

수정 전에는 `markChanged()` 프로덕션 호출이 0곳이라 `'pending'`에 도달할 길이 없었고,
`backoffMs()`를 계산만 하고 아무도 기다리지 않았다. 새 테스트 4건:

```
✓ 저장 성공이 onSaved로 나온다 — 복제기가 변경을 아는 경로
✓ 보낼 것이 없으면 직렬화조차 하지 않는다 — 탭 전환마다 전체 스냅샷을 만들지 않는다
✓ offline이면 백오프만큼 기다렸다가 스스로 다시 시도한다
✓ stop()이 예약을 취소한다 — 화면을 떠난 뒤 복제기가 깨어나지 않는다
```

두 번째는 `body()` 호출 횟수를 세어 확인한다 — 변경 없이 세 번 sync해도 **1회**다.
세 번째는 예약된 함수를 실제로 발화시켜 `synced`가 되는 것까지 본다.

### 28-67-04 — 남은 맨 Error

새로 넣은 **소스 글자 훑기**를 `image.ts` 수정 전 상태에서 돌렸다:

```
$ git stash push src/ui/image.ts && npx vitest run src/errors.test.ts -t "맨 Error를 던지지 않는다"
     × 사용자에게 갈 수 있는 자리에서 맨 Error를 던지지 않는다 (28-67-04)
AssertionError: expected [ './ui/image.ts' ] to deeply equal []
+   "./ui/image.ts",
```

**28-67의 클래스 발견 방식은 이것을 원리적으로 못 잡았다** — export한 클래스를 찾지
`throw new Error(...)` 문장을 찾지 않기 때문이다. 이 훑기가 즉시 `src/domain/hash.ts`도 하나 더 찾아냈고,
그것은 개발자 실수(불변식)라 **이유와 함께** 테스트 안의 예외 목록에 적었다.

## 4. 진짜 Postgres 검증 — 이번 라운드의 핵심 증거

CI에 `server` job을 넣었고, **여기서도 같은 경로를 먼저 돌려 확인했다**
(이 컨테이너에 Postgres 16이 있었다):

```
$ psql "$DATABASE_URL" -f db/schema.sql
CREATE TABLE

$ psql "$DATABASE_URL" -c "\d snapshots"
    Column    |           Type           | Nullable | Default
--------------+--------------------------+----------+---------
 workspace_id | text                     | not null |
 rev          | bigint                   | not null |
 body         | text                     | not null |
 updated_at   | timestamp with time zone | not null | now()
Indexes:
    "snapshots_pkey" PRIMARY KEY, btree (workspace_id)

$ node scripts/api-server.mjs 3101
api-server listening on http://127.0.0.1:3101/api/snapshot
```

그 뒤 계약 테스트가 남긴 실제 행:

```
$ psql "$DATABASE_URL" -c "select workspace_id, rev, left(body,20) from snapshots limit 5;"
    workspace_id     | rev |          left
---------------------+-----+------------------------
 contract-mtng143m-2 |   1 | {"version":1,"요청":[{
 contract-mtng143y-3 |   2 | b
 contract-mtng1448-4 |   1 | 먼저 쓴 값
 contract-mtng144h-5 |   2 | A
```

**`A` 한 행이 낙관적 동시성의 증거다** — "동시 writer 둘 중 하나만 성공" 테스트가 A와 B를 동시에 썼고,
`where rev = $expected`가 하나만 통과시켰다.

API 규약도 진짜 서버에 대고 확인했다: 토큰 없음/틀림 → `401`, workspace 없음 → `400`,
본문 모양 어긋남 → `400`, `DELETE` → `405`.

### CI `server` job — 실제 로그 (PR #200, run 33920451288)

푸시 뒤 job이 돌았다. **초록**이고, 로그가 위와 같은 것을 CI에서도 보여 준다:

```
API 서버 기동 확인 (2초)

> banded-partner-platform@28.68.0 test:contract
> vitest run src/domain/ports.contract.test.ts

stdout | src/domain/ports.contract.test.ts > 계약 대상 (28-68) > 어떤 구현이 이 계약을 통과했는지 드러난다
[계약 대상] LocalSnapshotPort, MemoryRemotePort, HttpSnapshotPort

 ✓ src/domain/ports.contract.test.ts (34 tests) 271ms
 Test Files  1 passed (1)
      Tests  34 passed (34)

$ psql "$DATABASE_URL" -c "select count(*) as 스냅샷_행수 from snapshots;"
 스냅샷_행수
-------------
           4
```

서비스 컨테이너 로그:
```
2026-09-04 21:18:21.975 UTC [1] LOG:  starting PostgreSQL 16.15 (Debian 16.15-1.pgdg13+2)
2026-09-04 21:18:21.985 UTC [1] LOG:  database system is ready to accept connections
```

**진짜 Postgres 16.15에 스냅샷 4행이 실제로 저장됐다.** 그 4행을 쓴 것은 `HttpSnapshotPort` →
`api/snapshot.ts` → `pg` 경로다. 이번 라운드의 핵심 증거가 CI에서 성립했다.

`CONTRACT_API_URL`이 주어졌으므로 `HttpSnapshotPort`가 계약 대상에 **반드시** 들어와야 했고,
`[계약 대상]` 줄이 그것을 출력한다 — 조용한 축소를 막는 장치가 실제로 작동한다.

컨테이너 로그에 `FATAL: role "root" does not exist`가 10초 간격으로 두 번 찍혀 있다.
이것은 서비스 컨테이너의 헬스체크(`pg_isready`)가 OS 사용자 이름으로 붙어서 나는 것이고,
우리 단계는 전부 `$DATABASE_URL`(postgres 역할)로 붙는다 — 스키마 적용도 4행도 그 증거다.

`gates` job도 초록이다(2분 36초).

## 7. 정직하게 남기는 것

- **프로덕션 DB는 아직 안 붙었다.** `initReplicator()`의 원격은 여전히 `MemoryRemotePort`다.
  즉 **배포된 앱의 동작은 28-67과 같다** — 로컬이 진실이고 복제는 메모리 그림자다.
  붙이는 절차는 `서버_연결.md`에 있고, 붙일 때 바뀌는 것은 그 함수의 한 줄이다.
- **인증은 워크스페이스 경계이지 테넌트 경계가 아니다.** 공유 시크릿 한 겹이라
  **시크릿을 아는 누구나 전체 스냅샷을 읽고 쓴다.** 28-69의 일이다.
- **`server` job은 CI에서 초록이다** (위 4절에 로그를 인용했다). 로컬과 CI 양쪽에서 같은 경로가 돌았다.
- 배포 확인(`deploy-check`이 라이브 번들에서 `28-68`을 보는 것)은 **병합 뒤**에 읽고 보고한다.
  그 전에는 "배포됐다"고 적지 않는다.
- `api/` 함수가 프로덕션에서 실제로 서빙되는지는 환경변수가 없으면 **503**을 답하는 것까지만
  확인할 수 있다. 그 사실 그대로 적는다.
