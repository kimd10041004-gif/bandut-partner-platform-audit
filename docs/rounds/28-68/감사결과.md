"사용자별 분리"가 실제로 뜻할 수 있는 것은 둘이고, 하나만 지금 모델에서 가능하다:

### 28-68-01 (상) `rev`는 기기별 로컬 카운터다 — 낙관적 동시성이 성립하지 않고, rev가 같으면 **conflict 없이 조용히 덮어쓴다**

`platform.ts:3286` `this.rev = Math.max(this.rev, stored ?? 0) + 1` — 기기마다 독립적으로 증가하는 자기 카운터.
두 기기의 rev가 같아지는 것은 예외가 아니라 정상이다(각자 5번 저장하면 둘 다 5).

```
1. A(rev 5) write → 원격 {rev 5, A}. A.knownRemoteRev = 5
2. B(rev 5, 내용 다름) sync: read → remote.rev(5) > rec.rev(5) 거짓 → accept 안 함 → knownRemoteRev = 5
3. B write({rev 5, B}, expected 5) → `where rev = 5` 맞음 → 200. 원격 = B
4. A 다음 sync: knownRemoteRev(5) === revision(5) → 'synced' 즉시 반환, read조차 안 함
5. A 다음 저장(rev 6): write(rev 6, expected 5) → 또 맞음 → B를 통째로 덮는다
```

conflict가 **한 번도** 나지 않는 무결성 손실이다. 계약 테스트가 못 잡는 이유는 모든 케이스가 writer 하나이거나 rev가 다른 둘이기 때문이다.
곁들여 셋:
- `api/snapshot.ts:157` 검증이 `rev >= 0`뿐 — `{rev:1, expectedRev:500}`으로 **카운터를 되감을 수 있다**. 되감기면 다른 기기가 conflict + `remote={rev 1}`을 받고 `replicator.ts:231` `acceptOrReset`이 **rev를 비교하지 않고 무조건 accept** → 최신 상태를 rev 1 본문으로 되돌린다.
- read 경로(`:192` `remote.rev > rec.rev`일 때만 accept)와 conflict 경로(`:231` 무조건 accept)가 **누가 이기는지에 대해 서로 다르다** — 같은 상황이 `knownRemoteRev`가 캐시됐는지에 따라 반대 결과가 난다.
- **근본 수정**: 서버가 rev를 발급한다(`set rev = rev + 1 … returning rev`). 클라이언트 rev는 기대값으로만 쓴다. `$2 > rev` 불변식을 SQL이 지킨다.

### 28-68-02 (상) 배선을 살린 것이 새 결함 넷을 만들었다 — 그리고 라운드의 테스트가 그 메커니즘을 꺼 놓았다

`replicator.ts` / `PlatformContext.tsx`

**(a) 조기 반환은 저장 경로에서 도달 불가다.** `save()`가 `rev`를 올린 **뒤** `onSaved`를 부른다(`platform.ts:3286-3292`) → `markChanged` → `'pending'` → `armRetry(0ms)` → `run()`의 `knownRemoteRev === revision()`은 **구조적으로 거짓**. 결과: **57개 save 지점 하나하나가 전체 스냅샷(사진 포함, 들여쓰기)을 직렬화**해 페이지를 닫으면 사라지는 메모리 포트에 넣는다. 28-67은 focus 때만 했다. 28-68은 "매번 직렬화를 없앴다"고 적으면서 **탭 전환당 2회를 조작당 1회로 바꿨다** — 순손실이다.

**(b) 재시도 굶김.** `armRetry()`(`:102-109`)가 `cancelRetry?.()`로 기존 예약을 **무조건** 죽이고 다시 건다. `setStatus('pending')`은 매 저장마다 `armRetry`를 부른다(`:130`, 상태가 안 바뀌어도). 오프라인에서 `failures ≥ 5`(백오프 16초+)이면, 사용자가 16초보다 자주 저장하는 한 **재시도가 영원히 발화하지 않는다** — 정확히 동기화가 가장 필요한 때에.

**(c) conflict + `remote === null` 경로가 0ms 스핀.** `:220-228`이 `failures = 0`으로 되돌리고 `'pending'` → `armRetry(0)`. 이 경로는 실패를 세지 않는 **유일한** 실패 경로이면서 즉시 재예약한다. 서버가 반복해서 `remote:null`을 주면(지연 복제본, 행 삭제·재생성) 매크로태스크마다 **전체 스냅샷 직렬화 + read + write**를 무한 반복하고, detail 문자열이 상수라 `onStatus`는 첫 회 뒤 침묵 — CPU 100%인데 화면은 조용하다.

**(d) `stop()`이 끈적이지 않는다.** `:90-93`에 `stopped` 플래그가 없다. 언마운트 시 `stop()`이 돌아도, 진행 중이던 `run()`이 `setStatus('offline')`에 닿으면 `:130`이 **다시 armRetry** — 떨어져 나간 복제기가 백오프마다 영원히 깨어난다. `:87-88` 독스트링이 정확히 이 보장을 약속하지만 코드는 주지 않는다.

**(e) 테스트가 메커니즘을 꺼 놓았다.** `replicator.test.ts:34-36` 헬퍼가 모든 행동 테스트에 `scheduleRetry: null`을 넣는다. `markChanged → armRetry(0) → sync` — **유일한 프로덕션 트리거** — 를 태우는 테스트가 하나도 없다. (a)(b)(c)가 초록인 이유다. `:279-303`("직렬화조차 하지 않는다")은 수동 `sync()`만 세어 focus 경로를 검증하면서, 저장 경로에서는 거짓인 주장의 근거처럼 읽힌다.

### 28-68-03 (중) HTTP 경로 — 고칠 수 없는 오류를 영원히 재시도하고, CI 서버는 본문을 깨뜨리며 인증 전에 무한히 받는다

**(a)** `httpPort.ts:64,86` — non-200 전부 `unavailable`. 401(토큰 회전)·413(용량)·400·405가 "오프라인"으로 표시되고 30초마다 **영원히** 재시도한다. 413이면 수 MB 업로드 무한 반복. Vercel Functions 본문 상한(4.5MB급)이 `MAX_BODY_CHARS = 8MB`보다 작아 프로덕션에서는 8MB 검사에 닿기도 전에 플랫폼 413(JSON 아님) → "해석할 수 없습니다" → 같은 루프. `WriteResult`/`ReadResult`에 **비재시도 갈래(`rejected`)**가 필요하다.

**(b)** `scripts/api-server.mjs:40` `text += c` — Buffer를 청크마다 `toString`. 한글(3바이트)이 64KB 청크 경계에 걸리면 앞뒤가 각각 `U+FFFD`. **`JSON.parse`는 성공한다**(U+FFFD는 유효 JSON 문자) → 손상 본문이 DB에 그대로 저장. 계약 테스트 본문은 수십 바이트라 CI가 절대 못 잡는다. "CI가 검증한 서버"라는 신뢰가 여기서 거짓이 된다.

**(c)** `api-server.mjs:58` `readBody`가 `handleSnapshot`(=인증) **앞**이고 상한이 없다. 토큰 없는 클라이언트가 512MB를 흘리면 `data` 리스너 안에서 `RangeError: Invalid string length` → Promise executor의 try 밖 → `uncaughtException`으로 **프로세스 종료**. `MAX_BODY_CHARS`(`api/snapshot.ts:104`)는 `JSON.parse` 뒤라 파싱 비용을 못 막고, 이 상수의 테스트는 0건이다.

### 28-68-04 (중) 화면·게이트·문서가 코드와 어긋난다 — 주석이 코드보다 앞서고, 게이트는 자기 전제를 못 잡는다
