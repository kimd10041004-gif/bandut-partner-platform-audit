# 서버 연결 — 절차와 현재 상태 (28-68 작성 · 28-69 정정 · 28-70 완성)

28-67이 경계(`SnapshotPort`)를 놓았고, 28-68이 그 반대편(스키마·API·HTTP 어댑터)을 채웠고, 28-69가 붙여도
데이터가 깨지지 않게 고쳤고, **28-70이 계정·세션(인증)을 넣어 붙일 수 있게 했다.** 이 문서는 무엇이 있고,
프로덕션에서 켜려면 무엇을 해야 하는지를 적는다.

## 원칙 (28-68·28-69 감사 정정)

**워크스페이스는 하나다.** 스냅샷은 마켓플레이스 전체(모든 고객의 요청·모든 파트너의 입찰)다.
"사용자별 워크스페이스"는 마켓플레이스를 사용자 수만큼 쪼개는 것이라 성립하지 않는다.
`workspace` 파라미터는 CI 계약 테스트가 격리된 행을 쓰기 위한 것이고, 프로덕션은 `main` 하나다.

"사용자별 분리"가 뜻할 수 있는 것은 **인증**(서버가 확인한 계정·세션 — 28-70이 했다)뿐이고,
**인가**(자기 것만 읽고 쓰기)는 통째 스냅샷 모델에서 불가능하다 — 엔티티 단위 API가 있어야 한다.
로그인한 계정은 누구나 스냅샷 전체를 읽고 쓴다. 대신 `snapshots.updated_by`에 **누가 썼는지**가 남는다.

## 인증 모델

- 로그인은 `/api/auth`의 `login`이 처리하고 **불투명 토큰**을 발급한다. 서버에는 `sha256(토큰)`만 있다.
  만료는 도메인의 `SESSION_TTL_MS`(고객·파트너 24h, 관리자 8h), 로그아웃·정지·탈퇴·파기 때 폐기된다.
- 브라우저는 역할별로 토큰 하나씩(`banded-session-v1`) — 고객·파트너·관리자 동시 로그인 모델 그대로다.
- 클라이언트의 `AuthService`는 **거울**이다. 렌더 중 읽기(`sessionFor`·`listAccounts`·`accountFor`)는 그대로 동기,
  변경은 `authActions`(async)만. 거울에서 변경 메서드를 직접 부르면 던진다.
- 관리자 초기 비밀번호는 `ADMIN_PASSWORD` 환경변수. 없거나 8자 미만이거나 시연값(`bandut1234!`)이면 `/api/auth`가
  **503**이다 — 시연 비밀번호로 열리지 않는다. 행이 처음 만들어질 때 **소유자 `admin`**에게 적용되고,
  그 뒤는 관리자 화면의 비밀번호 변경이 진실이다.
- **관리자는 여럿이고 등급이 있다** (28-89-A). `AuthService.admins[]`에 `{id, name, grade}`가 있고,
  등급은 `owner`·`manager`·`viewer` 셋이다(표: `src/domain/adminGrade.ts`). 로그인하면 세션에 실리고
  **`sessions.grade` 열**에 저장된다 — 28-89 이전에 발급된 세션은 등급이 없어 아무 관리자 op도 못 한다
  (다시 로그인하면 실린다). 등급 변경·제거·비밀번호 초기화는 그 계정의 서버 세션을 전부 폐기한다.
  `api/auth.ts`는 op마다 필요한 등급을 보고 403, `api/snapshot.ts`는 **열람 등급의 `PUT`을 403**으로 막는다.
  **못 막는 것**: 스냅샷은 통째 쓰기라 서버가 `manager`와 `owner`를 `PUT`에서 구별하지 못한다 —
  매니저가 화면을 우회해 직접 PUT하면 파기·복원도 막히지 않는다. 엔티티 단위 API가 생겨야 막힌다(이월).
- OTP는 여전히 `register` 응답에 온다(시연). SMS 연동 지점은 `api/auth.ts`의 `register` 한 곳이다.
- 서버 모드에는 **시연 시드가 없다** — 첫 기기가 시연 데이터를 프로덕션 스냅샷으로 밀어 올리지 않게.

## 켜기 전 전제 (28-70 감사 · 28-71) — 이것을 읽지 않고 켜지 말 것

- **가입 코드를 아는 사람 = 마켓플레이스 전체의 읽기·쓰기 권한이다.** OTP가 응답에 실리는 시연 단계라 `verified`는 휴대폰 소유를
  뜻하지 않고, 로그인한 계정은 누구나 스냅샷 전체(모든 고객의 연락처·사진, 모든 파트너의 계좌 표기, 채팅)를 읽고 통째로 쓴다.
  그래서 `SIGNUP_CODE`(12자 이상)가 없으면 가입이 503이고, 코드는 **아는 사람에게만** 준다. 코드가 새면 바꾼다(기존 계정은 그대로).
  SMS 인증과 엔티티 단위 인가가 들어오기 전까지 이 플랫폼의 서버 모드는 **초대제 파일럿**이다.
- 관리자 정지(`setSuspended`)가 계정의 모든 세션을 즉시 폐기한다 — 코드가 샜을 때의 대응 수단이다.
- **잠금은 2단이고, 계정 잠금에는 IP 면제가 있다** (28-71-02 + 28-72-02 + 28-73-03).
  ① (계정, 요청 IP)당 5회 → 15분: 남의 IP에서 낸 실패가 내 로그인을 잠그지 않는다.
  ② **계정당 30회 → 15분**: IP와 무관한 카운터다. 단, **최근 30일 안에 그 계정으로 성공한 IP는 ②에서 면제**된다
  (계정당 5개까지 기억; 30일 지난 것은 로그인 때마다 `pruneTrustedIps`가 쓸어낸다 — 그 계정이 다시 오지 않아도.
  탈퇴하면 그 번호로 된 키는 즉시 버린다 — 28-75. 스윕은 **1시간 게이트**로만 돈다 — 로그인마다 전체
  계정을 훑으면 무차별 대입이 CPU를 계정 수만큼 먹는다. 게이트 시각(`trustedSweptAt`)은 스냅샷에 남는다:
  서버리스는 요청마다 인스턴스를 새로 만들어서 메모리에만 두면 게이트가 없는 것과 같다 — 28-76).
  **면제는 요청 IP를 믿을 수 있을 때만 성립한다**: `x-forwarded-for`·`x-real-ip`가 없으면 `api/auth.ts`가
  잠금 범위를 아예 넘기지 않으므로(28-75) 기록도 면제도 없다. 그러지 않으면 모두가 공유하는 `'unknown'`이
  신뢰 IP로 남아 **누구나** ②에서 면제된다. 그래서 30회를 채워 남을 잠그려는 시도가 **늘 쓰던 자리의 운영자를 막지 못한다** —
  ②가 없애려던 무차별 대입은 여전히 30회에서 막힌다(공격자의 IP는 성공한 적이 없다). ②가 없던 28-72까지는 IP를 바꾸면 카운터도 바뀌어 한 계정에 15분당 수천 회를
  시도할 수 있었다(28-72 감사 02). **이제 무차별 대입은 15분당 30회로 막힌다** — 이전 판 문서의 "(계정, IP)당 5회 + 8자 최소로
  막힌다"는 사실이 아니었다. 대가로 DoS는 여전히 가능하다: 남의 계정에 30회를 실패시키면 15분 잠근다(5회보다는 6배 비싸다).
- IP별 실패 제한(60초 20회 → 429, 가입 코드 오류는 5회분)은 서버리스 인스턴스 로컬이라 완화일 뿐이다.
- 잠금 범위와 IP 제한은 `x-forwarded-for`(없으면 `x-real-ip`)의 첫 IP를 믿는다 — **Vercel은 이 헤더를 덮어쓴다**.
  로컬 `scripts/api-server.mjs`는 클라이언트가 보낸 값을 그대로 쓰므로 인터넷에 노출하지 말 것.
  **둘 다 없으면** 모든 요청이 같은 값(`unknown`)을 쓰게 되어 잠금 범위와 IP 제한이 **전원 공유로 무너진다**(= 28-71-02 이전).
  그때 `/api/auth`가 프로세스당 한 번 경고를 남긴다(28-72-04c) — 프록시 없는 자체 호스팅이라면 로그에서 이 줄을 확인할 것.
- `SIGNUP_CODE`는 **12자 이상 무작위**여야 한다: `node -e "console.log(require('crypto').randomBytes(18).toString('base64url'))"`.
  `verifyOtp`도 가입 코드를 요구한다 — 대기 중 가입의 OTP를 남이 소진하지 못한다.
- `scripts/e2e-server.mjs`는 DB를 **비우고** 시작한다. DB 이름에 `test`가 **단어로** 들어가야 돌아간다
  (`bandut_test` ✓ · `bandut_latest` ✗ · `testdb` ✗ — 마지막은 안전한 방향의 오탐이다). `E2E_ALLOW_TRUNCATE=1`로만 강제할 수 있다.
  프로덕션 `DATABASE_URL`로는 절대 돌리지 말 것.
- 세션 행은 로그인 성공 때 30일 지난 만료·폐기 행이 정리된다. 별도 cron은 없다.
- 브라우저의 스냅샷이 손상돼 리셋되면 그 브라우저는 새 기기로 취급돼 원격을 받아들인다(커서를 지운다). 빈 로컬이 서버를 덮지 않는다.
- 로그인은 첫 접촉(원격 받아들이기)이 끝나야 끝난다 (28-71-01, 28-72-01에서 완성) — 로그인 직후의 저장(파트너 프로필 시드)이
  덮이지 않는다. 28-72까지는 다른 동기화가 진행 중이면 로그인이 **그것**을 기다리고 끝나 같은 증상이 남아 있었다.
- **conflict로 덮이는 이 기기의 변경은 보관된다** (28-72-03). 통째 스냅샷은 병합할 수 없어 덮이는 것 자체는 모델의 성질이지만,
  덮인 본문은 브라우저의 `banded-platform-v1:overwritten`(최근 3개)에 남고 관리자 설정의 백업 카드에서 **목록으로**
  전부 내려받아 같은 화면의 복원 입력으로 되살릴 수 있다(28-73-04).
- **보관함도 저장 용량을 쓴다** (28-73-01). 브라우저 한 오리진의 할당량은 스냅샷과 보관함이 함께 쓴다 —
  보관함은 한도의 1/4(약 1MB) 예산 안에서만 유지되고(넘치면 오래된 것부터 버린다), 관리자 "저장 용량" 카드와
  용량 가드가 **그 크기를 포함해** 계산한다. 그러지 않으면 가드가 통과시킨 저장이 브라우저에서 실패한다.

## 프로덕션에서 켜는 절차 (사용자 대시보드 — 이 순서대로)

1. **Neon 연결** — Vercel 대시보드 → 프로젝트 → Storage → Neon 통합. `DATABASE_URL`이 주입된다.
   **`-pooler` 엔드포인트를 쓴다** — `server/db.ts`의 `pg.Pool`은 서버리스 인스턴스마다 생기므로
   pooled 엔드포인트가 아니면 인스턴스 수 × 3 커넥션이 무료 티어 상한을 넘긴다.
2. **스키마** — `psql "$DATABASE_URL" -f db/schema.sql` (멱등).
3. **`ADMIN_PASSWORD`** — 8자 이상, 시연값이 아닌 것. 관리자 첫 로그인 비밀번호다.
   **`SIGNUP_CODE`** — 12자 이상 무작위(위 전제의 생성 명령). 가입 폼의 "가입 코드"에 넣어야 가입·인증된다.
4. **`VITE_AUTH_MODE=server`** — 빌드 환경변수. 이것이 없으면 배포된 앱은 지금처럼 로컬 모드다(동작 무변화).

> **28-87**: 켜기 전 확인은 `npm run preflight:server`가 하고, 절차·되돌리기·위험은
> **`28-87/서버_모드_전환.md`**에 있다. 그리고 지금 라이브가 **어느 모드로 서빙 중인지**는
> `deploy-check`가 서빙 번들의 `bandut-auth-mode:` 표식을 읽어 매 배포마다 보고한다 —
> 28-68 이후 스무 라운드 동안 프로덕션이 로컬 모드였는데 아무 기계도 그것을 말하지 않았다.
5. **재배포** → `/admin`에서 `admin` / `ADMIN_PASSWORD`로 로그인 → 헤더의 라운드 표기에 `data-auth-mode="server"`.
6. **확인** — 기기 둘로 가입·요청·입찰이 오가는지. CI의 `e2e:server`가 하는 것과 같은 여정이다.

1~3은 지금 해도 된다(해도 앱 동작은 안 바뀐다). 4를 켜기 전에는 배포 동작이 무변화다.
28-68 판의 `WORKSPACE_SECRET`은 **없앴다** — 인증 경로는 세션 토큰 하나다.

## 환경변수가 없을 때

`/api/snapshot`은 `DATABASE_URL`이 없으면 503, `/api/auth`는 `DATABASE_URL`·`ADMIN_PASSWORD` 중 하나라도
없거나 `ADMIN_PASSWORD`가 시연값이면 503, `register`는 `SIGNUP_CODE`가 없으면 503을 답한다. 인증 없는 저장소로 조용히 열리지 않는다.
DB 오류 원문은 서버 로그에만 남고 클라이언트에는 일반 문구가 간다.

## 본문 상한

Vercel Functions의 요청 본문 상한은 4.5MB급이다. `MAX_BODY_CHARS`는 그 아래인 **4MB**
(도메인의 `STORAGE_SOFT_LIMIT`과 같은 급). 넘으면 API가 413을 내고, 클라이언트는 `rejected`로 받아
**재시도하지 않는다**. CI 서버는 인증·파싱 **전에** 바이트 상한을 건다.

## 붙인 뒤 누가 이기는가

원격이 비었으면 밀어 올린다. 원격이 있고 이 브라우저가 한 번도 밀어 올린 적 없으면(커서 없음) 받아들인다.
그 뒤로는 "원격 rev가 내가 마지막으로 본 값과 다르면 남이 썼다 → 받아들인다". 이때 **마지막 반영 이후의
로컬 변경은 덮인다** — 통째 스냅샷은 병합할 수 없다. 화면은 덮인 로컬 변경이 있었을 때만 "덮였습니다"라고 말한다.

- 탭 복귀 때는 `head`로 rev만 확인한다 — 보기만 하는 기기도 남의 변경을 본다 (28-69-01).
- 커서(`banded-platform-v1:remote`)는 탭 사이에 공유된다 — 같은 브라우저의 두 탭이 서로를 conflict로 만들지 않는다.
  다른 탭의 저장(storage 이벤트)은 받기만 하고, 보내는 것은 변경을 만든 탭의 디바운스 몫이다 (28-69-02).

## 왜 `pg`이고 `@neondatabase/serverless`가 아닌가

CI의 평범한 `postgres:16` 컨테이너에 붙어야 하고, 그래야 **프로덕션과 CI가 같은 코드 경로**를 탄다.
대가는 위 1단계의 `-pooler`다.
