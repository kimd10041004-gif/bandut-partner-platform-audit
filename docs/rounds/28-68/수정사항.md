# 28-68 수정 사항

**서버 저장 계층 + 28-67 감사 4건.** 28-67이 놓은 경계(`SnapshotPort`)의 반대편을 채웠다 —
스키마·API·HTTP 어댑터를 만들고, **CI에서 진짜 Postgres 16에 대고** 검증한다.
그 전에 감사가 찾아낸 복제기의 치명 결함 셋을 먼저 고쳤다(서버가 붙는 순간 전부 발현하는 종류다).

## A. 28-67 감사 4건

### 28-67-01 (상) 예금주 실명이 평문이라 파트너 본인 열람권이 실패했다 — **재현됨**

**먼저 재현했다.** 예금주 = 가입명 ≠ 업체명인 계정에서:

```
PlatformError: 가명 처리에 실패했습니다 — 결과에 실제 식별자가 남아 있습니다: 김반듯
 ❯ assertNoRealIdentifiers src/domain/platform.ts:368:11
 ❯ PlatformService.exportPartnerData src/domain/platform.ts:3657:5
```

근본 원인은 `PayoutRecord.account`가 **문자열 한 덩어리**라는 것이었다.
`payoutAccountLabel()`은 계좌번호만 마스킹하고 예금주는 평문으로 남기는데, `markPayout`이 그 문자열을
통째로 저장했고, 열람권 JSON이 그것을 그대로 실었다. 28-66-02가 *"이미 마스킹된 본인 값"*이라 적은 것이
절반만 참이었다.

**고친 방식 — 빼지 않고 마스킹한다.** 28-66-02의 결론(근거는 줘야 한다)과 자체 검사(실명은 나가면 안 된다)를
둘 다 지킨다.

- `domain/auth.ts`: `maskHolder()`·`payoutAccountLabelMasked()`·`payoutAccountLabels()` 추가.
  예금주는 첫 글자만 남긴다(`김반듯` → `김**`). `assertNoRealIdentifiers`가 3자 미만을 건너뛰므로 2자 이름도 안전하다.
- `types.ts`: `PayoutRecord.accountMasked?` 추가. `account`(실명 포함)는 **운영 내부 근거**로만 남는다.
- `markPayout`이 표기 **두 벌**을 받는다 — `{ label, masked }`. 문자열 하나만 받던 때는
  호출부가 어느 쪽이 필요한지 고를 수 없었고, 그것이 정확히 이 사고였다.
- `EXPORT_PAYOUT_KEYS`: `'account'` → `'accountMasked'`.
- `partnerLedger`(정산 CSV)도 같은 값을 쓴다 — **CSV와 JSON이 같은 값을 준다**는 28-66-02의 결론을 지킨다.
- 관리자 두 화면(`AdminOverview`·`AdminSettlement`)이 `payoutAccountLabels(acc)`를 넘긴다.
  화면 표시에는 `.label`(실명)을 그대로 쓴다 — 관리자는 이체 확인이 필요하다.

**28-67의 회귀 테스트가 왜 못 잡았는가**: `markPayout(r.id, '국민 123-**-**7890')` —
예금주가 없는 문자열이었고 `extraNames`도 비어 있어 그 경로를 태우지 않았다.
28-65·28-66에 이어 **세 번째 같은 실패 형태**다. 새 테스트는 `payoutAccountLabels(...)`로
관리자 화면이 실제로 넘기는 값을 만든다.

### 28-67-02 (상) 복제기의 치명 결함 셋

`src/domain/replicator.ts` · `ports.ts` · 두 어댑터

**(a) `write()`에 try/catch가 없었다.** reject 한 번이면 `sync()`의 `await`가 throw →
`again` 재실행 블록에 도달하지 못해 **영구히 true**로 고착 → 상태 `'syncing'`에 멈춘 채 회복 불가.
→ `write()`를 감싸 `unavailable`로 정규화하고, **그것과 별개로** `sync()`도 감쌌다.
`run()`이 어떤 이유로 던지더라도 `again`이 고착되지 않는다(두 겹으로 잠근다).

**(b) `knownRemoteRev`를 `accept()`보다 먼저 갱신했다.** `accept`는 손상 본문에 던지도록
**설계된** 동작이고, 던지면 rev는 이미 갱신된 뒤라 다음 sync가 read를 건너뛰고 곧장 써서
**더 새로운 원격을 더 오래된 로컬로 덮었다**. `"남의 변경을 덮지 않는다"`가 정확히 깨졌다.
→ `acceptOrReset()`으로 묶었다. accept가 성공한 **뒤에만** rev를 갱신하고, 실패하면 `undefined`로 되돌려
다음 sync가 read부터 다시 한다.

**(c) `{rev: 0, body: ''}` 센티널이 영구 conflict 루프를 만들었다.**
→ 센티널을 없앴다. `WriteResult`의 conflict가 `remote: SnapshotRecord | null`이 되어
**타입이 분기를 강제한다.** `remote === null`이면 `knownRemoteRev = undefined`로 되돌려 다시 읽는다.

**곁들여**: offline 뒤에도 rev를 되돌려, 주석이 적은 *"재접속 시 다시 읽는다"*를 참으로 만들었다.

회귀 테스트 4건. **전부 수정 전 코드에서 실패하는 것을 먼저 확인했다**(검증결과.md에 출력 인용).

### 28-67-03 (중) 죽어 있던 배선을 살렸다

### 28-67-04 (중) 오류 규약을 계약에 넣고, 보증 문구 대신 **보증 자체를 넓혔다**

- **`ReadResult` 신설** — `read()`는 던지지 않는다. 28-67은 write에만 결과값 규약을 둬서
  `MemoryRemotePort.read()`는 던지고 `LocalSnapshotPort.read()`는 안 던지는 상태였는데
  공유 계약이 그것을 못 잡았다. 이제 계약 테스트의 각 구현이 **실패를 주입받아** 확인된다
  (로컬은 던지는 storage, 메모리는 `failFor`, HTTP는 닿을 수 없는 주소).
- `LocalSnapshotPort`가 접근 실패를 "비어 있다"로 바꾸지 않는다 — `{ok:false, detail}`이다.
  복제기가 "원격이 비었다"로 오해할 수 있던 자리다.
- `src/ui/image.ts:47`의 마지막 맨 `Error` → `ImageError`.
- 두 호출부(`CustomerRequest.tsx`·`Work.tsx`)를 `isKnownError`로 조였다 —
  28-67이 `ImageError`를 만든 목적이 이 두 줄인데 정작 거기는 그대로였다.
- **`errors.test.ts`에 소스 글자 훑기를 넣었다.** export한 *클래스*를 찾는 기존 방식은
  `throw new Error(...)` **문장**을 원리적으로 못 본다. 이제 소스를 정규식으로 훑는다
  (주석은 제거한다 — 규칙을 설명하는 문장이 스스로 위반으로 잡히지 않게).
  예외는 개발자 실수를 던지는 두 자리뿐이고 **이유와 함께** 테스트 안에 적혀 있다.
  이 훑기가 즉시 `src/domain/hash.ts`를 하나 더 찾아냈다.
- `errors.ts`의 보증 문단을 **두 겹**으로 나눠 정확히 적었다.

## B. 서버 저장 계층

### `db/schema.sql`
워크스페이스당 스냅샷 한 행. 낙관적 동시성이 **SQL 한 줄**이 된다 —
포트의 `expectedRev`가 그대로 `where rev = $4`가 되고, 0행이면 conflict다.
`body`는 `jsonb`가 아니라 `text`다: 도메인이 만든 바이트를 그대로 되돌려줘야 rev와 본문이 짝이 맞는다.

### `api/snapshot.ts`
`GET` → `{record}` · `PUT` → `200 {rev}` / `409 {reason,remote}` / `503`.
인증은 `Authorization: Bearer <WORKSPACE_SECRET>` 한 겹.
핸들러 본체(`handleSnapshot`)가 HTTP 프레임워크에 의존하지 않아서,
**Vercel 진입점과 CI의 최소 서버가 같은 함수를 부른다.**

`@neondatabase/serverless`가 아니라 `pg`를 쓴다 — CI의 평범한 postgres 컨테이너에 붙어야 하고,
그래야 프로덕션과 CI가 **같은 코드 경로**를 탄다.

### `tsconfig.api.json` — 게이트가 안 보는 코드를 두지 않는다
`tsconfig.json`의 `include`가 `["src", ...]`라 `api/`는 `tsc --noEmit` **밖**이었다.
28-64-01이 지적한 "게이트가 안 보는 코드"의 재발이다. `typecheck` 스크립트가 이제 둘 다 돈다.

### `src/domain/ports/httpPort.ts`
`SnapshotPort` 구현. **던지지 않는다** — fetch의 네트워크 오류·타임아웃·JSON 파싱 실패를
전부 결과값으로 옮긴다. 서버 응답의 모양도 검사한다(`recordOf`) — 어긋난 응답을 "비어 있다"로 삼지 않는다.

### CI `server` job — **이번 라운드의 핵심 증거**
`services: postgres:16` → 스키마 적용 → `scripts/api-server.mjs` 기동 → 계약 테스트.
DB 프로비저닝을 기다리지 않고 SQL·API·어댑터가 **진짜로** 검증된다.
`CONTRACT_API_URL`이 있으면 `HttpSnapshotPort`가 계약 대상에 **반드시** 들어오고,
안 들어오면 "계약 대상" 테스트가 실패한다 — 조용한 축소를 막는 장치다.

### `28-68/서버_연결.md`
Neon 연결 절차와, **지금 이 API는 워크스페이스 경계이지 테넌트 경계가 아니라는 사실**을 명시했다.
