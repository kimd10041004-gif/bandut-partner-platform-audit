# 28-81 감사결과 (GPT 감사자 역할)

**대상**: `6cb0a1a`(#222) + `52cc4d6`(#223) — 28-81이 새로 넣은 것.

라운드는 28-80 감사 4건을 전부 닫았고, 특히 **두 가지를 스스로 밝힌 것**이 좋다: 28-81-04는 수정 전에도
통과한다는 것(실패를 만들려고 도달 불가능한 상황을 꾸미지 않았다), 그리고 지표가 나타나는 쪽을 e2e가
덮지 못한다는 것(§3). 이 루프가 요구하는 정직함에 맞는다.

그런데 세 라운드에 걸쳐 랜딩을 정직하게 만드는 동안, **고객이 실제로 업체를 고르는 화면은 아무도 보지
않았다.** 01이 그것이고, 이번 감사에서 유일한 「상」이다.

---

## 01 (상) 랜딩은 깨끗해졌는데, **고객이 업체를 고르는 화면**은 여전히 시드를 내건다

부팅 경로를 그대로 태워 두 값을 나란히 찍었다(시드만 있는 첫 방문 상태):

```
랜딩 공개 지표 — {"totalRequests":0,"completedOrSettled":0,"winRate":null,"average":null,"reviewCount":0}
업체 카드     — 완료: 3 건 / 낙찰률: 100 % / 리뷰: 0 건 / 평점: null
```

`PartnerCard`(`src/ui/PartnerCard.tsx`)가 그리는 것:

```tsx
<span className="rate">{s.average === null ? '—' : `★${s.average}`}</span>
<span className="part">리뷰 {s.reviewCount}건</span>
<span className="part">완료 {s.completedCount}건</span>
<span className="part">낙찰률 {s.winRate === null ? '—' : `${s.winRate}%`}</span>
```

값은 전부 `partnerSummary()`에서 오고, 그 안은 **시드를 하나도 걸러내지 않는다**:

```ts
completedCount: counts.completed + counts.settled,
winRate: this.bidStats(partnerId).winRate,       // ← excludeSeeded를 넘기지 않는다
```

그리고 이 카드를 쓰는 화면은 `CustomerHome.tsx`와 **`CustomerEstimates.tsx`(견적함)** 이다. 견적함은
고객이 **여러 업체의 견적을 비교해 누구에게 맡길지 정하는 자리**다. 즉 시드가 만든 "완료 3건 · 낙찰률
100%"가 랜딩의 장식이 아니라 **구매 결정의 근거**로 들어간다.

이것이 「상」인 이유는 두 가지다. 첫째, 세 라운드(28-79·80·81)가 고친 것과 **같은 결함**인데 한 화면 옆에
그대로 있다. 둘째, 28-81은 `bidStats(partnerId, { excludeSeeded })`를 **바로 이번 라운드에 만들어 놓고**
`partnerSummary`에는 넘기지 않았다 — 도구를 손에 쥐고 옆을 보지 않은 것이다.

`UI_가이드.md`에 이번 라운드가 적은 규칙("공개 화면이면 `publicStats()`를 쓰고 값이 0이면 그리지 않는다")도
랜딩만 이야기하고 업체 카드를 말하지 않는다. 규칙이 좁게 쓰여 있어서, 규칙을 지켜도 이 화면은 남는다.

**고치는 방향**: `partnerSummary(partnerId, today, { excludeSeeded })`로 시드를 뺀 실적을 낼 수 있게 하고,
**고객에게 보이는 경로**(`PartnerCard`)는 그것을 쓴다. 파트너 자신의 대시보드·관리자 화면은 지금 값 그대로
둔다(그 사람들은 기기에 있는 것을 봐야 한다 — 28-80이 세운 구분과 같다). 실적이 0이면 랜딩과 같은 이유로
숫자 대신 "아직 실적 없음"을 보인다. `UI_가이드.md`의 규칙 문장을 "랜딩"이 아니라 **"고객에게 보이는 모든
화면"**으로 넓힌다.

## 02 (중) 히어로 지표의 **렌더링 경로**가 이제 어떤 테스트로도 덮이지 않는다

`검증결과.md` §3은 이렇게 적었다 — "그 방향은 e2e가 아니라 단위 테스트가 덮는다". **정확하지 않다.**
`publicStatsGate.test.ts`가 덮는 것은 **판단**(`showPublicStats`의 네 조합)이고, **렌더링**이 아니다.

그리고 이 저장소에는 `Landing`을 렌더하는 테스트가 **하나도 없다**:

```
$ grep -rln 'Landing' src --include=*.test.ts --include=*.test.tsx
(출력 없음)
```

로컬 모드에서 `showPublicStats`는 **항상 거짓**이므로, e2e 여정의 두 단언은 둘 다 "없다"이다:

```js
step('첫 방문(시연 데이터뿐): 히어로 실적 지표가 없다 (28-79-01)', (await page.$('[data-hero-stats]')) === null)
step('실제 요청 1건 등록 뒤에도 로컬 모드는 히어로 지표를 내걸지 않는다 (28-81-01)', … === null)
```

즉 **히어로 지표 블록의 JSX를 통째로 지워도 네 게이트가 전부 통과한다.** 28-80은 적어도 "보인다"를
단언했는데, 이 라운드가 그 단언을 뒤집으면서 **남은 단언이 항진명제가 됐다** — 게이트가 참인지 확인하는
것이 아니라, 참일 수 없는 것을 확인한다.

이것은 28-79 감사 04("회귀가 숨는 쪽만 본다")와 같은 병이고, 그때보다 나빠졌다. 그때는 조건의 한쪽만
고정된 상태였지만, 지금은 배포되는 모드에서 **양쪽 모두 관측 불가능**하다.

**고치는 방향**(택일 또는 조합):
1. `e2e:server` 여정을 완료·정산까지 늘리고 그 끝에서 "히어로 지표가 보이고 값이 실제와 같다"를 단언한다
   (§3이 "이 라운드 범위 밖"이라고 적어 둔 그것 — 다음 라운드의 범위로 가져온다).
2. `Landing`을 렌더하는 컴포넌트 테스트를 하나 둔다(`@testing-library/react`는 아직 없으므로 도입 비용이
   있다). 최소한 "`showPublicStats`가 참이면 `[data-hero-stats]`가 그려진다"까지.
3. 최소 조치로, `visual-check`가 서버 모드 빌드도 한 장 찍게 한다.

1번이 이 저장소의 결에 가장 맞는다.

## 03 (중) 삭제 직전 파일이 **원본(개인정보 포함)**인데 화면이 그렇게 말하지 않는다

28-81-02는 안전장치로 삭제 전 스냅샷을 내려준다. 그 한 줄:

```tsx
const { json } = platform.exportBackup('full')
downloadText(`banded-before-clearseed-${todayUTC()}.json`, json, 'application/json')
```

`'full'`은 **원본**이다 — 고객 이름·요청 내용·채팅 본문·사진이 모두 들어 있다. 이 저장소는 그 반대를
기본값으로 정해 두었다:

```tsx
const [mode, setMode] = useState<BackupMode>('pseudonymous')   // 백업 카드의 기본은 가명본
```

28-61·28-62·28-64가 여러 라운드에 걸쳐 세운 결정이고, e2e도 파일명으로 모드를 확인한다
(`dlP.suggestedFilename().includes('pseudonymous')`). 그런데 시연 삭제 경로는:

- 버튼 이름이 "**시연 데이터 지우기**"다 — 원본 백업을 만든다는 말이 없다.
- 파일명 `banded-before-clearseed-…`에 모드가 없다.
- 결과 안내가 "삭제 직전 상태는 banded-before-clearseed 파일로 내려받았습니다"라고만 하고 **원본이라는
  말을 하지 않는다**.

**선택 자체는 옳다** — 가명본은 복원할 수 없으므로(28-61) 되살릴 수 있으려면 원본이어야 한다. 문제는
선택이 아니라 **말하지 않은 것**이다. 운영자는 "시연 데이터를 지웠다"고 생각하는데 디스크에는 전체
개인정보 사본이 하나 더 생긴다. 운영 기록에는 남지만(`백업 내보내기 · 원본 · …`), 그것을 확인하려면
다른 탭을 열어야 한다.

**고치는 방향**: 결과 안내와 파일명에 원본임을 드러낸다(예: `banded-before-clearseed-full-…`), 그리고
확인 입력 옆에 백업 카드와 같은 한 줄 주의문을 둔다 — "되살릴 수 있도록 **원본** 백업을 내려받습니다
(개인정보 포함)". e2e 단언도 파일명으로 모드를 확인하게 한다.

## 04 (하) `CHAT_VIEWERS`가 `ChatSender`와 **타입으로 묶여 있지 않다**

28-81-04는 "키를 만드는 곳을 하나로"를 목표로 했고, 키 **모양**은 실제로 하나가 됐다. 그런데 뷰어 **목록**은
여전히 손으로 베낀 것이다:

```ts
// types.ts
export type ChatSender = 'customer' | 'partner'
// platform.ts
const CHAT_VIEWERS = ['customer', 'partner'] as const     // ← 위와 아무 관계가 없다
```

`ChatSender`에 값이 하나 늘면(예: 관리자 개입 대화) `CHAT_VIEWERS`는 조용히 옛 목록으로 남고,
`clearSeedData`와 `pruneChats`가 그 뷰어의 읽음 워터마크를 **지우지 않은 채** 고아로 남긴다.
컴파일러는 아무 말도 하지 않는다.

**고치는 방향**: `const CHAT_VIEWERS = ['customer', 'partner'] as const satisfies readonly ChatSender[]`
로 최소한 오타·잘못된 값을 막고, 더 나아가 누락까지 잡으려면 `Record<ChatSender, true>`를 하나 두고
그 키를 순회한다(빠뜨리면 타입 오류가 난다).

## 이번 감사에서 **문제 삼지 않은 것** (조용히 넘기지 않는다)

- **28-81-04가 수정 전에도 통과한다고 스스로 적은 것** — 오히려 좋다. 도달할 수 없는 상황을 꾸며 실패를
  만들어 내는 것이 더 나쁜 습관이고, 이 라운드는 그렇게 하지 않고 "구조 수정이라 회귀는 가드다"라고 적었다.
- **로컬 모드에서 지표를 아예 내리기로 한 판단** — 옳다. 방문자마다 다른 값을 "누적 실적"으로 내거느니
  비워 두는 것이 맞다. 02는 그 판단이 아니라 **그 판단을 관측할 방법이 없어진 것**을 문제 삼는다.
- **`bidStats`에 옵션을 더해 루프를 합친 것** — 계산이 한 곳이 됐다. 01은 그 합침이 아니라 **그 도구를
  옆 화면에 쓰지 않은 것**을 문제 삼는다.
- **§7의 해시 일치와 "직접 열어 본 것은 아니다"를 함께 적은 것** — 주장의 강도와 근거가 맞는다.
