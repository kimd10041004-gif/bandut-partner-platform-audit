# 29-18 — 봇이 사람 대신 가입해 본다

## 1. 왜 만들었나

가입 → 승인 → 권한 왕복을 재는 것이 이미 둘 있었는데 둘 다 반쪽이었다.

| 있던 것 | 보는 것 | 못 보는 것 |
|---|---|---|
| `tests/signupJourney.http.test.ts` | HTTP 요청·응답 | 폼, 단추, 다음 화면 |
| `e2e:next` | 화면이 200 인지, HTML 문자열 | 실제로 눌러서 되는지 |

29-16-1 이 정확히 그 틈에서 나왔다. `/companies` 는 200 이었고 HTML 도 맞았는데, 브라우저로 열면
돋보기 아이콘이 혼자 한 줄을 차지하고 문장을 밀어내고 있었다. **화면은 열어 봐야 안다.**

사장님이 프리뷰에서 손으로 돌아 보려던 왕복을, 봇이 대신 돈다.

## 2. 열여섯 줄

성공하는 길 하나만 보지 않는다. **막혀야 할 것이 안 막히는 것은 열려야 할 것이 안 열리는 것보다
나쁘다.** 그래서 거절돼야 하는 길을 먼저 깐다.

```
✓ 공개 로그인 화면에 관리자 선택지가 없다      (29-10)
✓ 가입 코드가 틀리면 거절한다
✓ 필수 동의 없이는 가입할 수 없다
✓ 가입 신청이 인증번호 화면으로 넘어간다
✓ 인증번호가 틀리면 거절한다
✓ 가입이 끝나면 파트너 정보 화면으로 간다
✓ 같은 번호로 다시 가입하면 거절한다
✓ 승인 전에는 업체 찾기에 안 보인다
✓ 업체 정보를 제출하면 화면에 남는다
✓ 승인 전에는 일감 화면이 막혀 있다            ← 이 줄이 없으면 아래가 공짜로 통과한다
✓ 관리자로 로그인된다
✓ 승인 대기 목록에 그 업체가 보인다
✓ 승인 뒤 대기 상태가 아니다
✓ 승인 뒤 파트너로 다시 로그인된다
✓ 승인 뒤 일감 화면이 열린다
✓ 승인 뒤 업체 찾기에 보인다
```

## 3. 만들면서 잡은 것 — 내 검사가 거짓말을 하고 있었다

첫 실행에서 `관리자로 로그인된다` 가 **통과**했는데, 그 다음 줄이 승인 목록을 못 찾고 멈췄다.
이상해서 브라우저 콘솔을 찍어 보니 로그인 자체가 실패하고 있었다.

```
[api] 422 /api/auth {"ok":false,"error":"관리자 계정 정보가 일치하지 않습니다 (남은 시도 2회)"}
URL after login: http://127.0.0.1:3216/login/admin
```

원인은 내가 쓴 한 줄이다.

```js
step('관리자로 로그인된다', /\/admin/.test(a.url()))
```

**로그인 화면 주소가 `/login/admin` 이라 `/admin` 을 그대로 포함한다.** 로그인에 실패해 그 화면에
그대로 남아 있는데도 조건이 참이 됐다. 통과가 찍히는 검사가 실제로는 아무것도 재지 않고 있었다.

로그인 화면을 벗어났는지를 함께 본다.

```js
const adminIn = /\/admin/.test(new URL(a.url()).pathname) && !/\/login/.test(new URL(a.url()).pathname)
```

`/login/partner` 도 `/partner` 를 포함한다. 파트너 재로그인 쪽에도 같은 함정이 있어 같이 고쳤다.

실패했을 때 무엇이 틀렸는지도 함께 싣는다. 로그인이 안 되면 화면 오류 문구에 더해
**저장된 비밀번호가 `ADMIN_PASSWORD` 와 다를 수 있다**고 적는다 — 비밀번호는 `auth_state` 행이
처음 만들어질 때만 심어지므로(`server/authState.ts`), 환경변수를 바꿔도 기존 행은 그대로다.
로컬에서 실제로 그것에 걸렸다.

## 4. 목록은 기다려서 본다

승인 대기 목록은 하이드레이트 뒤에 `fetch` 로 온다. `networkidle` 은 그 `fetch` 가 시작되기도 전에
끝날 수 있어서, 화면을 한 번 찍어 보는 방식으로는 있는 줄도 없다고 나온다. 줄이 뜰 때까지 기다리고,
안 뜨면 그때 화면을 그대로 실어 보고한다.

## 5. 쓰는 검사라서 문을 좁혔다

이 검사는 계정을 **실제로 만든다.** 그래서 `e2e:server` 와 같은 규칙을 건다 — 이름에 `test` 가 든
DB 에서만 돌고, `ADMIN_PASSWORD`(8자 이상)와 `SIGNUP_CODE`(12자 이상)가 없으면 시작하지 않는다.
지우는 코드는 두지 않았다. 매 실행이 새 휴대폰 번호를 쓰므로 쌓여도 서로 밟지 않는다.

CI 의 `server` 작업에 넣었다. 거기는 매번 새 Postgres 컨테이너라 이 조건이 저절로 맞는다.

## 6. 이 검사가 못 하는 것

**배포된 프리뷰를 재지 못한다.** 이 작업 환경에서 `*.vercel.app` 으로 나가는 연결이 막혀 있다
(`CONNECT tunnel failed, 403`). 그래서 같은 코드를 로컬에 띄워 잰다. 코드도 DB 엔진도 같지만,
배포된 인스턴스 자체를 확인한 것은 아니다. 프리뷰에서의 확인은 여전히 사람 몫이다.
