매 실행이 새 휴대폰 번호와 새 업체명을 쓴다. 같은 DB 에 계정이 쌓이는 상태에서도 세 번 다 통과했다.

## 2. 만들면서 실제로 받은 실패

이 검사가 처음부터 초록이었던 것이 아니다. 두 번 빨갰고, 둘 다 원인이 달랐다.

**(가) 내 단언이 거짓 통과를 내고 있었다.**

```
✓ 관리자로 로그인된다          ← 실제로는 실패한 로그인이었다
✗ 승인 대기 목록에 그 업체가 보인다
```

브라우저 콘솔을 찍어 원인을 봤다.

```
[api] 422 /api/auth {"ok":false,"error":"관리자 계정 정보가 일치하지 않습니다 (남은 시도 2회)"}
URL after login: http://127.0.0.1:3216/login/admin
```

`/login/admin` 이 `/admin` 을 포함해서, 로그인 화면에 그대로 남아 있는 상태가 통과로 잡혔다.
로그인 화면을 벗어났는지를 함께 보도록 고쳤다. `/login/partner` ↔ `/partner` 도 같은 모양이라
함께 고쳤다.

**(나) 목록을 너무 일찍 찍었다.**

```
✗ 승인 대기 목록에 그 업체가 보인다
locator.fill: Timeout 30000ms exceeded
```

목록은 하이드레이트 뒤 `fetch` 로 온다. `networkidle` 이 그 `fetch` 시작 전에 끝날 수 있다.
줄이 뜰 때까지 기다리도록 고쳤다.

**(다) 로컬 DB 의 관리자 비밀번호가 환경변수와 달랐다.**

(가) 를 고친 뒤 드러난 진짜 상태다. `auth_state` 행이 예전 실행에서 다른 `ADMIN_PASSWORD` 로
이미 만들어져 있었고, 비밀번호는 그 행이 **처음 만들어질 때만** 심어진다(`server/authState.ts`).
그래서 환경변수를 바꿔도 기존 행은 그대로다.

기존 데이터를 지우지 않고 **새 검사용 DB(`bandut_bot_test`)를 만들어** 돌렸다. 검사도 이 상황을
말하도록 고쳤다 — 로그인이 실패하면 화면 오류 문구와 함께 "저장된 비밀번호가 ADMIN_PASSWORD 와
다를 수 있다"를 싣는다.

이 셋은 앱의 결함이 아니라 **검사와 로컬 환경의 문제**였다. 앱은 매번 옳게 동작했다 — 틀린
비밀번호를 거절했고, 시도 횟수를 셌다.

## 3. 게이트

| 게이트 | 결과 |
|---|---|
| `npm run check` | **756 통과 / 42 건너뜀** |
| `npm run e2e:signup` | **16 통과 ×3** |

`e2e:signup` 은 DB 가 필요해 `check` 밖에 있다. CI 의 `server` 작업에 단계를 넣었다 — 거기는 매번
새 Postgres 컨테이너라 이 검사가 요구하는 조건(이름에 test 가 든 빈 DB)이 저절로 맞는다.

## 4. 확인하지 못한 것

**배포된 프리뷰는 재지 못했다.** 이 작업 환경에서 `*.vercel.app` 으로 나가는 연결이 막혀 있다.

```
curl: (56) CONNECT tunnel failed, response 403
```

같은 코드를 로컬에 띄워 쟀다. 코드도 DB 엔진도 같지만 배포된 인스턴스 자체를 확인한 것은 아니다.
프리뷰에서의 확인은 여전히 사람 몫이고, 이 검사가 그것을 대신했다고 적지 않는다.
