# 참고 v17 대조 — 무엇을 가져오고 무엇을 버리는가

`docs/rounds/28-90/참고_v12_대조.md`를 **대신한다**. v12 대조는 28-91~28-97로 7항목까지 끝냈고(1~7 ✓),
그 뒤 더 발전한 참고본(v17)을 받았다. 사용자 결정: **지금 저장소를 집으로 두고 코드베이스와 디자인을 v17로 갈아탄다.**

## 1. v17이 우리보다 나은 결정적 지점 — 저장 모델

|  | 우리 (28-97까지) | v17 |
|---|---|---|
| 저장 단위 | 마켓플레이스 **전체가 JSON 스냅샷 하나** (상한 4MB) | 엔티티별 표 30개 |
| 인가 | 서버는 통째 보관만 — 주문 소유자를 판정하지 못한다 | 행 단위로 검사 |
| 사진 | 스냅샷 안에 data URL (용량을 먹는다) | 비공개 객체 저장소 + 메타데이터 제거 + 30일 만료 |
| 불변식 | 애플리케이션 코드만 | **DB 트리거**(일정 충돌·감사로그 불변·계약/메시지 불변·접수 중단…) |
| 목록 | 전부 메모리 | LIMIT/인덱스 |

28-97 문서에 적은 "서버가 주문 소유자를 판정하지 못한다"가 이 모델의 한계였다. 보관함·가명본·용량 가드·rev 충돌
감지는 전부 **그 덩어리를 지키려고 만든 장치**다 — 모델을 바꾸면 함께 사라진다. 이것이 "도태되어 발전이 막힌 부분"의 정체다.

## 2. 기능 대조

이미 우리에게 있는 것(28-91~28-97로 따라잡음): 복수 공종 접수·안전 검토·연락처/주소 가림·계약서·일정 변경 제안·
추가 공사 VAT·전/후 사진·결제 멱등 키·부분 환불·정산(총액−환불−수수료)·분쟁·후기·알림·상담·감사로그·파트너 승인·정산 계좌.

| 5 | 비공개 사진 저장(구조 검증·메타 제거·만료) | 29-5 |
| 6 | 파트너 포트폴리오·업체 상세·후기 답변 | 29-6 |

### 2-1. 29-2와 29-3을 왜 나눴나

처음에는 앱 셸·화면·세션·배포를 한 라운드에 넣으려 했다. 실제 코드를 읽고 나눴다.

v17은 Next.js 16 + React 19이고 우리는 Vite + React 18이다. React를 두 벌 둘 수는 없으니 프레임워크를 바꾸면
SPA·`vite build`·`e2e`·`visual-check`가 한꺼번에 깨진다 — **고 생각했다.**

> **29-3 정정.** 실제로 해 보니 아니었다. React 19 하나로 올려도 **옛 SPA가 그대로 빌드되고 e2e 여정도 전부
> 통과한다.** 우리 SPA가 React 19에서 사라진 API를 안 쓰기 때문이다. 그래서 화면 전환은 쪼갤 수 없는 덩어리가
> 아니었고, 29-3은 **앱 셸을 세우기만** 하고 배포 전환·삭제는 29-4로 미룰 수 있었다. 아래 문단은 그때의 판단
> 근거로 남겨 둔다 — 틀린 가정이 라운드 계획을 어떻게 좁혔는지가 기록으로 남아야 한다. 그런데 거기에 세션 연결과 저장소 연결까지 얹으면, 무언가 실패했을 때 **원인이 프레임워크인지 인증인지
저장소인지 가릴 수가 없다**.

그래서 쪼갤 수 있는 절반을 먼저 뗐다:

- **29-2 (이번)** — v17 도메인을 우리 `api/`에 그대로 올린다. 우리 세션이 신원을 만들고, 29-1의 `pgDatabase`가
  저장소가 된다. **화면은 한 줄도 안 바뀐다.** SPA·게이트·배포가 전부 그대로 살아 있으니 CI가 계속 초록이고,
  실패하면 원인은 서버 경로 하나뿐이다.
- **29-3** — 그 위에 화면을 얹는다. 서버가 이미 증명돼 있으니, 이때 깨지는 것은 프레임워크·화면뿐이다.

v17에서 신원이 만들어지는 자리는 `app/api/[...path]/route.ts` **한 곳뿐**이고(전체 API가 그 파일 하나다),
그 아래 모든 서비스가 `User`를 첫 인자로 받는다. 그래서 로그인 교체는 그 세 줄을 우리 `sessionOf`로 바꾸는 일이다.

## 3. 우리 것 중 v17에 없어서 **지키는 것**

> **사용자 결정: 로그인과 검증 체계는 우리 것으로 간다.** 코드베이스와 디자인만 v17로 갈아탄다.

### 3-1. 로그인은 우리 것

v17은 로그인을 **호스트가 검증한 헤더**에 의존한다(`app/chatgpt-auth.ts`, `oai-authenticated-user-*`). Cloudflare
Sites 전용이고, 그 헤더를 넣어 주는 주체가 없는 곳에서는 **누구나 남의 신원을 주장할 수 있다**. v17 README도 다른
호스팅으로 옮기면 세션 검증으로 바꾸라고 적었다. 우리에게는 이미 그것이 있다.

| v17 | 우리가 대신 쓰는 것 |
|---|---|
| `getChatGPTUser()` + `oai-authenticated-user-id` 헤더 | `server/session.ts`의 `sessionOf(db, workspace, bearerOf(headers))` — 토큰 해시로 세션 표를 조회 |
| 첫 로그인 소유자에게 ADMIN 부여 | `api/auth.ts`의 가입 코드·OTP·관리자 등급(`adminGrade.ts`) |
| (없음) | 로그인 실패 잠금, IP 실패 제한(`server/rateLimit.ts`), 세션 만료·폐기 |

**붙이는 방법**: v17 서비스는 첫 인자로 `User`(`{id,email,name,role,…}`)를 받고 그 안에서 `role(u,'ADMIN')` 같은
게이트를 건다. 그러니 우리 세션 → `User` 한 번만 옮겨 주면 v17 코드는 그대로 돈다. 신원을 만들어 내는 자리는
`app/chatgpt-auth.ts`가 아니라 **우리 세션 조회 한 곳**뿐이어야 한다 — 29-2에서 그 어댑터를 쓴다.
v17의 `identity(userId, email, name)`는 그 계정을 users 표에 만들어 주는 자리로만 쓴다.

### 3-2. 검증 체계도 우리 것

v17은 브라우저 E2E가 미검증이라고 스스로 적었고, 배포 확인 장치도 없다. 우리 쪽 게이트를 그대로 유지한다.

- `npm run check`(포맷·타입·단위·빌드) · `npm run e2e`(여정) · `visual-check` · `npm audit --audit-level=high`
- CI `server` job: 계약 테스트 + 서버 e2e + **`npm run test:pg`**(v17 도메인을 진짜 Postgres에서)
- 병합 뒤 `deploy-check`가 라이브 번들에서 라운드 문자열을 확인한다.
- 라운드마다 **수정 전 실패를 먼저 인용**하고 `docs/rounds/<라운드>`에 남기는 방식도 그대로 간다.

여기에 v17이 가진 것 하나를 더한다: **DB 트리거**(일정 충돌·감사로그 불변·계약/메시지 불변·접수 중단). 앱이 우회해도
저장소가 막는다.

- IP 실패 제한(`server/rateLimit.ts`), 보안 헤더(`vercel.json`)도 그대로 유지한다.

## 4. 하지 않는 것

- Cloudflare Workers/D1/R2로 호스팅을 옮기지 않는다. Next.js는 Vercel에서 그대로 돈다.
- v17의 ChatGPT 로그인 어댑터(`app/chatgpt-auth.ts`)는 **가져오지 않는다** (§3-1).
- v17 소스는 **포맷을 고치지 않는다** — 원본과 대조할 수 있어야 하므로 prettier 대상에서 뺀다.
