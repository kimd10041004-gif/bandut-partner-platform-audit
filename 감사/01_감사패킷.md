## 0. 먼저 — 제가 낸 버그 하나와 그 고침 (자진 신고)

감사 자료를 만들려고 제 코드를 다시 읽다가 **제가 29-31 에서 낸 버그**를 찾았습니다.
찾고, 재현하고, 29-32 에서 고쳤습니다. 이 저장소의 코드는 **고친 뒤**입니다.

**증상**: 업체가 공개한 **커버·로고가 손님에게 403**. 그 업체 본인과 관리자에게만 보였습니다.

```
tests/companyPage.http.test.ts (수정 전 프로브)
AssertionError: 비로그인 손님이 커버를 못 본다: {"error":"이 사진을 볼 수 없습니다."}
expected 403 to be 200
```

**원인 — 공개 경로가 둘인데 하나만 봤다.** `lib/media.ts` 의 `openPortfolioPhoto()` 가 아는
공개 조건은 "게시된 작업사례(`portfolio_cases.asset_id`)에 붙어 있는가" 하나뿐이었습니다.
커버·로고는 작업사례가 아니라 공개본 설정(`company_pages.published_config`)의
`coverAssetId`·`logoAssetId` 로 걸립니다. 29-31 이 그 경로를 만들어 놓고 공개 판정에 넣지 않았습니다.

**보안 등급: 낮음 — 과다 차단(fail-closed)입니다.** 남의 사진이 새는 방향이 아니라 내 사진이
안 나오는 방향입니다. 기능 결함이지 노출 사고가 아닙니다.

**왜 게이트를 통과했나 — 이쪽이 더 중요합니다.** `e2e:roles` 의 단언이 약했습니다.

```js
await C.locator('[data-company-cover]').waitFor({ state: 'visible' })
```

Playwright 의 `visible` 은 **DOM 에 있고 박스 크기가 0 이 아니면** 통과합니다. CSS 가
`.company-cover { height: clamp(150px,26vw,300px) }` 로 높이를 주기 때문에, 이미지 요청이
403 으로 깨져도 요소는 "보이는" 상태입니다. **그림이 떴는지는 잰 적이 없었습니다.**
HTTP 테스트도 공개본 **JSON** 만 확인하고 사진 **바이트**는 받아 보지 않았습니다.

29-31 문서에 "저장되는 것과 보이는 것은 다르다" 고 써 놓고 한 층 아래에서 같은 실수를 했습니다.

**29-32 가 고친 것** (`docs/rounds/29-32/` 에 전문):

| 파일 | 변경 |
|---|---|
| `lib/media.ts` | `shownOnPage()` 순수 함수 + `openPortfolioPhoto()` 가 두 번째 공개 경로를 본다. 조건은 사례와 같다 — `APPROVED` · `suspended=0` · **공개된** 설정에 걸린 사진만. `published_config` 가 `text` 컬럼이라 (포트가 Postgres·SQLite 양쪽) JSON SQL 함수 대신 **코드에서 파싱**하고, 파싱 실패는 `false` 로 **닫는다** |

> 바이트·부수효과를 확인하지 않은 자리. 지도는 [`03_게이트_지도.md`](03_게이트_지도.md) 입니다.

## 4. 인증·세션·권한 (코드 근거)

### 세션 쿠키 (`server/session.ts`)

```
bandut_session=<token>; Path=/; HttpOnly; SameSite=Lax; Max-Age=<ttl>[; Secure]
```

- `Secure` 는 https 일 때만 붙입니다. 로컬·CI 는 http 라 붙이면 브라우저가 버립니다 → **운영에선 반드시 붙어야 함**
- **CSRF**: 쓰기 요청의 쿠키는 `Origin == Host` 또는 `Sec-Fetch-Site: same-origin` 일 때만 신뢰 (`cookieTrusted`)
- **Bearer 토큰은 그대로 받습니다** (봇·테스트·옛 SPA용). Bearer 는 CSRF 검사를 거치지 않습니다 — 설계상 의도

**제가 가장 불안한 곳 — 여기를 봐 주세요**

1. 쓰기 요청에 `Origin` 도 `Sec-Fetch-Site` 도 **둘 다 없을 때** 어떻게 되는지. 거부가 맞습니다. 확인 부탁드립니다.
2. Bearer 우회로가 실질적 CSRF 구멍이 되는 조건이 있는지. 토큰이 브라우저에 저장되지 않는다는
   전제가 실제로 지켜지는지 (로그인 응답 **본문**에 토큰이 남아 있다면 XSS 가 읽을 수 있습니다).
3. `SameSite=Lax` 는 top-level GET 이동에 쿠키를 붙입니다. GET 으로 상태를 바꾸는 라우트가 하나도 없는지.

### 세션 수명 (`server/domain/auth.ts` `SESSION_TTL_MS`)
역할별로 다릅니다. 관리자가 가장 짧습니다.

### 비밀번호 (`server/passwordHasher.ts`)
`scrypt$<N>.<r>.<p>$<salt hex>$<key hex>` · N=2^15 · r=8 · p=1 · key 32B · `timingSafeEqual` 비교.

### 권한 모델
- 도메인이 `User` 를 첫 인자로 받아 `role()` 로 스스로 막습니다.
- 사진 권한은 `marketplace.photoPermission` / `community.assetPermission` / `uploadPermission` 에 위임.
- 증빙 사진은 **거래 당사자**(고객·선택된 파트너)만 (`lib/media.ts` 의 `tradeParty()`).
- 저장소 키는 `assertSafeKey` 로 경로 탈출을 막습니다.

## 5. 아스트라에게 특히 부탁드리는 것

우선순위 순입니다.

1. **약한 단언 전수조사** — §0 과 같은 모양. `visible` 로 이미지 로드를 갈음한 자리, 응답 JSON 만
   보고 바이트·부수효과를 확인하지 않은 자리. 봇 7종 + HTTP 테스트 전부.
   지도: [`03_게이트_지도.md`](03_게이트_지도.md)
2. **위험 스위치 가드** — `AUTH_DEV_OTP`, `E2E_ALLOW_TRUNCATE` 가 운영에서 켜질 수 있는 경로가
   있는지. 29-28 이 봇 안전장치를 넣었다고 주장하는 지점입니다.
   목록: [`02_운영_현황.md`](02_운영_현황.md) §3
3. **CSRF 경계** — §4 의 세 가지 의문.
4. **도메인 우회** — 어댑터(`server/marketplaceApi.ts`, 분기 84개)가 도메인을 건너뛰고 표를
   직접 만지거나 권한 판단을 복제한 곳.
5. **사진 권한 대칭성** — 주문 사진·증빙·작업사례·커버/로고 네 종류의 열람 규칙이 서로 일관된지.
   §0 은 그 대칭이 깨진 한 사례입니다. 다른 사례가 더 있는지.
6. **29-29 가 지운 `/api/payments`** — 같은 성격의 "화면이 안 쓰는데 열려 있는" 라우트가 더 남았는지.
7. **서버리스 가정 위반** — 프로세스 메모리에 상태를 두거나, SSE·스트림이 Vercel 함수 수명을
   넘어 산다고 가정하는 자리.
8. **Postgres/SQLite 양쪽 포트** — 한쪽에서만 도는 SQL, 트랜잭션 경계, N+1.

발견은 **심각도(상/중/하)** 와 **재현 가능한 실패 시나리오**(어떤 입력 → 어떤 잘못된 결과)로
적어 주시면 그대로 라운드로 만들 수 있습니다. 추측은 추측이라고 표시해 주세요.

## 6. 되짚기 — 제 실수의 패턴

최근 라운드에서 제가 놓친 것은 전부 같은 모양이었습니다.
**"장치가 있다" 와 "장치가 실제로 그 일을 한다" 를 구분하지 않은 것.**

- 29-29 에서 쿠키로 401 을 없앴다고 보고했지만, 그 자리에 **503** 이 있었습니다(두 번째 벽을 못 봄).
- 29-31 에서 커버가 "보인다" 고 보고했지만, **요소만 있었고 그림은 없었습니다**.

감사에서 이 패턴을 기준으로 봐 주시면 제가 또 어디서 같은 실수를 했는지 가장 빨리 나올 것 같습니다.
